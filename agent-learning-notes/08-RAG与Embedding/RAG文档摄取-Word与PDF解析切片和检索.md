# RAG 文档摄取：Word 与 PDF 的解析、切片和检索

## 核心结论

RAG 处理 Word 和 PDF 的真正难点通常不在向量检索，而在文档摄取：

```text
文件识别与路由
→ 内容和版面解析
→ 阅读顺序与结构恢复
→ 质量校验
→ 结构感知切片
→ 向量与关键词索引
→ 混合召回和重排
→ 上下文组装与引用
```

如果解析阶段把标题、段落、表格和阅读顺序弄错，后续模型、Embedding 和检索再强，也只能处理错误输入。

---

## 1. Word 与 PDF 的本质差异

### Word

现代 `.docx` 本质上是带结构标记的 OOXML 文档，通常可以直接识别：

- 标题层级
- 段落
- 列表
- 表格
- 页眉和页脚
- 批注与脚注

难点主要在：

- 图片中的文字
- 文本框与浮动对象
- 公式
- 图表
- 嵌入的 Excel 或其他 OLE 对象
- 复杂页眉页脚
- 修订记录
- 视觉阅读顺序与 XML 顺序不一致

因此，“Word 有结构”不等于“直接抽取段落就完整”。

### PDF

PDF 首先是一种固定版式格式，许多文件主要保存字符或图像在页面上的坐标，而不保存可靠的标题、段落和表格语义。

常见类型：

| 类型 | 特征 | 主要处理方式 |
|---|---|---|
| 原生文本 PDF | 可选择和复制文字 | 文本提取 + 版面恢复 |
| 扫描 PDF | 页面本质是图片 | OCR + 版面分析 |
| 混合 PDF | 部分文字、部分扫描页 | 按页检测和路由 |
| 带标签 PDF | 包含一定结构标签 | 利用标签，但仍需验证 |

PDF 并非绝对“没有结构”：Tagged PDF 可能包含阅读顺序和语义标签，但现实文档中标签经常缺失或不可靠。

---

## 2. 先分类，再选择解析路线

不要让所有文件走同一个解析器。

### 文件级路由

```text
识别文件类型和 MIME
→ 检查文件完整性、加密和页数
→ 判断 Word / 原生 PDF / 扫描 PDF / 混合 PDF
→ 选择解析器和降级路径
```

### PDF 页面级判断

可结合：

- 是否存在可提取文本
- 文本覆盖率
- 每页字符数量
- 图片覆盖率
- 字体和文字对象
- OCR 与原生文本的一致性

混合 PDF 应按页处理，不能因为第一页有文字就跳过全文件 OCR，也不能对所有页面重复 OCR。

---

## 3. 解析阶段要恢复什么

推荐把文档转换为统一的结构化块，而不是只保存纯文本：

```json
{
  "document_id": "contract_001",
  "page": 12,
  "block_id": "p12_table_02",
  "block_type": "table",
  "section_path": ["第三章", "付款条件"],
  "reading_order": 8,
  "text": "...",
  "bbox": [82, 310, 1140, 650],
  "parser": "layout_parser_v2",
  "confidence": 0.93
}
```

关键结构：

- 标题层级
- 段落和列表
- 页面与阅读顺序
- 表格行列和合并关系
- 图片、图注和附近文本
- 页眉页脚
- 文件、页码和位置来源

这些元数据会直接影响切片、过滤、引用和问题定位。

### 表格与图片的专用表示

表格不能只转成一段按视觉顺序拼接的文字。至少应保留：

- 表名和表格编号
- 表头、行名、列名
- 单位和币种
- 合并单元格关系
- 跨页连续关系
- 原始页码和坐标

图片、流程图和统计图可以生成检索摘要，但还应保留：

- 图片类型
- 图题和附近说明
- 关键实体、数值和关系
- 页面与坐标
- 原图引用
- 生成摘要所用模型和版本

生成的图片描述只是派生数据，不能替代原图。高风险结论应允许 Agent 或人工重新查看原始页面。

## 4. PDF 的主要失败模式

| 问题 | 结果 | 治理方式 |
|---|---|---|
| 双栏或多栏 | 左右栏交叉读取 | 版面区域检测与阅读顺序恢复 |
| 跨页表格 | 表头丢失、行被拆散 | 表格连续性识别、重复表头 |
| 合并单元格 | 字段和值错位 | 表格结构识别与规则校验 |
| 扫描模糊或倾斜 | OCR 错字、漏字 | 去噪、矫正、分辨率检测 |
| 页眉页脚重复 | 每个 Chunk 都含噪声 | 模板检测与去重 |
| 公式和特殊符号 | 内容损坏 | 专用公式解析或图像保留 |
| 图文关联丢失 | 图与说明分离 | 保留坐标和邻近关系 |
| 加密或损坏文件 | 无法解析 | 输入校验并转人工 |

对合同、图纸和报价等高风险文档，解析结果应可回看原页或原始区域，而不是只留下无法追溯的文本。

---

## 5. OCR 与多模态的使用边界

### OCR 适合

- 扫描文字识别
- 标准表格
- 固定版式票据
- 印刷体文档

### 多模态模型适合

- 复杂版面理解
- 图文关系
- 不规则表格
- 需要结合视觉信息判断的页面

### 生产组合

```text
原生解析优先
→ 低文本页进入 OCR
→ 复杂或低置信度区域进入多模态
→ 规则校验
→ 必要时人工确认
```

不应默认把整份文档全部发给多模态模型。这样通常成本更高、延迟更长，也更难保证结构稳定和数据边界。

---

## 6. 解析质量门禁

在切片入库前检查：

- 页数是否一致
- 每页是否成功产生内容
- 标题层级是否异常
- 阅读顺序是否合理
- 表格行列是否完整
- OCR 置信度是否过低
- 是否出现大段乱码
- 是否存在异常重复
- 关键字段是否缺失

处理策略：

```text
高置信度
→ 正常入库

中等置信度
→ 使用备用解析器、OCR 或多模态复核

低置信度
→ 阻止自动入库并转人工
```

“识别不出来就硬塞进向量库”会把解析错误永久扩散到后续检索和回答。

---

## 7. 结构感知切片

### 为什么不能只按字数切

固定长度切片可能：

- 把一句话从中间切断
- 让标题与正文分离
- 拆散完整表格
- 丢失合同条款的上下文
- 让召回片段缺少主语或适用条件

### 推荐优先级

```text
标题章节
→ 段落与列表边界
→ 表格、代码块和公式整体
→ Token 上限
→ 必要的邻接重叠
```

每个 Chunk 应继承：

- 文档和版本
- 章节路径
- 页码
- 块类型
- 权限标签
- 解析器版本
- 原始块引用

### Chunk 大小不是固定答案

“400—800 Token、约 20% 重叠”只能作为某些文本问答场景的实验起点，不能直接套用。

应根据以下因素评测：

- 问题粒度
- 文档结构
- Embedding 模型
- 检索 Top-K
- 上下文窗口
- 表格和条款长度
- 延迟与成本

表格、合同条款和工程清单可能需要专门的切片策略，而不是与普通段落共用参数。

### 语义切片

语义切片可以寻找主题变化边界，但会增加 Embedding 和计算成本。是否值得使用，应通过解析质量、检索指标和最终任务质量验证，不能预设固定提升幅度。

### 重叠不是越多越好

重叠用于保留跨边界的指代、术语定义和前置条件，但过大也会造成：

- 候选片段高度重复
- 有效信息增量下降
- 同一来源挤占上下文
- Token、重排和生成成本增加

重叠度应结合段落长度、主题密度和真实召回结果调整。判断标准不是“是否设置了重叠”，而是正确证据能否完整召回，同时避免大量重复噪声。

### 为 Chunk 补充上下文

孤立 Chunk 可以附加简短的章节上下文，例如：

```text
文档：采购合同 v3
位置：第五章 / 违约责任 / 第 12 条
内容类型：合同条款
```

优先使用可确定的文档元数据、标题路径和邻接关系。若使用模型自动生成 Chunk 摘要，需要：

- 保留原始文本
- 标记生成模型和版本
- 防止摘要加入原文没有的事实
- 在检索评测中验证是否真的改善效果

自动生成的上下文只能辅助召回，不能成为唯一证据。

## 8. 入库与索引设计

建议同时保存三层数据：

```text
原始文件
  ↓
结构化文档块
  ↓
用于检索的 Chunk
```

不要只保存向量。需要能够：

- 重新切片
- 更换 Embedding
- 修复解析错误
- 回溯原文
- 更新文件版本
- 按权限删除或重建索引

索引通常包括：

- 向量索引
- BM25 或全文索引
- 元数据索引
- 权限和版本过滤字段

---

## 9. 混合召回与重排

### 向量检索

擅长语义相近表达，但可能漏掉：

- 精确编号
- 型号
- 专有名词
- 金额和日期

### 关键词检索

擅长精确术语、编号和稀有词，但对同义表达较弱。

### 推荐流程

```text
查询理解或改写
→ 向量召回
+ BM25/全文召回
+ 元数据过滤
→ 融合去重
→ Reranker 重排
→ 上下文预算内选取
```

重排有助于把最相关候选放到前面，但也增加延迟和成本。需要用真实问题集评估收益。

---

## 10. 上下文组装与来源引用

进入模型的上下文应包含：

- Chunk 正文
- 文档名称和版本
- 章节
- 页码
- 原始块或页面引用

回答时应能够展示：

```text
结论
→ 引用的文档
→ 页码或章节
→ 对应原文
```

引用不仅提升可信度，也支持人工复核、错误定位和评测。

注意：有来源不等于结论正确。仍需验证引用是否真的支持回答。

## 11. 将 PDF 能力封装为 Agent 工具

Agent 不应每次把整份 PDF 塞进上下文。可以把能力拆成受控工具：

| 工具 | 职责 |
|---|---|
| `search_document` | 检索相关段落和结构块 |
| `read_page` | 读取指定页面及附近内容 |
| `extract_table` | 返回指定表格的结构化数据 |
| `analyze_figure` | 按需理解图片、图表或流程图 |
| `get_source` | 返回原页、坐标和引用信息 |

调用方式：

```text
简单事实问题
→ 直接检索并引用

明确页码或条款
→ 精确定位 + 读取原页

表格问题
→ 表格索引或 extract_table

图表问题
→ 读取页面 + 按需调用视觉工具

跨章节比较
→ 制定受限阅读计划 + 多次检索 + 合并证据
```

每个工具应具备：

- 清晰输入 Schema
- 用户和文档权限校验
- 页数、次数、Token 和成本预算
- 结构化输出
- 原始证据引用
- 超时、错误码和审计记录

工具化读取并不意味着所有问题都必须由自主 Agent 规划。确定性强的查询应优先走固定检索流程，只有真正需要多步阅读时才启用规划。

## 12. 评测体系

### 解析层

- 文本字符或字段准确率
- 阅读顺序准确率
- 表格结构准确率
- 页、块和图片覆盖率
- 低置信度识别率

### 切片层

- 关键事实是否完整落在某个 Chunk
- 标题与正文关联率
- 表格拆分错误率
- 重复率和平均 Chunk 大小

### 检索层

- Recall@K
- Precision@K
- MRR / NDCG
- 无关候选比例
- 关键编号精确命中率

### 回答层

- 答案正确性
- Faithfulness
- 引用完整性
- 引用支持度
- 拒答准确率
- 人工接受率

必须保留“解析失败”和“检索失败”的独立标签，避免把全部问题都归因于模型。

## 13. 面试回答模板

### 60 秒版本

```text
RAG 处理 Word 和 PDF 的难点首先是文档摄取，而不是向量检索。

我会先识别文件类型。Word 可以利用标题、段落和表格结构，
但还要处理图片、文本框、公式和嵌入对象。

PDF 则要区分原生文本、扫描和混合类型。
原生 PDF 做文本与版面解析，扫描页走 OCR，
复杂表格或低置信度区域再用多模态兜底。

解析后不会直接按固定字数切片，而是按标题层级、段落、
表格和页面结构切分，并保留文档、章节、页码和权限元数据。

入库时同时建立向量和关键词索引；
查询阶段做混合召回、过滤和重排，
最后在上下文中保留来源引用。

生产上还要做解析质量门禁和分层评测，
否则解析错误会污染整个检索链路。
```

### 面试追问准备

- 如何判断 PDF 是否需要 OCR
- 双栏 PDF 如何恢复阅读顺序
- 跨页表格怎样处理
- Chunk 大小如何确定
- 为什么使用混合检索
- 如何验证 Reranker 有收益
- OCR 置信度低时怎么办
- 文档更新和删除如何同步索引
- 如何保证文档权限
- 如何定位错误发生在解析、检索还是生成

## 14. 面向当前报价中台的落地映射

当前系统已经具备：

- Excel 报价需求解析和标准化
- 图纸与图像识别链路
- Milvus 向量检索
- BM25 + RRF 混合检索
- 成本库结构化查询
- 报价证据链和人工预审

若后续增加 Word/PDF 合同、投标文件或规范文档，可复用现有能力并补充：

1. 文件级和页面级解析路由
2. 统一文档块 Schema
3. 页码、坐标、章节和解析器版本
4. 表格及跨页结构恢复
5. 解析质量门禁
6. 文档权限和版本过滤
7. 原页引用与可视化复核
8. Word/PDF 专项黄金测试集

结构化成本数据仍应优先使用 SQL 和业务查询；不要为了统一技术栈，把所有表格和价格数据都转成文本向量。
