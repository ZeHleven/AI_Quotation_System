# 企业知识库搭建方法论：经典 RAG、GraphRAG 与 Agentic RAG

## 视频核心观点

企业知识库的目标不是把所有资料都塞进 AI，而是让组织在真正需要时能够：

```text
找到 → 理解 → 验证 → 复用
```

企业不应一开始就追求最复杂的技术。更合理的顺序是先判断：

1. 谁在使用知识库
2. 是否可以使用在线方案
3. 业务问题到底有多复杂
4. 再选择经典 RAG、GraphRAG 或 Agentic RAG

---

## 一、企业知识为什么难以统一利用

企业知识通常散落在多个 SaaS 和业务系统中：

- IM 工具：沟通记录与临时决策
- 协作文档：项目过程和方案沉淀
- 代码仓库：技术信息与变更历史
- CRM/业务系统：客户、订单与业务数据
- 邮件和会议纪要：关键决策与背景信息

问题不是企业没有知识，而是：

> 每个系统只拥有局部信息，没有统一的知识入口。

这会导致检索困难、信息孤岛、上下文缺失和重复沟通。

---

## 二、两种在线知识库方案

### 方案一：独立知识中枢

独立知识中枢跨多个系统建立统一搜索和问答入口。

```text
Slack / 飞书 / 钉钉 ─┐
Notion / 文档        ├──► 统一 AI 搜索与问答
GitHub / GitLab      ┤
Salesforce / CRM     ┘
```

适合：

- 工具数量多
- 信息分散在不同厂商
- 需要跨系统检索
- 希望建立统一知识入口

视频以 Glean 一类产品作为示例。

### 方案二：嵌入式 AI

AI 直接嵌入已有办公套件：

- 文档中的 AI 总结与撰写
- 表格中的 AI 分析
- 邮件中的 AI 摘要与回复

优点：

- 使用体验自然
- 用户无需切换工具
- 与既有办公流程结合紧密

限制：

- 覆盖范围受办公套件边界影响
- 跨厂商系统的信息可能难以统一

### 如何选择

| 企业现状 | 更适合的方向 |
|---|---|
| 深度使用单一办公套件 | 优先考虑嵌入式 AI |
| 工具多、系统复杂、知识分散 | 优先考虑独立知识中枢 |
| 对数据主权和私有化要求高 | 考虑自建或私有部署 |

两类在线方案有一个共同前提：企业数据需要交给第三方平台处理。

---

## 三、什么时候需要自建

如果企业对以下事项有强要求，就应认真评估自建或私有化部署：

- 数据主权
- 访问权限
- 操作审计
- 模型和检索链路可控
- 私有化部署
- 数据不离开指定环境

常见于：

- 金融
- 医疗
- 法律
- 政企
- 涉密或高敏感业务

### 工程化补充

“在线方案”和“完全自建”并非只能二选一，还存在混合模式：

- SaaS 前端 + 私有数据连接器
- 托管模型 + 私有向量库
- 私有部署的商业产品
- 自研业务层 + 托管基础设施

真正应评估的是数据流、权限、审计、保留策略和供应商边界，而不只是服务器放在哪里。

---

## 四、自建知识库的三种复杂度

视频将自建企业知识库归纳为三层：

```text
L3  Agentic RAG   主动决策与智能体
          ↑
L2  GraphRAG      理解关系与结构
          ↑
L1  经典 RAG      查资料的基础
```

这里的关键是：

> 递进，不是替代。

复杂方案通常仍会复用经典检索能力。

---

## L1：经典 RAG

### 基本流程

```text
文档
  ↓
切片 Chunk
  ↓
Embedding 向量化
  ↓
写入向量数据库
  ↓
用户查询
  ↓
召回相关片段
  ↓
LLM 根据片段回答
```

经典 RAG 解决的核心问题是：

> 从大量文档中找到与问题最相关的内容。

### 适合的问题

- 制度问答
- 产品手册查询
- 操作流程查询
- 单篇或局部文档内容检索
- 有明确关键词或语义指向的问题

### 优点

- 结构相对简单
- 建设成本较低
- 容易迭代
- 评测路径较清晰
- 适合先完成 MVP

### 局限

经典 RAG 擅长“查资料”，但不天然擅长跨文档关系。

例如：

```text
A 项目 → B 部门 → C 客户
```

如果信息分散在多个片段中，单纯调整 Chunk 大小不一定能恢复完整关系。

---

## L2：GraphRAG

GraphRAG 不只保存文档片段，还抽取实体和关系，形成知识图谱或关系网络。

```text
文档
  ↓
实体抽取
  ↓
关系抽取
  ↓
实体消歧与合并
  ↓
构建关系网络
  ↓
图检索 / 多跳推理
```

关系示例：

```text
公司 ─拥有→ 产品
项目 ─涉及→ 人员
合同 ─关联→ 客户
客户 ─产生→ 风险
```

### 适合的问题

- 需要跨文档关联
- 需要多跳查询
- 涉及复杂实体关系
- 需要理解组织、客户、项目和事件之间的网络

### 与经典 RAG 的区别

| 维度 | 经典 RAG | GraphRAG |
|---|---|---|
| 主要存储 | 文档片段 | 实体和关系网络 |
| 典型检索 | 相似片段召回 | 关系路径和多跳检索 |
| 擅长问题 | 局部、直接问答 | 跨文档、关联性问题 |
| 建设成本 | 较低 | 较高 |
| 维护难度 | 中等 | 较高 |

### GraphRAG 的三类成本

#### 1. 建图成本高

- 实体抽取
- 关系抽取
- 实体消歧
- 大规模图数据构建

#### 2. 维护复杂

- 同一客户可能有多个名称
- 关系会随时间变化
- 历史关系可能失效
- 新数据需要持续增量更新

#### 3. 不一定值得

如果只是做制度问答、流程查询或简单知识检索，GraphRAG 的收益可能无法覆盖成本。

---

## L3：Agentic RAG

Agentic RAG 不只执行固定检索，而是让 Agent 根据问题动态决定：

- 如何拆解问题
- 选择哪个知识源
- 采用哪种检索方法
- 是否进行多轮检索
- 是否调用其他工具
- 如何综合不同结果
- 什么时候停止或转人工

```text
复杂问题
    │
    ▼
Agent 拆解子问题
    │
    ├──► 选择知识源
    ├──► 经典 RAG
    ├──► GraphRAG
    ├──► SQL / API
    └──► 多轮检索
    │
    ▼
综合判断与验证
    │
    ▼
最终结果
```

### 复杂问题示例

```text
过去三年制造业客户的交付问题，
与今年新产品规划有什么关系？
```

这类问题可能需要联合：

- 历史交付问题
- 客户反馈
- 产品规划
- 项目数据
- 供应链或质量记录

一次固定向量检索很难完整回答。

### Agentic RAG 的三个代价

#### 1. 慢

复杂问题可能触发多轮检索、多次模型调用和工具执行。

#### 2. 贵

模型、检索和工具调用次数增加，会提高 Token 与基础设施成本。

#### 3. 难测试

执行路径不是完全固定的，需要评测：

- 问题是否正确拆解
- 知识源是否选对
- 工具调用顺序是否合理
- 是否发生无效循环
- 最终依据是否完整

---

## 五、三种 RAG 不是强制升级路线

视频使用“三层递进”帮助建立直观认知，但工程上需要补充：

1. 经典 RAG、GraphRAG 并非严格的版本关系。
2. Agentic RAG 是编排与决策方式，不一定依赖 GraphRAG。
3. 一个 Agent 可以同时调用向量检索、BM25、SQL 和图查询。
4. 复杂度应由真实问题驱动，而不是为了技术先进而升级。

更准确的关系是：

```text
经典 RAG：一种检索方式
GraphRAG：一种关系化检索方式
Agentic RAG：动态选择和编排检索、工具的方式
```

## 六、企业知识库选型框架

### 问题一：给谁使用

需要确认：

- 用户是谁
- 数据权限如何隔离
- 是否需要多人协作
- 是否要求审计
- 是否存在特殊合规规则

### 问题二：能否使用在线方案

需要评估：

- 数据主权
- 数据敏感度
- 业务集成难度
- 检索和模型是否需要完全可控
- 对供应商锁定的接受程度

### 问题三：问题到底多复杂

| 问题类型 | 建议起点 |
|---|---|
| 简单制度或文档问答 | 经典 RAG |
| 跨文档实体关系与多跳问题 | GraphRAG |
| 需要拆解、选择知识源和调用多种工具 | Agentic RAG |

推荐路线：

```text
在线方案
   或
经典 RAG
   ↓（真实需求证明关系检索有价值）
GraphRAG
   ↓（真实需求需要动态规划和多工具协作）
Agentic RAG
```

不要因为方案名称更高级，就默认它更适合当前业务。

---

## 七、每一层应该怎么评测

### 经典 RAG

- Recall@K
- Precision@K
- MRR / NDCG
- 答案正确率
- 引用正确率
- 无答案问题拒答率

### GraphRAG

- 实体抽取准确率
- 关系抽取准确率
- 实体消歧准确率
- 多跳路径召回率
- 图数据新鲜度
- 跨文档答案正确率

### Agentic RAG

- 问题拆解正确率
- 知识源选择正确率
- 工具调用成功率
- 无效调用次数
- 任务完成率
- 端到端延迟与成本
- 执行轨迹稳定性

复杂度每提升一层，评测成本和运维成本也会同步上升。

---

## 八、对当前 AI 智能报价中台的启示

当前系统已经具备：

- Milvus 向量检索
- BM25
- RRF 混合融合
- 成本数据库
- 报价工具链
- 人工预审
- 异步任务
- 证据链与审计

### 当前更应优先做的事

- 继续提升混合检索召回与排序质量
- 维护真实报价与检索回归集
- 保证成本库数据质量
- 补齐引用、版本、权限和 Trace
- 把结构化成本数据优先交给 SQL/业务查询，而非全部向量化

### 暂不应为了技术升级而引入 GraphRAG

只有当真实业务反复出现以下需求时，才值得评估：

- 项目、客户、合同、材料和供应商之间的多跳关系
- 跨多个历史项目追溯风险传播
- 单纯向量检索无法恢复关键关系
- 关系查询带来的收益可以被评测证明

### Agentic RAG 的可落地点

未来可以让受控 Agent 在以下知识源之间选择：

- 成本数据库
- Milvus/BM25 混合检索
- 报价历史
- 项目进度数据
- 文件解析结果

但必须保留：

- 最大步骤和成本预算
- 工具白名单
- 权限校验
- 结构化输出
- 人工审核
- 完整执行轨迹

## 一句话总结

企业知识库建设应从真实用户、数据边界和问题复杂度出发：能用经典 RAG 解决的，不要急着上 GraphRAG；只有当任务确实需要动态拆解、多知识源选择和多轮工具调用时，再引入 Agentic RAG。
