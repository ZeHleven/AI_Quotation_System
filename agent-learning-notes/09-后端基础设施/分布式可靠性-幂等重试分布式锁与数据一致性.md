# 分布式可靠性：幂等、重试、分布式锁与数据一致性

## 核心结论

四个概念分别解决不同问题：

| 概念 | 解决的问题 |
|---|---|
| 幂等 | 同一意图重复到达，不重复产生业务效果 |
| 重试 | 暂时失败后再次尝试 |
| 分布式锁 | 多实例竞争同一临界资源 |
| 一致性模式 | 跨数据库、队列和外部服务协调结果 |

它们不能互相替代：

```text
重试没有幂等 → 重复副作用
锁没有 fencing → 旧持有者迟到写入
本地事务没有 Outbox → 数据与消息不一致
幂等没有业务范围 → 不知道“同一次”指什么
```

---

## 1. 幂等的业务定义

幂等不是“接口调用一次”，而是：

> 相同业务意图被处理多次，最终只产生一次预期业务效果。

需要定义：

- 谁发起；
- 什么操作；
- 针对哪个资源；
- 请求内容；
- 幂等有效期；
- 第一次是否成功；
- 重复请求返回什么。

### 幂等键

```text
tenant_id
+ operation
+ business_resource_id
+ client_request_id
```

如果客户端不能生成稳定 Key，可使用业务字段和内容哈希，但要防止把两个合法相同请求误判为重复。

---

## 2. 幂等实现方式

### 数据库唯一约束

适合创建资源和消费事件：

```sql
UNIQUE KEY uq_confirm_operation (
    tenant_id,
    operation,
    idempotency_key
)
```

### 条件状态更新

```sql
UPDATE quote_jobs
SET status = 'cancelled'
WHERE job_id = ?
  AND status IN ('queued', 'running');
```

重复取消影响 0 行，再查询并返回已有终态。

### 幂等记录表

```text
idempotency_key
tenant_id
operation
request_hash
status: processing/succeeded/failed
response_code
response_body
external_receipt
created_at
expires_at
```

处理：

```text
不存在 → 原子创建 processing
相同 Key + 相同 Hash + succeeded → 返回原响应
相同 Key + 相同 Hash + processing → 返回处理中
相同 Key + 不同 Hash → 409
```

### 版本号/乐观锁

```sql
UPDATE cost_items
SET status = 'active',
    version = version + 1
WHERE id = ?
  AND status = 'draft'
  AND version = ?;
```

避免后写覆盖先写。

## 3. 重试设计

### 错误分类

| 错误 | 是否自动重试 |
|---|---|
| 网络瞬断、连接重置 | 通常是 |
| 429 | 遵守 `Retry-After` |
| 部分 5xx | 有界重试 |
| 数据库死锁 | 短退避有限重试 |
| 参数、格式、Schema 错误 | 否 |
| 401/403 | 先修复身份或权限 |
| 业务状态冲突 | 通常否 |
| 外部操作结果未知 | 先用幂等键查询或确认 |

### 指数退避与抖动

```python
delay = min(cap, base * (2 ** attempt))
delay += random.uniform(0, jitter)
```

抖动避免大量客户端在同一时刻再次请求。

### 重试预算

同时限制：

- 单步骤最大次数；
- 整条链最大总时长；
- 总调用成本；
- 最大并发；
- 用户可接受等待；
- 外部 Provider 配额。

重试日志至少包含：

```text
attempt
error_code
retryable
delay
remaining_budget
trace_id
```

## 4. 外部副作用结果未知

最危险的情况：

```text
调用 N8N 推送
→ 对方成功
→ 响应在网络中丢失
→ 本地认为失败并重试
→ 重复推送
```

解决：

1. 调用前生成幂等键；
2. 外部服务按相同 Key 去重；
3. 本地保存请求和处理状态；
4. 超时后先查询结果，不直接换 Key 重试；
5. 保存外部回执。

如果外部系统不支持幂等，需要：

- 本地发送状态；
- 可查询业务标识；
- 人工核对；
- 尽可能设计补偿；
- 明确不能保证一次效果的边界。

## 5. 分布式锁

使用场景：

- 多实例只允许一个执行定时任务；
- 同一资源短时间内只能重建一次缓存；
- 同一批同步任务禁止并行；
- 无法仅靠数据库条件更新表达的临界区。

不应优先使用：

- 单行状态迁移：数据库条件更新更可靠；
- 同一数据库内的事务不变量：使用事务和锁；
- 仅为避免重复请求：使用幂等；
- 长时间不可中断的外部任务：锁超时后风险很高。

---

## 6. Redis 锁的最低要求

加锁：

```text
SET lock:key random-token NX PX ttl
```

解锁必须“比较 token 后删除”，用 Lua 原子执行：

```lua
if redis.call("get", KEYS[1]) == ARGV[1] then
  return redis.call("del", KEYS[1])
else
  return 0
end
```

不能直接 `DEL`，否则旧持有者可能删除新持有者的锁。

### 锁超时问题

```text
Worker A 获得锁
→ A 停顿超过 TTL
→ Worker B 获得新锁并写入
→ A 恢复并继续写入
```

仅有锁 Token 不能阻止 A 对数据库写入。需要 fencing token：

```text
每次获得锁得到单调递增版本
下游只接受版本不小于当前版本的写入
```

或者直接在权威数据库用状态版本和条件更新。

## 7. 租约与锁

| 机制 | 重点 |
|---|---|
| 锁 | 临界区互斥 |
| 租约 | 有限时间的任务所有权 |
| 心跳 | 执行者是否活跃 |
| Fencing Token | 拒绝旧所有者迟到写 |

长任务更适合租约而不是一个固定 TTL 的普通锁：

```text
lease_token
lease_expires_at
renew
takeover
conditional write
```

## 8. 跨系统一致性

### Outbox

同一数据库事务中写业务事实和待发布事件。解决“数据库成功、消息失败”的窗口。

### Inbox/消费去重

消费者记录已处理事件，解决重复投递。

### Saga

多个本地事务串联，失败时执行补偿：

```text
创建报价
→ 占用额度
→ 推送审批
→ 生成通知
```

如果推送失败，可释放额度；如果通知失败，通常只重试通知，不回滚报价。

### 人工确认

AI 场景的关键一致性手段：

```text
模型生成草稿
→ 系统校验
→ 人工确认
→ 正式副作用
```

人工 Gate 不能替代幂等，但能阻止不可靠模型输出直接改变事实。

## 9. Exactly-once 的边界

不要简单说“用了 Kafka/事务消息就 exactly-once”。

需要逐层说明：

```text
Broker 投递
消费者处理
数据库写入
外部 HTTP
邮件/钉钉
人工看到的结果
```

更稳妥的系统目标：

```text
不静默丢失
允许安全重放
重复不会重复生效
失败可观察
结果可对账
人工可介入
```

## 10. 报价中台映射

### 已有能力

- `quote_jobs.job_id` 唯一；
- 任务终态和状态条件提供部分重复保护；
- 取消重复请求可返回已有结果；
- Celery late ACK 支持故障重投；
- 报价预审和完整性 Gate 阻止缺失行直接下发；
- 成本条目状态变更有历史记录；
- Agent 资料研判链路已有租约、Checkpoint 和旧 Worker 写保护。

### 必须诚实的边界

- Celery 重投不代表业务 exactly-once；
- 普通报价链路的统一租约要按代码路径核对；
- `confirm_push` 的统一端到端幂等键仍是重要补强方向；
- 外部 N8N/Dify 是否支持同一幂等键，需要联动验证；
- 分布式锁不能替代 MySQL 事务、唯一约束和状态机。

### 推荐的确认下发幂等键

```text
quote_job_id
+ confirm_payload_hash
+ operation_type
```

本地幂等记录保存：

- 请求 Hash；
- 处理状态；
- N8N 请求 ID；
- 外部回执；
- 最终响应；
- 操作者和时间。

## 11. 面试回答

### 幂等和分布式锁有什么区别？

> 幂等保证相同业务意图重复执行时只产生一次效果；分布式锁只限制同一时间有一个持有者。锁过期、网络分区或 Worker 停顿后仍可能有旧持有者写入，所以锁不能代替幂等。状态迁移优先使用数据库条件更新和唯一约束，确需跨实例互斥时再加租约和 fencing token。

### 怎样设计重试？

> 我先按错误类型判断是否可恢复，只对网络瞬断、429 和部分 5xx 等做有限重试；使用指数退避、随机抖动和总预算，避免重试风暴。所有可重试副作用必须有稳定幂等键，外部结果未知时先查询原请求状态，而不是生成新请求重复执行。

### 数据库成功但发消息失败怎么办？

> 使用 Outbox，把业务数据和待发送事件写在同一个本地事务中，后台发布器扫描未发送事件并重试。消息可能重复发布，所以消费者用事件 ID 和唯一约束幂等处理。这样把不可控的双写转换成可恢复的最终一致。
