# 报价中台面试映射手册 05：模型网关、结构化输出与成本性能

## 使用方法

记住一条主线：

```text
按任务选模型
→ 由网关统一调用与记录
→ 用契约约束输入输出
→ 用超时、降级和熔断保可用
→ 用质量、延迟、成本共同决定是否发布
```

## 考前 2 分钟速记

| 问题 | 记忆句 |
|---|---|
| 为什么需要模型网关 | 隔离业务与供应商，统一鉴权、超时、日志、统计和故障治理 |
| 怎么选择模型 | 先满足任务能力和质量门，再比较 P95、失败率与单次成本 |
| JSON 怎么保可靠 | Schema 约束只是第一层，还要解析、Pydantic 校验、限次修复和保守降级 |
| 主模型失败怎么办 | 先判断错误类型，再做有限 fallback；不能无限重试 |
| 怎么降低成本和延迟 | 减少无关上下文、Tool 往返和无效修复，把复杂模型留给真正困难任务 |
| 怎么升级模型或 Prompt | 固定数据、版本和指标，离线回归后小流量灰度，支持快速回滚 |

---

## 先分清五个概念

| 概念 | 解决什么问题 | 当前项目对应 |
|---|---|---|
| Model Adapter | 屏蔽不同模型 API 差异 | OpenAI-compatible 资料研判模型适配器 |
| Model Gateway | 统一调用、日志、统计和熔断 | 平台 `model_gateway.py` |
| Routing | 选择主模型、备用模型或任务模型 | 显式配置 + DeepSeek 复用 + 智谱备用 |
| Output Contract | 保证结果可被程序消费 | Tool Schema + `AssessmentDraft` |
| Evaluation | 判断换模型是否真的更好 | 报价 Prompt 回归与 Agent 分层评测 |

> 网关解决“怎么稳定调用”，契约解决“返回能否消费”，评测解决“版本是否值得上线”。三者不能互相替代。

## 卡片 1：怎样选择和路由模型？

**一句话：** 不是选择“最强模型”，而是选择满足该任务质量门的最低综合成本方案。

### 决策顺序

```text
任务是否需要视觉、长上下文或 Tool Calling
→ 候选模型能否通过质量硬门
→ P95 和失败率是否满足 SLO
→ 单次成本是否可接受
→ 是否具备备用提供商
```

### 项目映射

资料研判 Agent 的模型配置顺序是：

1. `BID_INTAKE_MODEL_*` 显式配置优先；
2. 未单独配置时复用现有 DeepSeek 密钥和地址；
3. 备用模型可显式配置；
4. 未显式配置备用模型时，可复用已经配置的智谱兼容接口；
5. 主备地址和模型相同则不启用备用路由。

这避免了：

- 业务代码写死供应商；
- `.env` 重复保存同一密钥；
- 在配置不完整时静默猜测模型；
- 主备实际指向同一故障域。

### 面试中的设计取舍

| 做法 | 优点 | 风险 |
|---|---|---|
| 全部使用最强模型 | 实现简单 | 慢、贵，且不一定更稳定 |
| 全部使用小模型 | 成本低 | 复杂研判、Tool Calling 和长文档质量可能不足 |
| 按任务静态路由 | 可控、易审计 | 需要人工维护规则 |
| 按难度动态路由 | 有机会进一步降本 | 路由误判会直接造成质量退化 |

当前项目采用的是**配置与任务规则驱动的静态路由**，没有声称已经实现基于实时质量的智能动态路由。

### 30 秒回答

> 我选模型时先看任务能力，例如是否支持视觉、长上下文和原生 Tool Calling；然后用固定回归集设置质量硬门，只在通过硬门的模型中比较 P95、失败率和单次成本。报价中台的资料研判 Agent 支持显式主模型配置，也可以复用 DeepSeek，并配置智谱等备用模型。当前是可审计的静态路由，还没有做基于实时难度和质量预测的动态路由。

## 卡片 2：模型网关、重试、Fallback 和熔断怎样配合？

**一句话：** 超时限制单次等待，重试处理短暂抖动，fallback 切换故障域，熔断阻止持续打坏下游。

### 四种机制不能混用

| 机制 | 作用 | 适合场景 |
|---|---|---|
| Timeout | 限制一次调用最长等待 | 所有外部模型调用 |
| Retry | 再试同一路径 | 短暂网络失败、部分 429/5xx |
| Fallback | 切换模型或供应商 | 主供应商不可用或响应非法 |
| Circuit Breaker | 暂停调用持续失败的下游 | 连续错误、供应商故障 |

不应重试的典型问题：

- 请求参数或 Schema 本身错误；
- 鉴权配置错误且短期不会恢复；
- 内容被业务规则拒绝；
- 已经超过任务总预算；
- 非幂等副作用调用。

### 平台通用网关已经做了什么

`post_json_via_gateway()` 统一处理：

- `httpx.AsyncClient` 异步请求；
- `trust_env=False`，避免继承不受控代理；
- 超时；
- provider、model、endpoint、trace 和用户记录；
- HTTP 状态、延迟、输入/输出字符数和估算成本；
- 成功后关闭故障状态；
- 失败累计和熔断。

默认熔断参数：

```text
连续失败阈值：3
熔断恢复时间：60 秒
默认网关超时：20 秒
```

熔断粒度是：

```text
provider + endpoint_type
```

因此同一供应商的视觉接口故障，不必自动阻断其他类型接口。

### 资料研判 Agent 的主备切换

`FailoverBidAnalysisModel` 会：

- 正常时记录 `bid_model_route=primary`；
- 主模型出现网络、超时、指定 HTTP 错误或非法响应时调用备用模型；
- 备用接管后记录实际 `model_id` 和脱敏后的主模型错误；
- 当前适配器实例内主模型被禁用后，后续调用直接走备用；
- 主备都失败时返回安全的组合错误，不泄露密钥。

重要边界：

- fallback 恢复的是**可用性**，不代表质量、延迟和成本保持不变；
- 平台熔断器当前是进程内状态，不是跨 Worker 的分布式熔断；
- 当前通用网关没有对所有错误做自动重试，避免重试风暴；
- 资料研判 Agent 适配器尚未完全接入平台统一调用日志。

### 30 秒回答

> 我会把超时、重试、fallback 和熔断分层设计。超时控制单次等待，重试只处理短暂且安全的失败，fallback 切换供应商，熔断在连续失败后保护下游。项目的平台网关按 provider 和 endpoint type 统计失败，默认连续 3 次失败后熔断 60 秒；资料研判 Agent 还有独立主备适配器并记录实际路由。但 fallback 只说明任务恢复可用，必须继续监控备用模型的质量、P95 和成本。

## 卡片 3：怎样保证结构化输出可靠？

**一句话：** 不相信“模型说自己会返回 JSON”，而是把输出当外部不可信数据进行契约校验。

### 四层防线

```text
Prompt 中给完整 JSON Schema
→ Tool 参数使用严格 Schema
→ 输出解析并通过 Pydantic 校验
→ 失败后限次修复，仍失败则转人工复核
```

### 项目映射

资料研判 Agent 的输入输出约束包括：

- Tool 使用原生 Function Calling；
- Tool 参数设置类型、必填字段、范围和 `additionalProperties=false`；
- 最终对象必须符合 `AssessmentDraft`；
- `confidence` 限制在 0～1；
- 维度和政策因子不能重复；
- 证据引用必须保留完整 `EvidenceRef`；
- 信息不足时使用 `unknown`、缺失材料或待确认问题；
- 最终结果还要经过 `PolicyEngine` 和 Evidence Gate。

当模型输出不合法时：

1. 保存校验错误；
2. 将完整 `AssessmentDraft` Schema 再发给模型；
3. 默认只允许修复 1 次；
4. 仍失败则生成保守的人工复核草稿。

进入强制汇总阶段时，适配器会移除 `tools` 和 `tool_choice`，禁止模型继续调用 Tool，只能根据已有证据形成最终结果。

### 三个常见误区

| 误区 | 正确理解 |
|---|---|
| 温度设为 0 就一定返回合法 JSON | 低温只降低随机性，不能替代校验 |
| JSON 能解析就代表正确 | 类型、枚举、范围和业务约束仍可能错误 |
| 无限让模型修复更稳 | 会增加延迟和成本，也可能形成死循环 |

### 为什么规则要放在模型外

报价审批、证据完整性和人工确认属于硬约束。即使模型输出结构正确，也不能让模型自己决定是否绕过红线。

正确顺序是：

```text
模型生成候选
→ 程序校验结构
→ Policy/Gate 校验业务规则和证据
→ 必要时人工确认
```

### 30 秒回答

> 我把模型输出视为不可信外部输入。项目中 Tool 参数使用严格 JSON Schema，最终研判结果用 Pydantic 的 `AssessmentDraft` 校验，校验失败只修复一次，仍失败就转人工复核。模型生成之后还要经过独立的 PolicyEngine 和证据门，因此“JSON 合法”不等于“业务可下发”。进入预算末期时还会关闭 Tool Calling，避免模型继续循环。

## 卡片 4：怎样优化延迟、Token 和成本？

**一句话：** 先消灭无效上下文、无效 Tool 和无效重试，再考虑换小模型。

### 延迟拆解

```text
端到端耗时
= 输入解析
+ 模型排队与推理
+ Tool/检索往返
+ 输出校验与修复
+ 人工等待
```

只看一次 LLM 请求耗时，会漏掉 Agent 最常见的长尾来源：多轮 Tool 往返和修复。

### 项目中已经采用的手段

- 首轮只做一次宽检索，不并发堆叠相近查询；
- 优先读取少量关键证据，再按缺口定向补查；
- 对 ReAct 轮数、Tool 总数、单轮调用和重复参数设置预算；
- 预算接近耗尽时强制汇总；
- Tool Schema 限制 `top_k` 等输入范围；
- 受控状态只放模型真正需要的信息；
- 低温生成降低无意义波动；
- 平台调用记录延迟、输入和输出规模。

资料研判 Agent 默认预算包括：

```text
最大 ReAct 循环：8
最大 Tool 调用：24
单轮最大 Tool：3
相同参数最多调用：2
输出修复：1
证据门修复：1
```

全局上限是安全网，实际运行还使用更小的自适应阶段预算，避免为了“用满预算”继续检索。

### 成本治理的正确指标

至少同时观察：

- 单次任务输入/输出 Token；
- 单次任务总成本；
- 每个成功任务成本；
- fallback 后成本变化；
- Tool 次数和修复次数；
- P50、P95，而不只是平均耗时；
- 质量门通过率和人工介入率。

### 当前项目的真实计量口径

平台 `ModelCallLog` 已记录：

- provider、model、endpoint 和状态；
- `latency_ms`；
- `input_chars`、`output_chars`；
- `estimated_cost`；
- trace、用户、HTTP 状态和错误摘要。

管理员接口可按最近 1～168 小时聚合调用次数、平均延迟、字符数和估算成本。

但当前估算公式是：

```text
(输入字符数 + 输出字符数) / 1000 × 每千字符配置单价
```

因此要诚实说明：

- 这是容量和成本趋势估算，不是真实 Token 账单；
- 目前没有区分不同模型的输入、输出 Token 单价；
- 配置单价默认为 0 时不会产生有效成本估算；
- 当前聚合提供平均延迟，不是 P95；
- 资料研判适配器虽然收到 provider `usage`，尚未形成每次 Agent 运行的 Token/成本聚合。

### 缓存怎样判断是否安全

适合缓存：

- 相同模型版本下的确定性解析；
- 不含用户权限差异的公共只读结果；
- 以文件哈希、Prompt 版本和模型版本组成完整缓存键的中间结果。

不应直接缓存：

- 与用户、项目权限有关但缓存键未隔离的结果；
- 实时价格、库存或政策状态；
- 包含人工修改的最终审批结论；
- Tool 或知识库版本变化后仍可能复用的旧结果。

当前系统没有把智能语义缓存包装成既有能力，面试时应把它作为后续优化方案。

### 30 秒回答

> Agent 优化不能只换小模型，我会先拆解端到端耗时，找出模型推理、Tool 往返、修复和人工等待中的主要长尾。项目通过自适应 Tool 预算、重复调用限制、少量关键证据读取和预算末期强制汇总减少无效调用。平台已经记录字符规模、延迟和估算成本，但字符成本不等于真实 Token 账单，资料研判 Agent 的 usage 也还没有完成单次运行聚合，这是下一步成本治理重点。

## 卡片 5：怎样安全升级模型或 Prompt？

**一句话：** 没有固定输入、完整版本和多维指标，就无法证明新版本更好。

### 发布流程

```text
冻结评测集
→ 固定 Prompt、模型、Tool、Policy 和检索版本
→ 离线回归
→ 影子或小流量灰度
→ 对比质量、P95、失败率和成本
→ 达标后扩大流量，异常立即回滚
```

### 必须冻结的版本

- 模型和实际 primary/fallback 路由；
- Prompt；
- Agent Graph 和 State Schema；
- Tool Schema；
- Policy；
- 文档 manifest 和索引；
- 评测数据集指纹。

资料研判 Agent 当前已记录的主要版本包括：

```text
graph：bid_intake_graph_v3
state：bid_intake_state_v3
prompt：bid_intake_prompt_v3
policy：qs_bid_decision_policy_2026_01
tool schema：tender_evidence_tools_v1
model：运行时实际模型 ID 和路由
```

### 评价不能只看“答案更好”

| 维度 | 示例指标 |
|---|---|
| 结构 | JSON 合法率、修复率 |
| 事实与证据 | 引用支持率、缺证据率 |
| 业务 | 金额偏差、缺项率、打回率、人工修改率 |
| 可靠性 | 成功率、fallback 率、超时率 |
| 性能 | 端到端 P50/P95、Tool 次数 |
| 成本 | 单次成本、每个成功任务成本 |

### 当前报价 Prompt 回归能力

系统已能从真实确认、打回和字段修改记录构建回归用例，并统计：

- 金额绝对偏差和偏差率；
- 总价精确匹配率；
- 格式错误率；
- 缺项率；
- 打回率；
- 综合分和基线差异。

边界必须说清：

> 当前回归运行主要对已沉淀案例及其 Prompt 版本进行统计比较，候选 Prompt 自动调用模型重跑仍未完成。

所以它是可用的反馈基线，不应包装成完整的自动化模型评测平台。

### 30 秒回答

> 模型或 Prompt 升级前，我会固定数据集和模型、Prompt、Tool、Policy、索引版本，离线比较结构合法率、证据支持率、金额偏差、缺项率、P95、失败率和单次成本，再做小流量灰度并保留快速回滚。报价中台已经能从真实反馈构建 Prompt 回归案例并比较历史版本，但候选 Prompt 自动重跑还没完成，我会把它作为现有边界而不是夸大能力。

## 高频追问

| 追问 | 回答 |
|---|---|
| 为什么 429 不能无限重试 | 会放大拥塞；应退避、限制次数，必要时 fallback 或排队 |
| 401 应该重试吗 | 通常不应原路盲重试，应修复凭证或切换已验证的备用配置 |
| fallback 成功就算恢复了吗 | 可用性恢复，但质量、延迟和成本可能已经变化 |
| JSON Mode 和 Schema 校验一样吗 | 不一样；前者偏向格式，后者还检查字段、类型、范围和业务约束 |
| 温度低有什么用 | 降低随机波动，但不能保证事实正确或结构合法 |
| 为什么要限制修复次数 | 防止成本、时延和循环失控 |
| 字符成本能代替 Token 成本吗 | 不能，只能用于粗略趋势 |
| 为什么不缓存最终审批结果 | 权限、数据版本和人工决策变化后可能错误复用 |
| 小模型何时可以替换大模型 | 在同一固定评测集通过质量硬门后，再比较延迟和成本 |

记忆口诀：

> 能力定候选，质量过硬门，网关保调用，Schema 保消费，预算控往返，评测管发布。
