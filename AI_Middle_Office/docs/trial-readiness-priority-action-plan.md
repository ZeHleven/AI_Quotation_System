# 试运行就绪度优先行动清单与分阶段规划

更新时间：2026-06-03

## 1. 背景与目标

当前系统已经具备登录/RBAC 权限、报价工作台、需求单标准化、成本数据库、报价运营、项目进度、效率看板和经营总览等模块。现阶段不再以继续扩展业务模块为主要目标，而是把系统从“功能很多”收束成“小范围试运行随时可用、可演示、可交付、可维护”的状态。

本计划遵循以下方向：

- 冻结业务功能边界。
- 优先提升部署稳定性和试运行可恢复能力。
- 优先打磨核心路径体验，而不是继续增加复杂页面。
- 准备演示数据、试运行材料和交付文档。
- 等真实业务窗口出现后，再基于真实样本推进跨部门规则和正式生产上线。

## 2. 当前边界

### 2.1 当前适合做

- Windows 临时内网服务器启动、重启、健康检查和异常恢复。
- 其他电脑访问 Windows 主机的内网访问说明。
- 账号、权限、初始密码和密码维护的标准说明。
- 备份、恢复、日志和故障排查的试运行级说明。
- 登录、报价、需求单标准化、成本库、项目进度、经营总览等核心路径的体验梳理。
- 演示数据、演示脚本、试运行样例和反馈模板。
- 有效需求单、报价退回、无底价处理、项目节点证据、异常上报、每周指标等规则模板。
- 正式上线前的服务器、域名、HTTPS、备份、监控和权限审计清单。

### 2.2 当前不适合做

- 新增采购、合同、回款、复杂财务经营模型等跨部门模块。
- 在没有真实样本的情况下继续优化 AI 判断逻辑。
- 把项目进度规则、证据规则和跨部门交接规则过早写死。
- 把演示数据包装成真实 ROI 或真实经营成果。
- 为了“看起来完整”继续堆叠功能。

## 3. 优先行动总览

| 优先级 | 行动项 | 目的 | 建议阶段 |
|---|---|---|---|
| P0 | Windows 内网启动与访问收口 | 让系统能稳定启动，并让其他电脑知道访问哪里 | 阶段 1 |
| P0 | 健康检查与异常恢复收口 | 服务异常后能快速定位、重启和确认恢复 | 阶段 1 |
| P0 | 账号权限和安全口径收口 | 避免试运行中继续使用过时账号口径 | 阶段 2 |
| P0 | 备份与恢复说明收口 | 试运行前具备最低限度数据安全保障 | 阶段 2 |
| P0 | 试运行启动当天检查表 | 每次启动前用同一标准判断是否可用 | 阶段 3 |
| P1 | 试运行版用户手册 | 让业务员、管理员、老板知道该怎么用 | 阶段 3 |
| P1 | 前端关键路径体验验收 | 验证核心页面不是“能打开”而是“能顺畅完成任务” | 阶段 4 |
| P1 | 演示数据与沙盒包 | 在没有真实完整资料时支撑演示和回归 | 阶段 4 |
| P2 | 规则模板包 | 为后续老板/部门拍板预留标准模板 | 阶段 5 |
| P2 | 正式上线清单 | 把试运行和正式生产的边界讲清楚 | 阶段 5 |

## 4. 分阶段详细规划

## 阶段 0：冻结边界与基线确认

### 目标

确认本轮只做试运行就绪工作，不新增业务模块，不改变报价、成本、项目进度和 AI 判断规则。

### 范围

- 汇总当前系统模块和已完成能力。
- 确认本轮不做项。
- 确认当前环境基线：Windows 主机、CentOS 依赖、FastAPI 端口、Vite 管理台、旧 HTML 报价工作台。
- 确认哪些文档是当前有效，哪些文档需要更新或降级为历史参考。

### 具体任务

1. 建立“试运行就绪工作目录索引”，列出后续所有试运行相关文档。
2. 在 README 或专门索引文档中标注当前主入口文档。
3. 标注旧文档中容易误导试运行的内容，例如过时访问地址、过时账号密码、旧 materials 口径。
4. 明确本轮不新增 Alembic、不改业务数据库结构、不新增跨部门业务模块。

### 产物

- 试运行文档索引。
- 过时文档修订清单。
- 当前有效系统边界说明。

### 验收标准

- 后续实施人员能一眼知道：当前要做的是试运行就绪，不是继续扩业务。
- 文档中不再把临时内网试运行描述成正式生产。
- 过时账号、过时访问地址和旧业务口径被识别出来并进入修订清单。

### 风险与处理

- 风险：文档太多，使用者不知道看哪份。
- 处理：创建一个试运行总入口，只保留必要链接，其他材料作为附录。

### 明确不做

- 不设计采购、合同、回款。
- 不新增复杂经营驾驶舱。
- 不改变报价和成本库规则。

## 阶段 1：Windows 内网启动与访问收口

### 目标

把当前 Windows 电脑作为临时内网服务器的运行方式讲清楚、做稳定，并让系统启动后明确显示当前可访问地址。

### 范围

- 一键启动和重启脚本。
- FastAPI 监听地址策略。
- 当前访问地址显示。
- Windows 防火墙放行说明。
- 健康检查。
- 服务异常后的恢复步骤。
- 计划任务或看门狗状态确认。

### 具体任务

1. 梳理启动脚本入口，明确哪个脚本是试运行推荐入口，哪个脚本只用于开发或应急。
2. 将启动模式区分为：
   - 本机开发模式：监听 `127.0.0.1`，只允许本机访问。
   - 内网试运行模式：监听 `0.0.0.0` 或指定内网 IP，允许同一局域网其他电脑访问。
3. 启动完成后输出：
   - 本机访问地址。
   - 内网访问地址。
   - FastAPI 端口。
   - 当前 Windows 主机 IP。
   - 重要依赖健康状态。
4. 检查 pid 文件和进程状态，避免 pid 文件过期但服务未运行。
5. 将 `/health/live` 和 `/health/ready` 作为启动后验收标准。
6. 增加或完善异常恢复说明：
   - FastAPI 未监听。
   - Celery worker 未启动。
   - CentOS 依赖不可达。
   - RAG 检索超时。
   - N8N webhook 不可达。
   - Windows IP 变化。
7. 明确 Windows 防火墙处理方式：
   - 试运行前人工确认是否放行端口。
   - 记录端口、协议和适用网络。
   - 不在未确认情况下自动打开外部访问。
8. 检查计划任务是否存在，若使用计划任务，文档说明如何安装、查看、禁用和手动恢复。

### 产物

- 试运行启动说明。
- 内网访问说明。
- 异常恢复手册第一版。
- 启动健康检查清单。

### 验收标准

- 在 Windows 主机上执行推荐启动入口后，能看到明确访问地址。
- 本机能打开登录页。
- 同一局域网另一台电脑能打开登录页。
- `/health/ready` 返回 ready。
- 关闭 FastAPI 后，恢复步骤能在 5 分钟内指导重新启动。
- 当 CentOS 依赖不可用时，检查结果能明确指出是哪一项失败。

### 风险与处理

- 风险：Windows IP 会变化，其他电脑访问地址失效。
- 处理：文档中明确这是临时试运行方案；每次启动显示当前 IP；正式上线前迁移固定服务器或固定域名。

- 风险：监听 `0.0.0.0` 后暴露范围扩大。
- 处理：仅限内网试运行，保持 `PUBLIC_ACCESS_ENABLED=false`，不对公网开放。

### 明确不做

- 不配置公网访问。
- 不配置正式 HTTPS。
- 不把个人电脑方案描述成正式生产方案。

## 阶段 2：账号权限、安全口径与备份恢复收口

### 目标

让试运行人员使用受控账号进入系统，并在试运行前具备最低限度的数据备份和恢复说明。

### 范围

- 管理员账号。
- 业务员账号。
- 成本库相关角色。
- 老板/只读看板角色。
- 初始密码和强制改密。
- 账号禁用、重置密码和角色调整。
- 数据库和对象存储备份。
- 恢复演练说明。

### 具体任务

1. 修订过时账号说明，移除或降级 `admin / 123` 这类历史口径。
2. 将应急账号脚本明确标注为“救援脚本”，不能作为日常账号维护方式。
3. 整理试运行账号模型：
   - 系统管理员。
   - 报价业务员。
   - 成本库查看/编辑/审核/导出角色。
   - 项目进度维护人员。
   - 老板/管理层只读角色。
4. 写清楚每类角色可见模块和不可见模块。
5. 建立试运行账号初始化表：
   - 用户名。
   - 姓名。
   - 部门。
   - 角色。
   - 是否强制改密。
   - 是否启用。
6. 统一备份入口，明确推荐使用的备份脚本。
7. 将旧备份脚本中与旧 materials 或敏感默认密码相关的内容标为历史参考或待修订。
8. 增加恢复说明：
   - 备份文件在哪里。
   - 备份包含哪些内容。
   - 什么时候需要恢复。
   - 恢复前要先通知谁。
   - 恢复后如何验收。
9. 制定试运行期间最小备份频率：
   - 试运行前一次完整备份。
   - 每日结束后一次备份。
   - 重要演示或真实样本录入前后各一次备份。

### 产物

- 账号权限说明。
- 试运行账号初始化模板。
- 密码重置和账号停用说明。
- 备份与恢复手册。
- 备份验收记录模板。

### 验收标准

- 新用户不依赖共享管理员账号。
- 管理员知道如何创建、停用、重置账号。
- 业务员登录后只看到自己需要的核心模块。
- 成本库敏感操作有角色边界。
- 能找到最近一次备份，并能说明备份包含哪些内容。

### 风险与处理

- 风险：试运行为了方便共用管理员账号。
- 处理：试运行前准备个人账号；管理员账号只用于配置和救援。

- 风险：有备份但没人知道如何恢复。
- 处理：至少做一次恢复流程桌面推演，不一定立即恢复到真实环境。

### 明确不做

- 不接入企业统一身份系统。
- 不开放公网注册。
- 不为临时试运行做复杂审批流。

## 阶段 3：试运行启动当天检查与交付文档收口

### 目标

把系统从“开发者知道怎么跑”整理成“非开发人员也能按清单确认是否可以试运行”。

### 范围

- 启动当天检查表。
- 操作员手册。
- 管理员手册。
- 故障排查手册。
- 风险边界说明。
- 试运行反馈记录。

### 具体任务

1. 建立试运行启动当天检查表，至少包含：
   - Windows 主机开机并联网。
   - 当前 Windows IP 已记录。
   - FastAPI 已启动。
   - `/health/ready` 正常。
   - Celery worker 正常。
   - CentOS MySQL/Redis/RAG/N8N/MinIO 可达。
   - Alembic 版本符合当前 head。
   - `PUBLIC_ACCESS_ENABLED=false`。
   - 最近一次备份已完成。
   - 试运行账号已准备。
   - 演示样例已准备。
2. 更新试运行版用户手册：
   - 登录入口。
   - 报价工作台流程。
   - 需求单标准化流程。
   - 成本库查看和审核边界。
   - 项目进度页面怎么填。
   - 老板驾驶舱看哪些指标。
   - 常见错误提示怎么处理。
3. 更新管理员手册：
   - 用户和角色维护。
   - 健康检查。
   - 备份。
   - 重启。
   - 日志位置。
   - 异常升级路径。
4. 建立故障排查手册：
   - 其他电脑打不开。
   - 登录失败。
   - 报价任务卡住。
   - RAG 不返回。
   - N8N 不可达。
   - 成本库同步异常。
   - 项目进度保存失败。
5. 建立风险边界说明：
   - 当前是小范围内网试运行。
   - 不是正式生产环境。
   - Windows 主机关机、换网、IP 变化会导致访问中断。
   - 演示数据不能代表真实 ROI。
   - 跨部门规则尚未正式拍板。

### 产物

- 试运行启动当天检查表。
- 试运行版用户手册。
- 试运行版管理员手册。
- 故障排查手册。
- 风险边界说明。

### 验收标准

- 非开发人员可以按检查表判断系统是否可用。
- 业务员可以按手册完成一次报价演示。
- 管理员可以按手册完成一次账号创建和一次服务重启。
- 试运行风险能够被清楚解释给老板和参与人员。

### 风险与处理

- 风险：文档太长，没人看。
- 处理：主文档只保留核心步骤，详细说明放附录。

- 风险：用户手册和真实页面文案不一致。
- 处理：每次前端体验变更后，同步更新手册截图或文字。

### 明确不做

- 不把所有开发文档都塞进用户手册。
- 不要求业务员理解系统架构。
- 不把试运行文档写成正式生产运维制度。

## 阶段 4：核心前端体验与演示/沙盒包

### 目标

让业务员、管理员和老板在不学习复杂系统的情况下，能完成最关键的演示和试运行路径。

### 范围

- 登录后入口清晰度。
- 角色可见模块。
- 报价工作台步骤。
- 需求单标准化流程。
- 成本库关键操作。
- 项目进度简化体验。
- 老板经营总览。
- 空状态、错误提示、加载状态。
- 演示数据和沙盒样例。

### 具体任务

1. 以角色为单位做页面走查：
   - 业务员：登录、上传需求单、标准化、发起报价、预审确认、查看历史。
   - 成本库人员：查看成本条目、审核 draft、查看状态流向。
   - 项目人员：查看项目、更新任务、上传证据。
   - 老板：看经营总览、报价趋势、项目风险。
   - 管理员：用户维护、权限配置、健康检查入口。
2. 补齐关键页面的空状态：
   - 没有报价任务。
   - 没有成本条目。
   - 没有项目。
   - 没有看板数据。
   - 没有权限访问。
3. 补齐关键错误提示：
   - 文件格式不支持。
   - 需求单无法解析。
   - 报价任务失败。
   - 服务暂不可用。
   - 无权限操作。
4. 进行桌面和窄屏视觉检查：
   - 文字不溢出。
   - 按钮不重叠。
   - 表格可读。
   - 弹窗可关闭。
   - 加载状态不会让用户误以为系统卡死。
5. 建立演示数据包：
   - 1 份标准需求单样例。
   - 1 份复杂需求单样例。
   - 若干成本库 active/draft 样例。
   - 1 个报价成功样例。
   - 1 个报价退回样例。
   - 1 个无底价 draft 沉淀样例。
   - 1 个项目进度样例。
   - 1 个老板看板样例。
6. 建立演示脚本：
   - 5 分钟老板版。
   - 15 分钟业务员版。
   - 30 分钟管理员版。
7. 给演示材料加上明确说明：
   - 演示数据只用于展示系统能力。
   - 演示数据不能证明真实业务收益。
   - 真实 ROI 需要后续真实试运行样本验证。

### 产物

- 核心路径体验验收记录。
- 前端问题清单。
- 演示数据包。
- 演示脚本。
- 沙盒使用说明。

### 验收标准

- 业务员能在引导下完成一次需求单到报价预审的演示。
- 老板能在 5 分钟内看懂系统解决了什么问题。
- 管理员能找到账号、权限、健康检查和备份说明。
- 演示时不需要临时解释大量系统内部细节。

### 风险与处理

- 风险：演示数据过于理想化。
- 处理：至少保留一个复杂样例和一个异常样例，展示系统边界。

- 风险：为了演示继续加功能。
- 处理：只改体验、提示和材料，不新增业务链路。

### 明确不做

- 不新增花哨首页。
- 不新增复杂老板驾驶舱。
- 不把演示样例沉淀为真实业务结论。

## 阶段 5：规则模板与正式上线清单

### 目标

为后续真实业务窗口准备可拍板模板，同时把试运行和正式上线之间的差距讲清楚。

### 范围

- 有效需求单规则模板。
- 报价退回原因模板。
- 无底价项目处理模板。
- 项目节点证据要求模板。
- 异常上报模板。
- 每周经营指标模板。
- 正式上线前检查清单。

### 具体任务

1. 建立有效需求单规则模板：
   - 必填字段。
   - 可接受缺失项。
   - 需要人工确认的情况。
   - 不能进入报价的阻断条件。
2. 建立报价退回原因模板：
   - 需求不清。
   - 数量异常。
   - 单位不一致。
   - 无底价参考。
   - AI 预审不可信。
   - 需要业务员补充说明。
3. 建立无底价项目处理模板：
   - AI 可估价但必须人工确认。
   - 确认后可沉淀为 draft。
   - draft 不参与后续报价/RAG/兜底。
   - 人工审核 active 后才参与正式报价参考。
4. 建立项目节点证据要求模板：
   - 节点名称。
   - 是否关键节点。
   - 证据类型。
   - 是否硬门禁。
   - 缺证据处理方式。
5. 建立异常上报模板：
   - 异常类型。
   - 发现人。
   - 影响范围。
   - 临时处理。
   - 需要谁拍板。
   - 后续动作。
6. 建立每周经营指标模板：
   - 报价数量。
   - 报价成功率。
   - 首次响应速度。
   - 无底价项目数量。
   - 成本库 draft 转 active 情况。
   - 项目关键节点风险。
7. 建立正式上线清单：
   - 固定服务器。
   - 固定 IP 或域名。
   - HTTPS。
   - 数据库备份策略。
   - 备份恢复演练。
   - 日志和监控。
   - 账号权限审计。
   - 公网访问安全要求。
   - 运维负责人。
   - 生产故障响应机制。

### 产物

- 规则模板包。
- 每周试运行复盘模板。
- 正式上线前检查清单。
- 试运行转生产差距说明。

### 验收标准

- 老板或部门负责人可以基于模板快速拍板，而不是从零讨论。
- 模板不会把当前尚未验证的规则直接写死到系统中。
- 试运行参与者知道哪些问题是系统问题，哪些问题需要公司规则拍板。
- 正式上线前仍需补齐的服务器、安全、备份和运维事项清楚可见。

### 风险与处理

- 风险：模板被误认为最终制度。
- 处理：所有模板标题标注“待业务拍板”，并保留版本和确认人字段。

- 风险：正式上线清单被忽略。
- 处理：在风险边界说明中明确：未完成正式上线清单前，不建议扩大使用范围。

### 明确不做

- 不替公司决定最终跨部门流程。
- 不把规则模板直接变成系统强校验。
- 不承诺试运行系统具备正式生产 SLA。

## 5. 建议实施顺序

建议按以下顺序推进：

1. 阶段 1：Windows 内网启动与访问收口。
2. 阶段 2：账号权限、安全口径与备份恢复收口。
3. 阶段 3：试运行启动当天检查与交付文档收口。
4. 阶段 4：核心前端体验与演示/沙盒包。
5. 阶段 5：规则模板与正式上线清单。
6. 阶段 0 的边界冻结在所有阶段持续执行。

原因是：如果系统本身不能稳定启动、不能被其他电脑访问、账号和备份说不清楚，那么前端体验、演示脚本和规则模板都会缺少可靠基础。

## 6. 每阶段完成后的决策点

| 阶段 | 完成后判断 | 通过后动作 | 未通过动作 |
|---|---|---|---|
| 阶段 1 | 系统能否稳定启动并被内网访问 | 进入账号和备份收口 | 继续修启动链路，不做演示 |
| 阶段 2 | 账号和备份是否足够支撑试运行 | 进入启动检查和文档收口 | 先修安全口径和备份说明 |
| 阶段 3 | 非开发人员能否按文档启动和排障 | 进入前端体验和演示包 | 精简文档并补缺失步骤 |
| 阶段 4 | 业务员/老板能否看懂核心路径 | 进入规则模板和上线清单 | 先修核心页面体验和演示材料 |
| 阶段 5 | 是否具备等待真实业务窗口的交付材料 | 准备小范围试运行启动确认 | 保持冻结边界，补齐模板 |

## 7. 试运行启动前的最低通过线

进入真实小范围试运行前，至少需要满足：

- Windows 主机推荐启动方式稳定。
- 当前内网访问地址明确。
- 其他电脑可以打开登录页。
- `/health/ready` 正常。
- CentOS 依赖可达。
- Celery worker 正常。
- 最近一次备份完成。
- 试运行账号准备完成。
- 用户手册和管理员手册可用。
- 演示样例准备完成。
- 风险边界说明已向参与人员说明。
- 明确当前不是正式生产环境。

## 8. 后续建议

下一步建议优先实施“阶段 1：Windows 内网启动与访问收口”。这是所有后续试运行、演示和交付材料的地基。完成阶段 1 后，再进入账号、备份和文档收口，避免在服务不稳定的情况下过早打磨演示材料。
