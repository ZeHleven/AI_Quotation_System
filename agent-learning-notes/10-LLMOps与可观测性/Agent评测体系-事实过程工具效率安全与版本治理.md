# Agent 评测体系：事实、过程、工具、效率、安全与版本治理

## 核心结论

“任务完成了”不是生产级 Agent 的充分条件。还要回答：

```text
结论是否正确且有证据？
过程是否合理且可恢复？
工具是否选对、参数是否正确？
成本和延迟是否可接受？
是否越权，是否在高风险动作前停下？
这次结果由哪套 Prompt、模型、工具和数据产生？
```

完整评测闭环：

```text
定义成功标准
→ 建立金标与风险分层
→ 固定运行版本包
→ 离线回放
→ 多维指标与失败分类
→ 发布门
→ 灰度和线上监控
→ 人工反馈回流
```

> 资料说明：本笔记依据视频的公开简介、摘要和章节结构整理，并结合当前 AI 智能报价中台代码与验收记录扩展，不是逐字字幕。

## 1. 事实正确不等于语言通顺

大模型优化的是“生成合理的下一个内容”，不是从事实数据库中复制答案。因此最危险的结果往往是：

```text
表达流畅
+ 语气坚定
+ 没有可靠来源
+ 被下游当成事实执行
```

事实类任务需要把生成与核查分开：

```text
生成候选答案
→ 提取可核查断言
→ 检索或调用权威工具
→ 判断支持、冲突、过期或证据不足
→ 按风险决定回答、降级、补证据或转人工
```

### 什么是可核查断言

一句回答可能包含多个事实：

```text
该项目投标截止时间为 8 月 20 日，
保证金为 50 万元，
我方资质满足要求。
```

应拆成：

```json
[
  {
    "claim_id": "deadline",
    "claim": "投标截止时间为 8 月 20 日",
    "risk": "high",
    "required_source": "招标文件或补遗"
  },
  {
    "claim_id": "deposit",
    "claim": "保证金为 50 万元",
    "risk": "high",
    "required_source": "招标文件或补遗"
  },
  {
    "claim_id": "qualification",
    "claim": "我方资质满足要求",
    "risk": "critical",
    "required_source": "招标要求 + 企业资质数据"
  }
]
```

第三条不能只凭招标文件判断。招标文件只说明要求，是否满足还需要内部企业数据。

### 断言核验结果

| 状态 | 含义 | 系统动作 |
|---|---|---|
| supported | 权威证据明确支持 | 可引用 |
| contradicted | 权威来源与断言冲突 | 更正或阻断 |
| insufficient | 证据不足 | 标记未知或补资料 |
| stale | 来源已过期或被新版本替代 | 获取当前版本 |
| out_of_scope | 超出系统知识或权限 | 拒答或转人工 |

不能把“检索到相似片段”直接等同于 `supported`。还要检查来源、版本、适用对象和语义是否真正支持断言。

### 事实质量指标

| 指标 | 含义 |
|---|---|
| Claim Accuracy | 断言与金标一致的比例 |
| Evidence Coverage | 需要证据的断言中，有有效证据的比例 |
| Citation Precision | 引用是否真正支持对应断言 |
| Contradiction Rate | 与权威来源冲突的断言比例 |
| Appropriate Abstention | 证据不足时正确降级或拒答的比例 |
| High-risk Miss Rate | 高风险错误或缺失未被拦截的比例 |

高风险业务不能只看平均准确率。即使整体 98%，漏掉一次投标硬红线也可能不可接受。

## 2. Agent 五维评测

视频给出的五个维度可以整理为以下工程模型。

### 2.1 任务结果

关注最终业务目标：

- 任务成功率；
- 字段、分类或金额准确率；
- 事实断言正确率；
- 高风险问题召回率；
- 人工打回率；
- 人工修改率与修改幅度；
- 用户是否最终完成业务动作。

示例：

```text
task_success_rate
= 达到业务验收条件的任务数 / 全部有效任务数
```

“生成了 JSON”只是技术完成，不一定是业务成功。

### 2.2 过程质量

关注 Agent 是如何完成任务的：

- 规划是否覆盖必要步骤；
- 是否先获取证据再下结论；
- 是否发生无效循环；
- 出错后能否自我修正；
- 是否在预算耗尽时安全停止；
- 是否在证据不足时转人工；
- 状态迁移与恢复是否正确。

结果偶然正确，但过程存在越权、跳步或不可恢复，不应判为高质量。

### 2.3 工具调用质量

- 工具选择正确率；
- 参数合法率；
- 工具成功率；
- 必要工具漏调率；
- 无效工具调用比例；
- 相同参数重复调用率；
- 失败重试次数；
- 未授权工具请求次数。

两个常用方向：

```text
Tool Precision
= 有效且必要的工具调用 / 全部工具调用

Tool Recall
= 已完成的必要工具调用 / 应执行的必要工具调用
```

只追求 Precision，可能因为少调用而漏证据；只追求 Recall，可能造成过度调用和成本浪费。

### 2.4 成本与时延

至少分开记录：

```text
排队等待
上下文构建
模型首响应
模型生成
工具执行
重试与退避
人工等待
端到端总耗时
```

成本包括：

- 输入、输出和缓存 Token；
- 模型调用费用；
- 工具调用次数与费用；
- OCR、VLM、存储和向量检索成本；
- 重试与无效循环带来的浪费；
- 人工审核时间。

建议同时看：

```text
平均值 + P50 + P95 + P99
单位成功任务成本
单位正确结论成本
```

平均延迟可能掩盖少量极慢任务。

### 2.5 安全与可控性

- 越权工具调用率；
- 跨项目或跨账户访问次数；
- Prompt Injection 阻断率；
- 高风险操作是否经过人工确认；
- 敏感信息泄漏率；
- 不安全建议率；
- 取消、暂停和人工接管是否有效；
- 失败后是否留下可审计记录。

安全指标通常属于硬门槛：

```text
跨租户访问 = 0
审批绕过 = 0
危险写操作重复执行 = 0
硬红线召回率 = 100%
```

不能用“平均得分更高”抵消一次严重越权。

## 3. 评测对象不只是最终答案

一次 Agent 运行可以分成四种被评测对象：

| 对象 | 评测内容 |
|---|---|
| Output | 结构、事实、业务结果、引用 |
| Trajectory | 规划、循环、工具顺序、修复与停止 |
| System | 延迟、成本、重试、可用性、恢复 |
| Business | 人工节省、采纳率、周期和实际风险 |

评测数据必须能从 Trace 还原：

```text
输入版本
→ LLM 安全上下文
→ 计划与 Tool Call
→ 授权
→ Observation
→ 结构化结果
→ 规则和证据门
→ 人工最终结果
```

只有最终文本，就无法判断错误来自模型、检索、工具、规则还是输入。

## 4. Prompt 是运行环境，必须版本化

Prompt 的一个词变化就可能改变工具选择、输出格式和风险判断，因此要像代码一样管理。

视频强调至少记录：

- Prompt 模板版本；
- 实际运行 Prompt；
- 模型名称与参数；
- 工具和知识库版本。

生产系统还应形成完整的运行版本包：

```json
{
  "application_release": "2026.07.28",
  "graph_version": "bid_intake_graph_v3",
  "state_schema_version": "bid_intake_state_v3",
  "prompt_name": "bid_intake",
  "prompt_version": "bid_intake_prompt_v3",
  "prompt_template_hash": "sha256:...",
  "model_id": "provider/model-version",
  "model_parameters": {
    "temperature": 0.1
  },
  "policy_version": "qs_bid_decision_policy_2026_01",
  "tool_schema_version": "tender_evidence_tools_v1",
  "knowledge_or_manifest_version": 12,
  "knowledge_or_manifest_hash": "sha256:..."
}
```

### 是否保存完整 Prompt

为了复现，确实需要知道模型实际收到了什么；但普通日志不应直接保存敏感正文。

推荐分层：

```text
普通 Trace
→ 模板版本、哈希、变量名、脱敏摘要和输入引用

受控审计存储
→ 经加密和访问控制的实际渲染 Prompt
```

密钥、token、个人敏感信息和无必要的完整文档正文不能直接记录。

### Prompt 生命周期

```text
draft
→ candidate
→ shadow
→ canary
→ active
→ retired / rolled_back
```

不要直接覆盖 `active` 模板，否则旧结果无法复现，也无法快速回滚。

### 三种发布方式

| 方式 | 用途 |
|---|---|
| Shadow | 同一输入运行候选版本，但结果不影响业务 |
| Canary | 少量真实流量使用候选版本 |
| A/B | 稳定分组比较两个版本的业务效果 |

高风险业务优先 Shadow，再 Canary；不能用真实用户直接承担未经评测的试验风险。

## 5. Golden Dataset 的治理

### 案例结构

```json
{
  "case_id": "bid_eval_001",
  "input_reference": "immutable://...",
  "input_version": "manifest_v12",
  "expected_output": {},
  "required_claims": [],
  "required_tools": [],
  "forbidden_actions": [],
  "expected_decision": "manual_review",
  "hard_stop_expected": true,
  "allowed_error": {},
  "tags": ["qualification", "high_risk"],
  "gold_version": 3,
  "review_status": "approved"
}
```

### 样本分层

评测集不能只有正常案例，应包含：

- 高频正常任务；
- 缺字段和缺证据；
- 文档版本冲突；
- 工具超时、部分成功和错误 Schema；
- Prompt Injection；
- 高风险边界；
- 模型回退；
- 长上下文和高成本任务；
- 历史真实失败案例。

### Development 与 Holdout

```text
Development
→ 调 Prompt、规则和阈值

Holdout
→ 最终盲测，只用于发布判断
```

同一项目的不同版本不能分散到两组，否则会发生数据泄漏。Holdout 逐条答案也不应向调参者提前暴露。

### 金标不是永久真理

业务规则、价格、资质和政策会变化。金标需要：

- 创建人和复核人；
- 来源与依据；
- 生效时间；
- 修订版本；
- 不可变历史；
- 定期复审。

修订应新增版本，不能覆盖旧金标，否则历史评测无法复现。

## 6. 选择正确的评测器

优先级：

```text
确定性代码
→ 权威工具或数据库
→ 领域专家金标
→ LLM-as-a-Judge
```

### 确定性评测

适合：

- JSON Schema；
- 必填字段；
- 数值误差；
- 引用 ID 是否存在；
- 工具参数范围；
- 权限与状态迁移；
- 延迟和 Token。

### 专家评测

适合：

- 报价是否合理；
- 风险等级；
- 经营决策；
- 证据是否足以支持高风险结论。

### LLM-as-a-Judge

适合大规模初筛、摘要质量和开放式比较，但要控制：

- Judge Prompt 和模型版本；
- 评分量表；
- 位置偏差和文风偏好；
- Judge 与被测模型同源偏差；
- 多次评分一致性；
- 定期人工抽检。

高风险发布门不能只由一个 LLM Judge 决定。

## 7. 发布门：按风险阻止退化

一个候选版本的发布门可以写成：

```text
结构合法率不下降
任务成功率不下降
高风险召回率 = 100%
危险动作数 = 0
人工打回率不恶化
P95 延迟不超过预算
单位成功任务成本不超过预算
无跨租户和审批绕过
```

不同指标不能简单平均为一个总分。推荐：

```text
硬门槛
+ 质量比较
+ 成本时延预算
+ 人工批准
```

即使发布门通过，高风险策略也不应自动切换 active。

## 8. 离线评测与线上评测

### 离线

回答：

- 候选版本是否比基线更好；
- 哪类案例发生退化；
- 是否满足安全发布门；
- 失败能否稳定复现。

### 线上

回答：

- 真实流量是否发生分布漂移；
- 用户是否接受或修改结果；
- 人工接管率是否升高；
- 成本和 P95 是否恶化；
- 是否出现离线集未覆盖的新失败。

线上失败应回流：

```text
Trace
→ 人工复核
→ 失败分类
→ 新增或修订金标
→ 下次离线回放
```

没有反馈闭环，评测集会逐渐与真实业务脱节。

## 9. 当前报价中台的项目映射

### 9.1 统一报价 Prompt 回归

已经具备：

- 从人工确认、打回和逐字段修正生成锁定案例；
- 保存 Prompt、Workflow、Release、模型、知识集合和材料快照等运行元数据；
- 统计金额误差、漏项、格式错误、人工修改和打回率；
- 按 Prompt 版本聚合并与历史基线比较；
- 保留 AI 原始结果和人工最终结果。

关键边界：

> 当前 `prompt_regression` 主要统计已经发生过的历史案例，并未自动使用同一固定输入重新调用候选 Prompt。

因此它更准确的定位是：

```text
线上反馈沉淀
+ 历史版本质量报告
+ 候选重跑的数据基础
```

真正的候选 Prompt 回归仍需：

```text
冻结输入
→ 运行 baseline
→ 运行 candidate
→ 保存两个完整版本包
→ 在相同金标上比较
→ 通过发布门后灰度
```

这与项目当前暂缓的“候选 Prompt 自动重跑”一致。

### 9.2 报价资料研判 Agent

已经具备：

| 评测维度 | 当前实现 |
|---|---|
| 事实与证据 | EvidenceRef 校验、资料版本哈希、高风险结论必须有证据且读过上下文 |
| 任务结果 | 总经办金标、决策一致率、危险报价、硬红线召回 |
| 过程 | LangGraph Trace、推理轮数、停止原因、修复和人工暂停 |
| 工具 | 白名单、参数契约、总调用预算、重复参数调用限制 |
| 时延 | Trace 节点 `duration_ms`、运行开始和结束时间 |
| 安全 | 只读 MCP、scoped token、证据门、Human-in-the-loop |
| 版本 | graph、state schema、Prompt、policy、tool schema、model、manifest 版本 |
| 数据集治理 | 双人复核、项目级 Development/Holdout 隔离、不可变数据集指纹 |

### 9.3 已有发布门

政策候选评测已经要求：

- 无回放错误；
- 不增加危险报价；
- 硬红线召回率 100%；
- 金标一致率不低于 active；
- 金标一致率至少 80%；
- 即使通过，也不自动激活候选政策。

这体现了“安全指标不能被平均分抵消”。

### 9.4 仍需补强

1. **真实金标数量**：30 个临时验收样本证明流程可运行，但已在验收后清理，不能代表生产分布。
2. **候选 Prompt 自动重跑**：目前历史聚合多于真正的 baseline/candidate 同输入回放。
3. **断言级事实评测**：当前对高风险证据约束较强，但尚未对全部事实形成 supported/contradicted/insufficient 的断言级指标。
4. **Token 与货币成本**：资料研判 Trace 已记录节点时延和工具数，但未形成完整 Token、模型费用和单位成功任务成本。
5. **工具指标聚合**：单次 Trace 可见未授权、重复调用和预算停止，尚需形成版本级 Tool Precision、重复率和失败率面板。
6. **综合发布门**：政策发布门已成熟；Prompt、模型和图版本仍应统一接入质量、安全、成本和时延门槛。

## 10. 推荐的下一步实施顺序

### P0：形成统一 Eval Run

每次回放保存：

```text
dataset_version
baseline_bundle
candidate_bundle
case_results
five_dimension_metrics
failure_categories
release_gate
```

### P0：接通候选 Prompt 回放

复用现有锁定案例，但不覆盖历史结果，生成独立 candidate run。

### P0：积累真实金标

从人工确认、打回、资格冲突、证据缺失和运行事故中持续收集，并由不同人员复核。

### P1：补事实断言指标

优先覆盖：

- 截止时间；
- 保证金；
- 资格条件；
- 付款条件；
- 工期与范围；
- 硬红线。

### P1：补成本与工具面板

统计 Token、模型费用、调用次数、P95、重复调用率、无效调用率和人工接管率。

## 11. 面试表达

### 为什么事实回答不能只看通顺度？

> 流畅度只衡量表达质量。生产系统要把回答拆成可核查断言，用权威来源判断支持、冲突、过期或证据不足，并按风险决定自动回答、补证据或转人工。

### Agent 应该如何评测？

> 我会同时评测任务结果、执行过程、工具质量、成本时延和安全可控性。高风险召回、越权和审批绕过属于硬门槛，不能被平均得分抵消。

### 为什么要记录 Prompt 版本？

> Agent 的行为由 Prompt、模型、工具、知识和业务规则共同决定。只记录用户问题无法复现结果。每次运行要保存完整版本包，候选版本经过固定数据集回放、灰度和可回滚发布。

### 如何评价当前项目的 Prompt 回归？

> 项目已经把人工确认和修正沉淀成锁定案例，也能按 Prompt 版本统计金额误差、漏项和打回率。但目前主要是历史结果聚合，下一步要让同一固定输入真正重跑 baseline 与 candidate，才能形成严格的候选发布门。

## 12. 检查清单

### 数据

- [ ] 金标有来源、版本、创建人和复核人
- [ ] Development 与 Holdout 按项目隔离
- [ ] 正常、边界、失败、越权和高风险案例均有覆盖
- [ ] 线上新失败会回流评测集

### 版本

- [ ] Prompt、模型、参数、图、工具、政策和知识版本均已记录
- [ ] 实际运行 Prompt 可受控复现
- [ ] 候选版本不会覆盖 active
- [ ] 可快速回滚到完整旧版本包

### 指标

- [ ] 同时评测结果、过程、工具、效率和安全
- [ ] 事实结论有断言级证据指标
- [ ] 平均值之外查看 P95/P99 和失败分组
- [ ] 高风险指标使用硬门槛

### 发布

- [ ] baseline 与 candidate 使用相同固定输入
- [ ] Holdout 未参与调参
- [ ] 通过发布门后先 Shadow 或 Canary
- [ ] 高风险变更仍需人工批准
