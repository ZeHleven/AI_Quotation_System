# 异步任务工程：队列、状态机、取消、超时与恢复

> 配套实战：[练习 07：异步任务状态机、取消、超时、租约、Checkpoint 与恢复实战](./练习记录/07-异步任务状态机取消超时租约Checkpoint与恢复实战.md)

## 核心结论

异步任务不是把函数放进线程或队列就结束，而是一套可观察、可恢复的控制系统：

```text
任务事实
→ 调度
→ 领取
→ 执行
→ 进度
→ 取消/超时
→ 重试/恢复
→ 终态和审计
```

HTTP、队列和数据库各自负责不同问题：

| 组件 | 职责 |
|---|---|
| API | 验证输入和权限，创建任务，快速返回 |
| MySQL | 保存任务事实、状态、结果和事件 |
| Broker | 通知和调度待执行工作 |
| Worker | 执行模型、RAG、解析和工具调用 |
| Redis Result Backend | Celery 临时结果与控制，不替代业务状态表 |
| 前端 | 展示进度、失败、取消和人工确认 |

---

## 1. 哪些任务应该异步

- 执行时间不可预测；
- 超过普通 HTTP 等待体验；
- 依赖模型、OCR、RAG 或第三方服务；
- 需要进度、取消或恢复；
- 瞬时任务量可能超过处理容量；
- 可以与用户请求解耦。

短小、确定、无外部依赖的查询不应为了“架构高级”强行异步。

---

## 2. 任务状态机

推荐基础状态：

```text
queued → running → succeeded
                ↘ failed
queued/running  → cancel_requested → cancelled
queued/running  → timed_out
failed/timed_out/cancelled → 创建新的 retry job
```

复杂 Agent 可增加：

```text
waiting_human
resume_queued
recovering
blocked_stale_input
```

### 状态与阶段分开

`status` 保持少而稳定：

```text
queued / running / succeeded / failed / cancelled / timed_out
```

`stage` 描述执行位置：

```text
parsing_file
matching_cost
calling_n8n
retrieving_rag
building_preview
waiting_human
```

事件流保存每次变化，不能把所有细节塞进一个状态字段。

---

## 3. 创建任务的可靠顺序

基础顺序：

```text
校验权限与输入
→ MySQL 创建 queued 任务
→ 提交
→ 分发 job_id
→ 保存 broker task id
→ 返回 202
```

风险：

```text
数据库提交成功
→ 进程在分发前崩溃
→ 任务永久 queued
```

治理方式：

- Outbox；
- 定时扫描长期 queued 未分发任务；
- Dispatcher 状态字段；
- 调度操作幂等；
- 对 queued 年龄告警。

不要先发消息再写数据库，否则 Worker 可能拿到不存在的任务。

---

## 4. Worker 领取与所有权

队列消息只告诉 Worker“有任务”，业务库还应决定它是否有权执行。

最低保护：

```sql
UPDATE quote_jobs
SET status = 'running',
    started_at = NOW()
WHERE job_id = ?
  AND status = 'queued';
```

只有受影响行数为 1 的 Worker 获得执行权。

长任务可增加租约：

```text
worker_id
lease_token
lease_expires_at
last_heartbeat_at
```

所有写回带当前 `lease_token`，旧 Worker 失去租约后不能覆盖新结果。

## 5. 进度和心跳

进度不要只保存百分比。更有价值的是：

```json
{
  "stage": "retrieving_rag",
  "completed_items": 60,
  "total_items": 169,
  "message": "正在匹配成本与知识证据",
  "occurred_at": "...",
  "trace_id": "..."
}
```

心跳回答“近期是否有活动”，不能证明：

- Worker 仍持有任务所有权；
- 内部没有死循环；
- 外部副作用尚未重复；
- 任务一定能完成。

需要结合状态、租约、进度事件和下游指标。

---

## 6. 取消

取消是协作式协议，不是简单把状态改为 `cancelled`。

流程：

```text
用户请求取消
→ 权限与状态校验
→ cancel_requested
→ 通知队列/Worker
→ Worker 在安全点检查
→ 停止后续阶段
→ cancelled
```

如果外部副作用已经完成：

- 不能假装取消能够回滚；
- 应记录已完成步骤；
- 根据业务执行补偿；
- 向用户说明结果。

Worker 在以下位置检查取消：

- 每个批次开始前；
- 每次外部调用前后；
- 长循环固定间隔；
- 写最终结果前。

---

## 7. 超时

### 三种超时

| 类型 | 含义 |
|---|---|
| 请求超时 | 单次网络调用最长等待 |
| 任务时间上限 | 整个 Worker 任务最长执行 |
| 业务停滞超时 | 长时间无进度，被判定为异常 |

Celery 时间上限不等于业务超时。进程被终止后仍要：

- 写失败/超时状态；
- 释放租约；
- 保留 Checkpoint；
- 处理外部调用是否已成功；
- 决定是否重试。

---

## 8. 重试

### 新建重试任务还是覆盖原任务

推荐高风险任务新建重试记录：

```text
original_job_id
retry_job_id
attempt_no
retry_reason
```

优点：

- 每次尝试可审计；
- 输入、版本和结果不互相覆盖；
- 便于比较错误和耗时。

对内部步骤的短暂错误，可以在同一任务内有限重试，但也要记录尝试。

### 重试必须满足

- 错误可恢复；
- 操作幂等；
- 总预算未耗尽；
- 输入版本仍有效；
- 没有取消信号；
- 不会违反外部额度。

---

## 9. Checkpoint 与分批

长任务应在安全边界保存：

```text
已完成阶段
已完成行 Key
结构化中间结果
工具结果引用
输入版本
模型/Prompt/检索版本
下一步
```

### 分批执行

169 行报价可按 20 行分批：

- 控制模型上下文；
- 每批可独立重试；
- 记录行级完整性；
- 降低整单重做成本；
- 便于显示进度。

分批后必须处理：

- 结果顺序；
- 重复行；
- 缺失行；
- 批次部分成功；
- 合并时的输入版本；
- 未补价占位阻断。

## 10. Worker 并发模型

### IO 密集

模型、HTTP、数据库等待较多：

- 异步 IO；
- 线程；
- 合理连接池；
- 并发信号量。

### CPU 密集

PDF 解析、图像处理、Embedding 等：

- 多进程；
- 独立 Worker 队列；
- GPU 任务调度；
- 避免阻塞 API 事件循环。

### 不同任务分池

```text
short-io
long-llm
cpu-parse
gpu-embedding
priority-interactive
batch-low-priority
```

避免大文件任务把短查询完全堵住。

## 11. 当前 Celery 配置解读

`app/tasks/celery_app.py`：

```text
task_track_started=True
task_time_limit=配置值
worker_prefetch_multiplier=1
task_acks_late=True
broker_connection_retry_on_startup=True
visibility_timeout >= 任务上限 + 60 秒
result_expires=24 小时
```

关键理解：

- started 状态便于观察；
- prefetch=1 更适合长任务公平分配；
- late ACK 支持崩溃重投，但会重复；
- 可见性超时必须覆盖正常任务时间；
- Celery Result 过期不影响 MySQL 中的业务任务事实。

## 12. 报价中台映射

### 已有能力

- `quote_jobs` 保存状态、阶段、输入、结果、失败阶段和耗时；
- `quote_job_events` 保存结构化执行事件；
- `quote_dispatcher.py` 支持 `disabled/inline/local/celery`；
- 当前 Celery + Redis 支持后台任务；
- Runner 等待 N8N 时写心跳；
- 支持取消、超时标记和失败任务重试；
- 大清单支持分批、补报、完整性摘要和人工占位。

### 当前边界

- 普通报价任务的统一原子领取和 `lease_token` 需按实际路径继续核对；
- 任务创建与 Celery 分发之间存在典型双写窗口，生产化可用 Outbox/扫描器补强；
- 外部下发副作用必须单独验证业务幂等；
- `local` 线程模式适合开发，不具备独立 Worker 的完整故障恢复。

## 13. 面试回答

### 为什么 AI 任务适合异步？

> AI 任务通常包含文件解析、模型、RAG 和外部工具，耗时和失败率都不稳定。API 先把任务和输入版本写入 MySQL并返回任务 ID，Worker 从队列执行，前端查询状态和事件。这样可以避免长时间占用 HTTP 连接，还能提供进度、取消、重试和恢复，但必须额外设计状态机、重复执行保护和队列积压治理。

### Worker 崩溃后怎样恢复？

> 队列采用成功后 ACK，Worker 崩溃后消息可以重投；业务库通过条件更新或租约决定新 Worker 是否有执行权。长任务从持久化 Checkpoint 恢复，所有外部副作用使用幂等键。旧 Worker 的迟到写回必须携带租约 token，不匹配就拒绝。

### 心跳和租约有什么区别？

> 心跳表示近期还有活动，租约表示当前 Worker 是否仍拥有任务执行权。Worker 在线不代表它仍有权写这个任务；租约有效也不代表任务内部有进展，所以还要结合阶段、事件和停滞时间。

## 14. 动手练习

实现一个最小异步报价任务：

1. 创建任务并返回 `202`；
2. 条件更新领取任务；
3. 每处理 10 行写一次进度；
4. 支持 `cancel_requested`；
5. 网络暂时错误退避重试；
6. Worker 崩溃后任务重新投递；
7. 重复执行不会重复下发；
8. 最终保存状态、结果、耗时和事件。

故障注入：

- Broker 不可用；
- Worker 被终止；
- MySQL 写入失败；
- 模型超时；
- 同一任务重复投递；
- 取消与成功同时发生。
