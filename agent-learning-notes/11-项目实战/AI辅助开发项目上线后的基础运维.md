# AI 辅助开发项目上线后的基础运维

## 核心结论

项目能打开，只能说明部署成功；能长期稳定运行、故障后可恢复，才算真正上线。

个人项目和早期产品至少要建立五个闭环：

```text
能发现 → 能诊断 → 能恢复 → 能回滚 → 能控成本
```

AI 可以协助分析、生成命令和整理清单，但生产环境的控制权、变更审批和最终执行必须由人掌握。

---

## 1. 先确保故障能够被发现

### 外部可用性监控

为服务提供健康检查接口，并使用运行在系统之外的监控服务定时访问。

```text
外部监控
  ↓
健康检查连续失败
  ↓
邮件、短信或即时通信告警
```

监控不能与被监控服务完全运行在同一台机器上，否则整机故障时两者会一起失联。

### 主机和服务指标

最低限度应监控：

- CPU
- 内存
- 磁盘容量
- 服务或容器状态
- 请求成功率和延迟

磁盘尤其容易被忽视。日志、上传文件和容器数据持续增长，磁盘写满后可能导致数据库、应用和系统同时异常。

### 日志轮转

日志应设置：

- 单文件或总容量上限
- 保留天数
- 自动轮转
- 压缩和清理规则

日志既要能支持排障，也不能无限占用磁盘。

### 工程补充

健康检查最好分层：

| 类型 | 回答的问题 |
|---|---|
| Liveness | 进程是否还活着 |
| Readiness | 数据库、队列等关键依赖是否可用 |
| Synthetic Check | 用户的关键业务路径是否真的可完成 |

只检查接口能否返回 `200`，可能漏掉“应用活着但业务已不可用”的情况。

## 2. 故障发生后必须能诊断和恢复

### 不把生产服务器直接交给 AI

危险做法：

```text
让 AI 登录生产服务器
→ 边排查边修改
→ 删除、覆盖、重启或改配置
→ 无法确认它究竟动过什么
```

推荐顺序：

1. 下载并脱敏日志。
2. 明确告诉 AI：这是生产环境的日志。
3. 让 AI 分析可能原因和缺少的证据。
4. 让 AI 给出只读排查命令及每条命令的作用。
5. 人工审查并执行命令。
6. 把结果交给 AI 继续分析。
7. 形成变更方案，确认后再实施。

即使必须让 Agent 接入服务器，也应：

- 使用只读、最小权限账号
- 明确禁止删除、覆盖、重启和修改配置
- 先输出发现、证据、风险和处理方案
- 在任何写操作前暂停并等待人工批准
- 保留完整操作记录

> “只读命令”也可能产生高负载或泄露敏感数据，仍需人工审查。

### 日志要求

关键功能应在上线前记录必要的结构化日志，包括：

- 时间和环境
- 请求或任务标识
- 当前步骤
- 结果状态
- 错误码与必要上下文

禁止记录密码、密钥、Token、完整隐私数据和未经脱敏的业务文件。

### 回滚

每次上线前都要回答：

1. 当前稳定版本是什么？
2. 新版本出问题后怎样恢复？

不要用新版本覆盖唯一的稳定版本。生产运行稳定后，应打 Tag 或生成不可变制品，作为可追溯、可回滚的正式版本。

### 自动恢复

服务器重启后，应用、数据库和依赖服务应能按正确顺序自动启动。容器或进程还应设置合理的崩溃重启策略。

验证方式：

- 未上线时可直接执行重启演练。
- 已上线时应先备份并准备恢复方案，再在低峰维护窗口演练。

自动重启不能替代告警。需要同时配置退避和重启次数监控，避免服务陷入无限崩溃循环。

---

## 3. 数据必须真正可恢复

### 先列完整备份对象

通常包括：

- 数据库
- 用户上传的图片和文件
- 业务媒体素材
- 恢复服务所需的关键配置
- 必须保留的部署和版本信息

含密码、密钥的配置必须加密保存并限制访问。

### 用可接受的数据损失决定频率

如果最多只能接受丢失一天的数据，备份间隔就不能超过一天。这是恢复点目标（RPO）的基本思想。

还应定义恢复时间目标（RTO）：

```text
RPO：最多允许丢失多长时间的数据
RTO：故障后最多允许多久恢复服务
```

### 两条底线

1. 备份不能只放在原服务器或同一块磁盘上。
2. 备份完成后必须定期做真实恢复演练。

只有备份任务显示“成功”并不够：文件可能损坏、缺失或无法按预期恢复。

更稳妥的做法是参考 `3-2-1` 原则：

- 至少 3 份数据副本
- 使用 2 种不同介质或存储
- 至少 1 份位于独立故障域

---

## 4. 管理域名、证书和安全更新

### 到期提醒

需要跟踪：

- 域名续费日期
- HTTPS/SSL 证书有效期
- 证书自动续期是否成功

域名过期会导致服务无法访问；证书过期会触发浏览器安全警告，并可能让 API 客户端直接拒绝连接。

### 补丁与升级

框架、操作系统、面板和数据库都可能发布安全更新。长期不更新会暴露已公开漏洞，但升级也不能盲目执行。

安全升级流程：

```text
确认升级解决的问题和兼容性
→ 在开发或测试环境验证
→ 记录当前生产版本
→ 准备备份与回滚
→ 一次只改少量关键组件
→ 灰度或维护窗口发布
→ 验证并观察
```

数据库跨大版本升级风险较高，应单独制定迁移、验证和回退方案。

---

## 5. 防止密钥泄露和账单失控

主要风险：

- AI、支付、短信等 API 密钥泄露后被盗刷
- 恶意流量或服务器被当作攻击跳板
- 按量计费资源持续增长
- 异常循环导致模型调用量暴涨

最低防护：

- 云平台开启预算和消费告警
- 各 API 平台设置用量、速率和异常调用告警
- 密钥使用最小权限并定期轮换
- 不在代码、日志和公开仓库中保存密钥
- 监控 Token、短信、存储和网络流量

账单告警只能帮助发现异常；防止损失还需要限流、配额、熔断和密钥权限控制。

---

## 6. 新功能不能直接在生产环境试错

标准变更流程：

```text
写清目标和验收标准
→ 让 AI 先给方案与影响范围
→ 人工确认方案
→ 在独立分支开发
→ 本地或测试环境验证
→ 准备回滚
→ 发布到生产
→ 冒烟验证和持续观察
```

对 AI 辅助开发还要防止需求漂移：每次修改前固定目标、边界和验收标准，修改后对照确认 AI 没有悄悄改变业务含义。

---

## 7. 用 Git 管理生产版本

建议的最小版本策略：

```text
稳定生产版本（Tag）
├── feature/*：新功能
└── hotfix/*：生产问题修复
```

- 生产版本稳定后打 Tag。
- 新功能从独立分支开发。
- 紧急修复从对应生产版本建立 Hotfix 分支。
- 不在生产版本上边运行边修改。
- 合并和发布前审查变更内容。

让 AI 操作 Git 时，也应先让它说明准备创建、修改或删除什么，再由人工确认执行。

---

## 8. 把运维要求固化为清单

可让 AI 根据真实项目生成维护清单，推荐提示词：

```text
请只读检查当前项目、部署文档，以及我提供的生产环境信息，
不要自行连接或修改生产服务器。

请根据项目真实情况整理一份上线后维护清单，至少分为：
1. 日常检查
2. 每周或每月检查
3. 每次发布前
4. 每次发布后
5. 故障发生时

每项写清：
- 检查什么
- 去哪里查看
- 什么条件需要处理
- 下一步先收集哪些证据
- 哪些动作必须人工审批

无法确认的内容单独列为问题，不要猜测，
也不要直接执行任何生产环境操作。
```

服务器、依赖或部署结构变化后，应同步更新清单和 Runbook。

## 上线后最小维护清单

### 持续监控

- [ ] 外部可用性检查正常
- [ ] CPU、内存、磁盘和服务状态正常
- [ ] 错误率、延迟和关键业务路径正常
- [ ] 日志轮转和磁盘告警有效
- [ ] API 调用量和云账单无异常

### 定期检查

- [ ] 自动备份成功
- [ ] 异地或独立故障域副本存在
- [ ] 已按计划执行恢复演练
- [ ] 域名和证书未临近过期
- [ ] 安全更新已评估并排期
- [ ] 密钥权限、使用情况和轮换状态正常

### 每次发布前

- [ ] 需求、范围和验收标准明确
- [ ] 测试环境已验证
- [ ] 当前生产版本可追溯
- [ ] 数据和配置已按风险备份
- [ ] 回滚步骤已准备并验证
- [ ] 变更窗口和观察负责人明确

### 每次发布后

- [ ] 服务和依赖启动正常
- [ ] 健康检查与关键业务冒烟通过
- [ ] 错误率、延迟和资源指标无异常
- [ ] 数据结构与业务数据正常
- [ ] 稳定版本已标记并记录

### 故障发生时

- [ ] 先止损并确认影响范围
- [ ] 保存日志、版本、时间线和监控证据
- [ ] 优先只读排查
- [ ] 写操作已经人工批准
- [ ] 必要时回滚到稳定版本
- [ ] 恢复后补充复盘和防复发措施

## 面向当前报价中台的落地映射

当前系统已具备健康检查、任务事件、Celery Worker、报价运行看板、人工审核和证据链，可在此基础上补齐运维闭环，而不必重复建设业务能力。

### 建议重点

1. **监控链路**
   - 检查 FastAPI `/health/ready`
   - 监控 MySQL、Celery Broker/Worker、n8n、Dify、RAG 服务和 Milvus
   - 增加外部探测与关键报价路径的合成检查

2. **数据分级**
   - 明确 MySQL 中业务主数据和审计记录的备份策略
   - 单独保护用户上传文件、部署配置和密钥
   - 区分“必须备份的源数据”和“可以从源数据重建的索引”

3. **故障处理**
   - 先使用现有任务事件、日志和健康检查收集证据
   - 报价任务以 `job_id` 关联整个排查过程
   - 禁止 AI 未经确认直接修改 Windows 或 CentOS 生产环境

4. **发布与恢复**
   - 当前仍是内网开发验证阶段，正式上线前单独完成生产 Runbook
   - Runbook 至少覆盖服务重启、版本回滚、数据库恢复、队列积压和外部模型故障

5. **成本告警**
   - 对模型 API、云资源、短信或通知服务分别设置预算和用量告警
   - 结合任务量观察单次报价成本和异常重试造成的放大效应

## 一句话总结

AI 辅助开发降低了上线门槛，但没有消除运维责任；最低合格线是故障可发现、操作可审计、数据可恢复、版本可回滚、费用可预警。
