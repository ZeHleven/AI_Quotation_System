# RET-FACT-GATE-001 — 事实槽位工作状态与证据充分性门

日期：2026-07-30
当前阶段：代码、评测契约和 Development A 唯一一次正式影子评测已完成。
当前结论：事实状态保留用于可观测性；硬证据门未通过，不启用 `enforced`。

## Problem

冻结候选在唯一 Challenge 中取得 Hit@5 88.89%，但 Recall@5 只有47.59%。多数问题能碰到一条正确证据，却无法判断一个多事实问题是否已经被完整覆盖；无答案问题仍会返回弱相关Top5。

## 唯一变化

本实验只增加确定性的事实覆盖工作状态和证据充分性门，不修改：

- Query Planner的拆分规则；
- exact / semantic / hybrid路由；
- 候选Top20和最终Top5；
- RRF及候选覆盖选择；
- Embedding、切块和RAG服务；
- 自动第二轮检索；
- 父子结构检索、GraphRAG或长期Memory。

## 状态契约

每次 `search_tender_evidence` 后，LangGraph新增
`update_fact_coverage` 节点，从检索服务已经输出的
`coverage_need_queries`、`coverage_need_indexes`和上下文读取轨迹构建：

- `required_slot_count`：可评估事实数；
- `covered_slot_count`：至少有答案承载候选的事实数；
- `verified_slot_count`：候选上下文已被读取的事实数；
- `uncovered / candidate_covered / context_verified`；
- `not_assessed / candidate_sufficient / insufficient`。

普通Top5出现不等于证据充分。只有检索服务明确给出答案承载覆盖关系时，事实才能进入 `candidate_covered`；读取权威上下文后才进入 `context_verified`。

## 三种运行模式

| 模式 | 行为 |
|---|---|
| `off` | 不构建事实覆盖状态。 |
| `shadow` | 构建、持久化并在运行图谱展示，但不改变LLM输入和证据门结论。 |
| `enforced` | 把事实状态提供给LLM；存在未覆盖事实时，确定性证据门增加 `FACT_SLOT_EVIDENCE_INSUFFICIENT` 并阻止直接通过。 |

当前 `.env` 明确设置为 `BID_INTAKE_FACT_COVERAGE_MODE=shadow`。未经新的Development评测通过，不允许切换为 `enforced`。

## 新增评测指标

- 事实门评估覆盖率；
- 事实门与Gold完整性的对齐准确率；
- 事实门负样本准确率；
- 误充分率：Gold不完整却判断充分；
- 误拒答率：Gold已经完整却判断不足。

评测预测只保留脱敏后的槽位ID、类型、状态和证据ID，不保存事实原文与内部trace ID。

### 逐类诊断

- Q001：三项Gold完整进入Top5，事实门正确判断充分；
- Q003：四项Gold缺一项，事实门正确判断不足；
- Q006—Q008：传统检索仍各返回5条弱相关结果，原负样本准确率为0%，但事实门正确把三题全部判断为不足；
- Q002、Q004：只出现设计阶段名称的弱相关块，也被现有答案信号算法当成对应事实已覆盖，形成误充分；
- Q005：正确证据已经排在Top1，但“是否包含 + 还需承担什么配合”的关系型表达没有被答案信号识别，形成误拒答。

### 根因判断

当前事实槽来自表层并列短语。部分槽只保留“方案设计”“深化设计”等对象名称，丢失了“需要完成什么工作”“时间节点是什么”等待求属性；候选覆盖算法因此容易把“提到了对象”误当成“回答了事实”。相反，包含否定、排除和配合责任的关系型答案即使已召回，也可能无法被词法答案信号确认。

这说明“事实工作状态”本身有价值，但“候选覆盖=证据充分”目前不成立。若现在开启硬门，会同时产生错误放行和错误阻断。

3. 第一项机制的基础设施保留，但硬门候选判定需要结构化证据后重新验证。

5. 后续仍需新的Development B做跨项目验证；旧Holdout和Challenge不重跑。
