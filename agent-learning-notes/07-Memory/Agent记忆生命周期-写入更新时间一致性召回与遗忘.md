# Agent 记忆生命周期：写入、更新、时间一致性、召回与遗忘

## 核心结论

“能召回历史”不等于“会管理记忆”。生产级记忆系统必须管理完整生命周期：

```text
候选信息
→ 写入判定
→ 验证与分类
→ 版本化存储
→ 更新或失效
→ 权限与时间过滤
→ 检索和上下文排序
→ 归档、压缩或删除
```

不能用单一的 FIFO、LRU 或向量相似度决定所有记忆的命运。时间、相关性、事实正确性、重要度和合规性是不同问题。

---

## 1. 写入：不是什么都值得记

一条信息进入长期记忆前应检查：

| 维度 | 判断问题 |
|---|---|
| 稳定性 | 是长期事实，还是临时状态 |
| 未来价值 | 是否会影响后续决策 |
| 可复用性 | 是否适用于多个任务 |
| 验证状态 | 用户确认、工具验证，还是模型推测 |
| 来源 | 能否追溯到原始事件或业务记录 |
| 隐私 | 是否敏感，是否得到必要授权 |
| 已有记忆 | 是新增、重复、补充还是冲突 |

适合长期写入：

- 用户明确确认的稳定偏好
- 有来源的长期事实
- 项目级持续约束
- 重要决策及原因
- 多次验证有效的任务经验

不宜默认长期写入：

- 寒暄和低价值日志
- 一次性验证码
- 瞬时库存或临时工具输出
- 未经验证的模型推断
- 不必要的敏感信息
- 已可从正式业务库准确查询的数据副本

模型可以提出 Memory Candidate，但写入授权、Schema、敏感信息处理和状态变更应由 Runtime 或业务规则控制。

---

## 2. 更新：追加历史与维护当前状态

用户先说“我住在上海”，后来又说“我搬到北京”，系统不能只保留两条相似文本并让模型猜哪条有效。

推荐同时维护：

```text
事件历史：发生过哪些陈述和修改
当前视图：现在生效的值是什么
```

更新流程：

```text
识别主体与字段
→ 查询当前有效记忆
→ 判断新增、重复、补充或冲突
→ 关闭旧版本有效期
→ 写入新版本
→ 重建当前视图和检索索引
→ 记录变更事件
```

不要直接覆盖后丢失历史，也不要让所有旧版本继续作为“当前事实”被召回。

---

## 3. 双时间机制

时间状态至少包含两个维度：

### Valid Time

事实在现实世界中的有效时间。

```text
居住地 = 上海：2024-01-01 至 2026-07-20
居住地 = 北京：2026-07-21 起
```

### Transaction Time

系统何时获知并记录这条事实。

例如用户在 7 月 28 日才告诉系统“我从 7 月 21 日起搬到北京”，则：

```text
valid_from = 2026-07-21
recorded_at = 2026-07-28
```

双时间支持：

- 查询当前事实
- 回看某个历史时点
- 处理迟到数据
- 追踪系统何时知道某件事
- 审计错误决策当时使用了什么状态

对于无法确认的时间，不要伪造精确日期；应保存未知、近似或待确认状态。

---

## 4. 冲突处理

记忆冲突不能只靠“最后一条获胜”。

建议按以下顺序判断：

1. 是否为同一主体、同一字段或同一事件
2. 是否存在明确有效区间
3. 来源的权威性和验证状态
4. 新信息是替代、补充还是纠正
5. 是否需要用户或人工确认

示例：

```text
用户明确更新的当前地址
> 历史对话中的旧地址

正式成本库 active 记录
> 未审核的模型估算

当前生效制度
> 已废止旧版本
```

如果两条高可信信息无法消解，应保留冲突状态并阻止系统输出唯一确定结论。

---

## 5. 召回：先硬过滤，再软排序

推荐流程：

```text
租户、用户和权限过滤
→ 类型与状态过滤
→ 有效期与版本过滤
→ 精确字段查询
+ 语义或关键词召回
→ 去重与冲突检查
→ 相关性、时间、重要度、可信度排序
→ 上下文预算筛选
```

精确事实优先走键值、SQL 或业务 API；向量检索适合语义相近的事件、摘要和经验。

软排序可以考虑：

```text
score =
  relevance
  + recency
  + importance
  + confidence
  + source_quality
  - redundancy
```

这只是设计维度，不是通用公式。各项权重必须基于真实任务评测，安全约束和当前有效状态应作为硬规则，不能被低相似度淘汰。

---

## 6. 淘汰与遗忘：按类型制定策略

| 记忆类型 | 推荐策略 |
|---|---|
| 一次性工具结果 | 短 TTL，任务结束后删除或归档 |
| 当前对话窗口 | Token 预算 + 滑动窗口 + 摘要 |
| 临时任务计划 | 完成后归档，保留必要审计 |
| 确定性任务状态 | 按状态机迁移，不按相似度删除 |
| 用户档案 | 显式更新、版本化、支持用户修改 |
| 长期事实 | 有效期、来源和版本治理 |
| 情景记忆 | 时间衰减、重要度和复用价值综合判断 |
| 安全与合规规则 | 固定注入或硬策略保护，不能被普通淘汰算法删除 |
| 程序性技能 | 版本、测试和废弃流程 |

### 时序淘汰

包括 TTL、FIFO、LRU，优点是稳定、成本低，适合缓存和临时结果。

局限：

- 旧信息可能仍然重要
- 新信息不一定正确
- 最近访问不代表仍然有效

### 相似度淘汰

根据当前任务与记忆的相关性选择内容，适合构建本轮上下文。

局限：

- 暂时无关的安全约束仍必须保留
- 相似不代表正确或新鲜
- Embedding、阈值和查询表达会导致漂移

因此更稳的策略是：

```text
先按类型、权限、有效期执行硬规则
→ 再用相关性、时间衰减、重要度和去重做软排序
```

---

## 7. 压缩、归档、失效与删除不是一回事

| 操作 | 含义 |
|---|---|
| 压缩 | 保留核心语义，减少上下文或存储开销 |
| 归档 | 不参与日常召回，但保留历史和审计 |
| 失效 | 旧版本不再作为当前事实 |
| 删除 | 按用户请求、策略或合规要求移除数据 |

删除需要传播到：

- 主数据库
- 向量索引
- 搜索索引
- 缓存
- 派生摘要或用户画像
- 备份和审计系统允许处理的范围

不能只删除数据库一行，却让同一内容仍可从向量库召回。

---

## 8. 隐私与安全

Memory 往往包含用户长期信息，因此需要：

- 数据最小化
- 明确用途和保留期限
- 租户与用户隔离
- 写入、读取和删除权限
- 敏感字段加密或脱敏
- 用户查看、纠正和删除入口
- 访问与变更审计
- Prompt Injection 内容隔离

历史对话不能默认永久向量化。记忆中的文本也属于不可信数据，召回后不能当成系统指令执行。

---

## 9. 最小读写策略

### 写入

```text
交互事件
→ 提取候选事实或经验
→ 分类和敏感信息检测
→ 来源与置信度校验
→ 与当前有效记忆比较
→ 写入新版本或忽略重复
→ 更新索引和审计事件
```

### 读取

```text
当前任务与用户身份
→ 硬权限和时间过滤
→ 精确查询 + 语义召回
→ 冲突、重复和新鲜度检查
→ 上下文预算排序
→ 返回内容与来源
```

### 遗忘

```text
TTL、用户请求或治理策略触发
→ 判断压缩、归档、失效或删除
→ 传播到所有派生存储
→ 验证不可再召回
→ 记录合规事件
```

---

## 10. 评测与线上监控

重点指标：

- 错误写入率
- 重复记忆率
- 新状态覆盖旧状态的正确率
- 过期或越权记忆召回率
- 相关记忆 Recall@K 与 Precision@K
- 记忆冲突识别率
- 记忆导致的任务错误率
- 删除传播成功率
- 上下文 Token 与延迟

Bad Case 应至少标记：

```text
未写入
写错类型
写入了不应保存的信息
旧状态未失效
召回遗漏
召回过期或越权信息
冲突未识别
摘要失真
删除不完整
```

## 11. 面试回答模板

```text
记忆满了不能简单在“删最旧”和“删最不相关”之间二选一。

我会先按记忆类型治理：
临时对话和工具结果使用 TTL 或最近访问策略，
任务状态按状态机归档，
用户档案和长期事实按字段、版本和有效期更新，
安全约束则受硬策略保护。

写入前会判断稳定性、未来价值、验证状态、来源和隐私；
时间上同时记录事实有效时间和系统记录时间，
解决新旧状态冲突。

召回时先做租户、权限、状态和有效期硬过滤，
精确事实走结构化查询，
语义内容再按相关性、时间衰减、重要度和可信度排序。

遗忘还要区分压缩、归档、失效和删除，
并保证数据库、向量索引、缓存和派生摘要一致更新。
```

## 12. 面向当前报价中台的落地映射

报价中台适合优先治理以下“记忆式状态”：

| 信息 | 处理方式 |
|---|---|
| 当前报价任务进度 | 现有任务表和事件表，确定性恢复 |
| 人工确认的项目规则 | 结构化、带项目范围和版本 |
| 历史报价与修改 | 作为情景记录和评测数据，不直接当当前价格 |
| 正式成本价格 | 继续以 `cost_items.active` 为主数据 |
| 无底价候选 | 保持 `draft`，人工启用后才生效 |
| 成功复核经验 | 候选 Skill，经过审核和回归再发布 |

尤其要避免把历史报价向量召回结果直接当成当前有效底价。价格、版本、状态和生效时间必须由结构化业务规则控制。

---

## 一句话总结

Agent 记忆治理的关键，是让信息在正确时间以正确状态被写入、更新和召回，并能在过期、冲突或用户要求时可靠失效与删除。
