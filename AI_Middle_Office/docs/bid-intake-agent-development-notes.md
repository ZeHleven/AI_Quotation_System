# 报价资料研判 Agent 项目开发笔记

这份笔记记录 Agent 从发现问题、形成假设、设计方案、试错评测到接受或拒绝方案的完整链路。它服务于三件事：

1. 防止只保留“成功结果”，丢失真正有价值的工程判断；
2. 防止针对单一项目和评测题反复调参造成过拟合；
3. 为后续复盘、项目交接和面试表达保留可验证证据。

详细指标、冻结记录和逐实验报告仍以 `evals/bid_intake/retrieval/v1/` 为准，本笔记负责串联“为什么这样做”。

## 记录规则

以后每个重要问题必须按以下结构记录：

| 字段 | 要回答的问题 |
|---|---|
| Problem | 遇到了什么真实问题？影响什么业务判断？ |
| Observation | 实际观察到什么现象？ |
| Evidence | 有哪些日志、样本和指标支持？ |
| Hypothesis | 推测问题发生在哪一层？ |
| Alternatives | 考虑过哪些解决方案？ |
| Decision | 为什么选择当前实验，为什么暂不选择其他方案？ |
| Experiment | 唯一改变了什么？固定了什么？用什么数据验证？ |
| Result | 指标如何变化？改善和退化在哪里？ |
| Generalization | 是否跨问题、跨主题、跨项目成立？是否可能过拟合？ |
| Conclusion | 接受、部分接受、拒绝还是继续观察？ |
| Next | 下一步优化什么，为什么？ |

尚未实现或尚未评测的想法必须标记为“候选假设”，不能写成已经有效的系统能力。

## 检索优化主线回顾

| 阶段 | 问题与尝试 | 结果与判断 |
|---|---|---|
| `RET-EXP-001` | 每路召回数量和最终 Top5 使用同一个深度，正确证据可能在候选阶段过早被截断；将候选深度提高到20，最终仍返回5条。 | Development 的 Recall、MRR和nDCG均改善，延迟在门槛内，接受。说明“先扩大候选池、再精选”是有效的通用方向。 |
| `RET-EXP-002` | 合同风险题缺少宽泛事实支撑；增加语义伴随 Query。 | 部分问题改善，但总体证据不足，未启用。不能因为一个付款问题改善就扩大所有 Query。 |
| `RET-EXP-002B` | 曾考虑固定拆成预付款、进度款、结算款和质保金 Query。 | 在实施前取消。它直接来自单个失败题，项目和表达绑定明显，过拟合风险高。 |
| `RET-EXP-003A` | 尝试通用原子事实槽拆分，希望复合问题逐事实检索。 | Recall没有提升且延迟约翻倍，拒绝。概念合理不代表当前实现有效。 |
| `RET-EXP-003B` | 不增加 Query，只对已有候选做需求覆盖选择。 | Development 达到接受门槛，冻结后进入唯一 Holdout；Holdout正向检索条件性通过，但nDCG和负样本拒答失败。保留为候选，不标记生产就绪。 |
| `RET-EXP-004A` | 对已选证据扩展同文档相邻块。 | Recall没有提升，只改善部分排序，拒绝。说明“相邻”不等于“属于同一个答案”。 |
| `RET-EXP-004B` | 把锚点与相邻上下文作为证据组，避免上下文单独占用Top5。 | Recall只提升0.025且只改善一个项目，未达到跨项目门槛，拒绝。上下文分组仍可作为未来新实现的参考，但不能宣称有效。 |
| `RET-EXP-004C` | 准备继续增加关系表达归一化。 | 取消。沿单项目局部收益继续补规则会逐渐拟合评测题。 |
| `DATA-CHALLENGE-001` | 使用全新真实项目验证冻结候选的泛化能力。 | Hit@5 88.89%，但 Recall@5 47.59%、MRR 68.52%、nDCG@5 49.73%，负样本准确率0%；路由与Query数量准确率100%，P95 1677ms、错误0。完整门槛未通过，Challenge永久锁定。 |

这条链路的重要认识是：失败实验不是无效工作。它们帮助排除“单纯增加 Query”“盲目相邻扩展”“继续追加关系规则”等看似合理、实际收益不足或过拟合风险较高的路线。

## 2026-07-30：Top5覆盖不足后的架构判断

### Problem

唯一一次 Challenge 显示：Agent 经常能命中至少一条正确证据，但前5条证据不能完整覆盖多事实、跨文档和长表结构信息；资料没有答案时仍会返回弱相关证据。

### Observation与Evidence

- Hit@5为88.89%，说明9个正向问题中大多数至少碰到一条Gold。
- Recall@5只有47.59%、nDCG@5只有49.73%，说明正确证据覆盖不完整且排序质量不足。
- 路由和Query数量准确率均为100%，因此当前主要问题不再是“是否知道该找什么”。
- Q006的5个付款/质保事实只命中1个；Q008的长表结构证据完全未进入Top5；Q009无答案时仍返回5条结果。
- 运行错误为0、P95为1677ms，不能把失败归因于基础设施不稳定。

### Hypothesis

当前瓶颈更可能位于四个层面：

1. 多事实问题缺少“已覆盖/未覆盖事实”的显式任务状态；
2. 候选合并后仍容易被同类高分证据占满Top5；
3. 长表的Sheet标题、表头、楼栋和分区没有作为父级结构参与检索与上下文组装；
4. 检索层缺少证据充分性判断，总会返回固定数量结果。

### Alternatives

| 候选方案 | 可能收益 | 风险与局限 | 当前判断 |
|---|---|---|---|
| 增加模型上下文窗口 | 可以容纳更多证据 | 不能让未召回的证据自动出现，容易增加噪声和成本 | 不作为第一方案 |
| 长期Memory | 可保存历史项目经验 | 不能修复当前项目证据漏召回，还可能引入跨项目污染 | 当前不需要 |
| LangGraph工作状态 | 显式保存必要事实、已覆盖事实、未覆盖事实和检索轮次 | 需要新的多事实Development样本验证，第二轮检索也会增加延迟 | 高优先级候选 |
| 父子结构与上下文证据组 | 将Sheet/章节/表头与核心证据一起提供给LLM | 简单相邻块扩展已经失败，必须基于结构关系而不是物理相邻 | 高优先级候选 |
| 受控第二轮检索 | 只为未覆盖事实再次检索 | 如果事实槽定义或充分性判断错误，会放大调用次数 | 在工作状态之后验证 |
| 完整GraphRAG | 能沿实体关系连接合同、招标文件和清单 | 图谱抽取、实体消歧、更新、延迟和错误关系传播成本高；不擅长精确数值和长表行召回 | 暂不全量引入 |
| 选择性图扩展 | 只在跨文档关系型问题上，从高可信锚点扩展有来源的关系 | 仍需证明比结构检索和文档多样性选择有额外收益 | 中后期候选 |

### Decision

不直接把系统改成完整GraphRAG，也不引入长期项目记忆。优先研究的是“检索工作状态 + 结构化上下文 + 证据充分性门”：

```text
问题拆分
  → 建立required_fact_slots
  → 按槽位执行exact / semantic / hybrid / table检索
  → 记录covered_slots和uncovered_slots
  → 结构化父子证据组装
  → 只对未覆盖槽位进行受控第二轮检索
  → 证据充分性门
  → 完整回答或明确提示缺失资料
```

GraphRAG保留为按问题类型触发的增强通道：

```text
高可信锚点证据
  → 问题被判定为跨文档关系型
  → 沿有来源证据ID的关系扩展
  → 与普通检索候选合并
  → 覆盖选择与证据门
```

初期即使验证图关系，也优先使用轻量关系表，不预设必须引入Neo4j等独立图数据库。

### Generalization与过拟合控制

这个方向只有在以下条件满足时才属于通用优化：

- 不加入蓝城、楼栋编号或某道题的固定关键词；
- 从全新项目建立新的Development数据；
- 无答案、长表、多事实和跨文档场景都包含多个项目；
- 每次实验只改变一个主要变量；
- 同时记录Recall、MRR、nDCG、负样本准确率、误拒答率、延迟、Token和执行错误；
- 现有Holdout和`DATA-CHALLENGE-001`不重跑、不改Gold、不参与方案选择。

### Current result

2026-07-30已完成第一项的shadow实现：

- LangGraph新增`update_fact_coverage`节点；
- 能记录未覆盖、候选已覆盖和上下文已验证的事实槽；
- 证据门支持`off / shadow / enforced`，当前环境固定为`shadow`；
- 离线评测新增评估覆盖率、对齐准确率、误充分率和误拒答率；
- 相关回归`50 passed`。

Development A已从未参与旧评测的“总部基地设计任务书”建立8题（5题正向、3题无结果），经业务逐题复核后冻结并完成唯一一次正式shadow评测：

- 事实门评估覆盖率100%，负样本准确率100%，P95 982ms，错误0；
- 对齐准确率62.5%，低于80%门槛；
- 误充分率33.33%，高于0%门槛；
- 误拒答率50%，高于20%门槛。

传统检索在3道无结果题上仍都返回弱相关Top5，但事实门能全部判断为不足，证明状态机制对“缺资料”有价值。失败集中在正向关系判断：表层事实槽有时只保留对象名称，导致“提到对象”被误当成“回答属性”；否定、排除和配合责任等关系型答案即使已召回，也可能未被答案信号确认。

因此保留shadow状态与可观测性，但拒绝启用`enforced`。这次失败不能通过添加“方案设计”“中庭景观”等项目词或事后放宽阈值修补。

### Next

1. 结构化父子检索与上下文证据组已完成Development A验证，详细过程见下一节。
2. 再取得至少一个全新项目建立Development B，完成跨项目验证。
3. 在独立开关下进入受控第二轮检索，只补查第一轮后仍未覆盖的事实。
4. 之后才依次验证选择性图扩展和长期项目记忆。

## 2026-07-30：表格父子结构与上下文证据组

### Problem、Observation与Evidence

Development A的多事实题并非完全没有召回正确证据。对原始Top20候选逐题检查后发现：

- Q002三条Gold排名18、11、7；
- Q003四条Gold排名10、4、5、3；
- Q004四条Gold排名12、8、1、4。

这说明正确内容已经进入候选池，但DOCX表格被解析为独立行后，子行失去了共同表头，最终Top5也无法同时容纳多条同表答案。优化点应位于“结构语义与证据交付单位”，而不是继续增加Query或盲目扩大候选池。

### Hypothesis与Alternatives

通用假设是：使用同一文档版本内已有证据建立`章节/表头 → 子行`关系，再把同父、查询相关的子行作为一个有界证据组，能够恢复多行答案。

没有选择以下方案：

- 物理相邻扩展：旧实验已证明“相邻”不等于“同一答案”；
- 直接扩大TopK：会增加LLM噪声和成本，且不恢复表头语义；
- 完整GraphRAG：当前关系已经存在于文档结构中，先上图数据库属于过度设计；
- 项目关键词规则：会针对单一设计任务书过拟合。

### Experiment 001：只补父标题

第一版为候选附着真实父章节、DOCX表头或XLSX Sheet表头，父节点不占Top5，也不增加Query。

结果为Recall 65%→71.67%、MRR 56.67%→63.33%、nDCG 58.58%→63.27%，但只有Q002改善。预设要求至少2道正向题改善，因此第一版被拒绝。结论是父标题有帮助，但父标题本身不能把其他兄弟答案行送给下游。

### Experiment 002：同父兄弟证据组

第二版只增加一个变量：

- 同一真实表格父节点下必须已有Top5锚点；
- 从现有Top20候选池选择查询相关的兄弟子行；
- 最多1个父组、每组最多3条兄弟行；
- 兄弟行不占用5个锚点；
- 不增加检索Query，不启用第二轮、图扩展或Memory。

冻结门槛后唯一一次Development A结果：

- Hit@5锚点组：80%→100%；
- Recall@5锚点组：65%→90%；
- MRR：56.67%→63.33%；
- nDCG@5：58.58%→63.27%；
- Q002 Recall 0%→100%，Q004 50%→75%，其余正向题无退化；
- 事实门误充分率33.33%→20%，误拒答率50%→33.33%；
- Query数量准确率100%，P95 696ms，错误0。

需要准确解释指标：这里的`@5`是5个锚点证据组，不是最多5个独立文本块。Q002附着2个组内成员，Q003/Q004各附着1个；组内成员不占锚点位置，但会增加下游实际证据数。

### Conclusion、Generalization与Next

第二版通过Development A预设门槛，证明“同父结构关系”比“物理相邻”更适合长表多事实检索；第一版失败和第二版成功都保留。

它仍不具备生产启用条件：当前只有一个项目8题，Q003/Q004仍各缺1条Gold，也没有跨项目验证。实际环境继续保持结构开关关闭，后续必须由全新项目建立Development B；旧Holdout和Challenge不重跑。

下一实验是`RET-CONTROLLED-RETRY-001`：依据事实槽工作状态，只对第一轮后仍未覆盖的事实执行一次受控补查。这一步要单独冻结新增Query数、Recall收益、负样本误检、延迟和错误门槛，不能与结构组打包成一次不可解释的改动。

## 2026-07-30：未覆盖事实的受控第二轮检索

### Problem与Hypothesis

结构证据组后，Q003和Q004仍各缺1条Gold。假设是：只在第一轮“部分覆盖”时，对未覆盖事实补查一次，可以提高Recall，同时避免所有问题都付出第二轮成本。

安全边界提前固定为：零覆盖不补查、已充分不补查、最多1轮2条Query、Query仅来自未覆盖事实槽、不增加LLM调用。

### Experiment 001：重新融合全部候选

补查后把第二轮候选重新参与RRF和Top5选择。Q003 Recall从75%到100%，总Recall从90%到95%，但Q003 nDCG从51.43%降到24.63%，总体nDCG降到57.91%。

原因不是没找到证据，而是整合错误：三个原正确锚点被挤到一个组内。Recall按证据组成员计算，nDCG按锚点排序计算，因此出现“Recall升、排序降”。001拒绝。

### Experiment 002：保留锚点但不给补查导航权

第二版完全保留首轮锚点，消除了排序退化；但补查新增3个候选后，结构组仍按原全局分数选择旧父表，Recall没有变化。安全但无效，002拒绝。

### Experiment 003：补查只导航真实父节点

第三版继续保留首轮Top5和顺序，只使用每条补查Query首个具有真实表格父节点的结果，指定优先扩展哪个父表。该父表还必须包含首轮锚点，最多附着3个同父兄弟行。

结果：

- Recall 90%→95%；
- MRR和nDCG保持63.33%与63.27%；
- Q003 75%→100%，其余无退化；
- 只执行1条补查Query，3个负样本均触发0条；
- P95 687ms，错误0；
- 首轮锚点及顺序100%保留。

这说明第二轮检索更适合当“结构导航信号”，而不是重新排序全局候选。

### Fact Gate残留缺口

新增正确行进入证据组后，Q003的shadow事实门仍判断`insufficient`。原因是事实槽仍以表层词法匹配“竣工图分别要提交什么文件”，而表格行表达为“竣工图 | 施工变更后的竣工图纸 | 纸质2份+电子版”。Gold命中不能直接替代可解释的谓词验证。

因此003只通过检索门，不通过硬证据门；结构与补查开关都保持关闭，事实门继续shadow。未来要独立处理关系谓词确认，不能在本轮事后放宽阈值。

### Generalization与Next

003不含项目关键词，但Development A只有一个项目，且只有Q003触发补查。必须用新项目Development B验证。

下一项是选择性跨文档图扩展。由于当前8题全部来自单文档，不能用本数据集证明图扩展收益；可以先完成触发器、关系来源和失败回退契约，但正式效果必须等待含招标文件、清单、合同等至少两类文档的新Development样本。

## 2026-07-30：选择性图扩展与长期Memory决策

### 选择性图扩展

当前Development A的manifest已核验为1份文档。旧的多文档Challenge已经锁定，不能因为进入图扩展阶段就重新拿来调参。因此本阶段没有伪造A/B结果，而是冻结了实验契约：

- 必须同时出现至少两类资料角色和跨来源关系意图才触发；
- 图只包含case、文档版本、章节/表头、证据块和精确引用；
- 边必须有来源证据，不允许LLM自由推测后永久落图；
- 最多1跳、2个种子、4条扩展证据；
- 结果只进入证据组，不重排Top5，仍经过证据门。

没有直接上Neo4j。首版关系量和遍历深度很小，MySQL/MinIO已有关系足以验证价值；只有规模与延迟数据证明需要时才比较独立图数据库。

当前结论是`blocked_by_evaluation_data`，不是“图扩展已完成”或“图扩展无效”。正式试验需要一个全新项目，至少包含招标文件、合同和清单，并建立跨文档联合、冲突、负样本和单文档不触发题。

## 2026-07-30：取得全新跨文档项目并建立Development B复核稿

### Problem

`RET-GRAPH-EXPAND-001`已有触发、关系、预算和回退契约，但Development A只有一份设计任务书。旧Holdout和Challenge已经锁定，不能重跑，因此此前无法证明结构检索、受控第二轮和选择性图扩展能跨项目泛化。

### New evidence

取得“陵水福朋喜来登酒店项目样板间精装修工程”全新项目，资料覆盖：

- 招标文件；
- 7个Sheet的工程量清单；
- 施工合同；

## 2026-07-30：选择性图扩展首轮候选被拒绝

### Result

触发Precision和Recall均为100%，4个负样本没有误触发；但候选仍被拒绝：

- 总体Recall 59.83%→61.83%；
- 触发组Recall 49.44%→52.78%，只提升3.33个百分点，低于10个百分点门槛；

### Root cause

失败集中在两个通用实现问题，而不是触发器：

1. 表头识别只要求任意单元格包含两个通用词。普通招标范围行、答疑数据行也可能同时出现“项目、面积、名称”等词，因此被误当成父节点；
2. 答疑已经明确写出“清单第23项”和房型代码，但目标解析仍查询“清单序号23”。目标清单行只有“23”和房型代码，因而没有进入Top20。只读诊断改为“23 TK1”后，正确行排第1。

错误种子还会抢占4条扩展额度：Q004先给招标文件错误父节点3条额度，真正的清单表头只剩1条，最终只补回4条连续Gold中的1条。

### Decision与下一步

不降低门槛，不放宽触发器，不扩大图跳数或预算，也不加入项目专用关键词。首轮001永久保留为失败实验，生产开关继续关闭。
