# Embedding 模型选型：基准评测、索引迁移与生产治理

## 核心结论

Embedding 模型不是“榜单分数最高就最好”。生产选型要回答：

> 它能否在本公司的真实语料、真实 Query、延迟预算、硬件条件和权限边界下，让正确证据稳定进入候选集？

正确流程：

```text
明确检索任务
→ 建立真实 Gold Query—Evidence 集
→ 固定切片、索引和检索参数
→ 对比候选模型
→ 测召回、排序、延迟、吞吐和成本
→ 小流量影子验证
→ 蓝绿重建索引
→ 切换并保留回滚能力
```

Embedding 主要负责粗召回。它不能替代：

- BM25 对编号、型号和稀有词的精确召回；
- Reranker 对 Query—候选相关性的精细判断；
- 元数据过滤和业务权限；
- 事实库、证据门和最终答案校验。

---

## 1. 先明确要解决哪类检索

### 对称检索

Query 与文档形式接近，例如：

- 相似问题检索；
- FAQ 问题匹配；
- 重复文本发现。

### 非对称检索

短 Query 检索长文档，例如：

- “保证金如何退还”检索合同条款；
- “墙面 CT-1 的施工要求”检索工程说明；
- 风险问题检索招标资料证据。

企业 RAG 多数属于非对称检索。选型时必须确认模型是否适合 Query—Passage 检索，以及是否要求：

- Query 和 Document 使用不同前缀；
- 特定 instruction；
- 特殊 pooling 或归一化方式。

若训练方式要求前缀却在生产中遗漏，模型本身没变，召回仍可能明显下降。

---

## 2. 选型的八个维度

| 维度 | 要检查什么 | 常见风险 |
|---|---|---|
| 语言 | 中文、多语言、简称和中英混写 | 英文榜单很好，中文业务词召回差 |
| 领域 | 通用、法律、工程、金融、代码 | 通用语义相似不等于领域证据相关 |
| 任务 | 对称或非对称检索 | Query 与文档编码方式用错 |
| 输入长度 | 最大 Token、长文本截断策略 | 关键事实位于末尾而被截断 |
| 向量维度 | 存储、网络、内存和索引大小 | 维度越高不一定效果越好 |
| 部署 | 本地、API、GPU、CPU、离线能力 | 模型能跑但吞吐不够 |
| 合规 | License、数据外发、版本可获得性 | 生产环境无法合法或稳定部署 |
| 运维 | 版本、监控、重建和回滚 | 更换模型后旧新向量混用 |

不能只用一条“语义相似度示例”证明模型适合生产。

---

## 3. 建立真实评测集

### 3.1 Gold Query—Evidence

每条样本至少包含：

```json
{
  "query_id": "q_001",
  "query": "投标保证金退还条件是什么",
  "relevant_evidence_ids": ["doc3_v2_p18_c04"],
  "query_type": "exact_semantic",
  "difficulty": "medium",
  "must_not_retrieve": ["doc1_v1_p7_c02"],
  "is_answerable": true
}
```

### 3.2 测试集需要覆盖

- 精确编号、日期、金额和型号；
- 同义表达、口语和企业简称；
- 工程、合同和报价专业术语；
- 长条款、表格和跨 Chunk 问题；
- 新旧版本冲突；
- 多文档比较；
- 权限不可见资料；
- 知识库没有答案的问题；
- 易混淆的困难负例。

只用简单问题会高估模型效果。

### 3.3 数据集划分

- Development：用于调模型、切片、Top-K 和索引参数；
- Holdout：只用于最终比较；
- Regression：保存真实线上 Bad Case，防止后续版本回退。

同一文档的近似问题不要同时泄漏到 Development 和 Holdout。

---

## 4. 怎样公平比较模型

对比 Embedding 模型时，第一轮应固定：

- 原始语料；
- Chunk 内容和大小；
- Query；
- 向量数据库；
- 距离度量；
- ANN 参数；
- Top-K；
- 元数据过滤条件。

只改变 Embedding 模型，才能知道差异来自哪里。

第二轮再分别做联合优化：

- 模型 + 切片；
- 模型 + Query 前缀；
- 模型 + HNSW 参数；
- 模型 + 混合检索；
- 模型 + Reranker。

如果一次同时更换模型、切片、索引和 Reranker，就无法归因。

---

## 5. 核心指标

### 检索效果

| 指标 | 含义 |
|---|---|
| Recall@K | 正确证据是否进入前 K 个候选 |
| Hit@K | 每个 Query 是否至少命中一条正确证据 |
| MRR | 第一条正确证据排得有多靠前 |
| nDCG@K | 多个相关证据的整体排序质量 |
| Hard-negative error rate | 是否把语义相似但错误的片段排得过高 |

Embedding 粗召回阶段优先保证 Recall；最终排序再看 MRR、nDCG 和 Reranker 收益。

### 工程效果

- Query 编码 P50 / P95；
- 文档编码吞吐；
- CPU、GPU 和内存占用；
- 每百万 Chunk 的存储大小；
- 索引构建与加载时间；
- 单请求成本；
- 超时率和降级率。

### 端到端指标

- 最终答案正确率；
- Faithfulness；
- 引用支持度；
- 拒答准确率；
- 业务任务成功率。

模型 Recall 提升但最终答案没有改善时，应检查重排、上下文和生成链路，而不是直接认定新模型更好。

## 6. 向量、距离与索引必须匹配

### 6.1 维度

同一 Milvus Collection 的向量字段维度固定。更换为不同维度模型时，不能把新向量直接写入旧集合。

高维向量通常意味着：

- 更大存储和内存；
- 更高网络传输成本；
- 更慢索引和检索；
- 不保证更高业务 Recall。

### 6.2 距离度量

常见方式：

- COSINE：比较方向，适合已归一化或语义向量；
- Inner Product：与向量归一化和模型训练方式有关；
- L2：比较欧氏距离。

必须遵循模型推荐方式，并保证：

```text
文档编码方式
= Query 编码契约
= 向量归一化策略
= 索引 metric
= 查询 metric
```

不能建索引用一种 metric、查询又使用另一种。

### 6.3 ANN 索引

HNSW 等近似最近邻索引用速度换取部分召回。需要用真实数据校准：

- 构建参数；
- 查询参数；
- Recall 与延迟；
- 数据规模变化后的内存。

ANN 参数不应只复制示例配置。

## 7. Embedding 与 BM25、Reranker 的分工

```text
Query
→ Embedding 语义召回
  + BM25 字面召回
  + 精确匹配
  + 元数据过滤
→ RRF 融合
→ Reranker 精排
→ 证据选择
```

### Embedding 擅长

- 同义表达；
- 意图相近；
- 风险、原因和影响等语义问题。

### BM25 擅长

- 条款号；
- 物料型号；
- 文件名；
- 错误码；
- 罕见专业词。

### Reranker 擅长

- 在较小候选池中判断 Query 与片段是否真正相关；
- 纠正粗召回排序；
- 压低“看起来相似但不能回答”的片段。

因此，Embedding 选型不能只测纯向量；还要测它在现有混合检索中的边际收益。

---

## 8. 模型升级不能原地覆盖

Embedding 模型变更会影响整个向量空间。正确迁移：

```text
冻结旧版本配置
→ 建立新 Collection / 新索引版本
→ 使用同一文档快照重新编码
→ 校验数量、维度、哈希和权限
→ 影子查询比较新旧结果
→ 运行固定 Gold 集
→ 小流量切换 Alias
→ 观察线上指标
→ 全量切换或回滚
```

### 必须记录

- `embedding_model_id`
- `embedding_model_revision`
- `dimension`
- `normalize`
- `metric_type`
- `chunk_schema_version`
- `corpus_snapshot`
- `index_build_id`
- `created_at`

### 禁止

- 新旧模型向量写入同一空间后直接比较；
- 只更新 Query 模型而不重算文档向量；
- 没有 Gold 集就根据几条人工体验切换；
- 删除旧索引后才验证新模型；
- 把模型名称写死在多个服务中却不做版本审计。

---

## 9. 生产发布与回滚检查

### 发布前

- [ ] Gold 集覆盖真实业务和无答案问题
- [ ] 新旧模型使用相同语料快照
- [ ] Query / Document 编码契约正确
- [ ] 维度、归一化与 metric 一致
- [ ] Recall、MRR、nDCG 和 P95 达到门槛
- [ ] 权限过滤和版本过滤结果一致
- [ ] 新索引数量、哈希和抽样内容正确

### 发布中

- [ ] 影子流量不影响用户结果
- [ ] Alias 或路由可原子切换
- [ ] 旧索引保持可用
- [ ] 监控超时、空召回和降级

### 发布后

- [ ] 观察线上 Query 分布
- [ ] 对比无答案率和人工纠错
- [ ] 收集新 Bad Case
- [ ] 若退化，回切旧 Alias

## 10. 当前报价中台的真实映射

当前配置：

- Embedding：`maidalun1020/bce-embedding-base_v1`
- 维度：768
- 距离：COSINE
- 向量数据库：Milvus
- 索引：HNSW
- 当前检索参数：`ef=128`
- 词法通道：BM25 + jieba
- 融合：RRF
- Milvus 异常时可降级为 BM25-only

项目已经具备：

- 向量与 BM25 混合检索；
- exact / semantic / hybrid 自适应路由；
- 独立招标证据集合；
- active manifest、版本和项目范围校验；
- 成本库同步记录；
- 蓝绿 Collection / Alias 的工程基础；
- 检索评测框架和合成样本。

必须诚实说明的边界：

- 现有笔记和项目文档没有证明当前模型经过多模型正式选型胜出；
- 真实历史 Gold Evidence 规模仍不足；
- 不能宣称相对其他模型提升了某个百分比；
- Embedding 变更需要重建索引，不能热替换后继续使用旧向量；
- 当前 Reranker 尚未正式上线。

推荐下一步：

1. 从真实招标问答和检索日志建立 Holdout；
2. 固定 Chunk、BM25、RRF 和 HNSW 参数；
3. 对候选模型做离线对照；
4. 比较语义通道和完整混合链路的边际收益；
5. 达到门槛后再进行蓝绿索引迁移。

## 11. 面试回答模板

### 60 秒版本

> Embedding 选型不能只看公开榜单。我会先明确是中文企业文档的非对称检索，再建立真实 Query—Evidence Gold 集，覆盖专业术语、编号、同义表达、长条款、版本冲突和无答案问题。对比模型时固定切片、Top-K、向量库和 ANN 参数，主要看 Recall@K、MRR、nDCG，同时测编码延迟、吞吐、内存和索引大小。选定模型后也不会原地覆盖旧向量，而是用新 Collection 全量重建、影子查询、离线回归和 Alias 蓝绿切换，保留回滚。Embedding 只负责语义粗召回，生产中仍要结合 BM25、权限过滤、RRF、Reranker 和证据校验。

### 项目版本

> 报价中台当前使用 bce-embedding-base_v1、768 维、COSINE 和 Milvus HNSW，并与 BM25、RRF 组成混合检索。系统已经有 exact、semantic、hybrid 路由和 BM25 降级，但我不会说这个模型经过正式多模型选型胜出，因为真实 Gold Evidence 基线还需要扩充。合理的下一步是固定现有链路做候选模型消融，再通过新集合重建和 Alias 切换上线，而不是直接替换模型。

## 12. 常见面试追问

### 维度越高是否越好？

不一定。需要同时看真实 Recall、延迟、存储、内存和索引成本，高维只代表表示空间更大。

### 为什么换模型必须重建索引？

不同模型产生的向量不在同一个语义空间，维度和分布也可能不同。只更换 Query 侧模型会导致 Query 与文档向量不可比较。

### Embedding 好了是否还需要 BM25？

需要。企业语料含大量编号、型号、金额、文件名和罕见术语，BM25 常比语义向量稳定。应通过消融实验决定组合，而不是二选一。

### 怎样判断需要 Reranker？

如果正确证据通常能进入较大候选池，但在前几名排序较差，Reranker 可能有价值；如果正确证据根本没召回，应先修 Query、切片、Embedding 或召回通道。

---

## 一句话总结

Embedding 选型的本质不是选“最强模型”，而是用真实 Gold 集证明某个编码契约在既定语料、索引、延迟和成本条件下带来稳定召回，并确保模型升级可以重建、灰度和回滚。
