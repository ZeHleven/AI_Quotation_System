# RAG 引用与证据链：从片段溯源到结论级对齐

## 核心结论

引用不是回答末尾附几个链接。真正的证据链要把每个关键结论与实际使用的证据片段绑定起来，使系统同时具备：

- **可验证**：用户能核对原文
- **可追责**：能确认使用了哪个版本和来源
- **可调试**：开发者能定位检索、筛选或生成错误
- **可评测**：系统能检查结论是否有证据、证据是否支持结论

```text
原始文档位置
→ 带元数据的 Chunk
→ 召回与重排记录
→ 最终证据集
→ 结论—证据对齐
→ 用户引用与质量评测
```

---

## 1. 普通引用与证据链的区别

| 普通引用 | 证据链 |
|---|---|
| 回答末尾附文档链接 | 每个关键结论绑定具体 Evidence ID |
| 只能定位到整份文件 | 可定位到版本、章节、页码和原文片段 |
| 不清楚模型是否使用了该来源 | 保留实际进入上下文的证据 |
| 看起来“有出处” | 可以验证证据是否支持结论 |
| 难以定位错误环节 | 可回放召回、重排、组装和生成过程 |

引用存在并不代表引用正确。最常见的失败是：来源真实，但来源内容并不能支持模型给出的结论。

---

## 2. 证据链的四个阶段

### 2.1 摄取与切片：保留可追溯元数据

每个 Chunk 除正文外，至少应保存：

```json
{
  "evidence_id": "ev_contract_v3_p12_c04",
  "document_id": "contract_001",
  "document_version": "v3",
  "document_name": "采购合同_v3.pdf",
  "section_path": ["第五章", "违约责任"],
  "page": 12,
  "block_id": "p12_clause_04",
  "text": "...",
  "effective_at": "2026-07-01",
  "acl": ["role:legal"],
  "content_hash": "..."
}
```

只有文本而没有文件、章节、页码、版本和权限，后续就无法生成可靠引用。

### 2.2 检索与上下文组装：筛选真正可用的证据

召回候选不能全部作为证据。进入上下文前要检查：

- 与问题是否真正相关
- 是否包含完整的条件和结论
- 多个片段是否互相冲突
- 是否为当前有效版本
- 用户是否有权查看
- 粒度是否足够支持精确引用
- 是否与其他证据高度重复

召回解决“可能相关”，证据筛选解决“能否支撑回答”。

### 2.3 生成：让结论与证据显式对齐

推荐让模型先使用稳定的 Evidence ID，再由应用层渲染文档名、页码和跳转链接：

```json
{
  "claims": [
    {
      "claim_id": "claim_01",
      "text": "逾期超过 30 日可解除合同。",
      "evidence_ids": ["ev_contract_v3_p12_c04"]
    }
  ],
  "answer": "..."
}
```

生成约束应明确：

- 关键事实必须引用证据
- 每条引用必须支持对应结论
- 证据不足时拒答或说明不确定
- 不得把模型常识包装成文档结论
- 冲突证据必须显式展示，不能擅自合并成唯一答案

不要让模型先自由生成答案，再在末尾随意匹配几个来源。

### 2.4 评测与回放：判断错在何处

有了结论—证据映射，才能区分：

```text
没有召回正确证据
→ 检索问题

召回正确但未进入最终上下文
→ 重排或组装问题

正确证据已进入上下文但结论仍错误
→ 生成或约束问题

结论正确但引用错位
→ 对齐或渲染问题
```

## 3. 关键质量指标

| 指标 | 回答的问题 |
|---|---|
| 引用完整率 | 有多少关键结论附带引用 |
| 引用支持度 | 引用内容是否真的支持对应结论 |
| 证据覆盖率 | 最终证据是否覆盖回答所需事实 |
| 来源定位成功率 | 引用能否打开到正确版本、页码或片段 |
| 无依据结论率 | 回答中有多少内容无法由证据推出 |
| 拒答准确率 | 证据不足时是否正确拒答 |
| 权限与版本正确率 | 是否只使用用户有权访问的有效知识 |

指标必须以“关键结论”为粒度。只检查回答是否包含引用标记，很容易把虚假引用误判为合格。

---

## 4. 常见失败模式

| 失败模式 | 表现 | 治理方式 |
|---|---|---|
| 整篇文档级引用 | 用户找不到具体依据 | 定位到章节、页码和原文片段 |
| 先回答、后挂来源 | 引用与结论没有对应关系 | 使用 Claim—Evidence 结构化输出 |
| 召回多少就展示多少 | 引用多但噪声大 | 重排、去重、冲突和完整性检查 |
| 丢失版本信息 | 引用了过期制度 | 入库和检索阶段过滤有效版本 |
| 丢失权限信息 | 引用泄露受限内容 | 检索前和渲染前双重鉴权 |
| 只看答案正确性 | 无法判断是否依靠错误证据碰巧答对 | 同时评测 Faithfulness 和引用支持度 |
| 引用由模型自由编写 | 生成不存在的页码或来源 | 模型输出 Evidence ID，应用层渲染 |

## 5. 最小实现方案

```text
1. 文档解析时生成稳定的 document_id、version 和 block_id
2. Chunk 保存页码、章节、权限、有效期和原文位置
3. 检索日志记录候选 ID、通道、分数和重排结果
4. 上下文只使用经过筛选的 Evidence
5. 模型输出 Claim—Evidence ID 映射
6. 应用层验证 ID、权限和版本后渲染引用
7. 保存最终答案、证据集、模型和 Prompt 版本
8. 用引用完整率、支持度和拒答准确率做回归
```

高风险场景还应支持：

- 一键查看原页或原始区域
- 人工确认与修改记录
- 回答和证据快照
- 文档更新后识别失效引用
- 审计日志与数据脱敏

## 6. 面试回答模板

```text
RAG 做引用不只是为了让答案看起来可信，
而是要把生成结论和实际检索证据绑定起来。

我会在文档切片阶段保留文档、版本、章节、页码、权限等元数据；
在召回和重排后筛选真正相关、完整且不冲突的证据；
生成时要求每个关键结论关联 Evidence ID，
再由应用层渲染原文和来源，避免模型编造引用。

这样既方便用户核对，也能让开发者回放链路，
区分检索、上下文组装和生成问题。
评测时不能只看有没有引用，
还要看引用完整率、引用支持度、证据覆盖率和拒答准确率。
```

## 7. 面向当前报价中台的落地映射

当前报价中台已经具备成本证据、AI 原始报价、最终报价、人工改价来源和报价任务 Trace，方向上已经符合证据链原则。

后续可进一步统一为结论级追踪：

1. 为每条报价行生成稳定的 `claim_id`
2. 将成本条目、RAG Chunk、原始需求行统一映射为 `evidence_id`
3. 记录每个价格结论引用了哪些证据
4. 区分 AI 估价、成本库命中、人工改价和兜底填价
5. 在运营复核页展示“结论—依据—原始位置”
6. 对无底价、证据冲突和过期版本设置人工门禁
7. 将错误引用和无依据结论加入回归测试集

结构化成本价格应继续以数据库记录为主证据；RAG 片段适合补充规范、合同条款和说明性知识，两类证据不能混为同一种可信级别。

---

## 一句话总结

RAG 证据链的本质，是让每个关键结论都能追溯到实际使用、当前有效且有权限访问的原始片段，并让这条关系可以验证、回放和评测。
