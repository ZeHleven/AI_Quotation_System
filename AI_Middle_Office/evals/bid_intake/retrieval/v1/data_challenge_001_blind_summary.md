## 思维判断记录

| 层次 | 结论 |
|---|---|
| Observation | 路由与 Query 数量准确率均为 100%，但 Recall@5 只有 47.59%；9 个正向问题中 8 个至少命中一条，只有 1 个完全未命中。 |
| Evidence | 多事实题 Q003/Q004/Q006/Q007/Q010 只覆盖部分 Gold；Q008 的长表结构证据完全未进入 Top 5；Q009 在无证据场景仍返回结果。 |
| Inference | Agent 已大体“知道该怎么找”，主要瓶颈已从路由转移到有限 Top 5 预算内的事实覆盖和证据充分性判断。Hit@5 较高但 Recall/nDCG 低，说明“碰到一条正确证据”不能代表“足够支持完整研判”。 |
| Alternative explanation | 运行错误和延迟不是主要原因：错误为 0，P95 为 1677 ms；输入解析也不是 Q008 的唯一原因，因为 Gold 长表证据已经存在于冻结 manifest 中。 |
| Governance result | Q010 证明期次冲突隔离没有召回一期数据，输入治理有效；但不能用这一点掩盖检索覆盖不足。 |
| Decision | `RET-EXP-003B` 不通过完整泛化验收，不标记为生产就绪；保留为“正向检索条件性候选”。 |

## 下一步优化方向及原因

这些方向来自 Challenge 暴露的能力缺口，但任何阈值、规则和实现都只能在新建 Development 数据上设计和选择：

1. 建立新的通用 Development 项目集，优先补充多项目的无结果问题、长表结构问题、四个以上事实槽位问题和跨文档证据覆盖问题。原因是当前两个冻结评测集都暴露了拒答缺口，但负样本总量仍不足以安全设定阈值。
2. 第一优先级验证“证据充分性/拒答门”，让系统在只有弱相关结果时返回“资料未提供或证据不足”，而不是强行返回 Top 5。必须用新的正负 Development 样本共同测量误拒答和误命中。
3. 第二优先级验证长表结构索引与召回，把 Sheet 标题、楼栋、分区和表头等结构元数据作为通用可检索字段；不能加入“蓝城”“1#”“9#”等项目专属规则。
4. 第三优先级验证多事实覆盖与跨文档多样性，在固定 Top 5 预算内减少同类证据挤占，覆盖付款阶段、保证金、有效期、合同/招标/清单等不同事实与来源。
5. 每次只改一个主要变量，用新 Development 选择方案；现有 Holdout 和本 Challenge 永久锁定，只保留作历史审计，不能再次运行来挑选实现。
