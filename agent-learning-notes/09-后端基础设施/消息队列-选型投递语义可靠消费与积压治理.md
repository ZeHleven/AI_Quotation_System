# 消息队列：选型、投递语义、可靠消费与积压治理

> 配套实战：[练习 04：消息队列 Outbox、幂等消费、重试与死信实战](./练习记录/04-消息队列Outbox幂等消费重试与死信实战.md)

## 核心结论

消息队列解决的是时间和处理能力解耦：

```text
生产者现在提交工作
→ Broker 暂存和调度
→ 消费者按自身能力处理
```

它带来的收益包括异步、削峰、解耦和广播，但同时引入：

- 消息可能重复；
- 消息可能延迟；
- 消费者可能失败；
- 队列可能积压；
- 业务库写入和发消息可能不一致；
- 排障从一次函数调用变成跨进程数据流。

因此“使用 MQ”不等于“系统可靠”，可靠性仍需业务设计。

---

## 1. 为什么使用消息队列

### 异步

用户提交报价后不必等待模型和 RAG 完成：

```text
API 保存任务 → 返回 202
                  ↓
               队列
                  ↓
               Worker
```

### 削峰

瞬时进入 1000 个任务，但模型并发只允许 10 个时，队列吸收峰值，Worker 按容量消费。

队列只能延后压力，不能消灭工作量。持续流入大于处理能力，最终仍会积压。

### 解耦

报价完成事件可分别触发：

- 生成预审；
- 写审计；
- 更新看板；
- 通知用户；
- 生成成本候选。

生产者不需要同步等待所有下游。

## 2. 基本角色

| 角色 | 职责 |
|---|---|
| Producer | 生成消息，处理发送确认和失败 |
| Broker | 持久化、路由、排序和投递消息 |
| Consumer | 读取消息并执行业务 |
| Consumer Group | 多个消费者共同分担分区或队列 |
| Offset/ACK | 标记消费进度 |
| DLQ | 保存超过重试预算的消息 |

消息内容建议包含：

```json
{
  "event_id": "uuid",
  "event_type": "quote.job.created.v1",
  "occurred_at": "2026-07-30T10:00:00Z",
  "aggregate_id": "quote-job-id",
  "tenant_id": "tenant-id",
  "trace_id": "trace-id",
  "schema_version": 1,
  "payload": {}
}
```

不要把整个数据库对象无版本地序列化进消息。

## 3. Kafka、RocketMQ、RabbitMQ 与 Celery

| 技术 | 强项 | 典型用途 | 主要注意点 |
|---|---|---|---|
| Kafka | 高吞吐、可回放事件流、分区 | 日志、埋点、CDC、流处理 | 分区顺序、消费延迟、运维复杂度 |
| RocketMQ | 业务消息、延时/事务等能力 | 订单、支付、企业业务事件 | 依赖特性和生态选型 |
| RabbitMQ | 灵活路由、确认机制、传统队列 | 中小型业务异步和任务分发 | 队列堆积和单消息大小 |
| Celery | Python 任务调用与 Worker 管理 | AI 推理、文件解析、定时任务 | 它是任务框架，可靠性依赖 Broker 和业务设计 |

### 选型问题

1. 是任务分发还是可长期回放的事件流？
2. 吞吐和延迟是多少？
3. 是否需要严格局部顺序？
4. 是否需要延迟、优先级、路由或事务消息？
5. 团队能否运维该中间件？
6. 消息保留多久，是否需要重新消费？
7. Python 生态和现有系统怎样接入？

当前报价任务采用 Celery + Redis 已能满足 Python 后台任务。没有业务证据时，不应仅为简历把它替换成 Kafka。

## 4. 投递语义

### At-most-once

消息最多处理一次，可能丢失，不重复。

适合少量可丢数据，如部分非关键遥测。

### At-least-once

消息至少处理一次，不轻易丢，但可能重复。

多数业务系统采用这一语义，再通过消费者幂等控制重复副作用。

### Exactly-once

需要先问“在哪个范围内”：

- Broker 内部？
- 单一流处理事务？
- 数据库写入？
- 外部 HTTP 接口？
- 人工通知？

端到端 exactly-once 很难跨越多个异构系统。更可靠的表达是：

> 队列至少一次投递，业务通过幂等键、唯一约束和状态机实现一次业务效果。

## 5. 生产者可靠性

### 发送确认

生产者不能“调用发送函数后就认为成功”。需要：

- Broker 确认；
- 发送超时；
- 有限重试；
- 唯一 `event_id`；
- 发送失败告警。

### 数据库写成功但消息没发出去

危险顺序：

```text
INSERT quote_job
COMMIT
发送消息失败
```

数据库已经有任务，但 Worker 永远收不到。

推荐 Outbox：

```text
同一个 MySQL 事务：
  写业务表
  写 outbox_event
提交

后台发布器：
  扫描未发送事件
  发送到 Broker
  标记已发布
```

即使发布器崩溃，也能重新扫描；重复发布由消费者幂等处理。

## 6. 消费者可靠性

### ACK 时机

```text
先 ACK 再处理：进程崩溃可能丢任务
处理成功后 ACK：崩溃会重投，因此可能重复
```

关键业务通常选择处理成功后确认，并设计幂等。

### Celery 当前配置

项目 `app/tasks/celery_app.py` 中：

```text
task_acks_late = True
worker_prefetch_multiplier = 1
task_acks_on_failure_or_timeout = True
visibility_timeout > 任务时间上限
```

理解：

- late ACK：任务成功执行后才确认，更不容易因 Worker 崩溃而丢失；
- prefetch=1：避免一个 Worker 预取过多长任务；
- visibility timeout：超时未确认的消息可重新可见；
- 仍可能重复执行，所以外部副作用必须幂等。

### 幂等消费者

```sql
CREATE TABLE consumed_events (
    consumer_name VARCHAR(64) NOT NULL,
    event_id CHAR(36) NOT NULL,
    consumed_at DATETIME NOT NULL,
    PRIMARY KEY (consumer_name, event_id)
);
```

同一事务中：

1. 插入消费记录；
2. 更新业务数据；
3. 提交；
4. ACK。

重复消息插入冲突后直接返回已有结果。

## 7. 重试与死信

### 应重试

- 网络瞬断；
- 429；
- 部分 5xx；
- 临时锁冲突；
- 服务短暂不可用。

### 不应自动重试

- 参数错误；
- 无权限；
- 业务状态冲突；
- 文件格式不支持；
- Schema 不兼容；
- 确定性模型输入问题。

### 重试策略

```text
delay = min(cap, base × 2^attempt) + jitter
```

必须有：

- 最大次数；
- 最大总时长；
- 错误分类；
- 每次尝试记录；
- 超预算后进入 DLQ 或人工处理。

死信队列不是垃圾桶。必须有查看、修复、重放和审计流程。

## 8. 顺序与并发

全局严格顺序代价很高。多数业务只需要局部顺序：

```text
同一个 quote_job_id 的事件有序
不同任务可以并行
```

Kafka 常按业务 Key 进入同一分区；其他队列可通过单队列、路由或业务版本控制实现。

即使 Broker 保证投递顺序，消费者重试也可能造成业务完成顺序变化，因此状态机仍要拒绝旧版本写入。

## 9. 积压、背压和毒消息

### 关键指标

```text
生产速率
消费速率
队列长度 / Consumer Lag
消息最老年龄
成功率
处理耗时 P95/P99
重试率
DLQ 数量
Worker 利用率
```

### 队列积压处理

1. 判断突发还是持续容量不足；
2. 找到最慢阶段；
3. 临时扩消费者前确认下游承载能力；
4. 对不同任务分队列或分优先级；
5. 暂停非核心任务；
6. 限制入口，建立背压；
7. 修复后有序重放。

盲目扩 Worker 可能把 MySQL、模型额度或 RAG 服务压垮。

### 毒消息

同一条消息因数据问题每次都失败。必须：

- 有最大尝试次数；
- 保存失败原因和原始事件；
- 隔离到 DLQ；
- 不阻塞整个分区或队列；
- 修复后受控重放。

## 10. 报价中台映射

### 当前链路

```text
FastAPI 创建 quote_jobs
→ quote_dispatcher 按模式分发
→ Celery 把 job_id 发到 Redis Broker
→ Worker 执行 quote_job_runner
→ MySQL 保存状态、事件和结果
```

优点：

- 消息只携带 `job_id`，大输入保存在持久化存储；
- 任务有状态、事件、耗时和失败阶段；
- Worker 可健康检查；
- 支持取消、超时标记和重试。

继续学习的问题：

- “数据库创建任务”和“发送 Celery”之间怎样消除双写窗口？
- 普通报价任务是否需要统一领取租约？
- `confirm_push` 等外部副作用是否有端到端幂等键？
- 队列积压达到多大时应该限制新任务？

## 11. 面试回答

### 为什么使用消息队列？

> 报价链路包含文件解析、模型和 RAG 调用，耗时不稳定。API 先把任务事实写入 MySQL，再通过队列交给 Worker，前端获得任务 ID 后查询状态。这样可以异步响应、削峰和独立扩容 Worker，但也引入重复投递、积压和双写问题，所以还需要幂等消费者、状态机、健康检查和可观测性。

### 怎样防止消息丢失和重复？

> 生产端使用发送确认；业务库与消息之间使用 Outbox 消除双写窗口；Broker 做持久化和确认；消费者成功处理后 ACK。因为崩溃恢复可能重投，我不追求不现实的端到端 exactly-once，而是用事件 ID、唯一约束和条件状态更新保证重复消费只产生一次业务效果。

### 队列积压怎么办？

> 我先比较生产速率、消费速率和最老消息年龄，再通过 Trace 判断瓶颈是 Worker、数据库还是外部模型。只有下游有容量时才扩消费者，同时可按任务类型拆队列、暂停非核心任务并在入口建立背压。修复后按业务优先级受控消化积压，而不是直接清空队列。
