# Agent 可靠性工程：上下文、护栏、状态、评测与追踪

## 核心目标

生产级 Agent 的难点不是继续增加概念，而是控制模型和外部系统带来的不确定性。

可靠的 Agent 应满足：

```text
输入可控
状态可追踪
工具可验证
结果可评测
失败可恢复
风险可转人工
```

最重要的设计原则是：

> 确定的事情交给代码，不确定的事情交给模型，高风险的事情交给人工，所有事情都要留下记录。

---

## 1. Context Engineering：模型真正接收的内容

模型一次调用的输入通常由多部分组成：

```text
System Prompt
+ 用户问题
+ 历史对话
+ 当前任务状态
+ 业务数据
+ 知识库内容
+ 工具说明
+ 工具执行结果
```

对这些信息进行选择、组织、排序、压缩和更新，就是 Context Engineering（上下文工程）。

Prompt Engineering 关注“如何表达指令”，Context Engineering 的范围更广，还要决定：

- 应该放入哪些信息
- 信息来自哪里
- 哪些信息优先级更高
- 哪些信息需要删除或压缩
- 上下文什么时候更新
- 如何防止不可信内容覆盖系统指令

### 报价审核示例

不足的上下文：

```text
请审核这份报价是否合理。
```

更完整的上下文：

```text
项目所在地：东莞
项目类型：幕墙工程
报价版本：V3
材料清单：……
历史项目价格：……
当前有效成本参考：……
企业审核规则：……
允许偏差范围：……
当前用户权限：……
```

模型不是凭空获得业务能力，而是依赖系统提供的事实、规则和工具。

### 上下文的可信层级

可以给不同来源设置优先级：

```text
系统规则和权限
    ↓
经确认的业务规则
    ↓
当前任务结构化数据
    ↓
可信知识库检索结果
    ↓
工具返回结果
    ↓
用户自然语言
    ↓
未验证的外部内容
```

页面、文件、邮件和检索片段都可能包含错误信息或提示注入，不能把它们当作系统指令执行。

## 2. 上下文不是越多越好

上下文过多会带来：

- 重点被淹没
- Token 成本增加
- 响应变慢
- 关键约束被忽略
- 不相关信息产生干扰
- 敏感数据暴露范围扩大

报价审核 Agent 不需要读取全部公司介绍、全部历史聊天和全部项目文档，只需要与当前任务相关的信息。

### 信息分层

```text
必须信息
├── 当前报价
├── 审核规则
├── 当前项目背景
└── 当前有效参考价格

按需信息
├── 相似历史项目
├── 用户确认过的修改记录
└── 特殊业务说明
```

### 常见处理流程

```text
检索
  ↓
权限过滤
  ↓
相关性筛选
  ↓
去重与排序
  ↓
压缩或摘要
  ↓
构建最终上下文
```

### 需要保留的信息

压缩上下文时不能丢失：

- 关键数字和单位
- 来源标识
- 生效时间和版本
- 否定条件与例外条款
- 风险和不确定性
- 需要引用的原始证据

摘要可以节省 Token，但不应取代可追溯的原始记录。

## 3. Context Window 与预算

模型单次调用可接收的信息量有限，这个限制称为 Context Window。

占用上下文的内容包括：

- System Prompt
- 工具定义
- 历史消息
- RAG 片段
- 任务数据
- 工具结果
- 模型之前产生的内容
- 预留输出空间

即使没有超过窗口，也不代表模型能同等准确地利用每条信息。

### 上下文预算示例

```text
System Prompt：10%
工具定义：15%
任务数据：30%
知识检索：30%
历史记录：10%
预留输出：5%
```

比例只是说明预算意识，不是固定标准。实际分配应通过评测确定。

### 预算控制策略

- 按任务动态选择工具定义
- 只召回当前权限内的相关资料
- 对重复工具结果去重
- 把历史对话压缩成结构化状态
- 大文件放在存储中，只传引用和相关片段
- 将复杂任务拆成有状态的多个步骤
- 为输出保留足够空间

## 4. Memory 不等于聊天记录

把全部历史消息不断塞回模型，会造成上下文膨胀、噪声增加和隐私风险。

真正的 Memory 应经过提炼。

例如用户确认：

```text
这个项目的玻璃价格统一按东莞地区价格计算。
```

可以提取为：

```json
{
  "memory_type": "business_rule",
  "content": "该项目玻璃价格统一使用东莞地区价格",
  "project_id": 123,
  "source": "user_confirmed",
  "created_at": "2026-07-27"
}
```

### 四类 Memory

| 类型 | 内容 | 示例 |
|---|---|---|
| 会话记忆 | 当前对话刚发生的事情 | 用户上传文件、要求重新测算 |
| 任务记忆 | 当前任务进度 | OCR 完成、等待审核 |
| 用户记忆 | 跨任务偏好 | 习惯导出 Excel |
| 业务记忆 | 项目或企业规则 | 某客户必须使用指定品牌 |

任务状态与长期 Memory 在实现上可能使用相同数据库，但生命周期、可信度和读取方式不同，应分开建模。

## 5. Memory 写入必须受控

不受控的 Memory 写入可能产生：

- 错误记忆
- 重复记忆
- 过期记忆
- 敏感数据滥存
- 把模型推测当成事实

### 最低字段要求

```json
{
  "content": "客户要求使用A品牌铝型材",
  "memory_type": "business_rule",
  "scope": "project_123",
  "source": "user_confirmed",
  "confidence": 1.0,
  "created_at": "2026-07-27T10:00:00+08:00",
  "expires_at": null
}
```

建议额外记录：

- 来源记录 ID
- 创建人
- 最近验证时间
- 版本
- 敏感级别
- 是否允许被模型自动读取

### 写入流程

```text
识别候选记忆
    ↓
校验来源与作用域
    ↓
敏感信息检查
    ↓
去重与冲突检测
    ↓
必要时人工确认
    ↓
写入并记录事件
```

最重要的约束：

> 模型推测的内容不能直接写成长期事实。

## 6. Agent 决策与业务规则分离

完全让模型判断价格异常，会产生不一致。

确定性规则应写成代码：

```python
deviation = abs(current_price - reference_price) / reference_price

if deviation > 0.20:
    risk_level = "high"
elif deviation > 0.10:
    risk_level = "medium"
else:
    risk_level = "low"
```

再让 LLM：

- 解释风险原因
- 结合项目背景补充说明
- 生成复核建议

### 职责划分

```text
规则：
计算、阈值、权限、字段校验、状态转换

LLM：
理解、归纳、分类、解释、建议
```

### 选择标准

#### 适合规则

- 金额和税率计算
- 权限检查
- 必填字段检查
- 价格偏差阈值
- 任务超时判断
- 状态迁移合法性

#### 适合模型

- 图纸内容理解
- 材料名称归一化候选
- 风险原因总结
- 用户意图识别
- 复杂文本分类

#### 适合规则加模型

```text
模型提取字段 → 规则验证字段
模型识别材料 → 数据库匹配价格
模型生成建议 → 人工审核确认
```

## 7. Guardrails：限制 Agent 的行为

Guardrails 是围绕输入、输出、工具和流程建立的防护体系。

它用于降低：

- 非法工具调用
- 越权访问
- 格式错误
- 危险操作
- 敏感信息泄露
- 无限循环
- 提示注入

### 输入护栏

- 文件格式和大小是否合法
- 用户是否有权限
- 参数是否完整
- 内容是否包含敏感信息
- 外部内容是否可能包含提示注入

### 输出护栏

- 是否符合 JSON Schema
- 是否缺少关键字段
- 是否包含禁止字段
- 引用是否真实存在
- 数量、单位和价格是否符合业务规则

### 工具护栏

- 当前 Agent 是否允许调用
- 当前用户是否有权限
- 参数是否合法
- 是否超过速率或成本限制
- 是否属于写入或高风险操作
- 是否需要人工确认

### 流程护栏

- 最大执行步数
- 最大外部 API 次数
- 最大 Token 和时间预算
- 高金额操作必须审核
- 禁止直接删除业务数据
- 状态只能合法迁移

### 防御纵深

Guardrails 不能只写在 Prompt 中。

```text
Prompt 约束
   +
Schema 校验
   +
权限策略
   +
业务规则
   +
状态机
   +
人工审批
```

关键约束必须在模型之外强制执行。

## 8. 区分只读工具与写入工具

### 只读工具

- 查询报价
- 查询历史价格
- 读取图纸
- 搜索知识库

### 写入工具

- 修改报价
- 提交审批
- 发送通知
- 创建订单
- 删除数据

Agent 第一版建议：

```text
默认允许必要的只读能力
谨慎开放写入能力
```

### 写入工具的最低保障

- 最小权限
- Schema 校验
- 幂等保护
- 操作日志
- 变更前后差异
- 必要时人工确认
- 可恢复或补偿机制

例如发现价格异常时：

```text
Agent 生成修改建议
        ↓
人工确认
        ↓
系统执行修改
        ↓
记录审计事件
```

高风险写入工具不应允许模型绕过审批。

## 9. Tool Result 也不是天然可信

工具结果可能出现：

- API 返回空数据
- 数据库字段缺失
- 第三方返回旧数据
- OCR 格式错误
- 单位不一致
- 部分成功
- 结果被截断

### 标准结果信封

```json
{
  "success": true,
  "data": {
    "material_name": "Low-E玻璃",
    "price": 420,
    "unit": "m²"
  },
  "source": "material_price_db",
  "source_version": "2026-07",
  "timestamp": "2026-07-27T10:00:00+08:00",
  "expires_at": "2026-08-01T00:00:00+08:00",
  "partial": false,
  "error_code": null,
  "message": "查询成功",
  "retryable": false
}
```

Runtime 和 Agent 需要知道：

- 数据来自哪里
- 什么时候产生
- 是否仍然有效
- 是否只返回了部分结果
- 是否可以安全重试

模型不能把“成功返回”自动等同于“业务数据正确”。

## 10. Agent 状态机

生产级 Agent 不应只依赖一个无限循环。

示例状态机：

```text
CREATED
   ↓
PARSING
   ↓
RETRIEVING
   ↓
CALCULATING
   ↓
REVIEWING
   ↓
COMPLETED
```

异常和等待状态：

```text
FAILED_RETRYABLE
FAILED_TERMINAL
WAITING_USER
WAITING_REVIEW
RETRYING
CANCELLED
TIMED_OUT
```

每个状态只能进入合法的下一状态：

```text
CREATED → PARSING
PARSING → RETRIEVING
RETRIEVING → CALCULATING
```

不应无依据地：

```text
CREATED → COMPLETED
```

### 状态机的价值

- 进度清晰
- 支持恢复
- 支持局部重试
- 易于监控
- 便于排查
- 前端可展示真实进度
- 能阻止非法业务跳转

状态迁移应在数据库事务中校验，不能只在前端或 Prompt 中约定。

## 11. Checkpoint：从安全位置恢复

任务执行时间较长时，应在关键步骤保存 Checkpoint。

例如：

```json
{
  "task_id": "task_001",
  "checkpoint": "retrieval_completed",
  "checkpoint_version": 3,
  "ocr_result_id": "ocr_123",
  "vlm_result_id": "vlm_456",
  "retrieval_result_id": "rag_789",
  "created_at": "2026-07-27T10:10:00+08:00"
}
```

Worker 崩溃后：

```text
读取 Checkpoint
      ↓
验证产物仍然有效
      ↓
从成本计算继续
```

不需要重新执行 OCR、VLM 和检索。

### 适合保存 Checkpoint 的位置

- 文件转换后
- OCR 完成后
- VLM 识别后
- 材料匹配后
- 成本计算后
- 人工审核后

### Checkpoint 注意事项

- 保存引用和版本，不一定复制所有大结果
- 检查上游产物是否仍存在
- 保证恢复动作幂等
- 记录代码、模型和 Prompt 版本
- 系统升级后检查旧 Checkpoint 是否兼容
- 区分“步骤完成”和“副作用已提交”

消息队列通常只能保证至少一次投递，因此 Checkpoint 仍需与幂等机制配合。

## 12. Agent 评测的四个层次

### 结果评测

- 材料识别准确率
- 数量提取准确率
- 报价误差率
- 风险项召回率
- 引用正确率

### 过程评测

- 工具选择是否正确
- 工具参数是否正确
- 是否发生重复调用
- 是否调用不必要工具
- 是否正确停止或转人工

### 系统评测

- 任务成功率
- 平均耗时与分位延迟
- 超时率
- 重试率
- API 错误率
- Token 和基础设施成本

### 业务评测

- 人工耗时减少比例
- 复核错误减少比例
- 报价周期缩短比例
- 实际使用率
- 人工建议接受率
- 高风险漏检率

结果正确但成本过高、耗时过长或用户不采纳，仍不算成功的生产系统。

## 13. 建立最小评测集

第一版不一定需要几千条数据，可以从 30～50 个有代表性的案例开始：

```text
10 个正常报价
10 个材料缺失案例
10 个价格异常案例
5 个图纸模糊案例
5 个新材料案例
5 个边界情况
```

案例结构示例：

```json
{
  "case_id": "quote_eval_001",
  "input": "项目输入或输入引用",
  "expected_materials": [],
  "expected_risks": [],
  "expected_action": "manual_review",
  "tags": ["missing_material", "high_risk"],
  "dataset_version": "v1"
}
```

每次修改以下内容都应回归：

- Prompt
- 模型
- 检索策略
- Embedding
- 工具
- 业务规则

除了整体分数，还要保存失败样本和分类，避免平均值掩盖关键风险。

## 14. Agent Trace：记录完整执行链路

普通日志可能只显示：

```text
任务失败
```

Agent Trace 应能还原：

```text
用户提交任务
→ 读取项目
→ 调用历史价格工具
→ 返回 12 条记录
→ 调用偏差计算
→ 发现 3 个风险项
→ 生成审核报告
→ 转人工确认
```

### Trace 建议字段

- `trace_id`
- `task_id`
- 模型名称与版本
- Prompt 版本
- 工具名称
- 工具参数摘要
- 工具结果摘要
- 每一步耗时
- Token 使用量
- 异常类型
- 状态迁移
- 最终输出引用

### 隐私与安全

Trace 不是把所有原始内容无限期保存。

应考虑：

- 密钥和身份凭证脱敏
- 敏感字段屏蔽
- 大输入输出保存引用而不是全文
- 日志访问权限
- 保留周期
- 用户和项目隔离

有了 Trace，才能定位问题来自：

- 模型理解
- RAG 召回
- 工具执行
- 业务规则
- 数据质量
- 基础设施

## 15. Prompt 必须版本化

Prompt 应像代码一样管理：

```text
quote_review_prompt_v1
quote_review_prompt_v2
quote_review_prompt_v3
```

每次任务应记录：

```json
{
  "prompt_version": "quote_review_v3",
  "model": "model_x",
  "model_version": "2026-07",
  "temperature": 0.1
}
```

### 基本发布流程

```text
修改 Prompt
    ↓
跑固定评测集
    ↓
比较新旧版本
    ↓
小流量或影子测试
    ↓
监控线上效果
    ↓
全面发布或回滚
```

版本化的目的不是文件名好看，而是支持复现、比较、回滚和审计。

## 16. 模型路由

不是所有任务都需要最强模型。

```text
意图分类 / 字段格式化 / 简单摘要
→ 快、便宜的小模型

复杂图纸理解
→ VLM

风险分析 / 多步规划
→ 能力更强的模型

纯计算
→ Python 或规则

知识查询
→ RAG / SQL / 搜索工具
```

### 路由依据

- 输入模态
- 任务复杂度
- 风险等级
- 延迟目标
- 成本预算
- 数据地域和合规要求
- 模型当前可用性

### 模型路由也需要评测

路由错误可能导致：

- 简单任务成本过高
- 复杂任务能力不足
- 模型切换后输出协议不一致
- 回退模型改变业务结果

每条 Trace 应记录最终实际使用的模型和回退路径。

## 17. 模型置信度不能直接当真

模型输出：

```json
{
  "confidence": 0.95
}
```

不代表真实正确率是 95%。模型自报置信度通常未经过校准。

更可靠的风险评分应综合：

- 字段完整性
- 规则命中
- 检索结果数量和质量
- 来源是否一致
- 价格偏差
- 模型或工具冲突
- 是否使用回退或降级方案
- 历史评测中的错误概率

```python
risk_score = (
    missing_field_score
    + price_deviation_score
    + source_conflict_score
    + low_retrieval_score
)
```

根据经评测校准的风险分数进行分流：

```text
低风险 → 自动基础校验
中风险 → 普通人工审核
高风险 → 高级人工审核
```

## 18. 现有系统的升级路线

一个系统可以按四层逐步生产化：

### 第一层：工具化

```text
读取报价
查询历史价格
查询材料库
计算偏差
生成报告
```

### 第二层：状态化

```text
任务状态
步骤状态
失败原因
Checkpoint
```

### 第三层：Agent 化

```text
判断需要调用哪些工具
根据结果决定下一步
生成审核解释
```

### 第四层：生产化

```text
评测
Trace
权限
人工审核
重试与降级
Prompt 版本
```

### 当前 AI 智能报价中台的实际情况

根据当前项目状态，以上四层已经有较多基础：

- 已有同步和异步报价工具链
- 已有任务状态、任务事件与 Celery Worker
- 已有报价预审、人工确认和阻断规则
- 已有 RBAC、证据链和审计记录
- 已有 Prompt 回归、RAG 评测和质量报告
- 已有失败恢复、重试、草稿保存和历史追溯

下一步更值得聚焦：

1. 统一 FastAPI、Celery、n8n、Dify、RAG 的 `trace_id`
2. 建立明确的上下文预算和来源优先级
3. 为工具结果统一补齐新鲜度、部分成功和可重试标记
4. 将现有评测集按结果、过程、系统、业务四层归档
5. 补充 Prompt、模型、检索和工具版本的统一运行记录
6. 用真实试运行数据校准风险分流，而不是依赖模型自报置信度

## 生产可靠性检查清单

### Context

- [ ] 每次调用只包含当前任务所需信息
- [ ] 有明确的上下文预算
- [ ] 外部内容不能覆盖系统规则
- [ ] 关键事实保留来源、版本和时间

### Memory

- [ ] Memory 不是简单堆叠聊天记录
- [ ] 每条记忆都有来源、作用域和生命周期
- [ ] 模型推测不能直接写成长期事实
- [ ] 敏感内容有明确存储策略

### Guardrails

- [ ] 输入、输出、工具和流程均有校验
- [ ] 关键护栏在模型之外强制执行
- [ ] 只读和写入工具采用不同权限策略
- [ ] 高风险动作必须人工确认

### State 与恢复

- [ ] 状态迁移有数据库约束
- [ ] 长任务在关键步骤保存 Checkpoint
- [ ] 恢复动作具备幂等保护
- [ ] 失败原因可区分临时和永久错误

### Evaluation

- [ ] 有版本化的固定评测集
- [ ] 同时评测结果、过程、系统和业务价值
- [ ] 每次模型、Prompt、检索或规则变更后回归
- [ ] 保存失败案例而不只看平均分

### Trace

- [ ] 跨组件使用统一 `trace_id`
- [ ] 记录模型、Prompt、工具和状态迁移
- [ ] 日志中的敏感信息已脱敏
- [ ] 可以复现并定位一次失败任务
