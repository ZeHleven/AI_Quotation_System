# Agent 运行机制综合复习与面试手册

## 1. 先记住这一条主链路

```text
用户目标
  → 构造 Context
  → 规划下一步
  → 生成 Tool Call
  → 权限校验与沙箱执行
  → 获取 Observation
  → 更新 State / Checkpoint
  → 规则与结果校验
  → 必要时人工审核
  → 输出结果
  → Trace、指标与评测
```

一句话概括：

> Agent 不是“会调用 API 的大模型”，而是由模型决策、确定性工作流、受控工具、持久化状态、人工责任和评测闭环共同组成的可恢复执行系统。

面试时不要只介绍模型和 Prompt。生产级 Agent 的核心是：

- 决策是否可控；
- 工具是否安全；
- 状态是否可恢复；
- 结果是否可验证；
- 故障是否可定位；
- 业务责任是否有人承接。

## 2. 11 个必会主题总表

| 主题 | 一句话定义 | 生产重点 | 报价中台对应 |
|---|---|---|---|
| Function / Tool Calling | 模型按 Schema 生成调用意图和参数 | 参数校验、授权、超时、幂等、结果合同 | 招标证据检索、上下文读取、版本对比 |
| MCP | AI 应用连接工具、资源和提示模板的标准协议 | Host/Client/Server、传输、能力、安全边界 | Tender Evidence MCP |
| Workflow / 状态机 | 用确定性节点和条件边控制执行路径 | 显式状态、失败分支、恢复点 | LangGraph 报价资料研判图 |
| Planning / 任务分解 | 根据目标和 Observation 决定下一步 | 预算、退出条件、重规划、计划校验 | ReAct 检索与证据补全 |
| 短期 / 长期记忆 | 保存当前任务状态或跨任务经验 | 写入、召回、更新、遗忘、权限 | 当前以运行状态为主，长期记忆仍谨慎建设 |
| 上下文管理与压缩 | 在有限窗口中保留当前决策需要的信息 | 分层上下文、摘要、引用、预算 | manifest、证据片段、事实覆盖摘要 |
| Multi-Agent | 多个自治角色通过明确协议协作 | Handoff、共享状态、冲突、局部恢复 | 当前尚不是 Multi-Agent |
| Checkpoint / 任务恢复 | 持久化图状态和副作用进度 | 恢复语义、幂等、版本校验 | SQL Checkpointer、interrupt/resume |
| Human-in-the-loop | 在高风险节点暂停，由人确认或修正 | 责任边界、版本、幂等、超时 | 证据门后的人工审核 |
| 权限边界 / 工具沙箱 | 限制 Agent 能看什么、做什么、消耗多少 | 最小权限、隔离、出网、密钥、资源限额 | scoped token、只读 Tool；通用执行沙箱仍需按工具补强 |
| Agent 评测 | 同时评价结果、过程、工具、安全和成本 | 离线回归、线上指标、版本对比 | Prompt/RAG/政策校准、运行 Trace |

结论：这 11 项不是彼此独立的名词，而是一条执行链上的控制点。

## 3. 最容易混淆的概念

| 概念 | 它负责什么 | 它不负责什么 |
|---|---|---|
| Function / Tool Calling | 让模型输出结构化调用意图 | 不自动执行、不自动鉴权 |
| Tool | 完成一个有边界的动作 | 不应独自承担整条业务流程 |
| MCP | 标准化暴露和调用 Tool、Resource、Prompt | 不替代业务 Workflow、RBAC、沙箱和评测 |
| RAG | 从知识源检索相关证据 | 不等于记住用户偏好，也不保证生成正确 |
| Memory | 保存对未来任务有用的状态或经验 | 不等于把全部聊天永久存储 |
| Context | 本轮推理实际能看到的信息 | 不等于数据库中的全部数据 |
| State | 当前任务的结构化事实与执行位置 | 不一定会跨任务长期保留 |
| Checkpoint | State 的可恢复持久化快照 | 不自动保证外部副作用幂等 |
| Workflow | 规定节点、顺序、分支和责任 | 不一定需要模型自主规划 |
| Agent | 在约束内根据状态动态选择动作 | 不等于所有步骤都交给模型 |
| Multi-Agent | 多个自治角色按协议分工协作 | 不等于多模型、多 Tool 或并行函数 |

高频回答：

> Workflow 管路线，Agent 选动作，Tool 做具体事情，MCP 管连接协议，State 管当前事实，Checkpoint 管恢复，Memory 管跨时复用，Human 承担高风险责任，Evaluation 判断整套系统是否真的有效。

## 4. 一次生产级 Agent 运行的 12 步

### 第 1 步：接收目标并建立运行身份

创建 `run_id`、用户身份、租户、业务对象、版本和幂等键。没有稳定运行身份，后续无法审计、恢复或防重复。

### 第 2 步：装配最小 Context

上下文通常分为：

- 系统约束：角色、禁止事项、输出契约；
- 任务状态：目标、当前步骤、已完成动作；
- 业务事实：数据库记录、RAG 证据、用户输入；
- 可用能力：Tool Schema、预算、权限；
- 历史摘要：与本次任务真正相关的记忆。

不要把所有历史直接塞进 Prompt。应保留事实、结论、未决问题和引用，删除重复话术。

### 第 3 步：规划下一步

简单任务可以一步 Tool Calling；复杂任务采用 ReAct、Planner-Executor 或显式状态图。

计划必须带：

- 最大步数；
- Token、时间和 Tool 预算；
- 成功条件；
- 退出条件；
- 失败后的重试、降级或人工分支。

### 第 4 步：模型生成调用意图

模型只生成类似以下结构：

```json
{
  "name": "search_tender_evidence",
  "arguments": {
    "query": "投标保证金要求",
    "top_k": 5
  }
}
```

这只是提议，不是执行授权。

### 第 5 步：执行前校验

执行器应检查：

- Tool 是否在白名单；
- 参数是否符合 Schema 和业务约束；
- 用户、租户、项目和数据范围是否匹配；
- 操作是否需要人工批准；
- 是否超过步数、成本或并发预算；
- 幂等键是否已经成功执行。

### 第 6 步：在隔离边界内执行 Tool

按风险限制：

- 文件路径和可写目录；
- 允许的命令与子进程；
- 网络出口和目标域名；
- 服务身份与短期密钥；
- CPU、内存、并发、输出大小和执行时间。

沙箱解决“即使规划错误，影响范围也有限”；权限解决“主体是否允许执行”。两者不能互相替代。

### 第 7 步：把结果转换为 Observation

统一结果合同应至少包含：

```json
{
  "status": "ok",
  "data": {},
  "error_code": null,
  "retryable": false,
  "source_version": "v12",
  "trace_id": "trace_xxx"
}
```

HTTP 200 不等于业务成功。空结果、过期数据、部分成功都必须显式表达。

### 第 8 步：更新 State 并写 Checkpoint

保存：

- 已完成节点；
- Tool 调用与结果摘要；
- 当前事实和未决问题；
- 预算消耗；
- 版本信息；
- 人工暂停信息。

外部写操作还要记录副作用回执，恢复时不能盲目重放。

### 第 9 步：校验结果并决定是否继续

使用确定性规则检查：

- Schema 是否正确；
- 引用是否真实存在；
- 必要事实是否覆盖；
- 金额、权限和业务硬门槛是否满足；
- 是否出现循环、重复调用或低收益检索。

模型负责建议，规则引擎负责不可妥协的企业约束。

### 第 10 步：必要时进入人工审核

高风险操作不应只弹一个确认框，而要持久化：

- 人工看到的版本；
- 建议和证据；
- 允许动作；
- 审核人和时间；
- 决定及原因；
- 恢复命令和幂等标识。

### 第 11 步：完成、降级或补偿

任务可能：

- 正常完成；
- 返回部分结果；
- 降级为只读或规则模式；
- 等待补资料；
- 转人工；
- 触发补偿，而不是简单重试写操作。

### 第 12 步：记录 Trace、指标并进入评测

至少关联：

`trace_id → run_id → node → model_call → tool_call → evidence → policy → human_decision → final_result`

## 5. 报价中台的真实 Agent 映射

### 5.1 当前核心链路

```text
FastAPI 控制面
  → 创建持久化 Agent Run
  → Agent Worker
  → LangGraph StateGraph / ReAct
  → Tool 授权与预算控制
  → Tender Evidence MCP
  → Observation 与事实覆盖
  → PolicyEngine
  → 证据硬门槛
  → interrupt 人工审核
  → Command(resume)
  → SQL Checkpoint 恢复
  → 执行 Trace 与评测
```

### 5.2 Tool 与 MCP

当前 Tender Evidence MCP 暴露：

- Resource：`tender://current/manifest`
- `search_tender_evidence`
- `read_evidence_context`
- `compare_document_versions`
- `validate_evidence_refs`

安全设计：

- 模型不传 `case_id` 决定数据范围；
- Worker 为本次运行签发短期 scoped token；
- Token 绑定项目、assessment、run 和能力；
- 用户登录 Token 不直接透传给 MCP；
- 服务端从认证上下文取得范围；
- 当前 Tool 只读，并记录上下文读取留痕。

### 5.3 Workflow、Planning 与恢复

- LangGraph 显式定义节点、边和条件；
- ReAct 只负责受预算限制的局部决策；
- Tool 调用前经过授权节点；
- 模型输出后进行结构校验；
- PolicyEngine 和证据门执行确定性业务规则；
- SQL Checkpointer 保存节点状态；
- Worker 或进程重启后从最近状态恢复；
- 人工决定先落业务记录，再恢复原线程。

### 5.4 Context、Memory 与 RAG

当前系统已经有：

- 单次运行的结构化 State；
- manifest、检索片段、证据引用和事实覆盖；
- Checkpoint 和运行 Trace；
- MySQL + 混合检索的证据读取链路。

但要诚实说明：

- Checkpoint 是任务恢复，不等于长期记忆；
- RAG 是外部知识检索，不等于用户长期偏好；
- 当前长期记忆应先解决写入标准、时效、冲突、权限和遗忘，再逐步启用；
- 不应把未经确认的模型总结直接写成长期事实。

### 5.5 Multi-Agent 边界

当前报价资料研判系统是一个持久化 LangGraph Agent，虽然还有报价复核等独立 AI 能力，但尚未形成：

- Supervisor；
- Agent 间 Handoff 合同；
- 共享协作状态；
- 冲突裁决；
- 跨 Agent 局部恢复。

因此面试中应说：

> 当前采用单 Agent + 多 Tool + 确定性工作流，先把状态、权限、证据和恢复做稳。只有出现稳定的角色边界、不同权限域或独立上下文需求时，才考虑拆成 Multi-Agent。

这是工程取舍，不是能力不足。

## 6. 10 个高频面试问题与精简回答

### 1. Function Calling 和 MCP 有什么区别？

Function Calling 是模型生成结构化调用意图的机制；MCP 是 Host、Client 和 Server 之间发现并调用 Tool、Resource、Prompt 的标准协议。前者位于模型交互层，后者位于能力接入层，两者可以组合，但都不能替代业务鉴权和工作流。

### 2. Workflow 和 Agent 有什么区别？

Workflow 的路径主要由代码预先定义，适合稳定、可审计的流程；Agent 根据当前 Observation 动态选动作，适合路径不确定的任务。生产系统通常是 Workflow 包住 Agent，把自主性限制在局部。

### 3. 怎样防止 Agent 无限循环？

设置最大步数、总时限、Token 和 Tool 预算；检测重复动作与状态无进展；定义成功和退出条件；低收益时降级或转人工；将循环率、平均步数和无效 Tool 调用率纳入监控。

### 4. State、Memory 和 Checkpoint 的区别？

State 是当前运行事实；Memory 是未来任务可复用的信息；Checkpoint 是 State 的持久化快照。Checkpoint 解决恢复，不代表信息应该长期记住；长期记忆还需要写入、更新、冲突、权限和遗忘策略。

### 5. Checkpoint 能否保证 exactly-once？

不能。它只能恢复计算状态。数据库写入、消息发送、付款等副作用仍需幂等键、唯一约束、Outbox、回执和补偿。工程上通常追求 at-least-once 执行加业务幂等。

### 6. 怎样做 Human-in-the-loop？

在高风险节点持久化暂停状态、证据、版本和允许动作；人工决定用幂等命令落库；恢复前再次校验对象版本、权限和硬门槛；超时后提醒、取消或升级处理，而不是无限等待。

### 7. 如何防止提示注入操纵 Tool？

把外部文本视为不可信数据；模型不能扩大权限；Tool 白名单、参数 Schema、服务端鉴权和数据范围校验必须独立存在；高风险执行进入沙箱或人工审批；结果还要进行引用和业务规则验证。

### 8. 什么时候需要 Multi-Agent？

当任务存在稳定角色分工、不同工具或权限域、上下文需要隔离、工作可独立并行且 Handoff 能清晰验收时才值得使用。若只是步骤变多，优先单 Agent + Workflow，避免通信成本和责任漂移。

### 9. Agent 应该怎样评测？

不能只看最终答案。应分层评测事实正确率、任务成功率、计划质量、Tool 选择与参数、引用有效性、安全越权、人工介入、延迟、成本和恢复成功率，并把模型、Prompt、Tool、数据和策略版本一起记录。

### 10. 你的项目里怎样控制 Agent？

> 我们用显式 LangGraph 状态图包住 ReAct 循环，Tool 调用前做授权和预算控制，证据通过 scoped token 隔离的只读 MCP 获取，模型结果再经过结构校验、PolicyEngine 和证据硬门槛。高风险结论通过 interrupt 交给人工，状态写入 SQL Checkpoint，可在进程失败后恢复；运行过程有 Trace 和版本信息用于回放评测。

## 7. 故障定位顺序

不要先笼统地说“模型不稳定”，按链路分层排查：

1. **输入层**：文件、OCR、表格解析、用户参数是否完整；
2. **Context 层**：是否截断、混入过期事实、摘要丢失约束；
3. **Planning 层**：是否选错路线、循环或过早结束；
4. **模型层**：超时、限流、结构化输出失败、版本变化；
5. **Tool 层**：选错工具、参数错误、空结果、重复副作用；
6. **MCP / 网络层**：认证、传输、服务发现、超时和协议兼容；
7. **RAG / 数据层**：召回、重排、权限过滤、版本和时效；
8. **规则层**：Policy 或证据门是否误拦截；
9. **状态层**：Checkpoint 写入、恢复位置、状态版本；
10. **人工层**：审核超时、重复提交、旧版本批准；
11. **下游层**：消息、推送、数据库或第三方系统失败。

每一层都要有错误码、耗时、输入摘要、输出摘要和版本，而不是只保存一段最终文本。

## 8. 核心指标

### 结果指标

- 任务成功率；
- 事实正确率；
- 证据引用有效率；
- 人工验收通过率；
- 严重错误率。

### 过程指标

- 平均规划步数；
- 无效或重复 Tool 调用率；
- 计划重写率；
- 人工介入率；
- Checkpoint 恢复成功率；
- 超时与降级率。

### RAG 与 Tool 指标

- Recall@K、MRR、nDCG；
- 证据覆盖率；
- Tool 选择准确率；
- 参数合法率；
- Tool 成功率、P95 延迟；
- 幂等命中与重复副作用数。

### 效率与安全指标

- 端到端 P50 / P95 延迟；
- 单任务 Token 和费用；
- 每次成功任务的 Tool 次数；
- 越权阻断数；
- 沙箱违规数；
- 敏感数据泄露和高风险误执行数。

## 9. 设计时必须说明的取舍

| 取舍 | 推荐判断 |
|---|---|
| Agent 还是固定 Workflow | 路径稳定用 Workflow；局部不确定再引入 Agent |
| 单 Agent 还是 Multi-Agent | 默认单 Agent；角色、权限、上下文和验收边界稳定后再拆 |
| Prompt 规则还是 PolicyEngine | 软指导放 Prompt；金额、权限、合规硬规则写代码 |
| 重试还是补偿 | 无副作用读操作可退避重试；写操作先幂等，必要时补偿 |
| 全量历史还是摘要 | 保留事实、决策、未决项和引用；丢弃重复表达 |
| 长期记忆是否立即上线 | 先解决数据治理和评测，再逐步开放写入 |
| MCP 是否等于安全 | MCP 只提供协议边界；安全仍需身份、权限、沙箱和审计 |
| 模型是否直接产出业务结论 | 模型给建议，规则和人承担关键决策 |

## 10. 项目介绍的 30 秒答案

> 我做的不是简单 API 套壳，而是把 AI 智能报价中台逐步建设成可恢复、可审计的 Agent 系统。报价资料研判链路使用 FastAPI 控制面、持久化 Worker 和 LangGraph 状态图，ReAct 只在受控范围内规划；证据通过只读 Tender Evidence MCP 获取，并用短期 scoped token 做项目和能力隔离。模型输出还会经过 Schema、PolicyEngine 和证据门校验，高风险结论由 Human-in-the-loop 审核。SQL Checkpoint 支持中断恢复，Trace、Prompt、Tool、数据和策略版本用于故障定位及回归评测。当前刻意保持单 Agent 架构，等角色和权限边界稳定后再评估 Multi-Agent。

### 能否画出来

- [ ] Agent 主循环；
- [ ] Workflow 与 Agent 的组合；
- [ ] Tool Calling 到执行器的安全链路；
- [ ] MCP Host / Client / Server；
- [ ] State、Checkpoint、Memory 和 RAG 的关系；
- [ ] HITL 暂停与恢复；
- [ ] 报价中台真实运行链路。

### 能否讲清边界

- [ ] Tool Calling 不等于执行授权；
- [ ] MCP 不等于 Workflow 或安全系统；
- [ ] Checkpoint 不等于长期记忆或 exactly-once；
- [ ] RAG 不等于 Memory；
- [ ] 多 Tool 不等于 Multi-Agent；
- [ ] 模型建议不等于企业决策。

### 能否结合故障回答

- [ ] 模型超时怎样降级；
- [ ] Tool 重复执行怎样防；
- [ ] Context 过长怎样压缩；
- [ ] RAG 没召回怎样定位；
- [ ] Worker 重启怎样恢复；
- [ ] 人工重复点击怎样幂等；
- [ ] 提示注入怎样限制影响范围。

---

## 12. 三轮复习法

### 第一轮：记框架

只背：

`目标 → Context → Planning → Tool → 权限/沙箱 → Observation → State/Checkpoint → Policy → Human → Evaluation`

### 第二轮：讲项目

每个概念都回答：

1. 报价中台哪里用到了；
2. 为什么这样设计；
3. 防住了什么失败；
4. 当前还有什么边界。

### 第三轮：做追问

围绕“为什么不用更简单方案”“怎样恢复”“怎样防越权”“指标怎么定义”“失败怎么定位”进行模拟追问。回答时先给结论，再讲机制，最后落到项目证据。
