# 总经办立项标准校准协议

## 1. 样本来源

只使用以下两类样本：

- 已完成研判并由总经办独立复核的历史项目；
- 明确标记为 `synthetic` 的边界测试样本。

不要把 Agent 原建议直接复制为金标。金标应依据投标前专家复核、项目实际结果或两者综合形成，并填写理由。

## 2. 数据分层

- `development`：可用于分析错误、调整权重和阈值；
- `holdout`：只用于候选版本最终盲测，不参与逐项调参。

同一项目的不同报告版本不得跨 development/holdout，以免信息泄漏。

## 3. 重点指标

- 金标一致率：候选建议与总经办金标完全一致；
- 危险报价数：金标为不报价或硬红线，但候选建议报价/有条件报价；
- 硬红线召回率：金标硬红线被确定性硬规则识别的比例；
- 回放错误数：政策文件、样本或执行错误。

危险报价和硬红线召回优先于总体一致率，不能用更高的平均准确率掩盖红线漏判。

## 4. 候选版本门槛

候选版本进入总经办发布评审前至少满足：

- 总金标样本不少于30个；
- holdout样本不少于10个；
- 不报价样本不少于5个；
- 硬红线样本不少于3个；
- 回放错误为0；
- 不增加危险报价；
- 硬红线召回率100%；
- 金标一致率不低于active版本且不低于80%。

门槛通过不代表自动生效。必须由总经办单独批准新增规则版本并切换 `active_version.txt`。

## 5. 校准流程

1. 冻结历史研判的资料清单、经营因素和总经办金标。
2. 将样本分为 development 与 holdout。
3. 只在 development 上分析错误并形成新 YAML 版本。
4. 使用同一批不可变样本比较 active 与候选版本。
5. 只查看holdout聚合指标，确认发布门结果。
6. 保存报告并提交总经办评审。
7. 获得明确批准后，才允许在独立发布阶段切换active版本。

模板见 `evals/calibration_case_template.json`。

## 6. 候选提案生成边界

首版候选生成器只允许调整：

- `decision_thresholds.recommend_quote_min`
- `decision_thresholds.conditional_quote_min`

以下内容全部冻结：

- 经营因素及权重；
- 五档评分分值；
- 关键未知项定义；
- 报价与有条件报价的覆盖率门槛；
- 全部硬红线规则。

至少需要20个development样本，其中“不报价”不少于3个，“报价/有条件报价”合计不少于3个。候选搜索按以下顺序比较：

1. 危险报价数更少；
2. 硬红线漏判更少；
3. 回放错误更少；
4. 金标完全一致数更多；
5. 应追踪项目被错判为不追踪的数量更少；
6. 与active阈值的距离更小。

搜索期间禁止使用holdout。候选形成时应冻结全部样本快照和SHA-256指纹；Holdout只允许由总经办单独触发一次聚合盲测，不显示逐项答案，不允许根据盲测结果重跑同一候选。盲测通过只表示可以进入发布评审，不表示自动生效。

## 7. 金标复核与数据集冻结

生产校准数据必须满足：

1. 金标创建人与复核人不是同一账号；
2. 复核结果保存为独立不可变记录，不回写原金标；
3. 金标被修订时，新版本重新进入待复核，旧版本及其复核记录保留；
4. 同一项目的不同研判版本只能位于同一个数据分层；
5. 只有当前有效且复核通过的金标进入质量统计；
6. 达到样本结构门槛后生成不可变数据集版本和SHA-256指纹；
7. 候选提案必须显式绑定冻结数据集，不得临时读取实时金标集合。

复核退回的金标不得直接修改或覆盖，应由标注人形成新的金标版本并重新复核。数据集冻结后，新金标、修订或复核结果都不得改变该版本。
