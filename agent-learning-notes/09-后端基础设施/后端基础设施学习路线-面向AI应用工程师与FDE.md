# 后端基础设施学习路线：面向 AI 应用工程师与 FDE

## 核心结论

AI 应用工程师不只负责“调用模型”，还要保证请求能够被正确接收、排队、执行、重试、恢复和审计：

```text
API 接收请求
→ MySQL 保存业务事实
→ Redis 提供高速临时能力
→ 队列调度异步任务
→ Worker 调用模型、RAG 和工具
→ 幂等与状态机约束副作用
→ 限流、熔断和降级保护系统
→ Metrics、Log、Trace 验证质量与性能
```

学习目标不是成为数据库或中间件内核专家，而是能够：

1. 独立设计一条生产级 AI 业务链路；
2. 解释关键技术选择和取舍；
3. 定位数据库、缓存、队列、外部模型和应用代码中的瓶颈；
4. 用真实项目证据回答大厂面试追问。

## 1. 岗位所需深度

### P0：必须熟练

| 能力 | 达标标准 |
|---|---|
| MySQL 与 SQL | 能建模、写事务、看 `EXPLAIN`、设计联合索引、定位慢查询 |
| RESTful API | 能设计资源、状态码、错误结构、分页、鉴权和幂等接口 |
| Redis | 能设计 Cache Aside，并处理穿透、击穿、雪崩和一致性 |
| 异步任务 | 能设计状态机、进度、取消、超时、重试和故障恢复 |
| 幂等与重试 | 能区分重复请求与暂时失败，避免重复业务副作用 |
| 故障保护 | 能设置超时、限流、熔断、降级和资源隔离 |
| 性能优化 | 能用 P95/P99、慢查询和 Trace 找到真实瓶颈 |

### P1：需要理解并能设计

| 能力 | 达标标准 |
|---|---|
| 消息队列 | 能比较 Kafka、RocketMQ、RabbitMQ 和 Celery，处理重复与积压 |
| 微服务治理 | 能解释服务边界、发现、配置、健康检查、灰度和可观测性 |
| RPC/gRPC | 能解释与 REST 的差别，正确使用 Deadline 和错误码 |
| 分布式锁 | 能解释锁超时、续租、错误解锁与 fencing token |
| 高并发 | 能进行容量估算、压测、背压和连接池设计 |

### P2：暂缓深入

- MySQL、Redis、Kafka 源码；
- Raft、Paxos 的完整数学证明；
- 自研消息队列、数据库和服务网格；
- 纯中间件岗位级别的内核调优；
- 没有业务量和指标支撑的“亿级架构设计”。

## 2. 课程目录

| 顺序 | 专题 | 解决的问题 |
|---|---|---|
| 1 | MySQL、事务、索引与 SQL 优化 | 业务事实怎样正确、快速地保存和查询 |
| 2 | Redis 与缓存设计 | 怎样用空间换时间，同时控制一致性风险 |
| 3 | 消息队列 | 怎样解耦、削峰、异步执行并保证消息不静默丢失 |
| 4 | REST、RPC 与 gRPC | 服务之间怎样建立清晰、稳定的通信契约 |
| 5 | 微服务与服务治理 | 多服务系统怎样发现、配置、发布和观测 |
| 6 | 异步任务工程 | 长任务怎样排队、追踪、取消、重试和恢复 |
| 7 | 限流、熔断与降级 | 流量或依赖异常时怎样保护核心链路 |
| 8 | 幂等、重试、锁与一致性 | 重复和并发条件下怎样避免错误副作用 |
| 9 | 高并发与性能优化 | 怎样测量、定位和扩大系统容量 |
| 10 | 综合实战与面试 | 把知识映射到报价中台和系统设计题 |

## 3. 报价中台是最好的练习场

当前系统已经包含多个真实后端场景：

```text
Vue / 旧 HTML 工作台
        ↓
FastAPI 主网关
        ↓
MySQL：报价、成本、事件、审计等业务事实
        ↓
Redis + Celery：异步报价调度
        ↓
N8N / Dify / 模型网关 / GLM-4V
        ↓
RAG 服务 + Milvus
```

### 技术与代码映射

| 后端知识 | 项目入口 | 学习重点 |
|---|---|---|
| MySQL | `app/models/`、Alembic revisions | 数据约束、索引、事务和审计 |
| SQLAlchemy | `app/core/database.py` | Session、连接池、事务边界 |
| Redis | Celery Broker、结果后端、SlowAPI 存储 | 临时状态与事实数据分离 |
| 异步任务 | `quote_dispatcher.py`、`quote_job_runner.py` | 状态、心跳、取消和重试 |
| Celery | `app/tasks/celery_app.py` | late ACK、prefetch、可见性超时 |
| API | `app/api/v1/`、`app/core/responses.py` | 资源、权限、错误和版本 |
| 限流 | `app/core/rate_limit.py` | 登录保护、存储模式和多实例一致性 |
| 可观测性 | `quote_job_events`、`trace_id`、看板 | 从请求还原整条执行路径 |

### 面试中的诚实边界

- 系统是多服务 AI 应用架构，但不必包装成完整 Service Mesh；
- Celery late ACK 代表“至少一次”，不等于业务 exactly-once；
- Redis 是 Broker 和临时能力，不是报价、成本和审批的事实主库；
- 普通报价任务具备状态、事件、取消和重试，但任务租约与外部副作用幂等仍需按链路核对；
- 性能结论必须来自压测、指标和 Trace，不能只凭代码猜测。

## 4. 六周学习计划

假设每天学习 60～90 分钟：

| 周次 | 内容 | 必须完成的输出 |
|---|---|---|
| 第 1 周 | MySQL、事务、索引、`EXPLAIN` | 优化 5 条 SQL，解释索引选择 |
| 第 2 周 | RESTful API、Redis、缓存一致性 | 设计一个带缓存和错误契约的查询接口 |
| 第 3 周 | Celery、消息队列、异步状态机 | 实现任务创建、查询、取消和失败重试 |
| 第 4 周 | 幂等、重试、锁、Outbox | 为一个外部推送接口设计幂等方案 |
| 第 5 周 | 微服务、限流、熔断、降级 | 画出依赖图和故障保护策略 |
| 第 6 周 | 压测、性能优化、综合面试 | 输出压测报告和 3 分钟项目介绍 |

### 每天的学习闭环

```text
20 分钟：理解概念
20 分钟：阅读项目代码
20 分钟：写最小实验
10 分钟：口述面试答案
10 分钟：记录错误和边界
```

## 5. 每个专题的掌握标准

每篇笔记都使用同一套验收方式：

### 能解释

- 这个技术解决什么问题；
- 为什么不用更简单的方案；
- 它新增了什么复杂度；
- 失败后怎样恢复；
- 用什么指标证明有效。

### 能实现

- 写出最小可运行示例；
- 正确处理失败、超时和重复；
- 有数据约束、日志和测试；
- 能指出代码中的事实来源和副作用边界。

### 能面试

使用以下结构回答：

```text
结论
→ 业务问题
→ 设计方案
→ 关键实现
→ 指标或验证
→ 取舍与未完成边界
```

不要从技术名词开始堆栈。

## 6. 学完后的项目成果

建议围绕“异步报价任务”完成一个可演示的后端作品：

1. `POST /quote/jobs` 创建任务并返回 `202`；
2. MySQL 保存任务、输入摘要、状态和版本；
3. Worker 从队列执行模型/RAG 调用；
4. Redis 仅承担队列、限流或短期缓存；
5. 状态机禁止非法迁移；
6. 外部确认下发使用幂等键；
7. 暂时错误指数退避重试，确定性错误快速失败；
8. 外部依赖有超时、熔断和降级；
9. Trace 串联 API、任务、检索、模型和副作用；
10. 压测报告包含吞吐、P95/P99、错误率和瓶颈分析。

这比单独写一个“高并发 Demo”更适合 AI 应用岗位，因为它同时体现业务理解、AI 链路和后端工程能力。
