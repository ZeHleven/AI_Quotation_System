# 模型能力优化：Scaling、解码策略与微调

## 核心结论

模型效果不理想时，不能把所有问题都归结为“模型不够大”或“需要微调”。

```text
能力上限不足
→ 更强基座模型或训练阶段 Scaling

模型有能力，但单次回答不稳定
→ 推理阶段 Scaling、候选生成、验证与搜索

行为模式长期不稳定
→ 高质量数据 + 微调

缺少动态或私有事实
→ RAG

规则必须精确执行
→ 代码、工具、Workflow 和校验器
```

对应用工程师而言，通常不能控制模型的预训练，但可以控制：

- 选哪个模型；
- 给模型多少上下文；
- 使用什么采样参数；
- 是否生成多个候选；
- 如何验证和选择候选；
- 是否把稳定的人工纠错沉淀为微调数据。

> 资料说明：本笔记依据视频公开简介和章节摘要整理，并结合当前 AI 智能报价中台的实现扩展，不是逐字字幕。

## 1. 训练 Scaling 与推理 Scaling

### 训练阶段 Scaling

训练 Scaling 是在模型训练阶段增加或优化：

- 参数规模；
- 训练数据量与质量；
- 训练计算量；
- 训练步数；
- 模型架构与优化方法。

它会改变模型参数，目标是提高模型的能力上限。

经典 Scaling Law 研究发现，模型损失会随模型规模、数据量和训练计算量呈现可预测的幂律趋势。但这不等于只增加参数就一定最优：数据量、数据质量和计算预算必须协调。

### 推理阶段 Scaling

推理 Scaling 不重新训练模型，而是在回答当前问题时投入更多计算，例如：

- 允许模型进行更长的推理；
- 独立生成多个候选；
- 对候选投票或重排；
- 使用验证器检查答案；
- 搜索不同的中间推理路径；
- 根据问题难度动态分配计算预算。

它解决的是：

> 模型已经具备一定能力，怎样降低单次采样失误，把已有能力更稳定地发挥出来。

### 两者的核心差异

| 维度 | 训练 Scaling | 推理 Scaling |
|---|---|---|
| 发生时间 | 训练阶段 | 每次请求期间 |
| 是否修改模型参数 | 是 | 否 |
| 主要目标 | 提升能力上限 | 提升当前答案稳定性 |
| 主要投入 | 数据、GPU、训练时间 | Token、并发、延迟、验证器 |
| 成本形态 | 高额前置成本 | 随请求持续发生 |
| 应用团队可控程度 | 使用闭源 API 时很低 | 较高 |
| 典型风险 | 数据污染、过拟合、灾难性遗忘 | 延迟和成本膨胀、候选无法正确选择 |

### 推理计算不是越多越好

推理 Scaling 是否有效取决于：

1. 基座模型是否已经具备解决问题的基本能力；
2. 多个候选之间是否真的存在有价值的差异；
3. 是否有可靠的规则、奖励模型或人工标准选择答案；
4. 任务收益能否覆盖额外 Token、延迟和并发成本。

如果模型完全不懂某个领域，多生成十次可能只是得到十个不同的错误答案。

## 2. 自回归模型怎样生成答案

模型每一步都会计算下一个 Token 的概率分布：

```text
P(next_token | prompt, generated_tokens)
```

解码策略决定怎样从这个分布中选择下一个 Token。

### Greedy Decoding

每一步都选择概率最高的 Token：

```text
next = argmax P(token)
```

优点：

- 简单；
- 成本低；
- 相对稳定。

缺点：

- 早期一步选错后无法回退；
- 容易得到局部最优；
- 缺少多样性。

### Temperature

Temperature 调整概率分布的尖锐程度：

```text
P(token) = softmax(logits / temperature)
```

- 温度较低：概率更集中，回答更稳定；
- 温度较高：概率更平坦，候选更多样；
- 温度不是事实正确性的开关。

即使温度为 0，也不能保证跨供应商、模型版本和硬件环境完全可复现。

### Top-p

Top-p 只在累计概率达到阈值的最小 Token 集合中采样。

它根据当前概率分布动态调整候选集合，通常比固定 Top-k 更灵活。

## 3. 并行采样

并行采样是对同一个问题独立生成多个完整答案：

```text
同一个 Prompt
├── 候选 A
├── 候选 B
├── 候选 C
└── 候选 D
        ↓
规则、验证器、投票或人工选择
```

它是在“完整答案级别”探索不同路径。

### 适合场景

- 广告文案、标题、创意方案；
- 多种可行的规划方案；
- 数学或推理任务的自一致性投票；
- 有明确测试、规则或评分器的代码生成；
- 高价值任务的 Best-of-N 选择。

### 关键前提

生成多个候选不难，难的是怎样选择。

可靠的选择依据可以是：

- 可执行测试；
- JSON Schema；
- 业务硬规则；
- 数值校验；
- 独立验证模型；
- 人工复核。

如果仍然让同一个模型凭感觉选择，错误可能从“生成阶段”转移到“评选阶段”。

### 成本

若独立生成 `N` 个长度相近的答案，生成成本大致会接近单次生成的 `N` 倍，再加上验证或重排成本。

并行只能压缩部分墙钟时间，不能消除：

- Token 费用；
- 供应商速率限制；
- 并发槽位占用；
- 峰值资源压力。

## 4. Beam Search

Beam Search 在每个 Token 步保留得分最高的 `B` 条部分序列：

```text
第 1 步：保留 B 个前缀
第 2 步：扩展每个前缀，再保留总分最高的 B 个
...
直到生成结束
```

路径得分通常基于累计对数概率，并可能加入长度惩罚。

它是在“Token 路径级别”持续筛选高概率序列。

### 适合场景

- 机器翻译；
- 某些摘要任务；
- 语音识别；
- 输出空间较受约束、概率得分与任务质量比较一致的任务。

### 在开放式 LLM 任务中的限制

- 高概率不等于事实正确；
- 容易偏向常见、保守和模板化表达；
- 候选路径之间可能高度相似；
- Beam 越大，显存、计算和延迟越高；
- 长度偏差需要额外校正；
- 主流闭源 Chat API 通常不会直接开放 Beam Search。

因此，“Beam Search 更稳定”只是一种任务相关的经验，不是普遍结论。

## 5. 并行采样与 Beam Search 怎么选

| 任务 | 首选策略 | 原因 |
|---|---|---|
| 创意文案、方案发散 | 并行采样 | 需要完整答案之间的多样性 |
| 数学、代码等可验证任务 | 多候选 + 验证器 | 正确性可以被测试或计算 |
| 翻译、受限摘要 | Beam Search 可作为候选 | 序列概率更可能与质量一致 |
| 严格 JSON 或工具参数 | 低温度 + Schema + 校验重试 | 格式正确比路径多样更重要 |
| Agent 工具调用 | 单路径受控执行为主 | 多条路径会扩大副作用和权限风险 |
| 高风险决策 | 多候选 + 独立规则验证 + 人工确认 | 不能只依赖模型自评 |

### Best-of-N

Best-of-N 的流程是：

1. 生成 `N` 个候选；
2. 为每个候选评分；
3. 选择最高分候选。

它的上限不仅取决于候选生成质量，也取决于评分器能否识别真正正确的答案。

### Self-consistency

Self-consistency 常用于有唯一或可聚合答案的推理任务：

1. 采样多条推理路径；
2. 提取各路径的最终答案；
3. 对最终答案投票。

它不适合无法定义一致答案的开放式任务。

### Pass@k 不等于线上质量

`pass@k` 关注 `k` 个候选中是否至少存在一个正确答案。

线上系统最终只能交付一个结果，因此还必须评估：

- 正确答案能否被选中；
- 选择器的准确率；
- 最终答案成功率；
- 单次成功的成本和延迟。

## 6. 微调解决什么问题

微调是在预训练模型基础上，用特定数据继续更新部分或全部参数。

它更适合塑造稳定行为，例如：

- 固定输出结构；
- 稳定的行业表达方式；
- 特定分类或抽取任务；
- 工具调用习惯；
- 企业语气和风格；
- 用更小模型复现某个稳定任务能力。

### 微调与知识注入的边界

“微调不能补充知识”过于绝对。模型确实可能从微调数据中学到领域知识，但对经常变化、必须精确引用或需要权限控制的事实，微调通常不是首选，因为：

- 更新需要重新训练和发布；
- 很难确认模型在什么时候使用了哪条知识；
- 不容易删除或修正单条事实；
- 无法天然提供证据引用；
- 容易与旧知识发生冲突。

因此：

```text
动态事实、企业私有文档、实时价格
→ RAG 或业务数据库

稳定的输出习惯、分类边界、表达风格
→ 微调候选
```

RAG 与微调不是互斥关系。常见组合是：

```text
微调负责“怎样做”
RAG 负责“依据什么事实做”
工具负责“怎样产生真实副作用”
```

## 7. 微调七步流程

### 第一步：明确目标

先定义可测量的问题：

- 哪类输入当前表现不好；
- 期望输出是什么；
- 基线指标是多少；
- 多大提升才值得训练和运维成本。

“让模型更懂业务”不是可执行目标。

### 第二步：准备高质量样本

监督微调通常需要高质量的输入—输出对：

```json
{
  "instruction": "从报价需求中抽取标准字段",
  "input": "原始业务文本",
  "output": "经过人工确认的标准 JSON"
}
```

样本应覆盖：

- 正常场景；
- 边界场景；
- 容易混淆的反例；
- 拒答与安全场景；
- 真实业务分布。

### 第三步：清洗、格式化和切分

需要处理：

- 重复样本；
- 错误标签；
- 敏感信息；
- 相互冲突的答案；
- 数据泄漏；
- 训练、验证和测试集切分；
- Chat Template 与 Token 长度。

数据数量不能弥补标签质量问题。

### 第四步：选择微调路线

| 路线 | 特点 | 适用情况 |
|---|---|---|
| 全参数微调 | 更新全部参数，成本最高 | 有充足算力和大规模高质量数据 |
| LoRA | 冻结基座，训练低秩适配参数 | 常见的参数高效微调 |
| QLoRA | 量化基座并训练 LoRA | 显存受限的开源模型实验 |
| 云厂商托管微调 | 不自建训练基础设施 | 闭源模型支持且数据合规 |

在选训练路线前，应先验证 Prompt、RAG、工具和 Workflow 是否已经足够。

### 第五步：训练

训练阶段至少要版本化：

- 基座模型；
- 数据集快照；
- Chat Template；
- 超参数；
- 代码与依赖；
- 随机种子；
- Adapter 或模型产物。

只保存一个模型文件，无法支持审计和复现。

### 第六步：评估

评估必须使用未参与训练的保留集，并覆盖：

- 任务正确率；
- 格式通过率；
- 幻觉与拒答；
- 安全和越权；
- 原有通用能力退化；
- 延迟、吞吐和成本；
- RAG 引用与工具调用正确性。

不能只挑几个“看起来不错”的案例。

### 第七步：迭代、发布与监控

生产发布还需要：

- 基座与 Adapter 版本绑定；
- 灰度或影子流量；
- 线上质量监控；
- 数据漂移监控；
- 回滚机制；
- 新失败样本回流；
- 定期重新评测。

微调不是一次训练任务，而是一条持续的数据和发布流水线。

## 8. 什么时候不应该微调

遇到以下情况时，应先解决更基础的问题：

| 问题 | 优先方案 |
|---|---|
| Prompt 含糊或互相冲突 | 重写 Prompt 和输出契约 |
| 缺少实时业务数据 | RAG、数据库或工具调用 |
| 规则必须百分之百执行 | 代码校验和 Workflow |
| 只有少量未经确认的样本 | 先做人工标注和评测集 |
| 不知道当前基线 | 先建立可复跑评测 |
| 模型本身缺少核心能力 | 更换更强模型 |
| 只是偶发采样失误 | 低温度、重试或多候选验证 |
| 线上问题无法追踪 | 先补可观测性和版本记录 |

推荐决策顺序：

```text
定义失败类型和指标
→ Prompt / Schema
→ RAG / 数据库
→ 工具 / Workflow / 校验器
→ 模型路由
→ 推理 Scaling
→ 微调
```

## 9. 当前 AI 智能报价中台的实现映射

### 已有基础

当前系统已经具备一些模型优化和数据闭环基础：

1. `model_gateway.py` 统一封装多个外部模型调用，并记录状态、总延迟、字符量、成本估算和熔断状态。
2. 不同任务使用约 `0.05–0.25` 的低 Temperature，符合抽取、报价和审核任务偏确定性的要求。
3. `OpenAICompatibleBidAnalysisModel` 支持统一的模型、消息和工具调用协议。
4. `quote_feedback` 保存 AI 原始结果、最终人工结果、模型版本和 Prompt 版本。
5. `quote_corrections` 保存字段级修改前后值和修改原因。
6. `prompt_regression_cases` 保存 AI 输出、期望输出和修正记录。
7. 根目录 `eval/` 已有固定样本、离线评测适配器和报告结构。

这些资产使项目具备从真实反馈建立评测集、再考虑训练数据的基础。

### 当前没有的能力

代码中暂未发现：

- LoRA、QLoRA 或 SFT 训练实现；
- 训练数据构建和审批流水线；
- 模型产物注册与灰度发布；
- Beam Search；
- Best-of-N 或 Self-consistency；
- 任务级 Top-p 配置；
- 多候选评分器。

当前系统主要调用外部模型 API，因此不能直接控制供应商内部的训练与 Beam Search。

现有 Prompt 回归主要对已锁定的历史案例计算指标和版本差异，候选 Prompt 自动调用模型重跑仍是待办项。它是很好的评测基础，但还不是完整的模型训练或在线实验平台。

### 为什么现在不建议直接微调

当前报价系统的主要难点包括：

- 实时成本库事实；
- 需求单字段标准化；
- 报价行完整性；
- 规则式漏项检测；
- 成本依据与审计；
- 人工确认和下发门禁。

这些问题主要属于数据、规则、RAG、工具和 Workflow，不应交给模型参数记忆。

此外，人工确认结果可以成为训练数据候选，但不能直接拿数据库记录训练。还需要：

- 删除敏感客户和价格信息；
- 区分真正正确答案与临时人工妥协；
- 去重并防止同一项目跨训练集和测试集泄漏；
- 统一输入—输出契约；
- 人工复核标签；
- 记录数据来源和授权范围。

### 推荐升级顺序

#### P0：先把现有评测变成发布门禁

- 固定代表性样本；
- 对 Prompt、Workflow 和模型版本做真实重跑；
- 对比格式、完整性、金额偏差、延迟和成本；
- 失败时阻止版本发布。

#### P1：增加任务级解码配置

把以下配置集中为可版本化的 Task Profile：

```yaml
task: bid_intake_analysis
model: provider/model-id
temperature: 0.1
max_output_tokens: 4096
response_schema: assessment-draft-v1
candidate_count: 1
selection_policy: schema_and_rule_gate
```

避免每个服务在代码中散落不同参数。

#### P2：只在高价值任务试验多候选

适合优先试验的场景：

- 招标风险研判；
- 疑似漏项建议；
- 技术方案草稿。

推荐从 `2–3` 个候选开始，并使用现有业务规则或人工评审选择。报价计算、工具执行和外部推送仍应保持单路径、可审计。

#### P3：建立“评测集”和“训练集”隔离

```text
原始反馈
→ 脱敏
→ 质量复核
→ 去重
→ 数据集版本
├── 训练集
├── 验证集
└── 永不参与训练的保留测试集
```

#### P4：满足条件后再做微调 PoC

只有在以下条件同时成立时才值得启动：

- 某类稳定行为缺陷反复出现；
- Prompt、RAG、工具和更强模型均无法经济地解决；
- 已有足够且经过复核的代表性样本；
- 离线评测可以复跑；
- 数据合规和回滚方案明确；
- 预期收益高于训练、托管和维护成本。

## 10. 项目场景的策略选择

| 项目任务 | 推荐策略 | 不推荐做法 |
|---|---|---|
| 报价行结构化抽取 | 低温度、Schema、逐行完整性校验 | 用高温度增加“灵活性” |
| 成本底价查询 | 数据库/RAG + 证据链 | 把价格微调进模型 |
| 报价金额计算 | 确定性代码 | 让模型自行心算 |
| 漏项建议 | 规则候选 + 模型解释 + 人工确认 | 模型直接新增报价行 |
| 招标风险分析 | 工具检索 + 低温度；高风险时多候选验证 | 无证据自由生成 |
| 技术方案草稿 | 适度采样或多候选 | 单一模板长期固化 |
| 钉钉推送和任务变更 | 单路径、幂等、权限和确认门禁 | 多 Agent 同时执行副作用 |
| 稳定分类或字段抽取 | 数据成熟后可评估 LoRA/SFT | 没有基线就开始训练 |

## 11. 关键指标

### 推理 Scaling

- 最终答案成功率；
- Pass@k；
- 候选选择准确率；
- 每个成功答案的 Token 成本；
- P50/P95 延迟；
- 并发槽位和限流失败；
- 候选多样性；
- 验证器误判率。

### 微调

- 保留测试集指标；
- 相比基座和 Prompt 基线的增益；
- 格式通过率；
- 事实与引用正确率；
- 工具调用正确率；
- 安全与拒答回归；
- 通用能力退化；
- 训练、部署和单次推理成本。

只有“训练 Loss 下降”不能证明业务效果变好。

## 12. 常见误区

### 误区一：推理时间越长，答案一定越好

模型可能重复、偏航或放大错误。计算预算必须与问题难度和验证能力匹配。

### 误区二：Beam Search 就是更可靠的生成

Beam Search 优化的是序列概率，不直接优化事实正确性或业务价值。

### 误区三：并行采样就是同时请求几次

没有候选选择标准，多次请求只是增加成本。

### 误区四：Temperature 为 0 就完全可复现

模型版本、供应商实现、并行计算和服务更新仍可能造成差异。

### 误区五：微调可以替代 RAG

动态、精确、需引用和有权限边界的事实仍应由外部知识源提供。

### 误区六：人工修改记录可以直接拿来训练

生产数据必须经过脱敏、复核、去重、授权检查和数据集切分。

### 误区七：微调完成就不需要 Prompt

微调后的模型仍需要清晰的系统指令、上下文、工具契约和安全边界。

## 13. 面试表达

### 问：训练 Scaling 和推理 Scaling 有什么区别？

训练 Scaling 通过增加参数、数据和训练计算提升模型能力上限，会修改模型参数；推理 Scaling 不改参数，而是在单次请求中投入更多 Token、采样、搜索或验证计算，提高已有能力的发挥稳定性。前者是前置研发成本，后者是随流量增长的在线成本。

### 问：并行采样和 Beam Search 怎么选？

并行采样在完整答案级别探索多样性，适合开放式生成和有验证器的 Best-of-N；Beam Search 在 Token 路径级保留高概率前缀，适合输出空间受限、序列概率与任务质量较一致的任务。开放式 Agent 任务通常更重视工具约束、验证和业务规则，而不是盲目增大 Beam。

### 问：什么时候应该微调？

先确认问题属于稳定行为缺陷，并且 Prompt、RAG、工具、Workflow、模型路由和推理 Scaling 都不能经济地解决；同时要有高质量数据、保留测试集、数据合规、发布和回滚能力。否则微调只会把现有数据问题写进模型参数。

### 项目表达

> 当前项目以外部模型 API 为主，我没有把微调当作默认答案。系统已经沉淀 AI 原始输出、人工最终结果、字段级修正、Prompt 版本和离线评测资产；现阶段优先补真实重跑、任务级解码配置和发布门禁。只有稳定行为缺陷在评测中持续出现，才会将脱敏、复核后的反馈构造成训练集，开展 LoRA 或托管微调 PoC。

## 14. 检查清单

### 解码与推理

- [ ] 能区分 Greedy、Sampling、Best-of-N、Self-consistency 和 Beam Search
- [ ] 为每类任务定义 Temperature、最大输出和结构化约束
- [ ] 多候选方案有独立选择器或业务校验器
- [ ] 统计最终答案质量，而不只统计 Pass@k
- [ ] 观察候选数对成本、P95 延迟和限流的影响
- [ ] 有副作用的 Agent 步骤保持单路径、幂等和人工门禁

### 微调准备

- [ ] 已有可复跑基线
- [ ] 训练、验证和保留测试集严格隔离
- [ ] 样本经过脱敏、授权和人工复核
- [ ] 基座模型、数据集、模板和超参数可追踪
- [ ] 同时评估任务质量、安全、成本和延迟
- [ ] 有灰度、监控和回滚方案
- [ ] 能说明为什么 Prompt、RAG 或工具不足以解决问题
