# Agent 决策循环与执行架构

## 核心模型

Agent 的典型运行闭环可以概括为：

```text
理解目标
  ↓
规划下一步
  ↓
选择并执行动作
  ↓
观察执行结果
  ↓
更新状态
  ↓
继续或结束
```

常用术语：

```text
Reasoning → Planning → Action → Observation
```

真正区分 Agent 与普通聊天应用的，不是模型是否“思考”，而是系统是否具备：

- 目标驱动的多步执行
- 工具调用
- 状态更新
- 根据执行结果调整下一步
- 明确的终止条件

---

## 1. Reasoning：形成决策

Reasoning 负责理解当前任务并判断需要什么信息或动作。

例如审核报价时，Agent 需要判断：

- 当前输入是否完整
- 是否需要读取图纸
- 是否缺少成本参考
- 是否要查询历史项目
- 是否需要调用工具
- 是否应转人工处理

Reasoning 的产物应是可执行决策，而不是冗长的自然语言思考。

### 生产实践

系统可以记录：

- 选择了什么动作
- 选择动作的简短依据
- 使用了哪些输入和证据

不应依赖或持久化模型的隐藏思维链。审计需要的是可验证的决策轨迹，而不是未经验证的内部推理文本。

---

## 2. Planning：把目标拆成步骤

复杂目标需要拆成可执行任务。

```text
生成工程报价
   ↓
解析文件
   ↓
识别材料
   ↓
检索成本依据
   ↓
计算报价
   ↓
完整性校验
   ↓
生成 Excel
   ↓
人工审核
```

### 三种规划方式

| 方式 | 特点 | 适用场景 |
|---|---|---|
| 固定 Workflow | 路径预先定义 | 强规则、强审计业务 |
| ReAct | 每次观察后决定下一步 | 路径较短、需要动态工具选择 |
| Plan-and-Execute | 先形成计划，再逐步执行和修订 | 长任务、依赖关系明显 |

LLM 并非“一次只能想一步”。选择哪种方式，应取决于任务长度、风险、成本和可预测性。

### 好计划应包含

- 步骤
- 输入和输出
- 依赖关系
- 所需工具
- 完成条件
- 失败处理
- 是否需要人工确认

---

## 3. Action 与 Executor

Action 是 Agent 选择的具体动作：

- 查询数据库
- 执行 Python
- 调用 OCR
- 检索 RAG
- 生成 Excel
- 提交审核

模型只负责提出工具调用意图，真正执行通常由 Executor 完成。

```text
LLM 决策
   ↓
Executor
   ├── Schema 校验
   ├── 权限校验
   ├── 幂等检查
   ├── 超时与重试
   ├── 执行工具
   └── 记录日志
```

Executor 把概率性的模型决策转换为受控的软件执行。

---

## 4. Observation：读取并验证执行结果

Observation 是工具或环境返回的信息。

```text
Action：查询材料价格
Observation：东莞地区有效参考价为 420 元/㎡
```

Agent 根据 Observation 决定：

- 结果是否完整
- 来源是否可靠
- 数据是否过期
- 是否与其他来源冲突
- 下一步应该继续、重试、回退还是转人工

工具结果不能直接视为事实，仍需来源、新鲜度、格式和业务规则校验。

---

## 5. ReAct：边执行边调整

ReAct 源于 `Reasoning + Acting`，基本循环是：

```text
判断下一步
   ↓
执行动作
   ↓
观察结果
   ↓
更新判断
```

示例：

```text
目标：查询玻璃幕墙材料价格

动作：检索材料候选
观察：找到 3 种相似材料

动作：读取图纸规格
观察：规格为 6+12A+6 Low-E

动作：查询地区成本库
观察：找到东莞地区有效价格

结束：返回价格、来源和风险提示
```

ReAct 是常见模式，但不是所有 Agent 的唯一实现。高风险、强流程业务通常采用：

```text
确定性 Workflow + 局部 ReAct 决策
```

---

## 6. 循环与终止控制

更多步骤不等于更聪明。无界循环会增加：

- 延迟
- Token 和工具成本
- 重复调用
- 不一致结果
- 外部副作用风险

常见限制：

```python
MAX_STEPS = 10
MAX_TOOL_CALLS = 8
MAX_RETRIES = 3
```

还应限制：

- 总执行时间
- Token 预算
- 外部 API 成本
- 相同工具和参数的重复次数
- 状态无进展次数

### 终止条件

Agent 应在以下情况结束或暂停：

- 目标已经满足
- 输出通过验证
- 需要用户补充信息
- 需要人工审批
- 已达到预算或步骤上限
- 发生不可恢复错误

---

## 7. Tool Selection：选择正确工具

Agent 不应把所有工具都调用一遍，而应根据任务选择必要工具。

工具描述应说明：

- 能解决什么问题
- 什么时候使用
- 什么时候不要使用
- 输入输出 Schema
- 权限和风险级别
- 典型错误

### 提升选择准确率

- 工具名称语义明确
- 职责不重叠
- 描述简短且有边界
- 只暴露当前任务需要的工具
- 用评测集覆盖相似工具的混淆案例

工具过多会增加模型选择难度，也会占用上下文。

---

## 8. Tool Ranking：给候选工具排序

多个工具可能都能返回价格：

- 历史项目价格
- 当前成本库
- 市场参考价
- 供应商报价

不能固定认为某一种永远最好。排序应依据：

| 维度 | 问题 |
|---|---|
| 权威性 | 是否为企业认可的数据源 |
| 新鲜度 | 数据何时更新 |
| 适用范围 | 地区、规格、项目类型是否匹配 |
| 完整性 | 字段和样本是否充分 |
| 成本与延迟 | 调用代价是否合理 |
| 风险 | 是否需要授权或人工确认 |

可以由规则先过滤不合格来源，再让 Agent 在合格候选中选择。

---

## 9. Tool Composition：组合多个工具

复杂任务通常需要工具链：

```text
文件解析
  ↓
OCR / VLM
  ↓
材料标准化
  ↓
RAG / SQL
  ↓
确定性计算
  ↓
生成 Excel
```

组合工具时需要显式定义：

- 每一步的数据契约
- 上下游依赖
- 中间结果存储
- Checkpoint
- 失败补偿
- 幂等边界

工具组合不是把调用次数做多，而是让每个步骤承担清晰职责。

---

## 10. Reflection：完成后的复核

Reflection 是对候选结果进行再次检查。

```text
候选报价
   ↓
检查单位、数量和价格
   ↓
发现异常
   ↓
重新查询或修正
```

可用于：

- 检查遗漏
- 检查证据是否支持结论
- 检查输出是否满足要求
- 生成改进建议

### 局限

模型自我复核可能重复原来的错误，因此不能代替：

- Schema 校验
- 业务规则
- 独立数据源
- 确定性 Verifier
- 人工审核

Reflection 应有次数上限，并通过评测证明收益大于成本。

---

## 11. Self-Consistency：多路径聚合

Self-Consistency 的核心不是简单地把模型问三次后取平均值，而是：

1. 对同一推理任务采样多条候选路径
2. 对最终答案进行多数投票或一致性聚合

适合：

- 有明确答案的复杂推理
- 单次推理不稳定
- 错误可以通过多样化采样抵消

不适合：

- 外部事实本身缺失
- 高成本、低延迟任务
- 写入和审批等有副作用操作
- 多次调用高度相关、无法形成真正多样性

Self-Consistency 会显著增加 Token 与延迟，应先评测再使用。

---

## 12. Critic：独立评审

常见流程：

```text
生成候选结果
    ↓
Critic 检查问题
    ↓
生成修订结果
    ↓
Verifier 验证
```

Critic 可以是：

- 同一模型的第二次受控调用
- 不同 Prompt
- 不同模型
- 专门的规则与模型组合

不一定要建立一个完整的“Critic Agent”。多 Agent 会增加状态同步、成本和调试难度。

Critic 的输出也只是建议，仍需验证器或人工决定是否接受。

---

## 13. Verifier：确定性验证

Verifier 使用代码、规则或可验证数据检查结果。

```python
if area <= 0:
    raise ValidationError("面积必须大于 0")
```

常见验证：

- 字段完整性
- JSON Schema
- 数值范围
- 单位兼容
- 金额合计
- 状态迁移
- 权限
- 引用是否存在

Verifier 不只检查“格式是否合法”，也可以检查已被业务规则明确定义的合理性。

对于无法确定的风险判断，应交给模型解释或人工审核。

## 14. Runtime、Executor 与模型的关系

```text
Agent Runtime
├── Context 构建
├── Prompt 与模型调用
├── Planner / Workflow
├── State / Checkpoint
├── Tool Registry
├── Executor
├── Retry / Fallback
└── Logs / Traces
```

职责：

```text
LLM：理解与生成决策
Runtime：组织执行闭环
Executor：安全执行动作
Verifier：验证结果
Workflow：约束业务路径
```

Runtime 是控制中心，而不是替代 LLM 的另一颗“大脑”。

## 16. Coding Agent 执行架构示例

Coding Agent 也是 Agent Loop 的一种具体实现：

```text
用户需求
→ 组装项目配置、相关代码、任务状态、工具和记忆
→ 模型决定下一步动作
→ 读取或搜索代码
→ 修改文件
→ 执行构建与测试
→ 把真实结果作为 Observation 回灌
→ 修正方案或结束任务
```

它的工程价值不只来自模型，而来自四部分组合：

```text
模型 + 工具 + 有界循环 + 上下文工程
```

### 关键控制点

- 按需读取代码，不把整个仓库塞入上下文
- 历史过长时压缩已完成事项，保留未完成任务和关键约束
- 将计划、修改文件、测试结果和下一步持久化，支持中断恢复
- 命令或测试失败后，把错误作为新观察结果进入下一轮
- 用户追加要求时，在原任务状态上继续，而不是丢失上下文
- 读、搜索和测试可自动执行；删除、提交、发布等高风险动作需审批
- 使用沙箱、独立分支或 Worktree 隔离修改，审查后再合并

将记忆保存为 Markdown、YAML 或数据库记录只是实现选择。真正要求是状态可读取、可版本化、可恢复，并能在本轮上下文中按需使用。

## 17. 模式选型

| 场景 | 推荐模式 |
|---|---|
| 步骤固定、规则明确 | Workflow |
| 需要根据工具结果动态选择下一步 | ReAct |
| 长任务且依赖关系明确 | Plan-and-Execute |
| 结果可通过明确规则检查 | Verifier |
| 结果需要补充审阅 | Reflection / Critic |
| 高风险或不可逆操作 | Human-in-the-loop |

可以组合，但每增加一种模式都要承担额外的状态、评测、成本和调试复杂度。

## 18. 面试复习卡片

### 为什么不能直接相信 LLM？

模型具有概率性并可能产生幻觉。需要结构化输出、工具与规则校验、权限控制、Guardrails、证据链和人工审核。

### Workflow 和 Agent 有什么区别？

Workflow 按确定路径执行；Agent 在受控范围内动态决策。生产实践通常由 Workflow 控制主流程，Agent 处理不确定节点。

### RAG 为什么不等于向量数据库？

RAG 是从数据处理、切片、Embedding、存储、召回、重排、上下文构建到生成与引用的完整链路；向量数据库只是组件之一。

### Agent 为什么需要 State？

State 支持长任务、Checkpoint、失败恢复、重试、进度展示、审计和可观测性。

### Agent 选错工具怎么办？

通过清晰的工具描述、Schema、权限和参数校验减少错误；执行失败时按错误类型重试或回退；高风险动作转人工，并用 Trace 复盘。

### Reflection 能代替 Verifier 吗？

不能。Reflection 仍是概率性的模型复核；Verifier 通过代码和规则提供确定性约束。

## 对当前 AI 智能报价中台的启示

系统已经具备 Workflow、异步任务、人工预审、RAG、成本库、规则校验和证据链，不需要为了“Agent 化”推翻现有流程。

更合适的增量方向：

1. 在少数不确定节点引入受控的工具选择
2. 用 Trace 评估工具选择与组合是否合理
3. 把完整性、金额和状态检查继续留在 Verifier
4. 对 Reflection 和 Critic 做离线对比，证明收益后再上线
5. 高风险报价始终保留人工确认

## 一句话总结

Agent 架构的关键不是让模型思考更多，而是让 Runtime 在有限预算、明确工具、确定性验证和人工边界内，把“决策—执行—观察”闭环可靠地运行起来。
