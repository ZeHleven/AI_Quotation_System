# 评测、安全与治理综合复习与面试手册

## 使用方法

大厂 AI 应用岗位关注的不是“模型会不会回答”，而是：

```text
面对大量真实用户
系统能否防越权和泄露
结果能否被量化验证
变更能否安全发布
事故能否定位和追责
高风险决策能否由人接管
```

---

## 1. 一张图记住治理闭环

```text
用户身份与数据分类
        ↓
输入安全 / Prompt Injection 防护
        ↓
最小上下文、模型和工具权限
        ↓
模型输出 + Tool Call
        ↓
Schema / 内容 / 权限 / 业务校验
        ↓
低风险自动执行 ─── 高风险人工审核
        ↓
操作审计 + Trace + 错误分类
        ↓
线上反馈和失败样本
        ↓
脱敏评测集 + 自动回归
        ↓
版本发布门 + 灰度 + 回滚
```

安全控制运行过程，评测控制质量，版本治理控制变更，审计与人工机制控制责任。

---

## 2. 核心主题速记

| 主题 | 一句话记忆 |
|---|---|
| Prompt 注入 | 不可信内容试图改变模型行为，防护目标是限制影响 |
| 越权工具调用 | 模型提出动作，但独立授权节点决定能否执行 |
| 敏感信息泄露 | 从收集、传输、模型、日志、评测到删除全生命周期控制 |
| 内容安全 | 分别检查输入、输出和行为风险 |
| 用户隐私 | 目的限定、最小化、透明、保留与删除 |
| 权限控制 | RBAC + 资源 scope + 业务状态 + 下游重新鉴权 |
| 操作审计 | 记录主体、动作、资源、依据、版本、结果和回执 |
| 模型输出评测 | 结构、事实、证据、安全和业务正确性分层评估 |
| Agent 成功率 | 结果正确、过程合规、副作用正确且在预算内完成 |
| 延迟与 Token | 看 P95、TTFT、输入输出 Token 和成功任务成本 |
| 版本回归 | 完整运行清单与基线比较，通过发布门再灰度 |
| 人工兜底 | 高风险节点持久化快照，由授权人员决策并恢复 |

---

## 3. 三条绝对原则

### 原则一：Prompt 不是权限系统

系统 Prompt 可以降低误行为，却不能阻止攻击者利用模型发起越权请求。真实权限必须由应用和下游服务执行。

### 原则二：模型输出是不可信输入

模型生成的 JSON、SQL、HTML、工具参数和引用都需要解析、转义、鉴权和业务校验。

### 原则三：平均分不能抵消严重事故

一次真实越权、敏感泄露、审批绕过或关键金额错误，都可能阻断发布。

---

## 4. Prompt Injection 防御

攻击类型：

```text
直接注入：用户直接要求忽略规则
间接注入：攻击藏在 PDF、网页、RAG、工具结果
多模态注入：攻击藏在图片、二维码、音视频
```

防御：

```text
标记不可信数据
→ 控制上下文
→ 最小工具集合
→ 参数 Schema
→ 服务端资源鉴权
→ 高风险人工审批
→ 输出校验
→ 攻击集回归
```

面试表达：

> 我不把“识别所有注入”作为唯一目标，而是即使模型被影响，也无法获得额外数据、权限和不可逆执行能力。

---

## 5. 隐私、敏感数据与内容安全

### 数据生命周期

```text
收集：目的明确、最小化
传输：分类、权限过滤、脱敏
模型：选择允许的供应商和地域
存储：加密、权限、保留期
日志/Trace：脱敏摘要和引用
评测：授权、脱敏、去重
删除：主库、索引、缓存和备份策略
```

### 内容安全动作

- allow：正常处理；
- transform：脱敏或降低细节；
- review：转人工；
- block：拒绝并记录类别。

内容安全与权限不同：文本本身合规，也可能读取了不属于当前用户的数据。

---

## 6. 权限与工具治理

授权模型：

```text
subject + action + resource + scope + context
```

工具调用前检查：

- 工具是否允许；
- 参数是否符合 Schema；
- 用户是否有权限；
- 资源是否属于当前项目；
- 状态是否允许该动作；
- 是否重复或超预算；
- 是否需要人工批准。

下游系统必须重新鉴权，不能因为请求来自 Agent 就信任它。

---

## 7. 操作审计与人工兜底

### 审计字段

```text
用户与角色快照
Agent / Tool / Action
资源和作用域
授权与审批依据
Prompt、模型、数据、策略版本
脱敏输入摘要
结果、错误码、下游回执
trace_id / job_id / run_id
```

### Human-in-the-loop

```text
保存 Checkpoint 和审核快照
→ 展示证据、差异、风险和版本
→ 授权用户 approve / reject / revise
→ 校验角色、状态、版本和幂等
→ 恢复任务
→ 审计最终执行
```

审核期间数据变化，应使旧快照过期或重新确认。

## 8. 评测集与指标

### 测试集

| 集合 | 目的 |
|---|---|
| Development | 日常迭代 |
| Holdout | 最终盲测 |
| Regression | 线上问题防复发 |
| Adversarial | 注入、越权和泄露 |
| Canary | 真实流量小范围验证 |

### 指标

```text
输出：Schema、事实、引用、幻觉
任务：完成率、恢复率、人工接管
工具：选择、参数、成功、越权
RAG：召回、排序、证据、权限
安全：攻击成功、泄露、审批绕过
效率：P95、Token、成功任务成本
业务：完整率、金额偏差、打回率
```

Agent 任务成功不等于 HTTP 返回 200，也不等于流程没有抛异常。

---

## 9. Prompt 与完整运行版本

一次结果由以下版本共同决定：

```text
代码
+ 模型
+ Prompt
+ 参数
+ Tool Schema
+ Workflow
+ RAG/数据
+ Policy
+ 评测器
```

Prompt 版本还应包含变量、Few-shot、输出 Schema、工具描述和上下文组装策略。

生命周期：

```text
draft → candidate → canary → active → retired
```

---

## 10. 自动回归与发布门

```text
任一运行组件变化
→ 快速确定性测试
→ AI/RAG/Agent 评测
→ 与 active 基线比较
→ 安全硬门
→ 人工审批
→ 灰度
→ 线上指标
→ 全量或回滚
```

硬门：

- 越权执行 = 0；
- 敏感泄露 = 0；
- 高风险审批绕过 = 0；
- 确认需求行完整；
- 关键金额规则通过。

软指标：

- 平均质量；
- P95；
- Token 成本；
- 低风险人工接管率。

## 11. 错误分类

每个错误至少标记：

```text
layer：在哪一层
retryability：能否重试
severity：影响等级
```

层级：

```text
INPUT / AUTH / CONTEXT / RETRIEVAL / MODEL
PARSING / TOOL / WORKFLOW / DATA
DEPENDENCY / POLICY / HUMAN
```

错误码驱动：

- 重试；
- 降级；
- 转人工；
- 告警；
- Runbook；
- 自动加入回归集。

## 12. 报价中台真实能力矩阵

| 建议能力 | 当前状态 | 真实边界 |
|---|---|---|
| Prompt 版本管理 | 部分具备 | 有版本字段和回归记录，统一注册表可继续完善 |
| Agent/RAG 测试集 | 已具备基础 | Prompt、RAG、Retrieval Gold、Policy 数据集均已存在 |
| 自动化回归 | 部分具备 | pytest 和评测脚本较多，候选 Prompt 真实自动重跑未闭环 |
| 工具审计日志 | 部分具备 | Agent Trace、成本审计较强，尚未统一覆盖所有工具 |
| 用户和角色权限 | 已具备 | JWT、RBAC、role_version、角色事件 |
| 敏感字段脱敏 | 部分具备 | Agent Trace 和部分外发数据已脱敏，通用 PII/DLP 未统一 |
| 错误分类 | 部分具备 | 多处有 error_code，尚未统一层级、重试性和严重度 |
| 人工兜底 | 已具备 | 报价预审、证据门、Human Decision 与恢复 |
| 内容安全 | 尚需补强 | 无统一输入/输出内容安全服务 |
| Prompt Injection 红队 | 尚需补强 | 已有工具安全设计，缺系统化多模态攻击集 |
| 操作审计 | 部分具备 | 成本访问、角色、Agent 事件可追踪，未集中防篡改 |
| 生产发布门 | 尚未完整落地 | 正式生产灰度与自动停止/回滚尚未发生 |

## 13. 一分钟项目回答

> 报价中台的安全边界不依赖模型自觉。用户先经过 JWT 和 RBAC，角色变化通过 role_version 让旧 Token 失效；Agent 只看到受限工具，Tender Evidence MCP 使用项目级短期 scope，并由下游重新校验资源。报价下发、成本启用和证据不足场景进入人工审核。
>
> 可观测和审计方面，系统使用 trace_id 串联调用，Agent Trace 对密钥字段脱敏，成本库访问、角色变化和 Human Decision 都有结构化记录。评测方面已经有 Prompt Regression Case/Run、RAG 报告、Retrieval Gold、Policy 校准和大量 pytest。
>
> 我也会明确当前不足：通用 PII/DLP、统一内容安全、多模态注入红队、全工具统一审计、统一错误分类和生产自动发布门尚未完全落地。下一步应先统一数据分类、审计 Schema 和 Eval Run，再用安全硬门驱动灰度。

## 14. 高频面试题

### 1. Prompt Injection 能彻底防住吗？

> 很难保证识别所有攻击，因此重点是防御纵深和最小权限，让注入成功也不能造成越权数据访问或真实副作用。

### 2. 怎样防越权工具调用？

> 模型只提出调用，Runtime 校验工具、参数、用户、资源、状态和审批；使用短期 scope；下游完整中介重新鉴权。

### 3. 如何防敏感信息泄露？

> 数据分类和最小化、模型调用前权限过滤与脱敏、供应商合规、日志和评测集治理、输出 DLP、保留和删除策略共同控制。

### 4. 内容安全与 RBAC 的区别？

> 内容安全判断信息或行为类别是否允许，RBAC 判断当前主体是否有动作权限，二者需要同时生效。

### 5. Agent 任务成功率怎么定义？

> 达成业务目标、过程合规、副作用正确，并在时间与成本预算内完成；仅返回成功状态不够。

### 6. 如何建立 Agent 测试集？

> 从正常、边界、失败、无答案、攻击和线上缺陷分层采样，按项目隔离 Development 与 Holdout，生产样本先授权、脱敏和复核。

### 7. LLM Judge 能否代替人工？

> 适合规模化评估模糊质量，但要固定版本并用专家校准。金额、权限、Schema 和泄露等应优先由确定性规则判断。

### 8. Prompt 为什么要版本化？

> Prompt 是运行环境的一部分，变量、示例、Schema、工具描述和上下文策略都会改变结果；没有版本就无法复现、对比和回滚。

### 9. 回归评测怎样进入 CI/CD？

> PR 跑快速确定性集，合并或定时跑真实模型集，候选发布跑 Holdout 和安全集；与 active 基线对比，通过硬门后才灰度。

### 10. 错误分类有什么价值？

> 它统一决定重试、降级或人工处理，并支持告警、统计、Runbook 和失败样本回流。

### 11. 审计日志记录原始 Prompt 是否最好？

> 不一定。审计要能追责，但完整 Prompt 可能包含隐私和攻击载荷。通常保存版本、哈希、脱敏摘要、输入引用、动作和结果。

### 12. Human-in-the-loop 怎样避免形式化？

> 审核者必须看到证据、差异、风险和固定版本；决策结构化保存；恢复时重新校验权限、状态、版本和幂等；过期快照需重审。

### 13. 你项目目前最大治理缺口是什么？

> 现有控制分散在 RBAC、Agent Trace、成本审计和各类评测中，尚缺统一 DLP、内容安全、审计 Schema、错误分类与 Eval Run 控制面。

## 15. 三轮复习

### 第一轮：边界

脱稿解释 Prompt Injection、最小权限、隐私生命周期、审计与 Human-in-the-loop。

### 第二轮：评测

能设计数据集、指标、错误分类、Prompt 版本和发布门。

### 第三轮：项目

每个主题用三句话回答：

```text
项目已经具备什么
代码或数据证据是什么
还缺什么以及为何优先补
```

---

## 16. 面试前自查

- [ ] 不说“系统 Prompt 可以防住越权”
- [ ] 不把模型输出直接当可信命令
- [ ] 不把内容安全和权限控制混为一谈
- [ ] 不把字段遮罩当完整隐私治理
- [ ] 不把普通日志当完整审计
- [ ] 不把 HTTP 200 当 Agent 任务成功
- [ ] 不只看平均分
- [ ] 不用同一批数据无限调参后再声称测试通过
- [ ] 不让 LLM Judge 独自判定金额和权限
- [ ] 不把人工审核简化成无证据的确认按钮
- [ ] 不把尚未完成的 DLP、内容安全和生产发布门说成已落地
