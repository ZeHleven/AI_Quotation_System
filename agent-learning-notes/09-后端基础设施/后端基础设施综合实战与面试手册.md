回答结构：

```text
结论

→ 方案
→ 关键实现
```

## 1. 三分钟项目介绍

> 我做的是一套 AI 智能报价中台。前端提交文本、图片或 Excel 需求，FastAPI 负责鉴权、输入标准化和任务创建；长耗时报价通过 Redis 和 Celery 异步执行，Worker 调用 N8N/Dify、模型网关和 RAG 服务，MySQL 保存任务、成本、事件、人工草稿和审计事实。结果不会直接下发，而是先做成本参考、完整性检查、证据链和人工预审。系统还提供取消、失败重试、运行耗时、Trace 和运维健康检查。我在这个项目中重点解决的不是简单调用模型，而是异步任务可靠性、RAG 证据、人工 Gate、状态一致性和线上排障。当前仍诚实保留外部下发统一幂等、生产 SLO 和完整 Runbook 等上线前边界。

## 2. 综合系统设计题

### 题目

设计一个支持大文件、长耗时 AI 报价、人工确认和高并发的后台系统。

### 2.1 需求澄清

先问：

- 峰值任务量和并发；
- 单文件大小、页数、报价行数；
- 延迟目标；
- 是否允许排队；
- 报价是否属于高风险副作用；
- 租户和权限；
- 是否要求逐行完整；
- 外部模型额度；
- 数据保留和审计要求；
- 灾难恢复目标。

### 2.2 总体架构

```text
Client
  ↓ HTTPS
API Gateway / FastAPI
  ├─ Auth / RBAC / Rate Limit
  ├─ Object Storage
  └─ MySQL：task + outbox
         ↓
   Broker / Celery
         ↓
   Worker Pools
  ├─ Parse
  ├─ RAG
  ├─ Model
  └─ Validation
         ↓
   Preview + Evidence
         ↓
   Human Gate
         ↓
 Idempotent External Push
```

### 2.3 数据模型

核心表：

```text
quote_jobs
quote_job_events
quote_job_requirement_rows
quote_preview_drafts
idempotency_records
outbox_events
quote_cost_evidence
```

不变量：

- `job_id` 唯一；
- 状态只能合法迁移；
- 确认行必须逐行有结果或明确占位；
- 未补价占位不能下发；
- 同一幂等键只允许一个业务效果；
- 外部回执可追溯；
- 人工改动保留前后快照。

### 2.4 API

```text
POST /quote/jobs                 202
GET  /quote/jobs/{id}            200
GET  /quote/jobs/{id}/events     200
POST /quote/jobs/{id}/cancel     200/409
POST /quote/jobs/{id}/retry      202/409
POST /quote/jobs/{id}/confirm    200/409
```

创建与确认可接受 `Idempotency-Key`。

### 2.5 可靠性

- MySQL 先保存任务；
- Outbox 可靠发布；
- Consumer 至少一次；
- 条件更新/租约领取；
- Checkpoint 保存阶段；
- 错误分类后重试；
- DLQ/人工接管；
- 确认下发端到端幂等；
- 事件和 Trace 审计。

### 2.6 故障保护

- 用户、租户、模型维度限流；
- 总 Deadline 和依赖超时；
- RAG/模型熔断；
- 长短任务队列隔离；
- 队列积压时背压；
- 无证据结果显式降级；
- 高风险输出必须人工确认。

### 2.7 性能

- 文件走对象存储，不在数据库长期存 Base64；
- 列表不读取大 JSON；
- 索引匹配真实查询；
- RAG/模型调用有界并发；
- 大清单分批；
- Embedding 批处理；
- 记录各阶段耗时；
- 压测关注 P95/P99、Lag、错误和成本。

## 3. 高频面试题

### 1. MySQL 和 Redis 怎样分工？

> MySQL 保存报价、成本、权限和审计等业务事实，提供约束和事务；Redis 用于 Celery Broker、限流和可重建缓存。Redis 故障后业务事实仍可恢复，关键写操作不会只依赖缓存。

### 2. 怎样设计联合索引？

> 先从真实查询的等值过滤、范围、排序和返回列出发，用 `EXPLAIN ANALYZE` 验证扫描行、排序和回表。联合索引遵循左前缀，但列顺序不是只看区分度；还要考虑写入成本和是否存在更通用的索引。

### 3. 怎样保证缓存一致性？

> 使用 Cache Aside，MySQL 事务提交后删除缓存，失败通过重试或 Outbox 补偿，并设置有界 TTL。高风险操作回源数据库或校验版本；Key 包含租户、权限和数据版本。

### 4. 为什么使用队列？

> 长耗时 AI 任务需要异步响应和削峰。API 保存任务后返回 ID，Worker 按容量处理。但队列会引入重复、积压和双写问题，所以还要有 Outbox、消费者幂等、状态机、队列指标和背压。

### 5. Kafka、RabbitMQ、RocketMQ 怎样选？

> Kafka 适合高吞吐、可回放事件流；RabbitMQ 适合灵活路由的传统业务队列；RocketMQ 的业务消息和延时等能力较强；Python AI 任务可先使用 Celery。选型看任务还是事件流、吞吐、顺序、保留、路由和团队运维能力，不为技术栈数量而更换。

### 6. 怎样防止任务重复执行？

> Broker 至少一次意味着任务可能重投。Worker 用数据库条件更新或租约领取任务，外部副作用使用稳定幂等键，结果写入带状态或 fencing token。重复消息可以执行检查，但不能再次产生下发、扣费或通知。

### 7. 幂等、锁和事务有什么区别？

> 事务保证单个数据库内一组操作原子；锁限制并发进入临界区；幂等保证重复业务意图只产生一次效果。分布式锁过期后仍可能有旧持有者，所以还需要 fencing 或数据库版本约束，不能用锁替代事务和幂等。

### 8. 怎样处理数据库与消息双写？

> 在同一 MySQL 事务中写业务数据和 Outbox，后台发布器发送后更新状态。发布可能重复，因此消费者用事件 ID 和唯一约束去重。这样把不可恢复的双写窗口转换成可重试的最终一致。

### 9. 限流、熔断、降级有什么区别？

> 限流控制入口流量，熔断在依赖持续失败时停止调用，降级在完整能力不可用时返回明确的较弱结果。还要用超时限制等待、用资源隔离防止一个下游拖垮整个系统。

### 10. 怎样定位高延迟？

> 先看 P95/P99 和错误率，再用 Trace 拆分 API、数据库、队列等待、RAG、模型和持久化。数据库查慢查询和执行计划，队列看 Lag 和消息年龄，模型看 429、首 Token 和生成耗时。找到最大占比后在同一负载下验证优化。

### 11. REST 和 gRPC 怎样选？

> 浏览器和开放接口优先 REST；内部稳定、高频、强类型或流式链路可考虑 gRPC。gRPC 会增加 Proto 兼容、网关和观测治理，不能自动解决权限、超时和幂等。

### 12. 怎样取消一个异步任务？

> 先将状态改为 `cancel_requested`，Worker 在安全点检查并停止后续阶段，最后进入 `cancelled`。已发生的外部副作用不能靠改状态回滚，需要幂等查询、补偿或人工处理。取消接口本身也应幂等。

### 13. 怎样应对队列积压？

> 比较生产、消费速率和最老消息年龄，再确认瓶颈是 Worker 还是下游。扩 Worker 前先验证数据库和模型额度；同时拆分长短任务、暂停低优先级任务并在入口背压。修复后受控消化积压。

### 14. 怎样设计微服务边界？

> 以业务能力、数据所有权、独立扩缩容和团队责任划分。拆分前先做好模块化边界，拆分后要承担网络故障、数据一致性、版本兼容和可观测性成本。

### 15. 什么是高并发设计？

> 它不是中间件堆叠，而是在目标负载下控制并发、连接、队列和外部额度，使 P95/P99、错误率和成本满足 SLO。接近容量时应限流和背压，而不是让请求无限排队。

## 4. 五个 STAR 项目故事

### 故事一：异步报价

```text
S：同步报价链路包含解析、模型和 N8N，耗时不稳定。
T：改善等待体验并支持进度、取消和恢复。
A：任务先落 MySQL，再由 Celery 执行；状态和事件分开建模。
R：前端可快速获得任务 ID，后台可观测耗时和失败阶段。
边界：外部下发统一幂等仍需继续补强。
```

### 故事二：169 行完整性

```text
S：大清单可能被模型合并或漏行。
T：保证人工确认的每一行都有报价结果。
A：逐行 Key、分批 20 行、缺失补报、占位和确认前 Gate。
R：最终预审保留 169 行；未补价占位返回 409 阻断下发。
```

### 故事三：成本库事实源

```text
S：旧 materials 测试数据不能继续作为正式报价来源。
T：建立可审计的正式成本主库。
A：MySQL cost_items.active 作为事实源，状态历史、RAG 同步记录和证据快照。
R：旧材料写入与同步入口退役，正式报价只使用 active 条目。
```

### 故事四：Agent 卡死定位

```text
S：任务长期处于 running。
T：找到真实故障层并安全恢复。
A：沿 Trace/租约排查到旧 Worker 和旧 MCP 凭证，补初始化失败落库和租约释放。
R：新 Worker 第二次尝试接管并恢复到人工审核。
```

### 故事五：性能指标纠正

```text
S：历史成功任务 duration_ms 为 0，看板失真。
T：建立可信报价速度基线。
A：修复新任务真实耗时写入，备份后回填历史异常记录。
R：速度看板可以基于真实任务统计，并继续支持 P95 分析。
```

只讲自己能用代码、测试或运行记录证明的故事。

## 5. 动手项目验收清单

### 正确性

- [ ] 任务与事件持久化；
- [ ] 合法状态迁移；
- [ ] 数据库约束而非只靠代码查重；
- [ ] 外部副作用幂等；
- [ ] 大清单逐行完整；
- [ ] 人工确认和审计。

### 可靠性

- [ ] Broker/Worker 故障可检测；
- [ ] 消息重复不重复生效；
- [ ] 暂时错误有限重试；
- [ ] 毒任务进入人工处理；
- [ ] 任务取消和超时语义明确；
- [ ] 数据库与消息双写可恢复。

### 性能

- [ ] 列表不读取大字段；
- [ ] 关键 SQL 有执行计划；
- [ ] 连接池和并发有限；
- [ ] 长短任务隔离；
- [ ] 队列有背压；
- [ ] P50/P95/P99 和错误率有报告。

### 安全

- [ ] JWT/RBAC；
- [ ] 资源归属和租户隔离；
- [ ] 限流；
- [ ] 文件和请求大小限制；
- [ ] 日志不泄密；
- [ ] 高风险结果人工 Gate。

```text

怎样证明有效？

```

## 7. 一页速记

```text
MySQL 管事实，Redis 管速度
Queue 管调度，State Machine 管生命周期
REST 管资源契约，gRPC 管内部强类型调用
Timeout 管等待，Retry 管暂时失败
Rate Limit 管入口，Circuit Breaker 管故障依赖
Fallback 管可用能力，Bulkhead 管资源边界
Idempotency 管重复效果，Lock 管并发临界区
Outbox 管业务与消息一致，Saga 管跨服务补偿
Metrics 看趋势，Trace 看单次链路，Log 看具体事件
性能先测量后优化，项目先讲业务价值再讲技术
```
