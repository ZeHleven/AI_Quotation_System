# AI 落地工程师（FDE）：Agent 知识体系与学习路线

## 核心目标

目标不是停留在调用大模型 API，而是能够独立完成 Agent 的：

- 需求分析与系统设计
- 功能开发与工具集成
- 测试评估与质量控制
- 部署上线与持续运维

真正的 Agent 不是单独一个大模型，而是一整套能够感知、决策、执行和反馈的系统。

## Agent 整体架构

```text
                 用户
                  │
            Web / App / 企业微信
                  │
                  ▼
          Agent（推理 + 调度）
                  │
      ┌───────────┼────────────┐
      ▼           ▼            ▼
   LLM 推理      Memory       Planner
      │           │            │
      └──────┬────┴────────────┘
             ▼
        Tool Calling
             │
 ┌──────┬────────┬───────────┐
 ▼      ▼        ▼           ▼
数据库  MCP     API 接口    Python 执行
```

可以把 Agent 的核心组成概括为：

```text
Prompt + Context + Model + Planning + Tools + Memory
```

生产系统还必须补充：

```text
Evaluation + Observability + Security + Human-in-the-loop
```

当任务跨越文本、图片、PDF、OCR 或音视频时，还要把中间结果当成有 ID、版本和依赖关系的资产，并支持质量检查和局部重做，详见 [多模态 Agent 架构：流水线、资产一致性与局部重做](../02-Agent核心架构/多模态Agent架构-流水线资产一致性与局部重做.md)。

## 1. LLM：Agent 的推理核心

LLM 负责理解问题、推理、判断意图并作出决策。

例如，用户提出“帮我生成一份工程报价”，模型需要理解这并非一次简单问答，而可能包含：

1. 获取图纸或需求清单
2. 识别材料与施工项目
3. 计算工程量
4. 查询材料或成本价格
5. 生成报价结果
6. 导出 Excel

常见模型包括 GPT、Claude、Qwen、DeepSeek 和 GLM。

学习重点：

- 模型能力边界
- 上下文窗口与 Token
- 结构化输出
- 幻觉与不确定性
- 模型选择、成本与延迟

当多个业务和模型进入生产环境后，还要掌握统一网关、Token/并发限流、阶段延迟和安全缓存，详见 [LLM 平台工程：统一网关、资源限流、延迟拆解与安全缓存](../10-LLMOps与可观测性/LLM平台工程-统一网关资源限流延迟拆解与安全缓存.md)。

理解这些工程指标前，需要先掌握 Transformer、注意力计算、Prefill/Decode 和 KV Cache，详见 [Transformer 推理基础：注意力、QKV 与 KV Cache](../04-LLM与Prompt/Transformer推理基础-注意力QKV与KVCache.md)。

模型效果不足时，还要区分能力上限、采样不稳定、动态知识和稳定行为缺陷，再选择模型路由、推理 Scaling、RAG 或微调，详见 [模型能力优化：Scaling、解码策略与微调](../04-LLM与Prompt/模型能力优化-Scaling解码策略与微调.md)。

模型进入应用后，还要统一管理 Token、上下文、Prompt、结构化输出、Streaming、模型路由、大小模型协同、量化与推理服务，详见 [模型应用基础综合复习与面试手册](../12-面试与职业发展/模型应用基础综合复习与面试手册.md)。

面向真实用户时，还要把 Prompt 注入、敏感数据、内容安全、权限审计、人工审核、回归评测和版本发布门组成治理闭环，详见 [评测、安全与治理综合复习与面试手册](../12-面试与职业发展/评测安全与治理综合复习与面试手册.md)。

企业 Context 还必须把自然语言对齐到带作用域和版本的标准业务对象，并由 Runtime 显式提供当前时刻、业务时区和日历边界，详见 [企业语义与时间上下文：业务词典、标准化与时态治理](../03-生产级开发基础/企业语义与时间上下文-业务词典标准化与时态治理.md)。

## 2. Prompt Engineering：约束模型行为

Prompt 不只是用户输入的一句话。生产环境中的提示通常需要明确：

- 角色：模型扮演谁
- 目标：要完成什么任务
- 上下文：可依赖哪些信息
- 限制：哪些行为禁止发生
- 工具：何时以及如何调用
- 输出：返回什么数据结构

示例：

```text
角色：
你是一名工程预算专家。

目标：
根据需求和成本资料生成准确报价。

限制：
- 不得编造价格
- 必须引用可追溯的成本依据
- 信息不足时要求人工确认

输出：
返回符合约定 Schema 的 JSON。
```

学习重点：

- System、Developer、User 指令的职责划分
- Few-shot 示例
- 结构化输出与 Schema 校验
- Prompt 版本管理
- Prompt 回归测试

## 3. Memory：让 Agent 保留有用状态

Memory 用于保存用户、历史任务、偏好和工作进度等信息。

### 短期记忆

保存当前会话近期的上下文，例如最近若干轮对话。

### 长期记忆

保存跨会话仍有价值的信息，例如“用户偏好 Excel 格式”。

### 语义记忆

保存抽象后的事实或知识，例如“Leo 从事建筑行业”。

常见实现：

- Redis：短期状态、缓存、会话数据
- PostgreSQL/MySQL：结构化长期数据
- 向量数据库：语义检索型记忆

实践时还要考虑：

- 什么信息值得记忆
- 何时写入、更新和遗忘
- 如何避免错误记忆持续污染后续任务
- 隐私、权限和数据生命周期

## 4. RAG：为模型提供外部知识

RAG（Retrieval-Augmented Generation，检索增强生成）的基本思想是：

1. 先从知识库检索相关资料
2. 再把检索结果交给 LLM 生成答案

典型流程：

```text
问题
  ↓
查询理解与改写
  ↓
Embedding / 关键词检索
  ↓
向量数据库或搜索引擎
  ↓
召回 Top K
  ↓
重排与过滤
  ↓
LLM 生成
```

常见技术：

- 向量数据库：Milvus、FAISS、Chroma、pgvector
- 关键词检索：Elasticsearch、BM25
- 混合检索与融合：向量检索 + BM25 + RRF

RAG 的关键不只是“能搜到”，还包括召回率、准确率、切片策略、元数据过滤、重排和引用溯源。

多格式摄取方法见 [RAG 文档摄取：Word 与 PDF](../08-RAG与Embedding/RAG文档摄取-Word与PDF解析切片和检索.md) 和 [RAG 多格式文档摄取：Excel、图片与统一解析合同](../08-RAG与Embedding/RAG多格式文档摄取-Excel图片与统一解析合同.md)。

## 5. Embedding：把语义映射为向量

Embedding 将文本、图像等内容转换成数值向量，使系统能够计算语义相似度。

例如，“苹果”“香蕉”“水果”的向量距离通常较近，而“苹果”和“汽车”的距离通常较远。

主要用途：

- RAG 检索
- 相似内容搜索
- 推荐
- 语义记忆
- 聚类与去重

学习重点：

- 向量维度与模型选择
- Cosine、Dot Product、L2 等距离度量
- 文本切片对检索效果的影响
- 向量模型升级与重建索引
- 中文及行业语料的实际效果评估

完整的选型、对照评测和蓝绿迁移方法见 [Embedding 模型选型：基准评测、索引迁移与生产治理](../08-RAG与Embedding/Embedding模型选型-基准评测索引迁移与生产治理.md)。

## 6. Tool Calling：让 Agent 真正执行任务

Tool Calling 是 Agent 从“会回答”走向“会做事”的关键。

可调用的工具包括：

- 数据库和 SQL
- HTTP API
- Python 和 Shell
- Excel、PDF 和 OCR
- ERP、CRM
- 邮件、企业微信、钉钉

典型过程：

```text
用户目标
  ↓
模型判断需要使用工具
  ↓
生成符合 Schema 的调用参数
  ↓
系统执行工具
  ↓
模型检查结果并决定下一步
```

生产实践需要重点处理：

- 参数校验
- 权限控制
- 超时、重试与幂等
- 危险操作审批
- 工具结果过长或异常
- 调用审计

工具规模扩大后，选择本身会变成检索、排序与执行治理问题，详见 [Agent 工具与 Skill 路由：分层召回、重排、执行校验与 Workflow 边界](../05-工具调用与MCP/Agent工具与Skill路由-分层召回重排执行校验与Workflow边界.md)。

## 7. MCP：标准化工具与上下文接入

MCP（Model Context Protocol）可以理解为 AI 应用连接外部工具和数据源的一种标准接口。

例如，连接 GitHub 后，Agent 可以在授权范围内读取 PR、检查代码或执行仓库操作；连接文档系统后，可以检索、读取或更新文档。

学习重点：

- MCP Client、Server、Tool、Resource、Prompt 的基本概念
- 工具描述和输入 Schema
- 鉴权与权限边界
- 本地服务与远程服务
- 错误处理和安全审计

MCP 解决的是标准化连接问题，但不会自动解决业务流程、权限设计和工具可靠性。

完整的协议架构、版本、传输和安全边界见 [MCP 运行机制：架构、协议、传输、安全与 Tool Calling 边界](../05-工具调用与MCP/MCP运行机制-架构协议传输安全与ToolCalling边界.md)。

## 8. Planner：把复杂目标拆成可执行步骤

Planner 负责把复杂任务拆解成步骤，并根据执行结果决定下一步。

以工程报价为例：

```text
下载图纸
  ↓
OCR
  ↓
识别与分类
  ↓
查询材料和成本
  ↓
计算报价
  ↓
生成 Excel
  ↓
人工审核
```

常见方法：

- ReAct
- Plan-and-Execute
- 状态图与 Graph
- 受控 Workflow
- Tree of Thoughts（适合部分探索型问题）

学习 Planner 时应关注失败恢复、循环终止、上下文膨胀和成本控制，而不只是任务拆解。

## 9. Workflow：用确定流程约束执行

Workflow 强调预先定义的任务流程；Agent 强调根据上下文作出决策。

二者并非互斥。生产项目常采用：

```text
确定性 Workflow + 局部 Agent 决策
```

例如，报价流程中的“人工审核后才能下发”应由工作流强制保证；至于采用哪种检索策略，可以由 Agent 根据需求判断。

常见工具与框架：

- n8n
- Dify
- LangGraph
- Flowise

## 10. Multi-Agent：多个角色协作

Multi-Agent 把复杂任务分给不同角色，例如：

```text
协调 Agent
  ├── 报价 Agent
  ├── 采购 Agent
  ├── 审核 Agent
  └── 财务 Agent
```

它适合职责清晰、上下文可分离、确实需要并行或独立权限的场景。

不应为了“看起来先进”过早引入多 Agent。它会增加：

- 通信与协调成本
- 状态一致性问题
- 调试难度
- Token 和运行成本
- 权限与责任边界复杂度

应先把单 Agent 与工作流做稳定，再判断是否需要拆分。

系统方法见 [Multi-Agent 协作：角色编排、共享状态、故障治理与工程边界](../06-Agent规划与工作流/Multi-Agent协作-角色编排共享状态故障治理与工程边界.md)。

## 11. Evaluation：证明系统真的有效

Agent 上线后必须通过评测判断升级是否带来改善，避免“主观感觉更聪明”。

生产评测不能只看最终答案，还应覆盖事实证据、执行过程、工具调用、成本时延和安全可控性。详细方法见 [Agent 评测体系：事实、过程、工具、效率、安全与版本治理](../10-LLMOps与可观测性/Agent评测体系-事实过程工具效率安全与版本治理.md)。

常见指标：

- 任务完成率
- 答案或结构化结果准确率
- 工具调用成功率
- RAG 召回率、精确率和引用正确率
- 报价误差
- 延迟与 Token 成本
- 人工接管率
- 安全违规率

建议建立：

1. 固定回归数据集
2. 可重复的评测脚本
3. 上线前后的结果对比
4. 失败案例分类
5. 人工评审规则

## 12. Observability：定位线上失败原因

可观测性帮助回答：

- Agent 为什么失败？
- 失败发生在哪一步？
- 哪个模型、Prompt 或工具导致退化？
- 影响了哪些用户和任务？

基本组成：

- Logs：记录事件和错误
- Traces：串联一次任务的完整调用链
- Metrics：统计成功率、耗时、成本等指标
- Monitoring：持续监控系统状态
- Alerts：异常时主动告警

应给每次任务设置统一的请求 ID 或 Trace ID，以关联 LLM、RAG、MCP、OCR、数据库和工作流日志。

## 当前能力盘点

结合现有 AI 智能报价中台项目，可做如下判断：

| 技术 | 当前基础 | 下一步 |
|---|---|---|
| LLM | 已使用 | 补模型选型、成本和可靠性 |
| Prompt | 已实践 | 补版本管理和回归评测 |
| RAG | 已实践 | 深入召回、重排和评测 |
| Embedding | 已有概念 | 系统学习模型与距离度量 |
| Tool Calling | 已有白名单、调用预算和结构化工具合同 | 继续补写工具的审批、幂等和补偿 |
| MCP | 已完成真实 Tender Evidence MCP | 将 scoped token、资源隔离和鉴权预检沉淀为通用模式 |
| Workflow | 已有报价链路和持久化 Agent 状态机 | 补统一幂等合同与分层调度 |
| Planner | 已有 ReAct + LangGraph + Human-in-the-loop | 用真实失败样本优化路由和退出策略 |
| Memory | 有基础概念 | 实践写入、召回、更新和遗忘 |
| Multi-Agent | 尚未重点实践 | 放在单 Agent 稳定之后 |
| Evaluation | 已有 Prompt 回归、RAG 评测和政策校准数据集 | 积累真实金标并监控分布漂移 |
| Observability | 已有任务事件、安全执行 Trace 和运行图谱 | 贯通跨组件 Trace、Metrics 与告警 |

## 推荐学习顺序

### 训练规则：每节必须留下证据

不能只采用“阅读、划线、背诵”。每节至少完成：

```text
阅读
→ 关掉文档口述
→ 画图
→ 写最小代码和测试
→ 制造故障
→ 用日志、指标和 Trace 定位
→ 迁移到另一个业务场景
```

详细节奏和验收标准见 [从答案手册到能力训练体系：八周闭环训练计划](../12-面试与职业发展/从答案手册到能力训练体系-八周闭环训练计划.md)。

### 第一阶段：让 Agent 能可靠执行

1. Tool Calling
2. MCP
3. 权限、审批、重试和幂等

### 第二阶段：让复杂任务可控

4. Planner / ReAct / LangGraph
5. Workflow 状态管理与失败恢复
6. Human-in-the-loop

### 第三阶段：让系统可以稳定上线

7. Evaluation
8. Observability
9. 安全、成本和性能优化
10. Linux、Docker、Git、测试与 CI/CD
11. Kubernetes、灰度发布、SLO 与故障治理

### 第四阶段：扩展高级能力

12. Memory
13. 深入 Embedding 与 RAG 优化
14. Multi-Agent

## 与现有项目结合的实践建议

可以直接在 AI 智能报价中台中练习：

- Tool Calling：把查成本库、生成 Excel、推送报价封装为受控工具
- MCP：复盘现有只读 Tender Evidence MCP，并为未来写工具设计审批、幂等与补偿
- Planner：把报价任务建模为可追踪的状态图
- Evaluation：建立报价准确率、漏项率、工具成功率回归集
- Memory：保存用户偏好，但将报价事实与业务数据库分开
- Observability：贯通 FastAPI、n8n、Dify、RAG 和数据库的 Trace ID

项目练习后，还要把同一套能力迁移到知识助手、客服、手机助理、代码 Agent、合同审核和高并发 Agent 平台，避免只会复述报价中台。详见 [Agent 跨场景迁移训练](../11-项目实战/Agent跨场景迁移训练-六类系统设计与差异化取舍.md)。

## 一句话结论

生产级 Agent 与 Demo 的主要区别，不在于是否调用了更强的模型，而在于它是否具备可靠的工具执行、流程控制、评测体系、可观测性和安全边界。
