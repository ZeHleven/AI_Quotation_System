# 高并发与性能优化：指标、压测、容量与瓶颈定位

> 配套实战：[练习 08：高并发压测、容量估算与性能瓶颈定位实战](./练习记录/08-高并发压测容量估算与性能瓶颈定位实战.md)

## 核心结论

高并发不是“使用 Redis、异步和消息队列”三个词，而是：

> 在明确的负载、资源和质量目标下，让系统稳定处理请求，并能在接近容量时背压而不是雪崩。

性能优化顺序：

```text
定义 SLO 和负载
→ 建立基线
→ 压测并观测
→ 找最大瓶颈
→ 一次改变一个因素
→ 回归质量与正确性
→ 更新容量模型
```

优化没有测量的系统，容易把成本从机器转移到数据库、模型或人工。

---

## 1. 基础指标

### 吞吐与并发

| 指标 | 含义 |
|---|---|
| QPS/RPS | 每秒处理请求数 |
| TPS | 每秒完成事务数 |
| Concurrency | 同时处于处理中的请求/任务数 |
| Throughput | 单位时间处理的数据或任务量 |

近似 Little 定律：

```text
系统内平均并发 L = 到达率 λ × 平均停留时间 W
```

例如 10 个请求/秒、平均耗时 5 秒，系统内约有 50 个并发请求。

降低延迟不仅改善体验，也减少相同 QPS 下的资源占用。

### 延迟分位数

平均值会掩盖长尾：

- P50：典型体验；
- P95：95% 请求不超过该值；
- P99：长尾与故障放大；
- Max：只作诊断，容易受极端值影响。

AI 调用必须同时看：

```text
排队时间
首 Token 延迟
生成时间
总耗时
```

### 错误与饱和

```text
成功率 / 错误率
超时率
限流率
降级率
CPU / 内存
连接池使用率
队列长度与最老年龄
线程/进程/GPU 利用率
```

## 2. 先定义 SLO

示例，不代表项目当前正式目标：

```text
任务创建 API：
  可用性 ≥ 99.9%
  P95 < 300ms

报价任务：
  95% 在 3 分钟内生成预审
  任务静默丢失 = 0

报价完整性：
  确认行覆盖率 = 100%
  未补价占位不得下发
```

性能不能脱离质量。把 RAG、完整性校验或人工 Gate 删除，虽然更快，但不是合法优化。

---

## 3. 建立端到端耗时模型

```text
总耗时 =
  网关排队
  + API 处理
  + 数据库
  + 队列等待
  + Worker 排队
  + 文件解析
  + RAG 检索
  + 模型调用
  + 工具调用
  + 结果校验和持久化
```

每段记录：

```text
start/end
duration_ms
status
retry_count
input_size
output_size
dependency
trace_id
```

如果总耗时 180 秒，其中模型 160 秒，优化 FastAPI JSON 序列化几毫秒没有实际价值。

## 4. CPU 密集与 IO 密集

### IO 密集

等待：

- HTTP；
- MySQL；
- Redis；
- 对象存储；
- 模型和 RAG。

适合：

- `asyncio`；
- 异步客户端；
- 有界线程；
- 连接池；
- 并发信号量。

### CPU 密集

计算：

- PDF/OCR 后处理；
- 图像转换；
- Embedding；
- 压缩；
- 大量 JSON/Excel 计算。

适合：

- 多进程；
- 原生库；
- 批处理；
- 独立 CPU/GPU Worker。

Python 的 `async` 不能让 CPU 密集代码自动并行，也不能把同步阻塞库放进事件循环后期待高吞吐。

---

## 5. 并发控制

### 并发不是越大越好

增加并发可能遇到：

- MySQL 连接池耗尽；
- Redis 连接积压；
- 外部模型 429；
- 内存上升；
- 上下文切换增加；
- P99 变差；
- 队列重试放大。

用信号量限制外部依赖：

```python
model_semaphore = asyncio.Semaphore(8)

async def call_model(payload):
    async with model_semaphore:
        return await model_client.call(payload)
```

并发值由压测、Provider 额度和下游容量决定。

### 连接池

必须同时考虑：

```text
应用实例数
× 每实例 Worker/线程
× 每实例最大连接
≤ 数据库/Redis/HTTP 下游容量
```

池太小会排队，池太大会把下游压垮。

## 6. 常见优化手段与适用边界

### 缓存

适合重复读、重建成本高、允许短暂陈旧的数据。

必须衡量：

- 命中率；
- 一致性；
- 内存；
- 回源峰值；
- 权限与版本隔离。

### 批处理

将多次调用合并：

- 批量 SQL；
- 批量 Embedding；
- 多行模型请求；
- 批量对象存储元数据。

批次过大则增加单次延迟、内存和失败重做成本。

### 异步

减少线程等待并改善用户响应，但不会缩短外部模型本身的执行时间。

### 队列

削峰和调度，不会增加下游真实吞吐。持续积压说明容量或入口控制有问题。

### 数据库索引

减少扫描，但增加写入和存储成本。先看执行计划。

### 模型路由

简单任务使用轻量模型可降低延迟和成本，但必须用评测集验证质量，不能只看单次速度。

## 7. 压测设计

### 先定义负载模型

- 用户数量；
- 请求比例；
- 文件大小分布；
- 任务行数；
- 冷/热缓存；
- 模型成功、超时和 429 比例；
- 突发和持续流量；
- 测试时长。

不要只压 `/health`，它不能代表报价链路。

### 三种测试

| 类型 | 目的 |
|---|---|
| Load Test | 验证预期负载 |
| Stress Test | 找到容量拐点和失败方式 |
| Soak Test | 长时间运行发现泄漏、积压和连接问题 |

还可进行：

- Spike Test：瞬时流量；
- Failure Test：依赖故障；
- Recovery Test：恢复后是否正常消化积压。

### 隔离外部成本

压测 AI 链路时可分层：

1. Mock 外部模型，测 API、数据库和队列；
2. 使用受控沙箱，测真实外部依赖；
3. 小规模端到端，测最终体验和成本。

否则压测可能耗尽额度或违反 Provider 限制。

## 8. 瓶颈定位

### USE 方法

对资源观察：

- Utilization：利用率；
- Saturation：排队/饱和；
- Errors：错误。

### RED 方法

对服务观察：

- Rate：请求速率；
- Errors：错误；
- Duration：延迟。

### 常见症状

| 症状 | 可能原因 | 先查什么 |
|---|---|---|
| API P95 高、CPU 低 | 下游等待 | Trace、HTTP、连接池 |
| MySQL CPU 高 | 扫描、排序、并发查询 | 慢查询、执行计划 |
| Worker 全忙 | 长模型调用或任务过大 | 阶段耗时、任务类型 |
| 队列增长 | 消费能力低于生产 | Lag、最老消息、下游限额 |
| Redis 延迟高 | 热点、大 Key、阻塞命令 | 慢日志、内存、命令分布 |
| P99 急剧上升 | 饱和、GC、重试、锁等待 | 资源和长尾 Trace |
| 429 增加 | Provider 配额或限流 | 模型维度并发与 Token |

## 9. Profiling

### 应用

- CPU Profiler；
- 火焰图；
- 内存快照；
- 事件循环阻塞检测；
- GC 统计。

### 数据库

- 慢查询日志；
- `EXPLAIN ANALYZE`；
- 锁等待和死锁；
- 连接池等待；
- Buffer Pool 命中。

### 外部依赖

- DNS/连接/TLS；
- 首字节；
- 读取；
- 重试；
- 响应大小。

Profiling 应在可复现负载下进行，避免只看一次本地请求。

## 10. 容量估算

示例：

```text
峰值 120 个报价/小时
平均每个报价占用模型 60 秒
模型并发需求约 120 × 60 / 3600 = 2
```

再加入：

- P95 耗时；
- 突发系数；
- 重试；
- 安全余量；
- 不同模型/任务池；
- Provider 额度。

队列等待近似：

```text
等待时间 ≈ 队列中工作量 / 有效处理速率
```

容量报告必须写明假设，不能把估算当实测。

### 已有指标基础

- `quote_jobs.duration_ms`；
- `result_item_count`；
- `failure_stage`；
- `trace_id`；
- `quote_job_events`；
- 报价速度、响应速度和执行速度看板；
- Redis/Celery/RAG/N8N 等健康状态；
- 大清单分批、补报和完整性摘要。

### 建议的端到端性能拆分

```text
queue_wait_ms
file_parse_ms
cost_match_ms
rag_ms
model_ms
n8n_ms
preview_build_ms
db_persist_ms
total_duration_ms
```

同时记录：

- 文件大小/页数；
- 确认行数；
- 批次数；
- 模型和 Prompt 版本；
- RAG Top-K；
- 重试次数；
- 是否降级。

### 优化优先级

1. 消除无效等待、重复调用和无意义重试；
2. 降低大上下文和重复检索；
3. 对 CPU/IO 任务拆池；
4. 批量数据库和 Embedding；
5. 验证索引与列表查询；
6. 通过模型路由控制成本和延迟；
7. 最后才做低收益微优化。

## 12. 面试回答

### 怎样定位接口慢？

> 我先定义慢的是平均值还是 P95/P99，再用 Trace 拆分网关、数据库、队列、模型、RAG 和结果处理耗时。数据库看慢查询和执行计划，Worker 看排队与阶段耗时，外部调用看连接、首字节、重试和限流。找到占比最大的瓶颈后一次修改一个因素，并在相同负载下比较延迟、吞吐、错误率和成本。

### 怎样提升 AI 系统并发？

> 先区分 IO、CPU 和 GPU 工作负载。HTTP 和模型等待使用异步 IO 与有界并发；解析和 Embedding 使用独立进程或 GPU Worker；长短任务拆队列；数据库和外部模型设置连接池、信号量和背压。队列用于削峰，但持续积压需要增加有效处理能力或限制入口。最终用 P95、错误率、队列年龄和单任务成本验证。

### 缓存能解决所有性能问题吗？

> 不能。缓存只适合可重建、重复读取且允许一定陈旧的数据，还会引入一致性、热点和雪崩问题。如果瓶颈在模型推理、队列或慢写事务，缓存可能没有收益。我会先用 Trace 确认重复读占比，再评估 Key 隔离、命中率和失效策略。

## 13. 动手练习

### 压测报告

至少包含：

```text
环境和版本
数据规模
负载模型
并发和持续时间
P50/P95/P99
吞吐
错误/超时/限流
CPU/内存/连接池
队列长度和最老年龄
外部模型成本
瓶颈证据
优化前后对比
已知边界
```

### 故障场景

- MySQL 变慢；
- Redis 不可用；
- Worker 数量减半；
- 模型返回 429；
- RAG 超时；
- 200 个大清单同时进入。

验证系统是否背压、降级和恢复，而不是只看正常成功。
