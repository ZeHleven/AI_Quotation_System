# 生产级 Agent 系统架构：从 Gateway 到部署运维

## 核心结论

生产级 Agent 不是“一个模型加一段 Prompt”，而是：

```text
模型
+ Agent Runtime
+ 工作流
+ 工具
+ 数据与知识
+ 异步任务
+ 权限与审计
+ 评测与可观测性
+ 部署运维
```

可以把整个系统记成三大核心：

| 核心 | 组成 | 主要职责 |
|---|---|---|
| 控制核心 | Agent Runtime | 理解、规划、调度和决策 |
| 执行核心 | Tools + MCP | 连接并操作外部系统 |
| 生产保障 | Evaluation + Observability | 评测、监控、追踪和告警 |

## 七层生产架构

```text
┌───────────────────────────────────────────────┐
│ 1. 用户与接入层                                │
│ Web / App / 企业微信 / 钉钉 / API / 人工审核台  │
└──────────────────────┬────────────────────────┘
                       ▼
┌───────────────────────────────────────────────┐
│ 2. 接口与安全层                                │
│ API Gateway / FastAPI / 鉴权 / 限流 / RBAC      │
└──────────────────────┬────────────────────────┘
                       ▼
┌───────────────────────────────────────────────┐
│ 3. Agent 核心层                                │
│ Runtime / LLM / Prompt / Planner / Workflow    │
└──────────────────────┬────────────────────────┘
                       ▼
┌───────────────────────────────────────────────┐
│ 4. 工具与协议层                                │
│ MCP / HTTP API / Python / SQL / Shell          │
└──────────────────────┬────────────────────────┘
                       ▼
┌───────────────────────────────────────────────┐
│ 5. 异步任务与基础设施                           │
│ Queue / Redis / Worker / Scheduler / Retry      │
└──────────────────────┬────────────────────────┘
                       ▼
┌───────────────────────────────────────────────┐
│ 6. 数据与知识层                                │
│ 业务库 / 向量库 / 对象存储 / Memory             │
└──────────────────────┬────────────────────────┘
                       ▼
┌───────────────────────────────────────────────┐
│ 7. 评测、监控与部署                             │
│ Evaluation / Logs / Traces / Metrics / CI/CD   │
└───────────────────────────────────────────────┘
```

这些层并非只能从上到下单向运行。工具结果会返回 Runtime，Runtime 可能继续规划和调用；日志、追踪、权限及评测则横跨整个调用链。

## 1. 用户与接入层

接入层是任务进入 Agent 系统的入口。

常见入口：

- Web 或 App
- 企业微信、钉钉、Slack、Teams
- 对外或内部 API
- 管理后台
- 人工审核台

这一层除了收集用户输入，还可能负责：

- 文件上传
- 流式进度展示
- 人工确认与审批
- 失败重试入口
- 历史任务查看

对于高风险 Agent，人工审核台不是附加功能，而是系统控制边界的一部分。

## 2. 接口与安全层

这一层把外部请求转换为系统可以安全处理的内部任务。

### API Gateway

主要职责：

- 请求路由
- 鉴权
- 限流
- 请求大小限制
- 超时控制
- API 版本管理

### 应用服务

可使用 FastAPI、Spring Boot 等框架处理：

- 参数解析和 Schema 校验
- 用户身份识别
- 同步或异步任务创建
- SSE/WebSocket 进度推送
- 统一响应和错误处理

### 权限与审计

生产系统应明确：

- 谁能访问哪些数据
- 谁能调用哪些工具
- 哪些动作必须经过审批
- 每次操作由谁发起、何时发生、结果如何

常见机制包括 RBAC、数据隔离、操作日志和审计事件。

## 3. Agent 核心层

### Agent Runtime

Runtime 是 Agent 的运行容器和状态控制中心，负责：

- 构建模型上下文
- 调用 LLM
- 解析结构化响应
- 执行工具调用
- 保存中间状态
- 控制循环次数和终止条件
- 处理超时、重试和人工暂停

### LLM

负责意图理解、推理、生成与工具选择，但不直接承担确定性业务执行。

### Prompt

描述角色、目标、上下文、约束、工具规则和输出协议。

### Planner

根据目标和当前状态拆解任务，并决定下一步行动。

### Workflow

控制确定性的业务阶段、分支和状态迁移。

推荐的职责划分：

```text
Planner：决定“下一步做什么”
Workflow：限制“允许按什么路径做”
业务代码：保证“计算和规则一定正确”
```

## 4. 工具与协议层

工具层负责真正读取数据或改变外部世界。

常见工具：

- MCP Server
- HTTP API
- Python
- SQL
- Shell
- 文件解析、OCR、Excel
- ERP、CRM 和审批系统

### MCP 的位置

MCP 是一种标准化工具与资源接入方式。它与 HTTP API、Python 函数等处于同一工具接入层，而不是 Agent 的全部。

工具执行必须考虑：

- 输入参数校验
- 用户权限
- 超时
- 重试
- 幂等
- 审批
- 结果大小限制
- 调用审计

## 5. 异步任务与基础设施

耗时较长或不适合阻塞 HTTP 请求的任务，应进入异步处理链路。

### Task Queue

常见实现：

- Celery
- RabbitMQ
- Kafka
- 其他云消息队列

适合处理：

- OCR
- 大文件解析
- 批量报价
- 长时间模型推理
- 文档生成
- RAG 索引更新

### Redis

常见用途：

- 缓存
- 分布式锁
- Celery Broker 或结果状态
- 会话状态
- 幂等键
- 短期 Memory

Redis 不应成为所有业务事实的唯一持久化来源；关键业务记录通常仍应写入关系数据库。

### Worker

Worker 执行后台任务，如：

- OCR/VLM
- 文件解析
- Python 计算
- 批量数据处理
- 远程 API 调用

Worker 需要具备：

- 心跳
- 超时
- 有限重试
- 死信或失败记录
- 幂等执行
- 优雅停止

### Scheduler

负责：

- 定时任务
- 延迟重试
- 超时扫描
- 补偿任务
- 周期性评测

## 6. 数据与知识层

### 业务数据库

MySQL 或 PostgreSQL 用于保存：

- 用户和权限
- 任务状态
- 业务记录
- 审核结果
- 审计事件

### 向量数据库

Milvus、pgvector 等用于：

- 文档向量检索
- 语义相似搜索
- RAG 召回

### 对象存储

MinIO、OSS、S3 等用于保存：

- 用户上传的原始文件
- OCR 中间产物
- 生成的 Excel、Word、PDF
- 大型评测数据

数据库中通常只保存文件标识、元数据、权限和状态，不直接塞入所有大文件内容。

### Memory

Memory 可保存：

- 会话上下文
- 用户长期偏好
- 任务中间状态
- 经确认的长期事实

Memory、企业知识和业务事实应分开治理，避免权限、时效和可信度混乱。

## 7. 评测、监控与部署

### Evaluation

评测用于回答“系统是否真的变好了”。

常见指标：

- 任务完成率
- 结果准确率
- 工具选择正确率
- 工具执行成功率
- RAG 召回与引用正确率
- 人工接管率
- 延迟
- Token 与基础设施成本

应建立固定回归集，在修改模型、Prompt、工具或知识库后重复执行。

### Observability

可观测性用于回答“任务为什么成功或失败”。

需要记录：

- Logs：事件与错误
- Traces：完整调用链
- Metrics：成功率、延迟、Token、成本
- Alerts：异常和阈值告警

建议所有组件透传同一个 `trace_id` 或 `request_id`。

### Deployment

常见基础设施：

- Docker
- Kubernetes
- Caddy / Nginx
- CI/CD
- GitHub Actions

部署设计还包括：

- 环境变量和密钥管理
- 数据迁移
- 健康检查
- 灰度发布
- 回滚
- 备份与恢复
- 容量和并发规划

## 一次任务的十步流程

```text
1. 接收任务
   用户提交问题、文件或业务指令
        ↓
2. 身份与权限校验
   确认用户能访问哪些数据和工具
        ↓
3. 构建上下文
   组合 Prompt、历史记录、业务数据与知识库
        ↓
4. LLM 理解与规划
   识别目标、拆解步骤、选择工具
        ↓
5. 执行工具
   调用 MCP、API、数据库、Python 或外部系统
        ↓
6. 异步处理
   耗时任务进入队列，由 Worker 执行
        ↓
7. 结果校验
   规则检查、模型复核、人工审核或重试
        ↓
8. 生成最终结果
   输出文字、Excel、Word、审批结果或系统动作
        ↓
9. 记录与评测
   保存日志、Trace、成本、耗时和成功率
        ↓
10. 持续优化
   根据失败样本更新 Prompt、规则、知识库和流程
```

核心闭环：

```text
理解任务
  → 选择工具
  → 执行
  → 校验
  → 记录
  → 根据评测持续优化
```

## 当前 AI 智能报价中台的架构映射

以下映射结合当前项目现状整理：

| 生产架构层 | 当前项目组件 |
|---|---|
| 用户与接入层 | Vue 管理台、旧报价工作台、登录门户、管理后台 |
| 接口与安全层 | FastAPI 主网关、JWT、RBAC、统一鉴权依赖、管理员权限 |
| Agent 核心层 | 报价流程编排、Prompt、Dify + DeepSeek、GLM-4V |
| 工具与协议层 | n8n Webhook、RAG 服务、Excel 解析、成本计算、数据库接口 |
| 异步任务层 | Celery Broker/Worker、异步 `quote_jobs`、任务事件与状态 |
| 业务数据库 | 用户、报价任务、成本库、项目进度、审计记录 |
| RAG 与向量库 | RAG 服务、Milvus、Embedding、BM25 + RRF 混合检索 |
| 人工校验 | 报价预审、打回、确认推送、管理员运营复核 |
| Evaluation | Prompt 回归、RAG 评测、成本质量报告、业务验收用例 |
| Observability | 健康检查、任务事件、运行日志、看板指标和告警 |
| 部署 | Windows FastAPI/Vue + CentOS Docker Compose 服务 |

### 已具备的生产能力

- API 网关与统一鉴权
- 同步和异步报价链路
- Celery Worker
- 业务数据库与 Milvus
- 人工预审与高风险阻断
- 报价证据链和审计
- Prompt 回归与部分质量评测
- 健康检查与运营看板

### 后续值得继续补强

- 跨 FastAPI、n8n、Dify、RAG、Celery 的统一 Trace ID
- LLM、工具、检索和业务规则的分层指标
- Agent 回归数据集的持续维护
- 故障注入与自动恢复演练
- 正式生产 Runbook、灰度发布和回滚演练
- 密钥轮换、备份恢复和容量规划

## 学习时应重点记住

1. LLM 只是推理组件，Runtime 才负责运行闭环。
2. 工具调用必须受权限、Schema、超时和审计约束。
3. 耗时任务要进入队列，HTTP 请求不应无限等待。
4. 业务事实写入数据库，文件进入对象存储，语义知识进入检索系统。
5. 关键业务规则不能只写在 Prompt 里。
6. 没有评测，就无法证明一次升级是进步还是退化。
7. 没有 Trace，就很难定位跨多个组件的真实故障。
