# 生产级 RAG 工程闭环：数据治理、检索、生成、评测与反馈

## 核心结论

RAG 不是“文档切片 + Embedding + 向量数据库”，而是一个持续运行的工程闭环：

```text
数据治理
→ 文档摄取与索引
→ 查询理解
→ 多路召回与重排
→ 上下文组装
→ 基于证据生成
→ 分层评测
→ 线上反馈回流
→ 数据和策略迭代
```

向量数据库只是其中一个组件。生产系统还必须解决版本、权限、数据新鲜度、检索噪声、答案忠实度、评测和持续迭代。

---

## 1. 离线索引与在线问答

### 离线侧

```text
数据源接入
→ 清洗、去重、权限与版本处理
→ 文档解析和结构恢复
→ Chunk 与元数据生成
→ Embedding
→ 向量、关键词和结构化索引
```

### 在线侧

```text
用户问题
→ 权限校验
→ Query 分类、改写或扩展
→ 多路召回
→ 融合、去重和 Rerank
→ 上下文预算与证据组装
→ 模型生成或拒答
→ 引用、日志和反馈
```

离线侧决定知识是否干净、完整和可追溯；在线侧决定能否把正确证据稳定交给模型。

---

## 2. 数据治理

许多 RAG 项目效果差，根因不是模型不够强，而是知识源本身失控：

- 新旧版本同时存在
- 重复文档反复入库
- 已删除或失效内容仍可召回
- 权限没有同步到索引
- 缺少文档生效时间和适用范围
- 解析失败却继续入库
- 文件更新后只增加新索引，没有清理旧索引

### 文档状态

建议为知识对象建立明确生命周期：

```text
draft
→ validating
→ active
→ superseded / archived
→ deleted
```

只有经过校验且当前生效的内容才参与正式检索。

### 最小元数据

```json
{
  "document_id": "contract_001",
  "document_version": "v3",
  "chunk_id": "contract_001_v3_p12_c04",
  "title": "采购合同",
  "section_path": ["第五章", "违约责任"],
  "page": 12,
  "source_system": "contract_center",
  "business_line": "procurement",
  "effective_from": "2026-07-01",
  "status": "active",
  "acl": ["role:legal", "project:p001"],
  "parser_version": "pdf_parser_v2",
  "indexed_at": "2026-07-28T10:00:00+08:00"
}
```

元数据既服务检索过滤，也服务权限、引用、更新和故障定位。

### 更新与删除

需要明确：

- 文档的稳定 ID 和版本 ID
- 增量更新还是全量重建
- 旧 Chunk 如何失效
- 删除请求如何传播到所有索引
- Embedding 或切片策略变化后如何重建
- 索引构建失败如何回滚

不能只写入新向量而不管理旧数据。

---

## 3. 文档摄取决定质量上限

不同数据源需要不同解析路线：

- Word：标题、段落、表格、图片和嵌入对象
- PDF：原生文本、扫描、混合、表格和多栏版式
- 网页：正文、导航、动态内容和更新时间
- 代码：文件、符号、调用关系和版本
- 结构化数据：优先使用 SQL、API 或业务查询

切片应优先服从标题、段落、表格和业务信息单元，不应只按固定字数截断。

详见：[RAG 文档摄取：Word 与 PDF 的解析、切片和检索](./RAG文档摄取-Word与PDF解析切片和检索.md)。

## 4. 检索质量

单一向量检索无法稳定覆盖全部查询。

| 检索方式 | 擅长 |
|---|---|
| 向量检索 | 同义表达和语义近似 |
| BM25/全文检索 | 编号、术语、错误码、型号 |
| 元数据过滤 | 时间、版本、权限、项目、状态 |
| 结构化查询 | 金额、数量、聚合和精确业务字段 |

推荐链路：

```text
多路召回
→ 权限与版本过滤
→ 融合去重
→ Reranker
→ 动态筛选
→ 上下文组装
```

需要管理：

- 候选集大小
- Top-K
- 分数阈值
- 结果去重
- 来源多样性
- 上下文预算
- 延迟和成本

详见：[RAG 检索策略：混合召回、融合、Rerank 与动态 Top-K](./RAG检索策略-混合召回融合重排与动态TopK.md)。

---

## 5. 上下文组装

不能把全部召回结果直接塞给模型。

组装前应处理：

- 重复或高度相似片段
- 已过期或冲突版本
- 与问题无关的邻接内容
- 相同来源占满上下文
- 片段缺少标题、单位或适用条件
- 超出 Token 预算

建议上下文条目保留：

```json
{
  "evidence_id": "ev_001",
  "text": "...",
  "document": "采购合同_v3.pdf",
  "section": "第五章 / 违约责任",
  "page": 12,
  "retrieval_channel": ["bm25", "vector"],
  "rerank_score": 0.86
}
```

模型看到的应是少量、完整、可区分来源的证据，而不是未经整理的候选堆积。

---

## 6. 基于证据生成

检索正确不代表生成一定正确。模型仍可能：

- 误解证据
- 忽略限制条件
- 把多个版本混合
- 补充证据中不存在的内容
- 引用了片段但结论不受其支持

生成约束：

- 只能基于给定证据回答
- 关键结论必须附带引用
- 区分事实、推断和建议
- 证据不足时明确拒答或请求补充信息
- 发现冲突版本时停止给出唯一结论
- 高风险业务保留人工确认

RAG 只能降低幻觉风险，不能从机制上消除幻觉。

---

## 7. 分层评测

不能只评价最终答案“读起来是否自然”。

### 数据与解析

- 文档覆盖率
- 解析成功率
- 重复率
- 版本和权限正确率
- 表格、图片和阅读顺序准确率

### 召回

- Recall@K
- Precision@K
- 关键编号命中率
- 正确页面或章节命中率
- 无关候选比例

### 融合与重排

- MRR
- NDCG
- 正确证据进入最终 Top-K 的比例
- Rerank 前后提升

### 生成

- 答案正确性
- Faithfulness
- 引用完整性
- 引用支持度
- 拒答准确率

### 端到端

- 任务完成率
- 人工接受率
- 人工修改率
- P95 延迟
- 单次查询成本

### 黄金测试集的题型覆盖

测试集不应只有高频、答案明确的简单问题，还应覆盖：

- 高频事实题
- 边界条件与例外条款
- 同义和口语化表达
- 跨文档比较或汇总
- 编号、型号等精确查询
- 知识库中没有答案、应该拒答的问题

### 错误归因

```text
知识未收录
解析错误
Chunk 不完整
召回失败
过滤错误
融合或重排错误
上下文组装错误
模型误解证据
答案无依据
引用错误
```

只有分层归因，才能知道应该修改数据、解析器、检索、Prompt 还是模型。

---

## 8. 线上反馈闭环

需要回流的信号：

- 点赞、点踩
- 用户追问
- 无答案问题
- 人工纠错
- 人工最终采用的答案
- 被频繁引用但效果差的文档
- 搜索无结果和低分查询
- 线上错误及投诉

处理流程：

```text
收集反馈
→ 关联 Query、证据和版本
→ 分类根因
→ 修复数据或策略
→ 加入黄金测试集
→ 回归验证
→ 灰度发布
```

反馈不应直接自动改写正式知识。应经过审核和版本管理。

---

## 9. 可观测性与发布

每次 RAG 请求至少记录：

- Query 和改写结果的安全摘要
- 权限与元数据过滤条件
- 各路召回候选 ID
- 融合和 Rerank 结果
- 最终上下文 Evidence ID
- 模型和 Prompt 版本
- 引用
- 延迟、Token、成本和错误
- 用户反馈

敏感正文可保存受控引用，不必全部写入普通日志。

模型、Embedding、切片、解析器和检索参数都应版本化，并在固定测试集上回归后再发布。

## 10. 面试回答模板

### 90 秒版本

```text
我会把生产级 RAG 拆成离线索引和在线问答两条链路。

离线侧先做数据治理，处理文档清洗、去重、版本、权限和状态，
再按数据类型解析结构，生成带来源和权限的 Chunk，
最后建立向量、关键词和必要的结构化索引。

在线侧先做权限校验和 Query 理解，
通过向量、BM25 和元数据过滤多路召回，
融合后使用 Reranker 精排，再按 Token 预算组装证据。

生成阶段要求模型只根据证据回答，
关键结论带来源，证据不足时拒答。

评测会拆开看解析、召回、重排、生成和引用，
线上再把用户纠错、无答案问题和 Bad Case
回流到知识治理与黄金测试集。

向量数据库只是组件，真正难点是这套链路能否
长期运行、定位问题、控制权限并持续迭代。
```

### 面试加分点

- 能区分检索错误和生成错误
- 能说明删除、更新和权限同步
- 能给出实际评测指标
- 能讲一次 Bad Case 如何进入回归集
- 能解释为什么不把结构化业务数据全部向量化

## 11. 面向当前报价中台的落地映射

当前系统已经具备：

- `cost_items.active` 作为正式成本数据源
- Milvus + BM25 + RRF 混合检索
- 成本库 RAG 同步记录
- 报价成本证据链与人工预审
- Prompt 回归案例和运行记录
- 用户反馈、报价修正和 RAG Trace

下一阶段更值得补强：

1. 统一文档、Chunk、Embedding、解析器和索引版本
2. 建立正式 RAG 黄金查询集
3. 分别统计召回、融合、重排和最终答案质量
4. 明确索引更新、删除和回滚流程
5. 贯通 Query、候选、证据与人工修改的 Trace
6. 使用真实试运行数据验证阈值和 Top-K

结构化成本库应继续以 MySQL 业务查询为主，向量检索负责名称变体、语义匹配和知识文本，不要让向量库替代主数据治理。

## 一句话总结

生产级 RAG 的核心不是“把知识放进向量库”，而是让数据、检索、生成、评测和反馈形成可追溯、可回归、可持续运营的闭环。
