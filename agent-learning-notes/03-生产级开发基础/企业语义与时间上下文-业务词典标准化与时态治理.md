# 企业语义与时间上下文：业务词典、标准化与时态治理

## 核心结论

企业 Agent 要正确理解一句话，至少要回答两个问题：

```text
用户说的业务对象究竟是什么？
这句话在什么时间边界下成立？
```

因此，生产级 Context 不能只提供聊天记录和检索片段，还应显式提供：

```text
企业语义 = 标准对象 + 别名 + 定义 + 口径 + 作用域 + 版本
时间上下文 = 当前时刻 + 业务时区 + 业务日期 + 日历规则 + 数据有效时间
```

业务词典解决“同词不同义、同义不同词”；可信时间上下文解决“今天、最近、当前、最新、截止”等表达随运行时刻变化的问题。二者缺一，模型即使语言通顺，也可能在业务对象或时间边界上稳定地产生错误。

> 资料说明：本笔记依据视频公开简介和章节摘要整理，并结合当前 AI 智能报价中台代码核对扩展，不是逐字字幕。

---

## 1. 为什么不能全靠模型自己理解

通用模型学到的是公共语义，而企业系统需要的是本组织当前生效的业务口径。

例如：

| 用户表达 | 可能的标准对象 | 仅靠语言相似度的风险 |
|---|---|---|
| 平米、平方米、m2 | 单位 `㎡` | 单位无法稳定聚合或换算 |
| 工程量、数量、预估数量 | 字段 `quantity` | 把多个数字选错为工程量 |
| 项目特征、规格型号、做法 | 字段 `spec` | 与项目名称、备注混淆 |
| 甲供、甲限、指定品牌 | 不同报价约束 | 风险责任和价格口径不同 |
| 最近一周 | 一个绝对日期区间 | 受当前日期、时区和周定义影响 |
| 最新价格 | 某个有效时点的价格版本 | 误把最后写入的数据当作当前有效数据 |

Embedding 和 LLM 可以帮助召回候选，却不能替代企业对“哪个对象才是标准答案”的治理。

```text
语义相似 ≠ 同一业务对象
名称相同 ≠ 计算口径相同
最近写入 ≠ 当前有效
模型知道日期 ≠ 系统时间边界一致
```

## 2. 业务词典不是简单的同义词表

一个可治理的词条至少应包含：

```json
{
  "term_id": "quote.unit.area",
  "canonical_name": "平方米",
  "canonical_value": "㎡",
  "object_type": "unit",
  "aliases": ["平米", "m2", "M2"],
  "definition": "面积计量单位",
  "scope": {
    "tenant_id": "enterprise_001",
    "department": "budget",
    "scenario": "quotation"
  },
  "constraints": {
    "dimension": "area",
    "allowed_fields": ["unit"]
  },
  "owner": "预算部",
  "source": "企业报价字段规范",
  "status": "active",
  "version": "v3",
  "effective_from": "2026-07-01T00:00:00+08:00",
  "effective_to": null,
  "updated_at": "2026-07-20T09:30:00+08:00"
}
```

视频强调的核心要素包括术语名称、别名、业务定义、适用范围、计算口径、负责人和更新时间。工程上还应补齐：

- 稳定的标准 ID，而不是只保存显示名称；
- 租户、部门、场景和用户角色等作用域；
- 生效时间、失效时间和版本；
- 数据来源与负责人；
- 单位、字段类型和允许值等约束；
- 冲突项、禁配项和人工确认策略；
- 草稿、已启用、已归档等生命周期状态。

### 业务词典、主数据、知识库的边界

| 能力 | 主要回答 |
|---|---|
| 业务词典 | 一个词在当前业务中是什么意思 |
| 主数据 | 企业认可的客户、材料、项目等对象是什么 |
| 本体/知识图谱 | 对象之间有什么类型和关系 |
| RAG 知识库 | 哪些文档片段可以支持当前问题 |
| Prompt | 本次模型应遵守什么任务规则 |

业务词典可以连接这些系统，但不能被某一段 Prompt 或一次向量检索完全替代。

## 3. 从自然语言到标准对象的解析链路

推荐把解析过程做成可观察的流水线：

```text
原始表达
  → 字符与格式归一化
  → 精确标准词命中
  → 别名命中
  → 作用域和上下文消歧
  → 候选召回与排序
  → 约束校验
  → 置信度分流
  → 标准对象或人工确认
```

结果不应只返回一个标准值，还要保留解释：

```json
{
  "raw_value": "平米",
  "canonical_id": "quote.unit.area",
  "canonical_value": "㎡",
  "match_type": "alias_exact",
  "dictionary_version": "v3",
  "scope": "enterprise_001/budget/quotation",
  "confidence": 0.99,
  "alternatives": [],
  "requires_confirmation": false
}
```

关键原则：

1. **保留原文**：标准化字段不能覆盖原始输入。
2. **返回标准 ID**：显示名称以后可以改，ID 应保持稳定。
3. **记录匹配原因**：精确、别名、规则、向量或人工选择要可区分。
4. **先规则后模型**：确定性映射先处理，LLM 只复核不确定项。
5. **低置信转人工**：不要强行把每个表达映射成一个对象。
6. **人工修正可回流**：但先成为候选规则，审核后才能启用。

### 冲突词如何处理

同一个词可能在不同团队中含义不同。正确处理顺序是：

```text
租户
→ 部门或角色
→ 业务场景
→ 当前数据源
→ 对话中已确认对象
→ 候选排序
→ 无法唯一确定时询问用户
```

不能只按“最相似”选择。词典需要允许同名词条存在，并通过作用域和上下文决定本次含义。

## 4. 标准化不等于静默改写

企业系统常同时需要三层数据：

| 层级 | 示例 | 用途 |
|---|---|---|
| 原始层 | `M2`、`项目特征描述` | 审计、回看和重新解析 |
| 标准层 | `㎡`、`spec` | 计算、检索、聚合和接口交换 |
| 业务对象层 | `quote_line.unit.area` | 权限、规则、责任人和流程联动 |

错误做法：

```text
用户输入 → 模型改写 → 只保存改写结果
```

推荐做法：

```text
保存原文
  + 保存标准结果
  + 保存映射版本和证据
  + 保存人工修正事件
```

这样词典升级后可以重新计算标准结果，也能解释历史任务为什么得到当时的结论。

## 5. 为什么必须显式传入当前时间

模型参数中的世界知识存在截止日期；即使模型偶尔能说出今天，也不能把它当作可信时钟。时间敏感任务必须由运行时提供当前时间。

仅传：

```text
今天是 2026-07-28
```

仍然不够，因为业务还需要知道：

- 当前时刻和时区；
- 一周从星期几开始；
- “最近七天”是否包含今天；
- 工作日、节假日和补班规则；
- 截止日是否包含当天；
- 数据以产生时间、入库时间还是生效时间排序；
- 哪个知识、价格和政策版本在该时刻有效。

### 推荐的 `TimeContext`

```json
{
  "now_utc": "2026-07-28T03:15:00Z",
  "business_timezone": "Asia/Shanghai",
  "local_now": "2026-07-28T11:15:00+08:00",
  "business_date": "2026-07-28",
  "week_start": "MONDAY",
  "calendar_id": "CN_WORKDAY",
  "calendar_version": "2026-v1",
  "request_received_at": "2026-07-28T03:14:58Z"
}
```

该对象应由可信 Runtime 在每次任务开始时生成，作为只读上下文提供给模型和工具。不能接受用户文本覆盖 `now_utc`、业务时区或日历版本。

## 6. 把相对时间转换成绝对区间

模型看到“最近一周”时，不应只把原表达传给数据库。系统应先按统一规则解析：

```json
{
  "raw_expression": "最近一周",
  "resolved_start": "2026-07-22T00:00:00+08:00",
  "resolved_end": "2026-07-28T11:15:00+08:00",
  "timezone": "Asia/Shanghai",
  "start_inclusive": true,
  "end_inclusive": true,
  "resolution_rule": "rolling_7_calendar_days_including_today",
  "time_context_id": "tc_20260728_031500"
}
```

需要明确区分：

| 表达 | 可能口径 |
|---|---|
| 最近 7 天 | 滚动 7×24 小时，或包含今天的 7 个自然日 |
| 本周 | 从业务周起始日到当前时刻 |
| 上周 | 上一个完整业务周 |
| 今日截止 | 当日 23:59:59，或当前营业结束时刻 |
| 三个工作日内 | 必须读取业务日历 |
| 最新版本 | `effective_at <= now` 中版本最高者 |

对外回答最好同时返回原表达和已解析日期范围，便于用户发现口径误解。

### 招投标截止时间还要补什么

截止时间至少应保存：

```text
原始表达
绝对时间
时区
是否含边界
来源文件与页码
解析置信度
规则或人工确认状态
```

只有字符串 `2026-08-20 10:00`，无法判断它属于哪个时区，也无法证明来自哪一版招标文件。

## 7. 时间不只有 `created_at`

生产系统应区分：

| 时间 | 含义 |
|---|---|
| `event_time` | 业务事件实际发生时间 |
| `observed_at` | 系统看到该事件的时间 |
| `ingested_at` | 数据进入本系统的时间 |
| `processed_at` | Agent 处理完成的时间 |
| `effective_from/to` | 规则、价格或词条的有效区间 |
| `expires_at` | 缓存、授权或证据的失效时间 |
| `as_of` | 本次判断所依据的业务时点 |

例如“最新成本价”通常应查询：

```text
status = active
AND effective_from <= as_of
AND (effective_to IS NULL OR effective_to > as_of)
```

而不是简单使用：

```sql
ORDER BY created_at DESC
```

### 时间也必须进入缓存与 Trace

只按问题文本做语义缓存，会把昨天的“今日报价”错误复用到今天。缓存键或命中校验至少要考虑：

```text
tenant / permission scope
canonical business objects
business_date or as_of bucket
dictionary version
knowledge and price version
policy version
```

Trace 应记录本次运行收到的 `TimeContext`，这样才能复现“当时为什么认为某条价格或政策有效”。

## 8. 词典与时间规则都必须版本化

这两类配置会直接改变模型结论，应按代码和 Prompt 的标准治理：

```text
草稿
→ 评测
→ 人工审批
→ 小范围发布
→ 监控
→ 全量启用或回滚
```

每次运行至少绑定：

```text
dictionary_version
unit_rule_version
business_calendar_version
prompt_version
model_id
knowledge_version
as_of
```

### 建议评测集

业务语义评测：

- 同义不同词；
- 同词不同义；
- 部门、租户和场景冲突；
- 单位、规格和数量粘连；
- 未登录词；
- 人工修正后的回归。

时间评测：

- 今天、昨天、最近七天、本周、上周；
- 月末、年末和闰年；
- 工作日、节假日和补班；
- 截止时间边界；
- 规则新旧版本交替；
- 延迟到达、过期数据和未来时间；
- 不同时区的用户与数据源。

### 关键指标

```text
标准对象准确率
别名命中率
歧义率
未映射率
错误映射率
人工确认率
人工修正率
相对时间解析准确率
截止时间边界错误率
过期数据误用率
版本可复现率
```

高命中率不等于高质量。把未知词强行映射会降低未映射率，却提高更危险的错误映射率。

## 9. 当前 AI 智能报价中台的实现映射

以下结论来自 2026-07-28 对项目代码和文档的核对。

### 已有的企业语义基础

1. **报价需求标准化**
   - `requirement_standardizer.py` 已定义标准字段、强弱别名、价格列、单位归一化和单位族；
   - 同时保留 `raw_text`、原始单元格、字段映射、数量来源、候选值、置信度和人工确认标记；
   - 这已经是“原始层 + 标准层 + 人工兜底”的正确骨架。

2. **招标业务对象**
   - `bidding_business_objects.py` 已把要求和风险映射为对象类型、子类型、标准标题、责任角色和业务动作；
   - 对象保留标准值、来源位置、原文、证据、置信度和抽取方式；
   - 大对象、弱拆分和低质量代表证据会进入 LLM 或人工复核，而不是全量交给模型自由判断。

3. **图纸项目词库与工程量标准**
   - `drawing_project_lexicon.py` 保存人工项目名、强弱识别词、标准项目编码、标准单位选项、映射理由和来源行；
   - 未匹配标准编码的词条只作为候选，不直接生成最终工程量；
   - 工程量标准库和报价规则另有版本与 `active` 状态。

4. **证据与人工确认**
   - 标准化结果和业务对象均保留原始证据；
   - 低置信、冲突或缺字段项可以转人工，而不是让 LLM 静默补齐。

### 已有的时间治理基础

1. `app/core/time_utils.py` 已统一定义：
   - 新运行记录使用 aware UTC；
   - 展示和业务日使用 `Asia/Shanghai`；
   - 历史 naive 时间按应用时区显式解释；
   - ISO 时间支持带 `Z` 的 UTC 格式。
2. 报价、响应和执行看板会返回 `timezone=Asia/Shanghai`。
3. 每日 Agent 调度器已有可配置时区，并向调度状态提供 `current_time`。
4. 项目文档已经明确承认历史数据存在 UTC aware 与上海 naive 混用，并采用渐进迁移。

### 仍需收口的缺口

| 缺口 | 影响 |
|---|---|
| 字段别名、图纸词库、业务对象标签和单位规则分散在多个服务 | 修改难以统一评测、审批和回滚 |
| 部分词条只有代码常量，缺少统一 ID、作用域、负责人和生效区间 | 无法完整回答“谁定义、对谁生效、何时有效” |
| 资料研判 Agent 的 `system_prompt` 和 `state_view` 未收到可信 `TimeContext` | 相对时间、截止时间和“当前有效”判断仍可能漂移 |
| 招标日期目前主要抽取为原始日期字符串 | 时区、边界、来源和确认状态还不是统一时间对象 |
| 未发现统一的企业业务日历及版本 | 工作日、节假日和结算周期无法统一计算 |
| 历史 naive/aware 兼容仍存在服务内补偿逻辑 | 跨模块统计和故障复现成本较高 |
| 时间、词典版本尚未统一进入 Agent Trace 和缓存边界 | 历史结果难以完全复现，缓存可能跨时态误命中 |

### 推荐升级顺序

#### P0：统一可信时间上下文

在 Agent Runtime 生成只读 `TimeContext`，注入模型、工具和 Trace：

```text
now_utc
business_timezone
local_now
business_date
calendar_id / version
request_received_at
```

相对时间必须由统一解析器转为绝对区间；模型只解释业务意图，不自己决定系统时钟。

#### P0：建立统一语义注册表

不必立即做大型知识图谱。先为高价值对象统一：

```text
canonical_id
canonical_name
aliases
object_type
scope
constraints
owner
source
status
version
effective period
```

第一批可收口字段别名、单位、报价约束、招标业务对象和常用工程项目词条。

#### P1：版本、事件和回归集

- 词典修改走草稿、审核、启用、归档；
- 人工改映射记录前后值和理由；
- 运行记录绑定词典、日历和规则版本；
- 将真实歧义词、错映射和截止时间问题沉淀为回归案例。

#### P1：业务日历与截止时间对象

统一工作日、节假日、补班、结算周期和边界包含规则；把招标截止时间升级为带来源、时区、置信度和确认状态的结构化对象。

#### P2：按需引入本体或知识图谱

只有当跨域关系推理、复杂层级和影响分析成为真实瓶颈时，再把标准词典扩展为本体或知识图谱。当前阶段先把确定性语义和时间契约做稳。

## 10. FDE 面试表达

### 问：为什么大模型应用要维护业务词典？

可以回答：

> 通用模型理解的是公共语义，企业系统需要的是带作用域、版本和计算口径的标准业务对象。业务词典不是同义词表，而是自然语言到标准 ID 的治理层，要保存别名、定义、作用域、负责人、来源和有效期。解析时先做确定性归一和约束校验，再让模型处理歧义，低置信项转人工，同时保留原文和映射版本，保证审计与回归。

### 问：为什么要显式传入当前时间？

可以回答：

> 模型不是可信时钟，“最近一周”“今天截止”“最新价格”都依赖当前时刻、业务时区、日历和数据有效期。Runtime 应每次生成不可被用户覆盖的 TimeContext，把相对时间解析为绝对区间，并让模型、数据库、工具、缓存和 Trace 共用同一边界。这样才能避免时区、节假日、版本生效时间和历史复现问题。

### 项目故事

可以按以下结构讲当前报价中台：

```text
问题：
甲方 Excel 字段、单位和项目名称不统一；历史时间又混有 UTC aware 与上海 naive。

已有方案：
标准字段别名 + 单位归一 + 原始行追溯 + 置信度/人工确认；
招标业务对象 + 来源证据 + 选择性 LLM 复核；
共享 UTC/Asia-Shanghai 时间工具和业务日看板。

识别出的缺口：
语义规则分散，Agent 缺少结构化可信时间，业务日历和词典版本未统一进入 Trace。

下一步：
统一语义注册表和 TimeContext，再用真实错映射、相对时间和截止时间案例做回归。
```

这比只说“我用 Prompt 告诉模型今天几号、再加一个同义词表”更接近生产级 FDE 的回答。

## 11. 落地检查清单

### 企业语义

- [ ] 业务对象有稳定的标准 ID
- [ ] 原始表达与标准结果同时保存
- [ ] 词条包含别名、定义、口径、作用域和负责人
- [ ] 同名冲突按租户、角色、场景和数据源消歧
- [ ] 区分精确、别名、规则、向量、模型和人工映射
- [ ] 低置信和多候选结果会转人工
- [ ] 人工修正先成为候选规则，审核后才启用
- [ ] 词典版本进入运行记录、缓存和评测

### 时间上下文

- [ ] 当前时间由 Runtime 生成，不由模型猜测
- [ ] 同时保存 UTC 和 IANA 业务时区
- [ ] 相对时间转换为可审计的绝对区间
- [ ] 明确区间边界是否包含
- [ ] 工作日计算绑定业务日历及版本
- [ ] 区分事件、入库、处理、生效和失效时间
- [ ] “最新”按业务有效时间而不是最后写入时间计算
- [ ] TimeContext 进入工具参数、Trace、缓存和评测
- [ ] 历史 naive 时间的解释规则明确且可迁移
