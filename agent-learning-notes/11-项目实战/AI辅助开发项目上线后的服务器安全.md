# AI 辅助开发项目上线后的服务器安全

## 核心结论

服务器安全的第一步不是安装更多安全工具，而是回答：

> 这台服务器到底向公网开放了什么，为什么必须开放，谁能够访问？

最小闭环：

```text
盘点资产
→ 识别公网入口
→ 关闭非必要入口
→ 收紧身份与权限
→ 分步修改
→ 内外双向验证
→ 定期复查
```

AI 可以帮助生成只读检查命令、解释证据和设计方案，但不能未经确认直接登录并修改生产服务器。

---

## 1. 区分应用安全与服务器安全

### 应用安全

关注：

- 用户能否绕过前端直接调用接口
- 普通用户能否执行管理员操作
- 是否存在越权、注入和不安全文件上传
- API Key 是否被写进前端
- 接口是否正确鉴权、限流和校验

### 服务器安全

关注：

- 谁能够登录服务器
- 哪些端口和服务暴露在公网
- 数据库、缓存和管理面板是否对外开放
- `.env`、`.git`、日志和备份能否通过网站下载
- 操作系统及关键组件是否仍在维护期

两层必须同时治理：

```text
服务器防护严密 + 应用存在越权
→ 数据仍可能被应用主动泄露

应用代码安全 + 数据库直接暴露公网
→ 数据仍可能被外部扫描和攻击
```

## 2. 理解端口与完整暴露链路

IP 类似楼的地址，端口类似楼内不同服务的房间号。

| 服务 | 常见端口 |
|---|---:|
| HTTP | 80 |
| HTTPS | 443 |
| SSH | 22 |
| MySQL | 3306 |
| Redis | 6379 |

端口号只是定位服务，真正的公网暴露由多层共同决定：

```text
程序监听地址
→ Docker 端口发布
→ 主机防火墙
→ 云安全组或路由/NAT
→ 公网实际探测结果
```

### 监听地址

- `127.0.0.1`：通常仅本机访问
- 私网 IP：通常仅私有网络访问
- `0.0.0.0`：监听全部 IPv4 网卡，是否能从公网到达还取决于后续网络规则

### Docker 端口

容器内开放端口不等于向宿主机或公网发布。应检查 Compose 或运行参数中的端口映射。

例如：

```yaml
ports:
  - "3306:3306"
```

这可能把数据库端口发布到宿主机全部网卡。若只需宿主机访问，可以按实际架构绑定到回环地址，或根本不向宿主机发布，仅让容器通过内部网络通信。

### 防火墙与安全组

主机防火墙和云安全组是两道独立关卡，不能检查一个就假定另一个安全。修改 Docker 网络规则后也要重新验证，因为不同运行环境对防火墙规则的处理方式可能不同。

最终结论必须以授权范围内的公网实测为准。

## 3. 必须守住的四道门

### 3.1 数据库和缓存

数据库存放真实业务数据，通常没有理由让整个互联网直接连接。

优先连接方式：

1. 应用和数据库同机：本机或容器内部网络。
2. 分机部署：云私网、VPN 或受控网络。
3. 确需跨网访问：只允许明确来源，启用强认证、加密和审计。

检查项：

- 数据库、Redis 实际监听的地址
- Docker 是否发布数据库端口
- 主机防火墙和安全组是否放行
- 数据库账号是否为最小权限
- 默认账号、弱密码和匿名访问是否存在
- 是否启用连接审计和异常告警

不要为了临时调试把生产数据库开放给公网。若问题只能用生产数据复现，应经过授权，仅导出必要数据，脱敏后放入隔离环境，并在问题解决后按规则清理。

### 3.2 SSH 远程登录

推荐顺序：

1. 创建普通运维账号。
2. 配置密钥登录。
3. 在保留当前会话的情况下，新开连接验证密钥可用。
4. 确认拥有云控制台、VNC、串口或其他救援入口。
5. 再关闭密码登录。
6. 禁止 `root` 直接远程登录，通过受控提权执行管理任务。
7. 若条件允许，仅允许固定 IP、VPN、堡垒机或可信网络访问。

额外防护：

- 登录失败告警和自动封禁
- 最小化 `sudo` 权限
- 密钥定期轮换
- 离职或设备丢失后及时撤销密钥
- 保留登录和提权审计

> 修改 SSH 或防火墙最容易把自己锁在服务器外，必须先确认备用入口并保留现有连接。

### 3.3 网站可下载的敏感文件

高风险文件：

- `.env`
- `.git/`
- 应用日志
- 数据库备份
- 配置文件
- 调试输出
- 临时压缩包

这些文件可能包含数据库密码、支付密钥、模型 API Key 和完整业务数据。

治理方式：

- Web 根目录只放公开静态文件
- 配置、日志和备份存放在 Web 根目录之外
- Web 服务器显式拒绝访问隐藏文件和敏感后缀
- 构建和发布流程排除 `.env`、`.git`、备份及调试文件
- 从公网验证常见敏感路径无法下载
- 如果曾经暴露，按泄露事件处理并轮换相关密钥

仅把密钥从仓库删除还不够；历史提交、构建产物、日志和缓存中可能仍有副本。

### 3.4 无用端口与过期组件

每多暴露一个服务，就增加一份攻击面。

检查对象：

- 不再使用的服务和容器
- 测试端口
- 数据库和缓存
- 管理面板
- Docker API
- 调试接口
- 操作系统、Web 服务器、数据库、缓存和依赖组件

处理原则：

- 不需要的服务停止并移除公网入口
- 优先使用仍在维护的长期支持版本
- 安全更新及时评估
- 先在测试环境验证兼容性
- 生产更新前备份并准备回退
- 更新后检查网站、后台、队列和定时任务

不要盲目追逐最新大版本，也不能长期停留在已经停止安全维护的版本。

## 4. AI 辅助安全检查的正确流程

### 第一轮：只读检查

推荐提示词：

```text
我的项目已经部署在 Linux 服务器上。
请帮我做一轮只读的服务器安全检查。

不要修改配置、安装软件、删除文件或重启服务，
也不要自行连接生产服务器。

请先询问并确认：
- 操作系统及版本
- 部署方式
- 使用的云平台或网络环境
- Web、数据库、缓存、容器和管理面板

然后提供少量、只读的检查命令，并逐条说明：
- 命令用途
- 是否可能产生负载或暴露敏感信息
- 预期结果
- 如何脱敏后把结果交给你分析

需要覆盖：
1. 实际监听的端口、进程和监听地址
2. Docker 发布到宿主机的端口
3. 数据库、缓存、SSH、管理面板的暴露情况
4. 主机防火墙规则
5. 需要我到云平台人工核对的安全组规则
6. .env、.git、日志和备份是否可能被公开下载
7. 操作系统及关键组件是否仍在维护期

只检查我拥有并明确授权的 IP 和域名。
最后按“证据、风险、处理方向、可能影响”输出问题清单。
```

### 第二轮：解释风险

对每个问题要求 AI 回答：

- 入口是否真的能从公网访问
- 证据是什么
- 服务是否被业务使用
- 关闭后会影响什么
- 不处理的最坏后果是什么

AI 无法解释清楚的项目，不应直接修改。

### 第三轮：一次只处理一项

```text
请先给处理方案，不要执行。

说明：
1. 准备修改什么
2. 为什么修改
3. 影响哪些服务
4. 修改前如何备份
5. 失败后如何恢复
6. 服务器内部如何验证
7. 公网外部如何验证

如果涉及 SSH 或防火墙，
先确认我有救援入口，并提醒我保留当前 SSH 会话。
命令一次只提供一小组，等我反馈结果后再继续。
```

### 第四轮：双向验证

每次修改后都要验证：

- 应关闭的入口已无法从公网访问
- 仍需提供的功能可以正常使用
- 后台、队列和定时任务未被误伤
- 日志和监控没有出现新异常

安全组、主机防火墙、监听地址和 Docker 映射发生变化后，都应重新执行检查。

---

## 5. 最小验收标准

- [ ] 普通网站原则上只公开必要的 80/443 入口
- [ ] SSH 只向受控来源开放
- [ ] SSH 密钥登录已经验证
- [ ] 密码登录和 `root` 直登已按计划关闭
- [ ] 数据库与缓存只允许本机、私网或明确来源访问
- [ ] 管理面板和调试接口未对全网开放
- [ ] `.env`、`.git`、日志与备份无法通过公开网址下载
- [ ] 生产数据不会未经审批复制到个人设备或外部 AI
- [ ] 操作系统及关键组件处于维护期
- [ ] 安全更新具有测试、备份、回退和验证流程
- [ ] 已从服务器外部复核实际公网暴露面
- [ ] 端口、账号和组件清单有人维护并定期复查

---

## 6. 这些措施不能替代 DDoS 防护

DDoS 通过大量流量或请求耗尽带宽和服务资源，不一定需要进入服务器。

通常需要：

- 云厂商 DDoS 防护
- CDN
- WAF
- 流量清洗
- 限流和弹性策略
- 应急封禁与切换方案

关闭无用端口可以减少攻击面，但不能让单台服务器具备对抗大规模 DDoS 的能力。

## 7. 面向当前报价中台的安全映射

当前环境采用 Windows 网关与 CentOS 服务器双机部署，正式生产前应执行一次完整的暴露面审计。

### 服务边界

| 组件 | 当前端口 | 建议边界 |
|---|---:|---|
| FastAPI 主网关 | 9000 | 通过受控入口访问，不直接无条件暴露公网 |
| n8n | 5678 | 仅允许网关、管理网络和必要回调来源 |
| RAG 服务 | 8001 | 仅内部服务访问 |
| Milvus | 19530 | 仅私网或容器网络访问 |
| MySQL、Redis/Broker | 依实际配置 | 不对公网开放 |
| Dify、RAGFlow 管理界面 | 依实际配置 | 限制来源并启用强认证 |

### 专项检查

1. 检查 `rag_docker/docker-compose.yml` 的所有 `ports` 映射。
2. 在 CentOS 上核对实际监听地址、`firewalld` 和 Docker 网络规则。
3. 核对路由器、云安全组或 NAT 端口映射。
4. 从受控的外部网络验证真实暴露端口。
5. 确保 `AI_Middle_Office/.env` 不在 Web 根目录、静态资源或构建产物中。
6. 确认旧 `index.html`、管理端 API 和健康接口没有泄露配置或敏感诊断信息。
7. 对管理员入口、成本库和报价证据链继续执行 RBAC、最小权限和审计。

### 当前最重要的系统风险

项目文档显示服务器仍使用 CentOS 7.9。CentOS 官方已于 2024 年 6 月 30 日结束 CentOS Linux 7 的维护，此后不再发布常规安全更新，应把操作系统迁移作为正式生产前的独立安全项目，而不是在现有机器上直接进行高风险原地升级。[CentOS 官方说明](https://blog.centos.org/2023/04/end-dates-are-coming-for-centos-stream-8-and-centos-linux-7/)

迁移应包含：

- 目标发行版和版本选型
- 依赖、Docker 和驱动兼容性验证
- 新环境并行搭建
- 数据备份及恢复演练
- 服务逐项迁移与验收
- 回退窗口和旧环境下线计划

## 一句话总结

服务器安全不是把所有端口都关掉，而是让每个公网入口都有明确业务理由、最小访问范围、可靠身份验证、可审计变更和持续复核。
