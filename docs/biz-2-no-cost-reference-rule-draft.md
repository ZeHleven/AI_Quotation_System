# BIZ-2 无底价项目处理规则草案

> 状态：规则草案已形成，待业务确认与后续开发排期（2026-05-27）
> 用途：规则草案 + 操作 SOP + 后续开发建议
> 边界：本文只定义规则，不改代码、不改报价价格口径、不自动启用成本库条目、不启动 Phase 4b/4c/6，不启动 BIZ-1b/BIZ-1c/BIZ-1d。

## 1. 核心结论

无底价项目允许 AI 先给出估价，但必须在预审单中明确提示：

```text
无成本库参考价，AI 估价，仅供参考，请人工确认价格依据
```

业务员可以在预审单中手动填写或修正无底价项目的单价和合计。人工确认报价并下发后，这些无底价条目应进入成本库待审核区，但只能以 `draft` 状态保存，不能自动成为 `active`。

只有成本部业务员、管理员或老板人工复核并启用为 `active` 后，同样条目后续再次报价时，价格才允许出现在预审单的成本库参考价中。

## 2. 已确认业务口径

| 问题 | 规则 |
|------|------|
| 无底价时是否允许 AI 估价 | 允许，但必须标记为 AI 估价，仅供参考 |
| 人工填写单价/合计后能否下发 | 可以下发 |
| 下发后是否进入成本库 | 必须进入成本库待审核 |
| 进入成本库后的状态 | 只能是 `draft` |
| `draft` 是否参与后续报价底价参考 | 不参与 |
| 什么时候参与后续报价 | 人工审核并启用为 `active` 后 |
| 谁能确认/审核 | 成本部业务员、管理员、老板 |
| 是否按金额门槛区分 | 暂不区分 |
| 是否按项目类型区分 | 暂不区分 |
| 是否自动沉淀为正式成本库 | 不允许自动成为 `active` |

## 3. 术语定义

| 术语 | 定义 |
|------|------|
| 成本库参考价 | 来自 `cost_items.active` 的正式成本条目价格 |
| 无底价项目 | 当前报价行没有命中可用的 `cost_items.active` 成本库参考价 |
| AI 估价 | AI 在没有成本库参考价时生成的建议单价/合计 |
| 人工确认价 | 业务员在预审单中手动填写或确认后的单价/合计 |
| 待审核成本条目 | 从已确认报价沉淀到成本库的 `draft` 条目 |
| 正式成本条目 | 经人工审核启用后的 `active` 条目 |

无底价判断只看 `active` 成本库。已有 `draft`、`archived` 或旧 `materials` 数据不能作为报价底价参考。

## 4. 业务流程

```text
甲方需求单/报价需求
  -> 成本库 active 匹配
  -> 命中 active：展示成本库参考价
  -> 未命中 active：允许 AI 估价并标记无底价
  -> 预审单人工确认或修正单价/合计
  -> 确认报价并下发
  -> 无底价条目进入成本库 draft
  -> 成本部/管理员/老板人工复核
  -> draft 启用为 active
  -> 后续同类需求才展示成本库参考价
```

## 5. 预审单规则

### 5.1 展示规则

无底价行必须展示以下信息：

- 项目名称
- 规格/项目特征
- 数量
- 单位
- AI 估算单价
- AI 估算合计
- 成本库参考价为空
- 风险提示文案：`无成本库参考价，AI 估价，仅供参考，请人工确认价格依据`
- 人工单价/系统合计编辑入口

### 5.2 操作规则

无底价行可以执行：

- 保留 AI 估价并人工确认
- 修改单价
- 修改系统合计
- 补充价格依据或备注
- 打回重填

无底价行不能执行：

- 自动使用成本库底价兜底
- 自动变成正式成本库条目
- 未经人工确认直接下发

### 5.3 确认推送规则

允许确认推送的条件：

- 无底价行已有正数单价
- 无底价行已有正数系统合计
- 业务员已人工确认价格依据
- 不存在未处理的阻断行
- 不存在未补价的 AI 缺失占位行

必须阻断推送的条件：

- 无底价行单价为空、0 或非法
- 无底价行系统合计为空、0 或非法
- 行仍处于“AI 未返回，需人工补价”的占位状态
- 预审完整性仍为不完整，且没有生成可人工补价的占位行

## 6. 成本库沉淀规则

### 6.1 生成 draft 的时机

确认报价并下发成功后，系统应把本单中的无底价人工确认条目写入成本库待审核区。

写入时机建议为：

```text
/confirm_push 成功记录报价历史
  -> 提取无底价且已人工确认的预审行
  -> 写入 cost_items draft
  -> 写入 cost_item_history
```

如果钉钉推送失败，原则上不应生成成本库 draft，避免“未成交/未下发”的价格进入待审核池。

### 6.2 draft 条目字段建议

| 成本库字段 | 建议值 |
|------------|--------|
| `status` | `draft` |
| `source` | `ai_suggested` |
| `category` | 待分类 |
| `subcategory` | 可为空或待分类 |
| `item_name` | 预审行项目名称 |
| `spec` | 预审行规格/项目特征/备注 |
| `unit` | 预审行单位 |
| `price` | 人工确认后的单价 |
| `price_type` | `combined` |
| `notes` | 记录来源报价任务、原始行号、AI 估价、人工确认价和价格依据 |
| `created_by` | 确认报价的用户 |

如后续需要完整追溯，建议新增字段或新表记录：

- 来源报价任务 ID
- 来源报价历史 ID
- 来源确认清单行 key
- 原始 Sheet
- 原始行号
- AI 原始估价
- 人工确认价
- 人工确认备注
- 待审核原因
- 审核人和审核时间

涉及新增字段或新表时，必须走 Alembic。

### 6.3 去重与覆盖规则

生成 draft 时建议按以下字段判断是否已有相似待审核条目：

```text
item_name + spec + unit
```

建议策略：

- 已有相同 `active`：不再新建 draft，只记录“报价时未命中但疑似已有 active，需检查匹配规则”。
- 已有相同 `draft`：更新或追加来源记录，避免重复堆积。
- 已有 `archived`：新建 draft，但在备注中提示曾有停用条目。
- 完全无相似条目：新建 draft。

首版如不做复杂去重，也至少要在成本库待审核列表中展示重复提示，防止成本部重复启用。

## 7. 审核启用规则

### 7.1 审核角色

允许审核无底价 draft 的业务角色：

- 成本部业务员
- 管理员
- 老板

当前系统落地时需要把这些业务角色映射到实际 RBAC 角色或账号组。没有映射前，不应放开给普通员工批量启用。

### 7.2 审核动作

审核人可以：

- 修改项目名称
- 修改规格/项目特征
- 修改单位
- 修改单价
- 补充分类和子类
- 补充价格拆分字段
- 启用为 `active`
- 停用或归档为 `archived`

审核人启用为 `active` 前必须确认：

- 项目名称足够标准
- 规格描述足够清晰
- 单位正确
- 价格口径符合成本部规则
- 不是重复条目
- 不是一次性临时报价，不应进入正式成本库

### 7.3 启用后的效果

`draft -> active` 后：

- 后续报价可以命中该条目。
- 成本库参考价可以出现在预审单中。
- 成本库前置上下文可以把该价格传给 AI。
- RAG 同步时可以进入 active 成本知识。

仍为 `draft` 时：

- 不进入报价底价参考。
- 不进入成本库前置上下文。
- 不触发成本库底价兜底。
- 不作为“有成本库参考价”展示。
- 不同步到 RAG active 成本知识。

## 8. 业务员 SOP

### 8.1 预审时看到无底价提示

当预审单出现：

```text
无成本库参考价，AI 估价，仅供参考，请人工确认价格依据
```

业务员需要：

1. 查看 AI 估算单价和合计。
2. 根据经验、供应商报价或内部沟通确认价格。
3. 必要时修改单价和系统合计。
4. 在备注中补充价格依据。
5. 确认无误后再下发。

### 8.2 不能直接确认的情况

以下情况应打回或暂停：

- 业务员无法判断价格是否合理。
- 项目名称或规格不清，成本部无法后续审核。
- 数量或单位不确定。
- AI 估价明显偏离常识，但没有依据修正。
- 该条目属于一次性特殊项目，不适合进入成本库。

### 8.3 下发后说明

下发成功后，业务员应知道：

- 本单报价已按人工确认价下发。
- 无底价条目会进入成本库待审核。
- 待审核条目不会马上影响后续报价。
- 成本部启用为 `active` 后，后续同类条目才会出现成本库参考价。

## 9. 管理员/成本部 SOP

### 9.1 查看待审核条目

管理员或成本部应在成本库页面筛选：

```text
status = draft
source = ai_suggested
```

重点查看：

- 项目名称
- 规格
- 单位
- 人工确认单价
- 来源报价任务
- 来源用户
- 来源时间
- 价格依据备注
- 是否与现有 active 重复

### 9.2 审核处理

对每条 draft：

1. 核对名称、规格、单位是否标准。
2. 核对价格是否符合成本部口径。
3. 必要时补充分类、子类和拆分价。
4. 如果可以复用，启用为 `active`。
5. 如果只是临时报价，保留 draft 或归档。
6. 如果明显错误，归档并写明原因。

### 9.3 后续报价验证

启用为 `active` 后，可以用相同或相似需求重新发起报价，验证：

- 预审单能命中成本库参考价。
- AI 来源能识别为有成本库参考。
- 不再显示“无成本库参考价”的提示。
- 如果 AI 报 0 元，成本库兜底可按原规则生效。

## 10. 后续开发建议

### 10.1 最小开发方案

不新增数据库结构，复用现有 `cost_items`：

- 在 `/confirm_push` 成功后扫描预审行。
- 找出 `cost_reference.matched=false` 或无 active 成本参考的行。
- 只处理已人工确认且单价/合计为正数的行。
- 写入 `cost_items`，状态为 `draft`，来源为 `ai_suggested`。
- 把报价任务 ID、原始行号、AI 估价、人工确认价写入 `notes`。
- 写入 `cost_item_history`。

优点：开发快，不新增 Alembic。  
缺点：来源追溯依赖 `notes`，后续查询和去重能力弱。

### 10.2 推荐开发方案

新增独立的“无底价成本候选”记录或给 `cost_items` 补充来源字段。

建议字段：

| 字段 | 说明 |
|------|------|
| `source_quote_job_id` | 来源报价任务 |
| `source_quote_history_id` | 来源报价历史 |
| `source_requirement_row_key` | 来源确认清单行 |
| `source_sheet` | 来源 Sheet |
| `raw_row_index` | 原始行号 |
| `ai_unit_price` | AI 原始估价单价 |
| `confirmed_unit_price` | 人工确认单价 |
| `confirmed_total_price` | 人工确认合计 |
| `confirmation_note` | 人工确认依据 |
| `review_status` | 待审核、已启用、已归档 |

涉及新增字段或新表时，必须新增 Alembic revision。

### 10.3 前端开发建议

预审弹窗增加：

- 无底价醒目标识。
- 固定提示文案：`无成本库参考价，AI 估价，仅供参考，请人工确认价格依据`。
- 人工确认价格依据输入框。
- “确认后进入成本库待审核”的提示。
- 未填写正数单价/合计时禁用确认推送。

成本库页面增加：

- 来源筛选：`source=manual` 用于人工改价，`source=ai_suggested` 用于 AI 建议或人工采纳 AI 建议。
- “报价沉淀候选”标签或筛选入口。
- 来源报价任务快捷查看。
- 重复条目提醒。
- 批量启用前二次确认。

### 10.4 后端开发建议

后端需要保证：

- 只在 `/confirm_push` 成功后生成 draft。
- draft 不参与报价参考。
- draft 不进入 RAG active 同步。
- draft 不能触发底价兜底。
- 重复生成时有去重或提示。
- 所有生成、修改、启用、归档动作写历史。

### 10.5 测试建议

至少覆盖：

- 无 active 成本参考时，预审显示 AI 估价提示。
- 手工补正单价/合计后允许确认推送。
- 推送成功后生成 `cost_items.draft`。
- draft 不参与下一次报价匹配。
- draft 启用为 active 后，下一次同类报价可命中。
- 未补正数单价/合计时 `/confirm_push` 返回 409。
- 已有相同 draft 时不重复生成。
- 已有 active 时不生成重复 draft。

## 11. 当前不做的事

- 不按金额门槛区分。
- 不按项目类型区分。
- 不让 AI 估价自动成为成本库正式价。
- 不让 draft 参与报价、RAG 或底价兜底。
- 不自动覆盖已有 active 条目。
- 不把人工确认价直接写成 `active`。
- 不迁移旧 `index.html` / `admin.html` / `app.html`。

## 12. 待确认事项

以下事项建议在进入开发前最终确认：

| 待确认项 | 建议 |
|----------|------|
| 成本部业务员在系统中的角色映射 | 明确对应 RBAC 角色或新增角色 |
| draft 候选是否需要独立菜单 | 建议在成本库页增加筛选入口即可 |
| 重复 draft 是覆盖还是追加来源 | 建议首版更新同名同规格同单位 draft，并记录来源 |
| 价格依据是否必填 | 建议必填，至少 5 个字 |
| draft 默认分类 | 建议“待分类/报价沉淀候选” |
| 启用 active 是否需要二次确认 | 建议需要 |

## 13. 结论

本规则允许无底价项目在当前报价中继续推进，但把“本单人工确认价”和“正式成本库底价”严格分开：

- 本单：AI 可估价，人工确认后可下发。
- 成本库：只沉淀为 `draft`，等待人工审核。
- 后续报价：只有 `active` 才能作为成本库参考价。

这样既不阻断业务报价，也避免 AI 估价未经成本部确认就污染正式成本库。
