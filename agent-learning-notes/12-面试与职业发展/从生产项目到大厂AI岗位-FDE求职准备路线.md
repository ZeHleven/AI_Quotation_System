# 从生产项目到大厂 AI 岗位：FDE 求职准备路线

## 核心策略

进入 AI 应用开发、Agent 工程、AI 交付或 FDE 相邻岗位，不需要先完成整个 AI 智能报价中台。

更有效的目标是：

> 把成本测算这条核心业务链做成真实生产案例，并用数据证明自己具备业务理解、方案设计、系统开发、生产交付和价值验证的完整能力。

求职竞争力主要来自生产证据，而不是功能数量：

```text
真实业务问题
→ 可运行的生产系统
→ 可量化的质量与效率
→ 可解释的技术决策
→ 可复用的交付方法
```

对工作经验较少的候选人，更现实的路线通常是先进入 AI 应用、Agent 全栈或 AI 交付岗位，再成长为直接负责客户现场和业务结果的 FDE。

> 岗位名称和年限要求会持续变化。招聘页面只能作为阶段性参考，不能当作固定行业标准。

---

## 1. 项目达到什么程度才具备求职价值

### 1.1 跑通真实生产闭环

核心链路：

```text
真实项目资料
→ 文件与图纸解析
→ 工程分项抽取
→ 材料和价格匹配
→ 成本测算
→ 人工复核与修改
→ 正式结果输出
→ 反馈和数据沉淀
```

验收标准：

- 业务人员可以脱离开发者指导独立操作
- 输入是真实项目，而不是专门准备的简单样本
- AI 结果可以修改、追踪、保存和恢复
- 失败任务可以重试、取消或转人工
- 正式结果能够进入实际业务流程
- 系统不因开发者不在现场而停止使用

这是全部准备工作的最高优先级。

### 1.2 用运行数据替代主观评价

建议积累一段连续试运行数据。原资料提出“6—8 周、30 份以上任务”，它是提高案例可信度的经验目标，不是招聘硬门槛。

| 指标 | 定义 | 能证明什么 |
|---|---|---|
| 原人工耗时 | 旧流程从接单到完成的总工时 | 业务基线 |
| AI 自动处理耗时 | 系统执行时间 | 系统性能 |
| 人工复核耗时 | 人员检查和修改时间 | 实际节省 |
| 任务成功率 | 正常形成可复核结果的比例 | 可靠性 |
| 人工修改率 | 需要修改的条目或任务比例 | 结果质量 |
| 漏项率 | 应报价但未覆盖的项目比例 | 完整性 |
| 人工接受率 | 无需重大修改即可采用的比例 | 业务可用性 |
| 单任务模型成本 | 模型、OCR、存储等可变成本 | 经济性 |
| 实际使用量 | 周或月任务数、活跃用户数 | 用户采用 |

推荐表达：

```text
系统连续运行 8 周，处理 42 个真实项目；
人工总耗时从平均 5 小时降至 2.1 小时；
任务成功率为 96%；
修改主要集中在非标准材料映射和特殊施工工艺。
```

不推荐只说：

```text
系统效率提高了 60%。
```

所有数字都应保留口径、时间范围和原始记录，避免只展示最好的样本。

## 2. 建立可回归的 AI 评测体系

必须能够回答：

> 更换模型、Prompt、知识库或流程以后，怎样证明系统变好了，而不是只在几个例子上看起来更好？

### 黄金测试集

首版可从 50—100 个脱敏代表性样本起步，逐步扩充。数量是经验建议，覆盖度比机械追求规模更重要。

建议覆盖：

- 不同文件格式、图纸质量和页数
- 简单、中等、复杂项目
- 标准与非标准材料
- 同名不同规格
- 常见漏项场景
- 异常文件、缺失字段和边界输入
- 曾经在线上失败或被人工大幅修改的案例

### 分层评测

| 层级 | 候选指标 |
|---|---|
| 文件解析 | 解析成功率、字段准确率、表格结构保留率 |
| OCR/VLM | 字段识别、区域理解、数量与单位准确率 |
| 分项抽取 | Precision、Recall、F1、漏项率 |
| 成本匹配 | Top-1、Top-3 命中率、错误匹配率 |
| RAG | Recall@K、Precision@K、MRR、证据相关性 |
| Agent | 任务完成率、工具选择和参数正确率 |
| 最终结果 | 人工接受率、修改率、无依据内容比例 |
| 工程表现 | 成功率、P95 延迟、Token 和单任务成本 |

每次修改模型、Prompt、检索、匹配规则或关键流程后自动运行回归，并保留版本间对比。

## 3. 补齐生产工程闭环

### 必须能够证明

- 登录、RBAC 和数据访问隔离
- 完整任务状态和步骤事件
- 超时、重试、取消和失败恢复
- 幂等性，避免重复报价和重复写入
- 统一任务 ID、结构化日志和错误追踪
- 数据库、文件备份和恢复演练
- 开发、测试与生产环境分离
- 自动化测试和发布前验证
- 版本管理、回滚和人工兜底
- 模型用量、成本、服务指标和告警

### 有实际需求时再增加

- 灰度发布
- 限流、熔断、降级和背压
- 模型路由
- Prompt 与知识库版本管理
- 敏感数据脱敏和操作审计
- OpenTelemetry、Prometheus、Grafana
- Langfuse 等 LLM 可观测工具

不要求为简历堆齐所有工具。面试价值来自：

1. 为什么出现这个问题；
2. 为什么选择当前方案；
3. 方案的代价和边界；
4. 如何验证真的有效。

---

## 4. 证明用户采用，而不只是完成部署

“服务器可以访问”不等于业务落地。

需要保留：

- 活跃用户和任务使用记录
- 用户培训与操作手册
- 人工复核边界
- 问题和反馈台账
- 人工修改原因分类
- 改动进入评测集或优化计划的记录
- 流程改造前后的对比

这部分证明的是 FDE 很看重的组织推动能力：

```text
理解业务
→ 与用户共创流程
→ 推动试用
→ 处理现场问题
→ 形成稳定使用习惯
```

## 5. 用 ROI 说明业务价值

基础模型：

```text
年度节省工时
= 单份任务节省时间 × 每月任务数 × 12

年度人力价值
= 年度节省工时 × 专业人员综合小时成本

年度净价值
= 人力价值
+ 响应速度提升带来的价值
+ 错误减少带来的价值
- 模型费用
- 服务器和存储费用
- 开发、维护和培训成本
```

推荐描述：

> 系统预计每年释放约 X 小时专业人员工时，使造价人员可以处理更多项目，并减少重复整理工作。

谨慎使用“节省了几个人”等难以验证的结论。效率提升不一定等于裁减岗位。

## 6. 求职作品集

项目上线后至少准备：

1. 一页项目案例
2. 10—15 页项目汇报 PPT
3. 5 分钟脱敏演示
4. 系统架构图
5. 业务流程改造前后对比
6. 评测报告
7. ROI 测算
8. 一次生产故障或问题复盘
9. 5—10 张关键决策卡
10. 第一版企业 AI 落地方法论

### 一页案例结构

```text
业务背景
→ 原流程痛点
→ 解决方案
→ 核心架构
→ 生产规模
→ 质量、效率、成本数据
→ 关键挑战与决策
→ 业务价值
```

### 决策卡

每张卡回答：

- 当时的问题是什么
- 有哪些候选方案
- 为什么选择当前方案
- 放弃了什么
- 出现了什么结果
- 如果重做会怎样改

适合准备的主题：

- 为什么使用模块化单体而不是立即拆微服务
- 为什么采用人工预审，而不是全自动下发
- 大清单为什么分批处理并保留占位行
- 无底价项目为什么只能沉淀为 Draft
- 如何处理成本库证据链和审计
- 为什么建立评测回归而不是继续修改 Prompt

## 7. 什么时候可以开始投递

下面 10 项完成 7—8 项，就具备开始投递的合理基础。它是自检工具，不是企业统一标准。

- [ ] 核心链路进入真实生产或受控试运行
- [ ] 业务人员能够独立操作
- [ ] 已积累一批真实任务
- [ ] 有连续多周运行记录
- [ ] 有明确的人工耗时前后对比
- [ ] 有准确率、漏项率和人工修改率
- [ ] 有日志、重试、权限、备份和监控
- [ ] 有固定评测集和自动回归
- [ ] 有架构图、案例 PPT 和脱敏演示
- [ ] 能讲清至少三个重大问题及决策过程

单独做好成本测算场景，已经可以支持投递：

- AI 应用开发工程师
- 大模型应用工程师
- Agent 全栈工程师
- AI 交付开发工程师
- 行业 AI 应用工程师

第二场景可以增强竞争力，但不应阻塞投递。优先选择与主链路共享数据和评测体系的小场景，例如风险审核、漏项检查或价格异常复核。

## 8. 学习优先级

### P0：直接支撑生产和求职证据

1. AI 评测与回归
2. 日志、Trace、指标和告警
3. 异步任务生命周期、幂等与故障恢复

目标：

> 输入一个任务 ID，可以还原它经过的步骤、模型和工具调用、耗时和成本、失败位置，以及人工修改内容。

### P1：Agent 工程深度

- Function/Tool Calling
- MCP
- 状态机和 LangGraph 思想
- 任务规划和上下文工程
- Human-in-the-loop
- 工具权限、重试和回滚
- Agent 评测
- 沙箱和安全边界

实践方向：

```text
风险审核 Agent
→ 读取成本清单
→ 查询历史价格
→ 查询材料知识库
→ 标记异常并给出证据
→ 人工确认
```

不要为了展示 Agent 而把确定性业务流程强行改成自主 Agent。

### P2：企业软件工程

- API 设计
- MySQL 索引和事务
- Redis 与消息队列边界
- RBAC 和操作审计
- 数据迁移与自动化测试
- CI/CD 和灰度发布
- 数据安全与脱敏
- 系统设计和容量规划

模块化单体并不落后。需要能够解释何时拆服务、解决什么问题，以及新增哪些复杂度。

### P3：云原生

建议顺序：

```text
Linux
→ Docker
→ Docker Compose
→ Kubernetes 核心对象
→ Helm
→ ConfigMap / Secret
→ 健康检查
→ 滚动更新
→ 资源限制和扩缩容
```

可以独立部署一套 Kubernetes 测试环境，演示升级、日志、Worker 扩容、回滚和密钥管理。但 Kubernetes 不应阻塞当前系统的受控上线。

### P4：通用面试基础

- 数据结构与算法
- 操作系统和网络
- 数据库、Redis 和消息队列
- 分布式系统
- 系统设计
- Python 语言机制和编码

时间安排可参考：

```text
每天 30 分钟算法
+ 30 分钟计算机基础或系统设计
+ 其余学习时间优先服务当前项目
```

语言优先级：

- 深入 Python
- Java/Spring Boot 掌握基础，可扩大企业研发岗位范围
- Go 作为加分项，暂不高于评测、可靠性和系统设计

## 9. 面向当前报价中台的差距判断

当前项目已经具备大量代码层生产能力：

- RBAC、权限事件和审计
- 报价任务状态、重试、取消和超时处理
- 人工预审、完整性阻断和证据链
- Prompt 回归、成本库治理和业务看板
- 健康检查、Celery Worker 和任务事件
- 大清单分批处理、占位和失败恢复

因此，下一阶段不应继续用功能数量证明能力。最大的证据缺口是：

1. 正式或受控生产运行尚未完成
2. 缺少连续多周的真实用户和任务数据
3. 需要统一最终求职指标口径
4. 需要把现有回归能力整理为正式评测报告
5. 需要完成生产 Runbook、恢复演练和发布证据
6. 需要把技术成果转化为案例、演示和决策故事

一句话判断：

> 当前主要短板不是“系统功能不够”，而是“尚未把已有能力转化为可信的生产证据和求职资产”。

## 10. 三个月执行路线

### 第 1 个月：完成受控上线

- 冻结非必要新功能
- 明确核心成本测算链路
- 完成业务验收和用户操作流程
- 确认权限、日志、重试、备份和人工兜底
- 建立指标基线
- 完成生产 Runbook 和恢复演练

### 第 2 个月：稳定运行和评测

- 积累真实任务
- 分类用户问题和人工修改原因
- 建立或扩充黄金测试集
- 固化模型、Prompt 和检索回归
- 统计质量、耗时、成本和使用量
- 形成用户反馈闭环

### 第 3 个月：作品集和投递

- 冻结第一版量化结果
- 完成 ROI
- 制作项目 PPT 和脱敏演示
- 更新架构图和流程对比
- 整理三到五个 STAR/决策故事
- 总结企业 AI 落地方法论
- 开始投递，不等待全部中台功能完成

## 求职表达模板

```text
我负责把公司成本测算流程从人工处理改造成 AI 辅助生产系统。

系统覆盖文件解析、工程分项标准化、成本库匹配、AI 报价、
人工预审、正式下发和反馈沉淀。

为了进入生产，我重点解决了大清单完整性、任务幂等、
失败恢复、成本证据链和人工审核边界。

系统连续运行 X 周，处理 X 个真实项目，
人工耗时从 X 降至 X，任务成功率为 X，
主要修改集中在 X。

我还建立了固定评测集和版本回归，
确保模型、Prompt 和知识库变更可以量化验证。
```

---

## 最终结论

现在最重要的三个转变是：

```text
从功能完成转向生产运行
从主观感觉转向评测数据
从个人经历转向可复制的方法论
```

技术学习前三名：

1. AI 评测与回归体系
2. 日志、监控和生产可靠性
3. Tool Calling、MCP 与状态管理

完成真实生产闭环并形成量化证据后，候选人的定位就不再只是“会调用模型”，而是“完成过企业 AI 项目交付”。
