# 报价中台面试映射手册 01：异步任务可靠性

## 使用方法

每道题只记一条主线：

```text
问题 → 方案 → 取舍 → 证据
```

回答时先讲 30 秒版本；面试官追问后，再补代码、指标和当前边界。

## 考前 2 分钟速记

| 问题 | 记忆句 |
|---|---|
| 为什么异步 | 长链路先落库再入队，前端只查状态 |
| 怎样追踪 | `status` 管结果，`stage + event + trace` 管过程 |
| 怎样重试 | 先区分错误；新建重试任务，不覆盖原记录 |
| 怎样防重复 | Celery 是至少一次，外部副作用必须业务幂等 |
| 怎样讲故障 | 旧 Worker + 旧凭证 + 租约未释放，修复后安全接管 |

## 卡片 1：为什么把报价改成异步任务？

**一句话：** 报价包含文件解析、模型调用和 n8n 工作流，耗时长且可能失败，异步化可以让请求快速返回，并支持进度、取消和恢复。

### 项目映射

- `POST /api/v1/quote/jobs` 先创建 `queued` 任务并持久化输入。
- `quote_dispatcher.py` 根据配置分发到 Celery、进程内线程或同步执行。
- 当前生产模式使用 Celery；前端通过任务查询和事件流获取进度。
- 结果先进入人工预审，确认后才允许正式下发。

### 关键取舍

- 优点：前端不必长时间占用 HTTP 连接，任务可追踪、取消和重试。
- 代价：必须额外处理状态一致性、重复投递、超时和 Worker 失联。

### 30 秒回答

> 报价链路包含 Excel 或图片解析、模型调用和 n8n 工作流，单次执行时间不稳定，所以我没有让前端一直等待同步请求，而是先持久化任务，再交给 Celery 执行。前端只负责查询状态和订阅事件，结果生成后进入人工预审。这样改善了用户等待体验，也为取消、重试、超时处理和故障追踪提供了基础。

---

## 卡片 2：怎样管理任务状态和进度？

**一句话：** 用状态表示任务结果，用阶段和事件解释执行过程，避免把所有信息塞进一个 `status` 字段。

### 项目映射

```text
queued → running → succeeded
                ↘ failed
queued/running → canceled
queued/running → timed_out
```

- `quote_jobs` 保存状态、阶段、失败阶段、结果摘要、耗时和 `trace_id`。
- `quote_job_events` 按顺序保存结构化执行事件。
- 等待 n8n 时默认每 15 秒写入一次心跳事件并更新 `updated_at`。
- 成功和失败路径都会写入 `duration_ms`、`finished_at` 和最终事件。

### 关键取舍

- `status` 保持少而稳定，方便查询和统计。
- 详细步骤放在 `stage + event` 中，便于排障但不会让状态机失控。
- 心跳只能证明近期有进展，不能单独证明 Worker 仍拥有任务执行权。

### 证据

- 报价速度看板已使用真实 `duration_ms`；历史 121 条成功任务的零耗时记录曾完成修复和回填。
- 测试覆盖任务事件、运行耗时和等待 n8n 时的心跳。

### 30 秒回答

> 我把任务最终状态和执行过程分开建模。`quote_jobs` 只保存 queued、running、succeeded、failed 等稳定状态，具体执行到文件读取、模型调用还是预审生成，则通过 stage 和顺序事件记录。每个任务还有 trace ID、失败阶段和耗时，因此拿到一个任务 ID，就能还原它在哪里失败、用了多久以及是否需要重试。

## 卡片 3：失败、取消和重试怎样处理？

**一句话：** 失败任务不在原记录上重新执行，而是保留原任务并创建新任务，使每次尝试都可审计。

### 项目映射

- 文件读取、额度、鉴权、网关返回和未捕获异常都有明确失败阶段。
- 管理员可把长时间无更新的活动任务标记为 `timed_out`，接口默认阈值为 30 分钟。
- 取消时先请求撤销 Celery 任务，再把数据库任务置为终态；Runner 每轮都会重新读取状态。
- 只有 `failed / canceled / timed_out` 可以重试。
- 重试会生成新的 `job_id`，并在首个事件中记录原任务 ID。
- 169 行确认清单曾按每批 20 行拆成 9 批；缺失行补报后仍未返回时生成占位行，未人工补价前禁止下发。

### 关键取舍

- 新建重试任务比覆盖原任务多占一条记录，但能保留每次尝试的输入、错误和结果。
- 自动重试只适合临时故障；权限、额度、数据错误等确定性问题应快速失败。
- 当前重试路径会复制主要输入和附件，但仍应继续验证确认需求行等关联数据是否完整继承。

### 30 秒回答

> 我把错误分成可重试和不可重试两类。临时网关错误、超时可以重试，但权限、额度和输入问题直接失败。重试时不覆盖原任务，而是创建新的任务并记录来源任务，这样每次尝试都有独立审计记录。大清单还会分批执行和定向补报，最终缺失项生成占位并转人工，避免为了“任务成功”而悄悄丢行。

## 卡片 4：Celery 重投时怎样避免重复业务结果？

**一句话：** Celery 的 late ack 提供的是“至少执行一次”，真正避免重复副作用还需要业务幂等。

### 项目映射

- Celery 配置了 `task_acks_late=True`、`worker_prefetch_multiplier=1` 和任务时间上限。
- Redis 消息可见性超时至少为 300 秒，且大于任务时间上限。
- Runner 发现任务已经处于终态时会直接退出。
- 取消操作重复调用会返回已有取消结果。

### 当前边界

- 普通 `QuoteJob` 还没有原子领取和 `lease_token`，两个 Worker 极端情况下仍可能同时看到非终态任务。
- `/confirm_push` 已校验任务归属、完整性和人工确认条件，但目前没有统一幂等键；客户端重复提交仍可能造成外部重复推送。
- 因此面试时只能说“已有部分重复保护”，不能说“报价链已经实现 exactly-once”。

### 推荐补强

```text
幂等键 = quote_job_id + 确认内容哈希 + 操作类型
```

- 数据库建立唯一幂等记录。
- 首次请求进入 `processing`，成功后保存外部回执。
- 相同键、相同内容直接返回原结果。
- 相同键、不同内容返回 409。
- 调用 n8n 时继续透传同一个幂等键。

### 30 秒回答

> Celery 使用 late ack 后，本质上是至少执行一次，Worker 崩溃时消息可能被重新投递，所以不能依赖队列保证 exactly-once。当前系统会用任务终态阻止明显重复执行，但外部确认下发还需要业务幂等。我会用任务 ID、确认内容哈希和操作类型组成幂等键，保存处理状态和外部回执，使重复请求返回原结果而不是再次推送。

## 卡片 5：讲一次真实的 Agent 卡死故障

**一句话：** 任务卡死的根因不是模型慢，而是旧 Worker 使用旧 MCP 凭证，并且预执行异常没有持久化失败和释放租约。

### 故障链

```text
启动脚本记录了 Python 包装进程 PID
→ 重启后遗留旧 Worker
→ MCP 进程使用新的临时 JWT secret
→ 旧 Worker 携带旧 secret 调用 MCP，返回 401
→ 异常发生在进入 LangGraph 之前
→ 旧失败路径没有写入 run_failed，也没有释放租约
→ 前端长期看到 running / queued
```

### 修复

- Worker 自报真实 PID，启动器精确管理进程。
- Worker 启动时先执行 MCP 鉴权预检。
- LangGraph 前的初始化异常也持久化为 `run_failed`。
- 失败时释放 `lease_token`，在预算内允许新 Worker 接管。
- 使用 SQL Checkpoint 保留可恢复状态，并拒绝旧 token 的迟到写回。

### 结果证据

- 受影响任务由新 Worker 在第 2 次尝试接管。
- MCP 从 401 恢复为 200。
- 运行图谱累计 75 个事件。
- 最终进入 `waiting_human / human_review`。
- 相关 Agent 可靠性回归为 `45 passed`。

### 30 秒回答

> 我处理过一次 Agent 长时间卡在 running 的问题。排查后发现并不是模型超时，而是重启后遗留的旧 Worker 还持有旧 MCP 凭证，调用新 MCP 得到 401，同时异常发生在进入 LangGraph 之前，原失败路径没有释放租约。我修正了 PID 管理，增加启动鉴权预检，并让所有初始化异常都持久化失败和释放租约。之后任务由新 Worker 在第二次尝试安全接管，并从 Checkpoint 恢复到人工审核阶段。

## 高频追问：四个概念不要混

| 概念 | 回答 |
|---|---|
| 心跳 | 证明 Worker 或任务近期还在活动 |
| 租约 | 证明当前 Worker 仍拥有执行权 |
| Checkpoint | 记录接管后从哪里继续 |
| 幂等 | 保证重复执行不会产生第二次业务效果 |

记忆口诀：

> 心跳看活性，租约管所有权，Checkpoint 管恢复点，幂等管重复副作用。

## 当前项目结论

| 能力 | 普通异步报价 | 报价资料研判 Agent |
|---|---|---|
| 持久化状态与事件 | 已有 | 已有 |
| 心跳/进度 | 已有 | 已有 |
| 取消、超时、重试 | 已有 | 已有 |
| 原子领取与任务租约 | 尚未统一 | 已有 |
| Checkpoint 恢复 | 无图级 Checkpoint | 已有 SQL Checkpoint |
| 人工暂停与恢复 | 预审后人工确认 | `waiting_human` 可恢复 |
| 外部副作用统一幂等 | 待补 | 人工命令部分已幂等 |

面试表达边界：

> 报价中台已经具备异步任务生命周期和故障恢复基础；资料研判 Agent 进一步落地了租约、旧 Worker 写保护和 Checkpoint。外部确认下发的统一幂等仍是上线前需要补齐的可靠性工作。
