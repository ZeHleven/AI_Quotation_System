# 练习 09：后端综合系统设计、容量估算与故障排查面试实战

## 演练结论

本次以“长耗时、高风险 AI 报价系统”为案例，通过 35 项断言：

- 完整方案通过 18 个架构维度审查；
- 脆弱方案被识别出 18 个风险；
- 720 单/小时、平均占用模型 45 秒时，基础并发为 9；
- 加入 1.1 倍重试、1.5 倍突发和 70% 目标利用率后，需要 22 个模型并发槽；
- 正确诊断任务未分发、模型饱和、重复推送、缓存雪崩、慢 SQL 和 RAG 不安全降级；
- 证据不足时明确返回“无法归因”，不靠重启和猜测掩盖问题。

面试回答主线：

```text
先讲业务目标
→ 再讲数据流和事实源
→ 再讲失败、重复和并发
→ 再讲指标与验证
→ 最后讲取舍和未完成边界
```

---

## 1. 三分钟系统设计答案

> 我设计的是一个支持文本、图片和 Excel 的 AI 报价系统。FastAPI 负责鉴权、限流、输入校验和任务创建；耗时任务先写入 MySQL 并返回 202，再通过 Outbox 和消息队列交给 Worker。MySQL 保存任务、状态、事件、输入版本、报价结果和人工审计，Redis 只承担队列、限流和可重建缓存，不作为业务事实源。
>
> Worker 按任务类型拆池，调用文件解析、成本库、RAG、模型和 N8N。消息采用至少一次投递，所以 Worker 通过条件更新或租约获得唯一执行权，长任务保存 Checkpoint，外部下发使用稳定幂等键。暂时错误有限重试，持续故障通过超时、熔断、隔离和背压控制。
>
> 报价属于高风险结果，模型输出先经过逐行完整性、成本证据和引用检查，再由人工确认；无证据或占位未补价时禁止下发。全链路记录 Trace、阶段耗时、队列等待、重试和模型版本。
>
> 容量通过峰值任务量、服务时间、突发和重试估算，再用 P95/P99、错误率和队列年龄压测验证。当前项目已有异步任务、事件、成本证据、人工 Gate、模型熔断和 Agent 租约恢复；统一 Outbox、外部下发端到端幂等和正式生产 SLO 仍需上线前专项验证。

## 2. 一张架构图

```text
Client
  │ JWT / Idempotency-Key
  ▼
FastAPI
  ├─ RBAC / Tenant Scope / Rate Limit
  ├─ Object Storage：大文件
  └─ MySQL：Job + Event + Outbox
                    │
                    ▼
             Redis / Celery
                    │
        ┌───────────┼───────────┐
        ▼           ▼           ▼
     Parse       RAG/Model    Push Worker
     Worker       Worker       Worker
        └───────────┼───────────┘
                    ▼
        Preview + Evidence + Quality Gate
                    ▼
               Human Review
                    ▼
          Idempotent External Push
```

关键分工：

| 组件 | 责任 |
|---|---|
| FastAPI | 接口契约、鉴权、输入和任务创建 |
| MySQL | 业务事实、约束、状态、事件和审计 |
| Redis | 队列、限流、可重建缓存 |
| Worker | 耗时执行、Checkpoint、重试和取消 |
| Object Storage | 大文件及哈希引用 |
| RAG / Model | 证据检索和生成，不直接成为业务事实 |
| Human Gate | 控制高风险副作用 |

## 3. 必须守住的 18 个设计点

### 数据与一致性

```text
1. 长任务返回 202
2. MySQL 是任务事实源
3. Redis 不是唯一业务事实源
4. Job 与 Outbox 同事务
5. Consumer 原子领取
6. 长任务保存 Checkpoint
7. 外部副作用有幂等账本
```

### 故障与容量

```text
8. 重试有错误分类和上限
9. 全链路 Deadline
10. 队列有界并背压
11. 依赖按粒度熔断
12. 降级结果明确标记
```

### 业务与安全

```text
13. 高风险结果人工确认
14. Trace 与阶段指标
15. 租户和资源归属校验
16. 状态和人工决策可审计
17. 大文件不长期塞入热数据行
18. 完整性、证据和占位质量 Gate
```

注意：这是本题“长耗时、高风险报价”的约束，不是所有小型 CRUD 系统都必须一次采用全部组件。

## 4. 数据模型与不变量

核心模型：

```text
quote_jobs
quote_job_events
quote_job_requirement_rows
quote_preview_drafts
idempotency_records
outbox_events
quote_cost_evidence
```

关键不变量：

- `job_id` 唯一；
- 状态只能合法迁移；
- 同一任务只有当前租约持有者可以写回；
- 每条已确认需求行必须有结果或明确占位；
- 未补价占位不能下发；
- 同一副作用幂等键只产生一次业务效果；
- 人工修改保留前后快照；
- 降级结果必须带来源、版本和时间；
- 跨租户查询在数据库条件中受限。

面试时先说不变量，再说表和中间件，设计会更有逻辑。

## 5. 容量估算题

题目：

```text
峰值：720 个报价/小时
平均模型占用：45 秒
重试放大：1.10
突发系数：1.50
目标利用率：70%
```

### 第一步：转换到达率

```text
λ = 720 / 3600 = 0.2 单/秒
```

### 第二步：Little 定律

```text
基础模型并发 = 0.2 × 45 = 9
```

### 第三步：加入重试和突发

```text
峰值并发需求 = 9 × 1.10 × 1.50 = 14.85
```

### 第四步：保留利用率余量

```text
需要的并发槽 = ceil(14.85 / 0.70) = 22
```

结果：

```text
22 个槽时利用率 = 67.5%
21 个槽时利用率 = 70.71%
```

因此按题目假设选 22。

必须补充：

> 22 是估算，不是生产实测。还要验证 Provider 额度、P95 模型时间、Token 分布、批次大小、数据库连接、Worker 数、成本和质量。

## 6. 故障排查通用框架

```text
1. 定影响：用户、租户、接口、开始时间、数据风险
2. 先保护：冻结危险副作用、限流、摘流、暂停低优先级任务
3. 留证据：Trace、事件、指标、日志、变更、外部回执
4. 分层定位：入口 → DB → Queue → Worker → RAG/Model → Push
5. 提假设：每个结论至少有两到三条独立证据
6. 单变量验证：避免同时改多个配置
7. 受控恢复：小流量、可回滚、观察错误和积压
8. 数据核对：重复、遗漏、状态和第三方副作用
9. 根因修复：代码、约束、配置、容量或流程
10. 防复发：指标、告警、测试、演练和 Runbook
```

不要一上来：

- 重启全部服务；
- 清空队列；
- 删除失败记录；
- 无限增加重试；
- 没有证据就归因数据库或网络。

## 7. 六类事故答题卡

### 事故一：创建成功，但任务不开始

信号：

```text
任务持续创建
Outbox 未发送年龄 480 秒
Outbox pending 160
Broker 健康
Worker 90% 空闲
```

判断：

```text
Dispatcher 停滞
```

止血：

- 限制非核心新任务；
- 恢复或切换 Dispatcher；
- 使用原事件 ID 重发 pending Outbox。

根治：

- 告警最老未发送年龄；
- Dispatcher 高可用且安全抢占；
- 发布和消费均幂等。

不要把 Broker 健康直接等同于整个任务链健康。

---

### 事故二：队列增长，吞吐不再提升

信号：

```text
队列每分钟 +60
Worker 忙碌 99%
模型利用率 99%
数据库 CPU 25%
完成吞吐保持不变
```

判断：

```text
模型容量饱和
```

止血：

- 入口背压；
- 暂停低优先级批处理；
- 只在已评测前提下使用备用路由。

根治：

- 压测模型并发和批次；
- 拆分交互与批处理队列；
- 设置模型并发、Token 和成本预算。

队列只削峰，不创造模型吞吐。

---

### 事故三：Worker 恢复后重复推送

信号：

```text
Broker 重投 8 次
同一业务对象出现 3 个外部回执
幂等账本复用率 0
```

判断：

```text
外部副作用幂等缺口
```

第一动作：

```text
冻结受影响的推送入口
```

然后：

- 保留任务、事件、Broker 和第三方回执；
- 核对重复影响；
- 用 `operation + object + version` 建幂等键；
- 唯一账本保存首次回执，重放返回原结果。

准确表述：至少一次投递，通过幂等达到有效一次业务效果。

---

### 事故四：缓存命中骤降，数据库暴涨

信号：

```text
缓存命中率下降 65 个百分点
数据库 QPS 变成 5 倍
大量 TTL 集中在 1 秒内
```

判断：

```text
缓存雪崩
```

止血：

- 限制高成本回源；
- 安全场景返回明确标记的旧值；
- 热 Key 使用 SingleFlight 受控重建。

根治：

- TTL 加随机抖动；
- 热点逻辑过期；
- 监控 Miss 来源和重建并发。

---

### 事故五：数据库和连接池同时变慢

信号：

```text
数据库 P95 = 1200ms
Rows examined / returned = 8500
连接池等待 P95 = 640ms
```

判断：

```text
低效 SQL 占用连接，引起池等待
```

止血：

- 限制问题查询入口；
- 保存 SQL、参数和执行计划；
- 保护数据库并发。

根治：

- 修复 N+1；
- 按真实查询设计联合索引；
- 用代表性数据执行 `EXPLAIN ANALYZE`；
- 回归结果正确性和写入成本。

不能看到 Pool Wait 就盲目扩大连接池，否则可能把 MySQL 压垮。

---

### 事故六：RAG 故障，但回答仍显示正常

信号：

```text
RAG 错误率 48%
证据覆盖率 35%
回答“成功率”99%
降级标记率 0%
```

判断：

```text
不安全的静默降级
```

止血：

- 暂停自动下发；
- 标记“证据不可用”；
- 转人工审核。

根治：

- 强制证据覆盖 Gate；
- 监控引用有效率和无依据回答率；
- 演练 RAG 故障和恢复。

AI 系统的“接口成功”不等于“业务结果可信”。

## 8. 证据不足时怎么回答

场景只有：

```text
3 个用户反馈偶尔慢
平均延迟 180ms
```

正确答案不是：

```text
一定是数据库连接池不足
```

而是：

> 当前证据不足以归因。我会先确认受影响请求、时间窗和 Trace，对比正常窗口的 P95/P99、阶段耗时、队列年龄、连接池等待、模型延迟与最近变更。在保留证据前不做全量重启。

面试官通常更认可有证据边界的判断，而不是自信地猜错。

| 运行健康和告警 | `queue_health.py`、`ops_monitor.py` |

### 面试中应主动说明的边界

- 普通报价任务创建与 Celery 分发尚不是统一 Outbox 模型；
- 普通报价任务没有 Agent Runtime 同等级的租约与 SQL Checkpoint；
- 外部 `confirm_push` 的统一业务幂等契约仍需专项核对；
- 端到端 Deadline 和分阶段 P95/P99 仍可补强；
- 正式生产 SLO、容量压测和 Runbook 尚未完成；
- 当前系统完善前不正式投入生产。

说清边界不是减分，而是证明你能区分“已有代码”“建议方案”和“生产验收”。

## 10. 高频追问简答

### 为什么 MySQL 和 Redis 都要用？

> MySQL 保存任务、报价、权限和审计事实，依赖事务与约束；Redis 用于队列、限流和可重建缓存。Redis 故障不能让业务事实丢失或失去审计。

### 为什么需要队列？

> AI 报价耗时和失败率不稳定，队列让 API 快速返回并削峰。但它也带来重复投递、积压和双写，所以还需要 Outbox、幂等、状态机和背压。

### 能保证 Exactly Once 吗？

> 我不会声称端到端 Exactly Once。Broker 采用至少一次，数据库原子领取限制执行所有权，外部副作用用稳定幂等键和唯一账本保证重复调用不重复生效。

### 为什么不全部拆成微服务？

> 先按业务能力和数据责任建立模块边界。只有独立扩缩容、故障隔离、技术差异或团队协作有明确收益时才拆进程，否则会提前承担网络、版本、一致性和运维复杂度。

### 当前离生产还缺什么？

> 统一 Outbox 与外部副作用幂等、正式 SLO、真实容量和长稳压测、备份恢复演练、告警阈值、生产 Runbook，以及安全与权限复核。

## 11. 面试答题模板

### 系统设计题

```text
1. 澄清规模、延迟、风险、租户和审计
2. 画主链路，说明同步与异步边界
3. 明确事实源、数据模型和不变量
4. 处理重复、双写、失败、取消和恢复
5. 设计限流、超时、熔断、隔离和降级
6. 估算容量，说明指标、压测和背压
7. 补安全、人工 Gate、取舍和未完成边界
```

### 故障题

```text
影响范围
→ 先保护业务与数据
→ 保存证据
→ 分层看 RED / USE / Trace
→ 提出有证据的假设
→ 单变量验证
→ 受控恢复
→ 数据核对
→ 根因修复和防复发
```

### 项目题

```text
业务问题
→ 我的职责
→ 方案与关键实现
→ 指标、测试或运行证据
→ 取舍
→ 当前边界
```

## 15. 最后一页速记

```text
MySQL 管事实，Redis 管速度，Queue 管调度
状态机管生命周期，租约管写权限，Checkpoint 管恢复
Outbox 管 DB 与消息，幂等账本管重复副作用
Timeout 管一次等待，Deadline 管整条链路
限流管入口，熔断管故障依赖，隔离管资源边界
证据 Gate 管可信，Human Gate 管高风险动作
RED 看服务，USE 看资源，Trace 看单次链路
容量先估算再压测，极限值必须保留余量
排障先保护和留证据，再定位、恢复、核对、防复发
只讲能证明的结果，主动说明未完成边界
```

完成这项后，后端基础设施核心面试主线已经闭环；后续更适合进入模拟面试和针对薄弱题复盘，而不是继续增加零散概念。
