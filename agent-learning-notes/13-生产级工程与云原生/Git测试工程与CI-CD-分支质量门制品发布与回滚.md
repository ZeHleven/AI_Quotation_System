# Git、测试工程与 CI/CD：分支、质量门、制品、发布与回滚

## 核心结论

生产发布不是“把代码复制到服务器”，而是一条可重复、可验证、可审计、可回滚的流水线：

```text
需求
→ 分支与提交
→ Pull Request
→ 自动检查
→ 构建不可变制品
→ 部署测试环境
→ 验收与审批
→ 灰度生产
→ 指标观察
→ 全量或回滚
```

Git 保存变更历史，测试提供质量证据，CI 自动执行质量门，CD 把同一制品安全地交付到各环境。

## 1. Git 与分支管理

### 1.1 先理解工作区、暂存区和提交

```text
工作区修改
  ↓ git add
暂存区：本次准备提交的内容
  ↓ git commit
本地提交历史
  ↓ git push
远端分支
```

提交应满足：

- 一次提交只表达一个完整意图；
- 代码、测试和必要文档一起提交；
- 不混入无关格式化或临时文件；
- 提交信息说明“做了什么、为什么”；
- 密钥和生产数据永不进入 Git。

### 1.2 分支策略

| 策略 | 特点 | 适用场景 |
|---|---|---|
| Trunk-Based | 短分支、频繁合并、主干随时可发布 | 自动化成熟、发布频繁 |
| GitHub Flow | 功能分支 + PR + 主分支部署 | 大多数 Web/AI 应用 |
| GitFlow | develop、release、hotfix 等长分支 | 多版本并行、发布节奏固定 |

对于报价中台，更适合短生命周期 `codex/*` 功能分支，通过 PR 合入 `main`。长期大分支容易出现冲突、集成延迟和“只在我机器上能跑”。

### 1.3 Merge、Rebase 与 Cherry-pick

- Merge：保留分支合并关系，适合共享分支；
- Rebase：重写本地提交基线，使历史线性；不要随意重写他人正在使用的公共历史；
- Cherry-pick：选择性复制提交，适合少量补丁，不应替代正常合并；
- Revert：用新提交撤销旧提交，适合已共享历史；
- Tag：标记发布版本，便于审计和回滚。

### 1.4 Pull Request 与分支保护

主分支应考虑：

- 禁止直接推送；
- 至少一名评审；
- 要求 CI 状态检查通过；
- 处理失效评审；
- 限制强推和删除；
- 必要时要求签名提交或线性历史。

注意：工作流文件写了 `pull_request` 触发，并不能证明仓库已启用分支保护；必须到远端仓库设置中核实。

## 2. 测试体系

### 2.1 测试分层

| 层次 | 验证目标 | 特点 |
|---|---|---|
| 单元测试 | 函数、规则、状态转换 | 快、隔离、定位准 |
| 契约测试 | API、事件、模型输入输出结构 | 防止上下游协议漂移 |
| 集成测试 | 数据库、缓存、队列、对象存储协作 | 更真实、成本更高 |
| 端到端测试 | 用户关键路径 | 覆盖广、定位较慢 |
| Smoke Test | 部署后核心能力是否可用 | 少而关键 |
| 回归评测 | Prompt、RAG、Agent 质量是否退化 | AI 应用特有 |

测试金字塔的重点不是固定比例，而是：

> 大量快速稳定的底层测试，少量高价值的跨系统测试。

### 2.2 单元测试

适合测试：

- 价格计算；
- 权限判断；
- 状态机转换；
- 文档字段标准化；
- 重试与幂等规则；
- RRF、阈值和候选筛选等纯逻辑。

原则：

- 一个失败能明确指出哪条规则被破坏；
- 不依赖真实网络、时间和随机数；
- 外部模型、时间和存储通过可控适配器替换；
- 同一输入结果稳定。

### 2.3 集成测试

适合验证：

- SQLAlchemy 与真实数据库方言；
- Alembic 从旧版本升级到 head；
- Redis TTL、锁和并发；
- Celery 入队、消费、重试和死信；
- FastAPI 路由、鉴权和事务；
- 对象存储上传下载；
- RAG 服务与向量库的协议。

SQLite 测试通过不代表 MySQL 一定通过。涉及锁、事务隔离、索引和 JSON/文本类型时，应在 CI 或预发布环境增加对应数据库测试。

### 2.4 AI 应用的特殊测试

不要只断言模型生成文本完全相等。应分层验证：

- 输出能否解析并满足 Schema；
- 工具选择和参数是否正确；
- 引用是否能回溯到证据；
- 必填报价行是否完整；
- 幻觉、无答案和权限边界；
- 延迟、Token、模型费用；
- 固定评测集上的质量趋势。

对外部模型：

- 普通 CI 使用 Fake/Mock，保证稳定和低成本；
- 定时或候选发布运行真实模型评测；
- 保存模型、Prompt、知识库和代码版本；
- 低于阈值则阻断发布。

### 2.5 防止脆弱测试

常见反模式：

- 依赖测试执行顺序；
- 使用共享脏数据库；
- 用固定 sleep 等待异步结果；
- 断言无关文案细节；
- Mock 过度，真实协议从未验证；
- 失败后简单重跑，掩盖 flaky。

正确做法是等待可观测条件、隔离测试数据、固定随机种子，并把不稳定测试当缺陷处理。

## 3. CI：持续集成

CI 的目标是让每次变更快速得到可信反馈。

推荐流水线：

```text
Checkout
→ 固定运行时与依赖
→ 静态检查/编译
→ 单元测试
→ 集成测试
→ 前端构建
→ 镜像构建
→ 依赖和镜像安全扫描
→ 生成版本化制品与报告
```

关键原则：

- 使用 lockfile 和固定运行时版本；
- 缓存依赖，但不缓存错误产物；
- 最小化工作流权限；
- PR 与主分支都运行关键检查；
- 取消同一分支过期运行，节省资源；
- 失败即阻断合并；
- 构建结果可追溯到 commit SHA。

CI 不是测试命令集合，还包括质量门、报告、权限和制品治理。

## 4. CD：持续交付与持续部署

- 持续交付：任何通过质量门的版本都具备可发布性，生产发布可保留人工审批；
- 持续部署：通过全部检查后自动进入生产。

高风险 AI 业务更适合先采用持续交付：

```text
自动构建与测试
→ 自动部署预发布
→ 人工验收/审批
→ 小流量生产
→ 自动指标门
→ 全量
```

### 4.1 构建一次，到处部署

同一个 commit 只构建一次不可变制品，以版本号或 SHA 标识；测试、预发布和生产部署同一制品，只改变外部配置。

如果生产重新构建，就无法证明上线的是已经测试过的内容。

### 4.2 环境与配置

开发、测试、预发布、生产应隔离：

- 数据库与队列；
- 密钥和外部账号；
- 域名和回调；
- 模型配额；
- 日志与权限。

配置也要有 Schema 和启动校验，避免缺少变量后运行到中途才失败。

## 5. 灰度、回滚与降级

### 5.1 灰度发布

灰度不是“先发一台就算完成”，还需要：

- 明确流量或用户范围；
- 新旧版本兼容；
- 对照关键指标；
- 设定观察时长；
- 定义自动停止和回滚阈值。

AI 报价系统可观察：

- API 5xx 和 P95 延迟；
- 报价任务成功率、排队时间和超时率；
- 预审完整率、人工打回率；
- RAG 无答案率和引用有效率；
- 单次报价 Token 与成本。

### 5.2 回滚不是一个按钮

需要分别考虑：

| 对象 | 回滚方式 |
|---|---|
| 应用 | 切回旧镜像或旧版本 |
| 配置 | 恢复上一版本配置 |
| Feature Flag | 关闭新路径 |
| 数据库 | 优先前向修复；破坏性迁移很难逆转 |
| 消息 | 保持消费者前后兼容，处理已发送旧事件 |
| 知识库/Prompt | 切回上一已评测版本 |

回滚前先判断旧版本能否读取新数据。若不兼容，直接回滚可能扩大事故。

### 5.3 降级

当完整能力不可用时保留核心业务，例如：

- 向量检索异常时回退 BM25；
- 模型不可用时保存任务并提示稍后处理；
- 运营看板异常不阻断报价；
- RAG 无可靠证据时返回“无法确认”，而不是编造；
- 高风险自动操作切换人工审核。

## 6. 报价中台的真实映射

### 已具备

仓库已存在两个 GitHub Actions 工作流：

1. 后端 CI：
   - Python 3.12；
   - pip 依赖缓存；
   - 编译 `app` 与 `tests`；
   - 运行 `pytest -q`；
   - 对 `main`、`codex/**` 推送及面向 `main` 的 PR 触发；
   - 同分支新任务可取消旧任务。
2. 前端 CI：
   - Node.js 22；
   - `npm ci`；
   - `npm run build`；
   - 同样具备路径过滤和并发取消。

项目还具备：

- 大量后端自动化测试；
- Alembic 迁移规范；
- 功能开关；
- 健康检查；
- 多处业务验收与回归记录。

### 尚未被证实或尚未完成

- 工作流文件不能证明远端分支保护已经启用；
- 当前 CI 尚未构建、签名和扫描生产镜像；
- 尚无完整的预发布到生产自动 CD；
- 尚无基于 SLO 的自动灰度判定；
- 当前正式生产上线尚未发生；
- SQLite CI 不能完全覆盖 MySQL 的锁、方言和迁移风险。

## 7. 面试回答模板

### 如何设计 AI 应用的 CI/CD？

> PR 阶段先做编译、静态检查、单元和集成测试，再运行结构化输出、工具调用、RAG 证据与权限边界的离线评测。合并后构建一次不可变镜像并部署预发布，执行迁移检查和关键路径 smoke。生产先灰度，观察技术 SLO 与质量指标，满足阈值再全量；异常时关闭功能开关、切回旧制品，并单独处理数据库与消息兼容。

### 单元测试和集成测试如何划分？

> 业务规则、状态转换和纯计算放单元测试；数据库事务、Redis、队列、对象存储及 API 协作放集成测试。外部模型在普通 CI 中使用可控适配器，候选发布再跑真实模型评测，兼顾稳定性、成本和真实性。

### 如何避免上线后无法回滚？

> 使用不可变版本制品、配置版本化和功能开关；数据库采用 expand-contract；事件和 API 保持兼容窗口；发布前验证旧版本能读取新数据；Runbook 明确应用、配置、数据和 Prompt/知识库各自的回退动作。
