# 报价资料研判 Agent 长期项目记忆决策

日期：2026-07-30
结论：`deferred_not_justified`

## 当前已经存在的“记忆”

- LangGraph State：保存一次研判中的问题、工具结果、事实覆盖状态和Human-in-the-loop状态；
- SQL Checkpointer/运行事件：用于暂停、恢复和审计同一次Agent运行；
- RAG证据库：保存项目原始资料的可检索内容。

这些分别是运行状态、审计记录和外部知识，不应全部混称为长期Memory。

## 为什么现在不增加长期项目记忆

目前发现的质量问题是表格结构丢失、多事实覆盖和跨文档关系尚未验证，不是Agent忘记了过去会话。现在引入长期向量记忆会带来：

- 旧项目经验污染当前项目；
- 过期资料覆盖新版本资料；
- 人工判断与原始证据混在一起；
- 租户、项目和权限隔离复杂化；
- 召回结果难以说明来自原文还是历史推断。

因此长期Memory不能修复当前检索缺口，反而会使评测归因更困难。

## 何时重新评估

只有出现以下真实需求后才进入独立实验：

- 同一项目跨多次会话反复确认相同背景；
- 人工对Agent结论的修正需要在后续研判复用；
- 总经办形成稳定、版本化的项目判断偏好；
- 已建立项目/租户隔离、来源、有效期、撤回和版本覆盖规则；
- 能建立“有Memory/无Memory”的独立Development与Holdout。

## 如果未来实现

首版只保存结构化、可撤回的人工确认事实：

- `project_id / tenant_id`
- 事实或决策类型
- 原始证据引用
- 人工确认人和时间
- 适用版本、有效期和撤回状态
- 是否允许进入后续模型上下文

MySQL保存权威元数据和生命周期；长文本可放对象存储；向量库只做候选检索，不能作为最终事实源。任何Memory命中都必须向用户展示来源，且不得覆盖当前项目最新原始资料。

## 当前下一步

不开发长期Memory。先完成新跨文档Development数据，再判断选择性图扩展是否有必要；图扩展仍无法解决的、真正跨会话重复问题出现后，才重新开启Memory实验。
