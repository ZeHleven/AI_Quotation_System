# AI 权限、审计与人机治理：RBAC、工具授权、操作审计与人工兜底

## 核心结论

安全 Agent 的控制链应该是：

```text
用户身份
→ 角色与资源权限
→ Agent 可见工具集合
→ 工具参数与业务前置条件
→ 高风险人工审批
→ 下游系统再次鉴权
→ 执行结果校验
→ 不可抵赖审计
```

模型可以提出动作，但不能给自己授权。权限决定“能不能做”，审计回答“谁在何时做了什么”，Human-in-the-loop 控制“哪些高风险动作必须由人承担责任”。

---

## 1. 认证、授权与审计

| 控制 | 问题 |
|---|---|
| Authentication | 你是谁？ |
| Authorization | 你能对哪个资源执行什么动作？ |
| Audit | 实际发生了什么，依据和结果是什么？ |

三者不能互相替代：

- 登录成功不代表有权查看所有成本；
- 有权限不代表动作不需要审批；
- 有审计日志也不能事后弥补越权执行。

---

## 2. RBAC、ABAC 与资源作用域

### RBAC

用户通过角色获得权限：

```text
user → role → permissions
```

适合权限集合稳定、职责明确的系统。

### ABAC

根据属性动态判断：

- 用户部门；
- 项目归属；
- 数据密级；
- 时间和网络；
- 任务状态；
- 金额或风险等级。

### 资源级授权

仅检查“是否是业务员”不够，还要检查：

```text
subject：当前用户
action：read / update / approve / push
resource：quote_job / cost_item / project
scope：tenant / project / owner
context：状态、风险、时间、版本
```

生产系统通常是 RBAC 定义基础能力，再用资源归属和业务状态做细化判断。

---

## 3. 完整中介与混淆代理

所有敏感请求都要在真正执行的位置重新鉴权，不能只依赖前端隐藏按钮或上游 Agent 判断。

混淆代理风险：

```text
普通用户
→ 诱导 Agent
→ Agent 使用共享管理员凭证
→ 读取或修改用户本无权访问的数据
```

防护：

- 工具尽量携带用户身份或受限委托凭证；
- scope 绑定租户、项目、动作和有效期；
- 下游用真实资源重新校验；
- 不接受模型随意传入用户 ID 或项目 ID；
- 写操作使用幂等键和版本检查。

---

## 4. 工具最小权限

越权风险来自三种“过多”：

- 过多功能：给了不需要的删除、发送、执行能力；
- 过多权限：工具身份可访问过多资源；
- 过多自治：高风险动作无需人确认。

### 工具分类

| 等级 | 示例 | 控制 |
|---|---|---|
| 低风险只读 | 查询公开规范 | 限流、审计 |
| 受限只读 | 查询项目证据、成本 | 资源 scope、字段过滤 |
| 可逆写入 | 保存草稿、创建候选 | 幂等、版本、审计 |
| 高风险写入 | 下发报价、启用成本 | 人工确认、双重校验 |
| 不可逆/外部副作用 | 删除、付款、公开发送 | 默认禁用或多方审批 |

不要给模型万能 Shell、任意 SQL、任意 URL 抓取或管理员 Token。

### 工具执行前

```text
工具是否在本次白名单
参数是否符合 Schema
用户是否有动作权限
资源是否属于授权范围
任务状态是否允许
是否重复调用
是否超过预算
是否需要人工审批
```

### 执行后

- 返回值符合 Schema；
- 实际影响范围与计划一致；
- 写入数量和对象可验证；
- 外部回执保存；
- 失败进入明确补偿或人工处理；
- 审计事件追加写入。

## 5. 操作审计

### 最小字段

```text
audit_id
timestamp
trace_id / run_id / job_id
actor_user_id
roles_snapshot
delegated_agent / tool
action
resource_type / resource_id
request_version
sanitized_input_summary
authorization_decision
approval_id
result_status
error_code
downstream_receipt
```

### 审计与普通日志的区别

| 普通日志 | 审计日志 |
|---|---|
| 用于调试和运维 | 用于责任追踪和合规 |
| 可采样、可按容量清理 | 保留期和访问更严格 |
| 关注程序事件 | 关注主体、动作、资源和结果 |
| 格式可能随代码变化 | Schema 应稳定、版本化 |

审计日志应：

- 追加写入；
- 限制修改和删除权限；
- 时间可靠；
- 敏感字段脱敏；
- 可按用户、资源、动作和 Trace 查询；
- 重要动作对账下游回执。

记录全部原始 Prompt 并不等于审计完整，反而可能泄露隐私。

## 6. Human-in-the-loop

### 什么时候必须人工

- 下发报价；
- 启用成本底价；
- 删除或覆盖数据；
- 证据不足但影响重大；
- 低置信度金额或工程量；
- 权限或政策冲突；
- 模型输出无法通过校验；
- 需要对外发布或承担合同责任。

### 人工审核不是一个“确认”按钮

审核页面应展示：

- 动作和影响范围；
- AI 原始结果与最终候选；
- 证据和来源；
- 规则、模型、Prompt、知识版本；
- 风险和失败原因；
- 修改前后差异；
- 审批人和时间。

### 可恢复的人工决策协议

```text
Agent 保存 Checkpoint
→ 创建待审批记录
→ 人工基于固定版本审核
→ 提交 approve / reject / revise
→ 校验角色、状态、版本和幂等键
→ 恢复任务
→ 记录决策与执行结果
```

审批期间原始数据或策略发生变化时，应提示过期并重新评估，不能把旧批准无条件应用到新版本。

### 双人审批

是否需要双人审批取决于金额、合规和不可逆性，不应所有操作一刀切。高风险动作可采用发起人与批准人职责分离。

---

## 7. 审计指标与告警

关注：

- 拒绝和越权尝试；
- 高风险工具调用数；
- 人工批准、拒绝和修改率；
- 审批等待时间；
- 重复副作用；
- 无对应审计记录的下游动作；
- 同一用户异常频率；
- scope 过期或跨项目访问；
- 敏感字段进入日志的检测结果。

严重事件应能从下游回执反查到用户、Agent Run、审批和版本。

## 8. 报价中台的真实映射

### 已具备

- JWT 登录和统一 `get_current_user`；
- Token 包含 `role_version`，角色变化后旧 Token 可失效；
- `admin`、`system_admin`、`viewer` 等角色检查；
- 用户角色分配与角色事件；
- 成本库访问有独立 `cost_access_audit_logs`，记录用户、角色快照、路径、IP、Trace 和结果；
- Agent 使用只读 Tender Evidence MCP 与项目级短期 scope；
- Agent Trace 记录工具步骤、安全摘要和错误码；
- 报价预审、`confirm_push`、成本启用等存在人工门；
- 资料研判 Agent 有持久化 Human Decision、Checkpoint、版本检查和恢复流程；
- 多个写入动作使用状态约束、幂等或版本冲突检查。

### 尚需补强

- 不是所有模型、工具和后台动作都进入统一审计 Schema；
- 普通应用日志与审计日志的脱敏策略还未完全统一；
- 审计记录尚未形成独立防篡改存储或集中 SIEM；
- 部分服务仍使用共享服务身份，需要继续细化用户委托上下文；
- 尚缺统一的高风险动作分级、审批矩阵和定期权限复核；
- 异常授权和审计缺失的自动告警仍需补齐。

## 9. 面试回答模板

### 如何防止 Agent 越权调用工具？

> 模型只负责提出工具调用。Runtime 先按任务生成最小工具白名单，再校验参数、用户角色、资源归属和业务状态；工具使用短期 scope，下游服务重新鉴权；写入有幂等和版本检查，高风险动作必须人工批准。即使 Prompt Injection 成功，权限边界仍能阻断真实副作用。

### 审计日志应该记录什么？

> 至少记录用户和角色快照、Agent/工具、动作、资源、授权与审批依据、脱敏输入摘要、版本、结果、错误码和下游回执，并用 trace_id 串联。审计日志应追加写入、限制修改、设置保留和访问权限。

### Human-in-the-loop 怎样设计？

> 在高风险节点持久化 Checkpoint 和待审批快照，审核者查看证据、版本和影响后提交结构化决策。恢复时重新验证角色、任务状态、版本和幂等键；数据变化导致快照过期时要求重新审核。
