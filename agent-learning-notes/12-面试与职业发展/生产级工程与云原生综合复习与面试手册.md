# 生产级工程与云原生综合复习与面试手册

## 使用方法

这份手册不是命令大全，而是大厂 AI 应用开发岗位的复习主线。

建议每个主题至少能回答：

1. 它解决什么问题？
2. 核心机制是什么？
3. 生产风险是什么？
4. 在报价中台中如何体现？
5. 项目还有什么没做？

---

## 1. 一张图记住生产交付闭环

```text
代码变更
  ↓
Git 分支 + PR + 评审
  ↓
CI：编译、测试、评测、安全检查
  ↓
构建不可变镜像
  ↓
测试/预发布环境验证
  ↓
灰度发布 + 健康检查
  ↓
日志、指标、Trace、质量信号
  ↓
SLO / 错误预算判断
  ├─ 正常 → 全量
  └─ 异常 → 降级、回滚、复盘
```

Linux 是运行基础，Docker 提供标准运行单元，Kubernetes 在多节点场景协调运行单元，CI/CD 控制变更质量，可观测性与 SLO 控制运行风险。

## 2. 十三个主题速记

| 主题 | 一句话记忆 | 面试重点 |
|---|---|---|
| Linux | 从进程、端口、网络、依赖、资源、日志定位故障 | 排障顺序与安全操作 |
| Docker | 镜像是不可变模板，容器是隔离运行进程 | 网络、卷、健康、权限 |
| Kubernetes | 控制器持续让实际状态接近期望状态 | 对象、Probe、资源、发布 |
| CI/CD | 自动建立从变更到可信发布的质量门 | 不可变制品、环境、审批 |
| Git | 用可审计历史协作和控制变更 | 短分支、PR、保护、回退 |
| 单元测试 | 快速验证隔离的业务规则 | 稳定、精确、无真实依赖 |
| 集成测试 | 验证数据库、队列、API 等真实协作 | 方言、事务、迁移、协议 |
| Prometheus | 采集和查询低基数时序指标 | 类型、标签、RED、告警 |
| Grafana | 用数据源建立总览、下钻和告警视图 | 看板分层，不是采集器 |
| OpenTelemetry | 统一生成、传播和导出遥测 | Span、Context、Collector |
| 三大信号 | Metrics 找范围，Trace 找阶段，Logs 找细节 | 用同一上下文关联 |
| 灰度/回滚/降级 | 小范围验证、异常撤回、故障保核心 | 数据兼容和质量门 |
| SLA/SLO | 用用户体验指标约束可靠性 | SLI、错误预算、Burn Rate |

## 3. 高频概念辨析

### 镜像、容器、Pod

| 概念 | 定义 |
|---|---|
| 镜像 | 分层的只读运行模板 |
| 容器 | 镜像启动后的隔离进程 |
| Pod | Kubernetes 最小调度单位，可含多个协作容器 |

### Compose 与 Kubernetes

| Compose | Kubernetes |
|---|---|
| 主要面向单机多容器 | 面向集群调度 |
| 学习和运维成本低 | 平台复杂度高 |
| 适合开发、内网和中小部署 | 适合高可用、弹性和标准化发布 |
| 不自动提供跨节点自愈 | 控制器持续调谐期望状态 |

### Liveness、Readiness、Startup

| 探针 | 含义 |
|---|---|
| Liveness | 是否需要重启 |
| Readiness | 是否可以接流量 |
| Startup | 慢启动是否已完成 |

### CI、持续交付、持续部署

| 概念 | 含义 |
|---|---|
| CI | 持续合并并自动验证 |
| 持续交付 | 随时可发布，生产可人工审批 |
| 持续部署 | 通过质量门后自动进入生产 |

### Metrics、Logs、Traces

| 信号 | 最适合的问题 |
|---|---|
| Metrics | 是否异常、影响多大 |
| Logs | 具体发生了什么 |
| Traces | 一次请求经过哪里、慢在哪里 |

### SLI、SLO、SLA、错误预算

| 概念 | 含义 |
|---|---|
| SLI | 实际测量值 |
| SLO | 内部可靠性目标 |
| SLA | 对外承诺与责任 |
| 错误预算 | SLO 允许的失败空间 |

## 4. 生产级排障统一框架

无论是 Linux、Docker 还是 Kubernetes，都可以用同一思路：

```text
1. 影响范围：谁受影响、从何时开始
2. 最近变更：代码、配置、数据、依赖、流量
3. 入口信号：成功率、延迟、错误类型
4. 分层定位：入口 → 应用 → 队列 → 数据 → 外部依赖
5. 资源状态：CPU、内存、磁盘、连接池、配额
6. 关联证据：trace_id、任务 ID、版本、时间线
7. 控制损失：限流、隔离、降级、切流、回滚
8. 验证恢复：核心 SLI 恢复且无新副作用
9. 复盘防复发：测试、监控、Runbook、容量、架构
```

面试时先说框架，再结合具体故障展开，显得有生产思维。

## 5. 报价中台的真实能力矩阵

| 能力 | 当前状态 | 项目证据或边界 |
|---|---|---|
| Linux 运维 | 部分具备 | CentOS 承载 RAG 服务，已有健康、日志、备份思路 |
| Docker Compose | 已使用 | 编排 Milvus、etcd、MinIO、Redis、RAG API |
| Kubernetes | 未落地 | 只有迁移设计能力，不能说成项目经验 |
| Git 分支协作 | 已使用 | 使用 `codex/*` 分支和提交历史 |
| 后端 CI | 已具备 | GitHub Actions：Python 3.12、compile、pytest |
| 前端 CI | 已具备 | GitHub Actions：Node 22、`npm ci`、build |
| 完整生产 CD | 未落地 | 没有生产自动部署和制品晋级链 |
| 单元/接口测试 | 已大量使用 | pytest 覆盖业务规则、API 与回归 |
| 真实依赖集成测试 | 部分具备 | CI 主要使用 SQLite，MySQL 等仍需补强 |
| 结构化日志/关联 ID | 已具备 | FastAPI 统一 `X-Trace-Id`，多处记录 trace_id |
| Prometheus | 未落地 | 需要指标端点、采集、规则和告警 |
| Grafana | 未落地 | 已有业务看板，但不是 Grafana 运维体系 |
| OpenTelemetry | 未落地 | trace_id 不等于标准分布式 Span 树 |
| 灰度和回滚设计 | 部分具备 | 功能开关、RAG 蓝绿/降级与运维文档；无完整生产灰度 |
| SLO/错误预算 | 未落地 | 有指标基础，尚无正式目标和 Burn Rate 告警 |

诚实表达模板：

> 当前项目在这一能力上做到 A，并通过 B 验证；C 尚未落地。若进入生产，我会按 D 的顺序补齐，而不会把设计方案描述成已上线经验。

## 6. 报价中台的生产化目标架构

```text
开发者
  ↓ PR
GitHub Actions
  ├─ 后端测试
  ├─ 前端构建
  ├─ AI/RAG 回归评测
  └─ 镜像扫描与制品生成
        ↓
预发布环境
  ├─ Alembic 迁移检查
  ├─ API/RAG/异步任务 Smoke
  └─ 人工业务验收
        ↓
生产灰度
  ├─ FastAPI / Worker / RAG
  ├─ MySQL / Redis / Milvus / MinIO
  └─ Feature Flag 与兼容迁移
        ↓
OTel Collector
  ├─ Metrics → Prometheus → Grafana/Alertmanager
  ├─ Traces  → Trace Backend
  └─ Logs    → Log Backend
        ↓
SLO + 质量指标
  ├─ 通过 → 全量
  └─ 失败 → 降级/回滚
```

这是目标设计，不代表当前已经全部实施。

## 7. 一分钟项目介绍

> 我做的是 AI 智能报价中台。FastAPI 作为主网关，报价任务通过异步状态机执行，RAG 服务结合 Milvus、BM25 和 RRF 检索，成本库使用 MySQL 管理有效版本，前端提供预审和人工确认。
>
> 工程上，RAG 侧已经用 Docker Compose 管理服务、网络、卷、健康检查和日志轮转；仓库有后端与前端 GitHub Actions CI，自动运行编译、pytest 和前端构建；应用统一生成 X-Trace-Id，并有 readiness、任务耗时、降级和回归评测机制。
>
> 我不会把未完成的能力包装成已上线：当前还没有 Kubernetes、Prometheus/Grafana、标准 OpenTelemetry Trace 和完整生产 CD。下一步会先定义报价成功率和端到端延迟 SLO，再接入低基数指标和 Collector，用业务质量与技术指标共同驱动灰度发布。

## 8. 高频面试题与精简答案

### 1. Linux 接口超时怎么排查？

> 先确认影响范围和最近变更；再看进程、端口、本机健康检查、DNS和网络；然后检查数据库、队列等依赖及 CPU、内存、磁盘、连接池；最后用 trace_id 关联日志。恢复时优先降级、限流或回滚，恢复后补防复发措施。

### 2. Docker 数据为什么会丢？

> 容器可写层随容器删除可能丢失。持久数据应放卷或外部存储，但卷也不是备份，仍需独立备份和恢复演练。

### 3. 为什么不直接上 Kubernetes？

> Kubernetes 解决多节点调度、高可用、弹性和发布治理，但增加平台复杂度。当前单机内网规模先用 Compose 更经济，等可用性和独立扩缩容需求明确再迁移。

### 4. Kubernetes 如何让发布无损？

> Readiness 保证未就绪副本不接流量，滚动策略控制新旧副本比例，优雅终止处理在途请求，新旧版本保持 API 和数据兼容，并在观测窗口内根据指标继续或回滚。

### 5. HPA 为什么不能只看 CPU？

> AI 异步系统的压力可能体现在队列积压、最老等待时间和模型并发。只看 CPU 可能扩容太晚，也可能把数据库连接或供应商配额打满。

### 6. 如何设计测试分层？

> 业务规则和状态转换放单元测试；数据库、Redis、队列和 API 协作放集成测试；关键用户路径用少量 E2E 和部署后 Smoke；Prompt、RAG、工具调用和证据质量再用固定评测集回归。

### 7. CI 和 CD 的差别？

> CI 自动验证每次集成；CD 把通过验证的不可变制品交付到环境。持续交付可保留生产审批，持续部署则自动进入生产。

### 8. 如何做数据库安全发布？

> 采用 expand-contract，先增加兼容结构，再部署兼容新旧结构的代码，完成回填和切换后才删除旧结构。数据库回滚通常比应用回滚困难，应优先前向修复。

### 9. Prometheus 为什么怕高基数？

> 每组标签值都会形成时间序列。把 user_id 或 trace_id 当标签会导致序列数量、内存和查询成本爆炸；这些信息应进入日志或 Trace。

### 10. OpenTelemetry 有什么价值？

> 它统一遥测生成、语义、上下文传播和导出。应用通过 OTLP 发给 Collector，可集中做批量、重试、脱敏、采样和多后端导出，减少对具体观测厂商的耦合。

### 11. 如何定义异步任务 SLO？

> 以最终完成且满足基本质量门的任务为成功事件，而不是创建接口返回 200；同时定义端到端延迟目标、统计窗口和排除规则，再计算错误预算。

### 12. 灰度失败如何处理？

> 先停止扩大流量，判断是否能关闭功能开关或降级；对比新旧版本的技术和业务质量指标；必要时切回旧制品，同时检查数据库、消息和缓存是否兼容；恢复后再复盘。

### 13. 你项目里最大的云原生不足是什么？

> 当前缺少统一的 Prometheus/Grafana/OTel 观测闭环和正式 SLO，因此已有 trace_id 与业务看板还不足以支持自动灰度决策。我会优先补 SLI、低基数指标、告警和跨 FastAPI/Celery/RAG 的上下文传播。

## 9. 系统设计题答题模板

遇到“如何让 AI 系统生产可用”，按下面顺序回答：

1. **目标**：用户路径、吞吐、延迟、可靠性和安全要求；
2. **架构**：入口、应用、队列、数据、模型、RAG；
3. **可靠性**：超时、重试、幂等、隔离、降级；
4. **部署**：容器、资源、健康检查、弹性；
5. **变更**：Git、测试、CI、制品、迁移；
6. **发布**：灰度、质量门、回滚；
7. **观测**：日志、指标、Trace、业务质量；
8. **治理**：SLO、错误预算、告警、Runbook、复盘；
9. **边界**：当前方案的成本、风险和下一步。

## 10. 三轮复习法

### 第一轮：概念复述

每天 30 分钟，能脱稿解释十三个主题的一句话定义和核心区别。

### 第二轮：项目映射

对每个主题写三行：

```text
已经做了什么
证据在哪里
下一步补什么
```

### 第三轮：故障与取舍

重点练习：

- RAG 服务超时；
- 队列积压；
- 发布后错误率上升；
- 数据库迁移失败；
- 容器频繁重启；
- 模型供应商限流；
- 指标正常但用户说结果错误。

每题都按“影响—证据—定位—止损—恢复—复盘”回答。
