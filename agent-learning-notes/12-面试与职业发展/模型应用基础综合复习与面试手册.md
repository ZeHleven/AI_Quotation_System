# 模型应用基础综合复习与面试手册

## 使用方法

这部分的面试目标不是证明你会训练大模型，而是证明你能：

```text
理解模型怎样接收输入和生成输出
→ 为任务选择合适模型与参数
→ 控制结构、延迟、成本和风险
→ 把模型接入可观测、可回滚的生产系统
```

---

## 1. 一张图记住模型应用链路

```text
文本 / 图片 / 文档
        ↓
预处理 + Prompt + Chat Template
        ↓
Tokenizer / Multimodal Processor
        ↓
上下文预算与模型路由
        ↓
Prefill：处理全部输入
        ↓
Decode：逐 Token 生成
  ├─ KV Cache
  ├─ Temperature / Top-p
  └─ Streaming
        ↓
JSON Schema / Pydantic / 业务校验
        ↓
结果、用量、质量和 Trace
```

自部署时，中间的推理由 vLLM 等服务承载；调用外部 API 时，供应商管理 GPU 和推理引擎，应用仍要管理路由、上下文、校验、成本和观测。

## 2. 十二个主题速记

| 主题 | 一句话记忆 | 工程重点 |
|---|---|---|
| Transformer | 用注意力让 Token 交换上下文信息 | Q/K/V、因果 Mask、Prefill/Decode |
| Token | 模型处理的离散单元，不等于字或词 | 计费、窗口、Tokenizer 匹配 |
| 上下文窗口 | 单次推理的总 Token 预算 | 输入、RAG、工具、输出统一预算 |
| Prompt | 把业务任务翻译成模型指令 | 目标、数据、规则、失败策略、版本 |
| 结构化输出 | 用 Schema 把生成结果变成接口契约 | 模型约束 + 程序校验 + 业务校验 |
| Temperature/Top-p | 调整采样分布和多样性 | 不是准确率开关，按任务评测 |
| KV Cache | 缓存历史 K/V，避免 Decode 重算 | 提速但占显存，不是 Agent Memory |
| Streaming | 边生成边返回或持续发送阶段事件 | TTFT、断线、背压、最终校验 |
| 模型路由 | 在约束下选择满足门槛的模型 | 能力、风险、合规、健康度、成本 |
| 大小模型协同 | 小模型处理简单任务，大模型升级复杂任务 | 级联条件、验证、失败边界 |
| 量化与 vLLM | 低精度节省资源，高效引擎提高服务能力 | 质量回归、PagedAttention、批调度 |
| 多模态 | 把图像、音频、视频特征接入语言模型 | 预处理、视觉预算、证据和复核 |

## 3. Transformer 最小面试模型

现代生成式 LLM 多为 Decoder-only Transformer：

```text
Token Embedding
→ 多层因果自注意力 + MLP
→ 词表 logits
→ 选择下一个 Token
→ 重复直到结束
```

注意力：

```text
Attention(Q,K,V)
= softmax(QKᵀ / √dk + Mask)V
```

- Q：当前位置在找什么；
- K：历史位置如何被匹配；
- V：匹配后取走什么内容；
- Mask：生成时不能看到未来。

推理分两段：

- Prefill：并行处理输入，生成各层 K/V；
- Decode：逐 Token 生成，每一步复用 KV Cache。

## 4. Token、窗口与成本

上下文预算：

```text
系统指令
+ 历史
+ 用户输入
+ RAG
+ 工具定义/结果
+ 多模态输入
+ 预留输出
≤ 模型窗口
```

长上下文会同时增加：

- 输入费用；
- Prefill 延迟；
- KV Cache；
- 信息干扰；
- 注入风险。

面试表达：

> 我不会用字符数当精确 Token 数，而会按实际模型 Tokenizer 预估，调用后使用 usage 结算；超限前先去重、检索、压缩和预留输出，关键字段不能静默截断。

## 5. Prompt 与结构化输出

Prompt 最小结构：

```text
目标
+ 输入边界
+ 任务规则
+ 输出 Schema
+ 无答案/失败策略
+ 必要示例
```

可靠输出四层：

```text
Prompt 约定
→ JSON Mode
→ JSON Schema / 受约束输出
→ Pydantic + 业务规则
```

模型生成合法 JSON，不代表金额、权限、引用和业务完整性正确。

报价任务还要校验：

- 每条确认需求是否有输出；
- 工程量、单价和合计是否一致；
- 成本证据是否存在；
- 无底价项目是否进入人工确认；
- 用户是否有权操作。

## 6. 参数与 Streaming

### Temperature 与 Top-p

- Temperature 越低，分布通常越集中；
- Top-p 限定累计概率候选集合；
- 抽取、报价和工具调用通常低随机性；
- 创意任务可以增加多样性；
- Temperature 为 0 不代表完全可复现。

### Streaming

```text
模型 Token 流：直接转发生成增量
业务阶段流：发送解析、检索、执行等事件
```

Streaming 改善用户感知 TTFT，但不会自动减少总成本。还要处理断线、取消、代理缓冲、背压、事件顺序和最终校验。

## 7. 模型路由与大小模型协同

路由顺序：

```text
模态/工具/Schema/窗口/合规过滤
→ 质量门
→ 延迟与预算
→ 实时健康度
→ 选择模型
```

典型协同：

```text
规则或小模型做分类、抽取、粗排
  ├─ 校验通过 → 返回
  └─ 不确定/高风险 → 大模型
                         ├─ 通过 → 返回
                         └─ 不通过 → 人工
```

不能只用模型自报置信度决定升级；应依据 Schema、证据覆盖、规则、独立验证器和业务风险。

Fallback 也必须满足上下文、工具、Schema、Prompt 和数据合规要求。

## 8. 量化与 vLLM

### 量化

量化对象可能是：

- 权重；
- 激活；
- KV Cache。

低精度可降低显存和带宽，但不保证更快，也可能损害 Tool Calling、结构化输出和长文本质量。

### vLLM

核心记忆：

- PagedAttention：用块管理 KV Cache，减少碎片和浪费；
- Continuous Batching：完成请求退出，新请求动态加入；
- OpenAI 兼容服务：降低协议迁移成本；
- 还可支持 Streaming、量化、并行和结构化输出等能力。

API 兼容不等于能力和参数语义完全一致，仍要契约测试和灰度。

### 性能指标

| 指标 | 含义 |
|---|---|
| TTFT | 首 Token 等待 |
| TPOT/ITL | 后续 Token 间隔 |
| E2E | 总耗时 |
| Throughput | 单位时间处理或生成 Token |
| Goodput | 满足 SLO 的有效吞吐 |

## 9. 多模态

简化链路：

```text
图片/视频
→ 解码、缩放、切图或抽帧
→ 视觉编码
→ 与文本表示对齐
→ 语言模型生成
```

生产中要组合使用：

- OCR：清晰文字，便宜且易审计；
- 版面解析：表格和文档结构；
- VLM：图文关系、符号、场景理解；
- 规则：数值、金额和完整性；
- 人工复核：低置信度和高风险。

必须保存原文件哈希、页码、区域、预处理、模型版本和证据。

---

## 10. 质量、速度与成本

先设最低质量和安全门槛，再比较达标方案：

```text
每成功任务成本
= 所有模型、重试、校验和人工成本
÷ 最终成功任务数
```

报价系统不能只看通用问答准确率，还要看：

- 确认行完整率；
- 金额正确率；
- 证据有效率；
- 人工打回率；
- P95 总耗时；
- 单次成功报价成本。

模型 A 更贵更慢但质量没有明显提升，就不应默认使用。

## 11. 报价中台能力矩阵

| 能力 | 当前状态 | 真实边界 |
|---|---|---|
| Transformer/KV Cache 理解 | 已形成笔记 | 外部 API 下不直接控制 GPU Cache |
| Token 与窗口 | 部分具备 | 尚无统一精确 Token 预算器 |
| Prompt | 已大量使用 | 版本快照仍可进一步统一 |
| 结构化输出 | 已具备 | JSON Mode + Pydantic + 业务校验 |
| 生成参数 | 已使用 | 多为任务级低 Temperature |
| Streaming | 已具备业务 SSE | 不能全部称为模型 Token 流 |
| 模型网关 | 已有骨架 | 多供应商协议和计费未完全统一 |
| 模型路由 | 部分具备 | 主要按业务配置，未形成动态路由控制面 |
| 大小模型协同 | 未系统落地 | 已有规则、专用模型和强模型分工基础 |
| 多模态 | 已深度实践 | 图片/PDF/图纸仍需持续积累金标 |
| 量化 | 仅理解和候选方案 | 未用于生成模型生产服务 |
| vLLM | 未落地 | 当前主要调用外部模型 API |
| 成本/速度/质量 | 部分具备 | 已记录耗时和估算成本，精确 Token/TTFT 需补 |

## 12. 一分钟项目回答

> 报价中台不是让一个大模型包办所有工作。图片和图纸先经过预处理、OCR或视觉模型，文本任务按用途调用不同供应商模型，RAG 使用专用 Embedding、BM25、RRF 和重排，最终通过 Pydantic、金额、证据和需求行完整性校验。
>
> 工程上已有统一模型网关骨架，记录供应商、模型、耗时和熔断状态；结构化任务使用 JSON 输出并做应用侧校验；前端通过 SSE 展示任务阶段。
>
> 当前主要使用外部 API，没有把 vLLM、生成模型量化和 GPU 集群说成已落地经验。下一步会先统一 Token、上下文、TTFT 和成本口径，再用真实报价评测集设计大小模型级联；只有开放模型质量达标且数据、规模或成本产生明确收益时才评估自部署。

## 13. 高频面试题

### 1. Transformer 为什么适合大模型？

> 自注意力能直接建模序列中任意位置关系，训练阶段比循环结构更易并行，并能通过多层、多头和规模扩展学习复杂表示。生成阶段仍要逐 Token Decode。

### 2. Token 和字数有什么区别？

> Token 由模型专用 Tokenizer 切分，可能是字、子词、标点或字节片段。同一文本换模型后 Token 数可能变化，所以窗口和计费必须按实际 Tokenizer 计算。

### 3. 上下文越长越好吗？

> 不是。长上下文会增加 Prefill、KV Cache、费用和干扰。应检索相关证据、去重、压缩历史并为输出预留预算。

### 4. 如何保证 JSON 输出？

> 优先使用 Schema 约束或 JSON Mode，再用 Pydantic 校验结构，并执行金额、权限、证据和完整性业务校验。失败只做有限修复重试。

### 5. Temperature 越低越准确吗？

> 它主要控制采样多样性，不能弥补知识、上下文和逻辑问题。事实正确性要靠模型能力、RAG、工具和验证。

### 6. KV Cache 为什么只缓存 K/V？

> 历史 Token 的 K/V 会被后续每一步重复使用，而 Query 只服务于当前要生成的位置。缓存 K/V 可避免重复计算历史表示。

### 7. Streaming 有什么风险？

> 需要处理断线、取消、背压、代理缓冲和事件顺序；部分结构化结果不能当完整对象使用，最终仍要通过校验。

### 8. 模型路由如何设计？

> 先按能力和合规过滤，再根据风险、质量、延迟、预算和健康度选择；记录策略与实际模型；Fallback 必须满足同一关键契约。

### 9. 为什么要大小模型协同？

> 大量简单任务用小模型可降低成本和延迟，复杂或高风险任务再升级大模型。前提是升级条件可验证，否则误路由会损害质量。

### 10. 量化一定更快吗？

> 不一定。它通常省显存和带宽，但速度取决于硬件、Kernel、Batch 和序列长度，还可能有反量化开销。

### 11. vLLM 的核心价值是什么？

> 它提供高效 KV Cache 管理、持续批处理和在线服务能力，可提高并发与吞吐；但仍要治理鉴权、配额、SLO、模型版本和质量。

### 12. 多模态模型能直接读懂所有 PDF 吗？

> 不能。PDF 可能包含文本层、扫描图、表格和复杂版面，应先解析、分页、切图，再组合 OCR、VLM 和规则，并保留证据定位和人工复核。

### 13. 什么时候自部署模型？

> 当数据不能外发、流量稳定、外部成本或限流成为瓶颈，且开放模型在业务集上达标、团队具备 GPU 运维能力时再考虑。

### 14. 怎样评价一个模型最适合生产？

> 先看是否达到业务质量和安全门槛，再看 P95、每成功任务成本、稳定性、合规和可运维性，而不是只看参数量或公开榜单。
