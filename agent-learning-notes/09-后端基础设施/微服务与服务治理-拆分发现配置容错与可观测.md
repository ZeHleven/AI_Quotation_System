# 微服务与服务治理：拆分、发现、配置、容错与可观测

> 配套实战：[练习 06：微服务超时、重试、熔断、降级、健康检查与隔离实战](./练习记录/06-微服务超时重试熔断降级健康检查与隔离实战.md)

## 核心结论

微服务不是把代码目录拆成多个进程，而是让服务拥有清晰的业务边界、数据责任和独立运行能力。

拆分后会新增：

```text
网络不可靠
配置分散
版本兼容
数据一致性
服务发现
故障传播
部署运维
全链路排障
```

因此：

> 能用模块化单体解决时，先做好模块边界；只有独立扩缩容、团队协作、故障隔离或技术差异带来明确收益时，再拆服务。

---

## 1. 单体、模块化单体与微服务

| 形态 | 优点 | 代价 | 适合阶段 |
|---|---|---|---|
| 单体 | 开发部署简单、事务直接 | 边界容易混乱 | 早期验证 |
| 模块化单体 | 保留简单部署，建立领域边界 | 需要严格代码约束 | 大多数业务早中期 |
| 微服务 | 独立部署、扩缩容和故障隔离 | 分布式复杂度高 | 边界和规模明确后 |

不要以代码行数为唯一拆分依据。

---

## 2. 服务边界

常见边界依据：

- 业务能力；
- 数据所有权；
- 变化频率；
- 性能和资源特征；
- 安全等级；
- 团队责任。

AI 平台可能形成：

```text
身份与权限服务
报价任务服务
成本库服务
文件处理服务
模型网关
RAG 检索服务
通知服务
运营与观测服务
```

但当前是否拆分，要看实际部署、负载和团队，不必一次到位。

### 数据所有权

真正的服务边界要求：

- 一个服务负责某类事实的写入规则；
- 其他服务通过 API/事件使用；
- 不随意跨服务直接写对方表；
- 读副本或数据同步需要明确一致性。

“每个服务一个数据库”是强化边界的方式，不是没有例外的教条。

---

## 3. API Gateway

网关常负责：

- TLS；
- 身份验证；
- 路由；
- 限流；
- 请求大小限制；
- Trace ID；
- 统一日志；
- 灰度和版本路由。

不应把所有业务逻辑塞入网关。业务授权和资源归属仍由后端服务验证。

当前 FastAPI 主网关同时承担业务 API。随着规模增加，可以区分：

```text
边缘网关能力
业务应用服务
内部 AI 服务
```

但没有真实瓶颈时不必提前增加一层。

---

## 4. 服务发现与负载均衡

### 静态地址

适合少量固定内网服务，例如当前配置中的固定 RAG 地址。优点简单，缺点是变更和故障切换依赖配置。

### DNS/注册中心

实例动态变化时，需要：

- 注册；
- 心跳；
- 健康实例列表；
- 客户端或服务端负载均衡；
- 下线摘除。

负载均衡策略：

- 轮询；
- 最少连接；
- 加权；
- 一致性哈希；
- 按租户或会话粘性。

有状态会话会使扩容和故障切换更困难，应把权威状态外置。

---

## 5. 配置与密钥治理

配置分类：

| 类型 | 示例 | 治理方式 |
|---|---|---|
| 普通配置 | 超时、并发、功能开关 | 环境变量/配置中心 |
| 敏感配置 | API Key、数据库密码 | Secret 管理 |
| 业务规则 | 状态迁移、审批条件 | 代码或可审计规则 |
| 动态开关 | 灰度功能 | Feature Flag |

要求：

- 开发、测试、生产隔离；
- 密钥不写入 Git；
- 变更可审计；
- 配置有类型、默认值和校验；
- 动态更新失败时有安全默认；
- 不同服务明确配置所有者。

---

## 6. 健康检查

### Liveness

进程是否还活着。失败时可重启。

### Readiness

服务是否准备好接收流量。数据库或关键依赖不可用时，可暂时摘流而不一定重启。

### Startup

慢启动服务是否完成初始化，避免启动期间被误判死亡。

健康检查不能执行昂贵业务。也不能只返回固定 `200`：

- 数据库连接；
- Redis Broker；
- Worker；
- RAG；
- 对象存储；
- 外部工作流。

依赖状态要区分“核心不可用”和“可降级”。

---

## 7. 超时、重试、熔断、隔离

服务调用的保护顺序：

```text
超时：限制单次等待
重试：处理短暂错误
熔断：连续失败时停止放大故障
隔离：限制一个依赖占用的资源
降级：返回可接受的较弱结果
```

如果每个服务都盲目重试三次，三层调用可能把一次请求放大为 27 次下游请求。

治理要求：

- 只在明确的层重试；
- 总 Deadline 向下传播；
- 重试有退避和抖动；
- 连接池/线程池按依赖隔离；
- 熔断恢复采用半开探测；
- 降级结果明确标识。

---

## 8. 服务间数据一致性

跨服务不能依赖一个本地数据库事务包住所有操作。常见方式：

### 事件最终一致

事实服务提交后发事件，下游异步更新自己的读模型。

### Saga

把长业务拆成多个本地事务，每步有补偿或人工处理。

### Outbox

确保“写业务事实”和“产生待发送事件”在同一数据库事务中。

### 人工 Gate

高风险 AI 结果先保存草稿，人工确认后才执行正式副作用。报价预审就是典型方式。

补偿不是简单的数据库回滚。例如通知已经发送后，补偿可能是再发一条更正通知。

---

## 9. 可观测性

### 三大信号

| 信号 | 回答的问题 |
|---|---|
| Logs | 发生了什么离散事件 |
| Metrics | 整体趋势和异常程度 |
| Traces | 一次请求经过了哪些服务和阶段 |

统一字段：

```text
trace_id
request_id
task_id
tenant_id
user_id（脱敏）
service
version
stage
error_code
duration_ms
```

服务治理没有可观测性，就无法知道超时来自网关、队列、数据库、RAG 还是模型。

## 10. 发布治理

### 滚动发布

逐步替换实例，要求新旧版本兼容。

### 蓝绿发布

准备两套环境，一次切流，回滚快但资源成本高。

### 灰度/金丝雀

先让少量用户或流量使用新版本，用指标决定继续还是回滚。

### 数据库变更

采用 Expand-Contract：

```text
先新增兼容字段/表
→ 部署兼容新旧结构的代码
→ 回填
→ 切换读写
→ 观察
→ 最后删除旧结构
```

不能假设所有实例同时完成升级。

## 11. 报价中台映射

### 当前结构

```text
Windows：
  Vue / FastAPI 主网关

CentOS：
  N8N / Dify / RAGFlow / Milvus / RAG API

共享依赖：
  MySQL / Redis / 对象存储 / 外部模型
```

它已经具备多服务和双机部署特征。

### 已有治理基础

- `/health/ready` 检查数据库、Broker、Worker 等；
- `ops_monitor.py` 聚合 MySQL、Redis、Celery、RAG、MinIO 和 N8N；
- 功能开关控制阶段性能力；
- FastAPI 统一鉴权和路由；
- 任务、事件、`trace_id` 和耗时支持排障；
- RAG 集合采用蓝绿别名策略。

### 当前边界

- 固定内网地址仍依赖配置管理；
- 不是完整容器编排或 Service Mesh；
- 服务级 SLO、自动熔断和统一配置中心仍需按生产规模建设；
- 微服务拆分不应优先于正式生产 Runbook 和可观测闭环。

## 12. 面试回答

### 什么情况下拆微服务？

> 我会先建立模块化单体和清晰数据边界。只有某个能力需要独立扩缩容、故障隔离、独立发布，或者由独立团队维护时才拆服务。拆分后必须同时承担网络超时、版本兼容、数据一致性和可观测性成本，所以不会只因为代码量增长就微服务化。

### 怎样治理服务依赖故障？

> 每个外部调用先设置明确超时，再只对可恢复错误做有界退避重试；连续失败通过熔断停止放大，下游资源通过独立连接池或并发信号量隔离，核心能力不可用时走明确降级。Trace 和服务指标用于判断故障点，降级结果必须标注，不能把无 RAG 证据伪装成正常答案。

### 报价中台算微服务吗？

> 它是双机部署的多服务 AI 应用架构，FastAPI、N8N/Dify、RAG 和 Milvus 具有独立进程与调用边界，但目前没有必要包装成成熟微服务平台。我更关注已经落地的服务健康、异步任务、权限、事件和 Trace，以及正式生产前仍需补齐的 SLO、发布和故障演练。

## 13. 动手练习

1. 画出报价中台服务依赖图；
2. 为每条调用标出协议、超时、重试、事实源和失败影响；
3. 区分核心依赖与可降级依赖；
4. 设计 liveness、readiness 和 startup 检查；
5. 设计一次模型网关灰度发布；
6. 为一个跨服务操作设计 Outbox 或 Saga。
