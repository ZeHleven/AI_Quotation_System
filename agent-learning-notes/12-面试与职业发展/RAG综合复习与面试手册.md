# RAG 综合复习与面试手册

## 1. 先记住完整链路

```text
知识源
→ 解析与结构恢复
→ 清洗、去重和质量门禁
→ 结构感知切片
→ 元数据、权限和版本
→ Embedding 与多种索引
→ Query 理解、拆分、改写和路由
→ 向量 / BM25 / 精确匹配 / 结构化查询
→ RRF 融合、去重和 Rerank
→ 权限与有效版本复核
→ 上下文选择和证据引用
→ 基于证据生成或拒答
→ 离线评测、线上监控和反馈更新
```

一句话：

> 生产级 RAG 不是“文档切片后放进向量库”，而是让当前有效、用户有权访问的知识，被稳定检索、正确排序、可靠引用、持续评测和安全更新的工程闭环。

## 2. 14 个必会主题总表

| 主题 | 一句话掌握 | 生产重点 |
|---|---|---|
| PDF、Word、Excel、图片解析 | 不同格式用不同解析器，输出统一结构化 Block | 阅读顺序、表格关系、原始位置、置信度 |
| 清洗、切片和元数据 | 按业务信息单元切片，不只按固定字数 | 来源、页码、Sheet、版本、ACL、哈希 |
| Embedding 选型 | 用真实 Gold 集选，不只看公开榜单 | Recall、延迟、成本、部署和迁移 |
| 向量检索 | 召回语义相近和同义表达 | metric、维度、ANN、Top-K |
| BM25 | 召回精确术语、编号、型号和文件名 | 中文分词、稀有词、字段权重 |
| 混合检索 | 组合语义、字面、精确和结构化通道 | 先保证 Recall，再控制噪声 |
| RRF | 按排名融合不同分数尺度的结果 | 简单稳定，但仍需真实评测 |
| Rerank | 对候选重新判断 Query—文档相关性 | 精度、延迟、吞吐和候选池大小 |
| Query 改写 | 纠错、补术语、拆问题、生成多表达 | 防止偏离原意和噪声放大 |
| 多路召回 | 多通道构建高召回候选池 | 路由、去重、来源覆盖和成本 |
| 权限过滤 | 只召回当前用户可见的知识 | 预过滤、事实库复核、渲染再鉴权 |
| 更新与版本 | 正式知识有状态、有版本、可失效 | 增量、重建、回滚、active manifest |
| RAG 评测 | 分层评价解析、召回、排序、生成和业务结果 | Gold 集、消融、Holdout、Bad Case |
| 幻觉与无答案 | 证据不足就澄清、补资料或拒答 | Claim—Evidence、阈值、证据门 |

这 14 项可以归为四层：

```text
数据层：解析、清洗、切片、元数据、更新
检索层：Embedding、向量、BM25、混合、RRF、Rerank、Query
安全层：权限、版本、引用、无答案
治理层：评测、监控、反馈和发布
```

## 3. 最容易混淆的概念

| 概念 | 负责什么 | 不负责什么 |
|---|---|---|
| Embedding | 将 Query 和内容映射到向量空间 | 不保证事实正确或用户有权限 |
| 向量数据库 | 存储、索引和搜索向量 | 不是权威业务事实库 |
| BM25 | 根据词频和稀有度做字面相关性检索 | 不擅长同义表达和深层语义 |
| RRF | 融合多路候选排名 | 不重新理解 Query 与文档语义 |
| Reranker | 重算 Query 与候选的相关性 | 不能召回候选池外的证据 |
| 元数据过滤 | 限定时间、项目、状态和权限范围 | 不能替代服务端鉴权 |
| RAG | 为模型提供外部证据 | 不能彻底消除幻觉 |
| 结构化查询 | 精确筛选、计算和聚合 | 不适合模糊语义问题 |
| RAG Memory | 检索外部知识 | 不等于保存用户长期偏好 |

高频回答：

> 向量找意思，BM25 找字面，精确匹配找编号，SQL 管结构化事实，RRF 合并名次，Reranker 做精排，元数据限定范围，证据门决定能不能下结论。

## 4. 离线摄取链路

### 4.1 不同格式怎样解析

#### Word

恢复：

- 标题层级；
- 段落和列表；
- 表格；
- 页眉页脚；
- 图片、批注、脚注和修订；
- 文本框与浮动对象。

#### PDF

先分类：

| 类型 | 处理方式 |
|---|---|
| 原生文本 | 文本提取 + 版面恢复 |
| 扫描件 | OCR + Layout |
| 混合 PDF | 按页路由 |
| 复杂图表 | 区域裁剪 + 多模态模型 |

#### Excel

识别：

- Workbook 和 Sheet；
- Sheet 角色；
- 多行表头和合并单元格；
- 明细、说明、规则、汇总和参考行；
- 原始值、标准值、公式和缓存值；
- 原始行、列和单元格范围。

#### 图片

组合：

```text
原图
→ OCR
→ Layout / 区域检测
→ VLM 理解复杂图文关系
→ 规则校验
→ 低置信度人工确认
```

VLM 摘要是派生数据，不能替代原图。

### 4.2 统一解析合同

```json
{
  "block_id": "doc001_v2_p12_table02",
  "document_id": "doc001",
  "document_version": "v2",
  "modality": "table",
  "block_type": "excel_row",
  "text": "...",
  "structured_data": {},
  "source_locator": {
    "page": 12,
    "bbox": [82, 310, 1140, 650],
    "sheet": null,
    "row": null
  },
  "parser_version": "parser_v3",
  "confidence": 0.96,
  "acl": ["project:p001"],
  "status": "active",
  "content_hash": "..."
}
```

统一的是输出合同，不是解析过程。

## 5. 清洗、切片和元数据

### 清洗

- 去页眉页脚和模板噪声；
- 去重，但保留版本关系；
- 统一数字、单位、日期和符号；
- 修复 OCR 常见错误；
- 分离说明、汇总和正式内容；
- 标记低置信度、损坏和阻断内容；
- 保留原始值，不可只留清洗结果。

### 切片优先级

```text
业务信息单元
> 标题 / 条款 / 表格 / 逻辑行
> 段落
> 固定长度
```

固定字数只适合作为兜底。Chunk 过小会丢失条件和指代，过大会引入噪声并增加成本。

每个 Chunk 应继承：

- 文档和版本；
- 标题路径；
- 页码或 Sheet/Row；
- 权限；
- 生效时间；
- 相邻关系；
- 解析器和切片版本；
- 内容哈希。

## 6. Embedding 模型怎样选

不能只问“哪个模型最好”，要先明确：

- 中文还是多语言；
- 通用还是工程、法律等领域；
- 对称还是 Query—Passage 非对称检索；
- 最大输入长度；
- 向量维度和存储成本；
- 本地或 API 部署；
- CPU/GPU 延迟和吞吐；
- License、隐私和版本可获得性。

### 公平评测

第一轮固定：

- 语料和 Chunk；
- Query；
- 向量数据库；
- metric；
- ANN 参数；
- Top-K 和过滤条件。

只更换 Embedding，比较：

- Recall@K；
- Hit@K；
- MRR、nDCG；
- 困难负例错误率；
- 编码 P95；
- 吞吐、内存、索引大小和成本。

### 升级原则

不同模型的向量不应混用：

```text
新 Collection 全量重建
→ 校验维度、数量、哈希和权限
→ 影子查询
→ Gold 集回归
→ Alias 小流量切换
→ 观察
→ 全量切换或回滚
```

## 7. 在线检索链路

### 7.1 Query 理解、拆分与改写

识别：

- 意图；
- 编号、金额、型号、文件名；
- 时间、项目、版本和权限范围；
- 单跳、多跳或比较问题；
- 是否可由知识库回答。

改写方式：

- 纠正口语和错别字；
- 补充企业术语和简称；
- 拆分复合问题；
- 生成多个检索表达。

风险：

- 改写偏离原意；
- 自动补充错误实体；
- 多 Query 放大成本和噪声。

应保存原始 Query、改写结果、路由、候选和兜底原因。

### 7.2 检索路由

| Query 类型 | 推荐通道 |
|---|---|
| 条款号、日期、金额、型号 | BM25 + 精确匹配 |
| 风险、原因、影响和建议 | 向量检索 |
| 同时含精确标识和语义问题 | 向量 + BM25 + RRF |
| 精确字段、聚合和计算 | SQL / 受控 API |

不是每个问题都必须跑最贵的混合检索。

## 8. 向量、BM25、RRF 与 Rerank

### 向量检索

擅长同义表达和语义近似。注意：

- 模型维度必须与 Collection 一致；
- Query 和 Document 编码合同一致；
- 归一化方式与 COSINE/IP/L2 匹配；
- HNSW 等 ANN 参数要用真实数据校准；
- 向量 Top-K 不是最终证据。

### BM25

擅长：

- 条款号；
- 专业名词；
- 物料型号；
- 错误码；
- 文件名；
- 罕见关键词。

中文通常需要分词、词典和字段权重治理。

### 多路粗召回

```text
Vector Top-N
+ BM25 Top-N
+ 精确编号
+ 元数据过滤
+ 结构化查询
→ 候选池
```

粗召回追求高 Recall，不直接把全部候选塞进 Prompt。

### RRF

```text
RRF(d) = Σ 1 / (k + rank(d))
```

优势：

- 不要求向量分数与 BM25 分数同尺度；
- 简单、稳定、可解释。

局限：

- 只利用排名；
- 不理解候选能否真正回答 Query；
- `k` 和各路候选数仍需评测。

### Reranker

```text
粗召回候选
→ Query—候选重新打分
→ 排序
→ 选择少量高质量证据
```

如果正确证据没进候选池，Reranker 无法补救；如果已召回但排序差，它才可能有效。

## 9. 权限、版本和索引一致性

### 权限

```text
用户 / 租户 / 项目身份
→ 检索前 ACL 过滤
→ 多路召回
→ 回事实库复核
→ 上下文组装
→ 原文或引用打开前再次鉴权
```

注意：

- 权限不能只写进 Prompt；
- 向量库过滤不能替代业务服务鉴权；
- 缓存键要包含租户、项目和权限版本；
- 日志不能泄露敏感正文。

### 知识生命周期

```text
draft
→ validating
→ active
→ superseded / archived
→ deleted
```

只有通过校验且当前有效的版本进入正式检索。

更新时处理：

- 稳定文档 ID 和版本 ID；
- 旧 Chunk 失效；
- 删除传播；
- Embedding 或切片变化后的重建；
- 构建失败回滚；
- active manifest 原子切换。

向量库是可重建索引，不应成为唯一事实源。

## 10. 上下文、引用、幻觉与无答案

### 上下文选择

最终上下文不是机械取前 K 条，需要兼顾：

- 相关性；
- 证据完整性；
- 来源覆盖；
- 新旧版本冲突；
- 相邻 Chunk；
- Token 预算；
- 权限和时效。

### Claim—Evidence

关键结论应关联 Evidence ID：

```json
{
  "claim": "投标保证金应在合同约定时间内退还",
  "evidence_ids": ["doc3_v2_p18_c04"],
  "confidence": 0.91
}
```

应用层验证 ID、权限、版本和哈希，再渲染文件、页码和原文，避免模型编造引用。

### 无答案处理

出现以下情况应拒答、澄清或补资料：

- 无相关证据；
- 只有低相关候选；
- 必要字段缺失；
- 来源冲突；
- 证据已过期；
- 用户无权访问；
- 解析置信度不足；
- 高风险结论没有完整证据。

RAG 只能降低幻觉风险，不能从机制上消除幻觉。

## 11. 分层评测

### 解析层

- 文本、表格、字段和阅读顺序准确率；
- Excel Sheet/表头/行类型准确率；
- OCR 和视觉区域准确率；
- 原始位置追溯成功率。

### 切片层

- 关键事实完整率；
- 跨块问题覆盖；
- 重复率；
- 平均 Chunk 大小。

### 召回层

- Hit@K；
- Recall@K；
- Precision@K；
- 各通道召回贡献；
- 权限与版本正确率。

### 排序层

- MRR；
- nDCG@K；
- Top-1 / Top-K 命中；
- RRF 和 Rerank 前后增益。

### 生成与证据

- 答案正确率；
- Faithfulness；
- 引用完整率和支持度；
- 无依据结论率；
- 拒答准确率。

### 端到端与工程

- 业务任务成功率；
- 人工修正率；
- P50 / P95；
- Token 和调用成本；
- 超时、空召回和降级率。

### 正确实验方式

```text
仅 BM25
→ 仅向量
→ 向量 + BM25
→ 增加 RRF
→ 增加元数据过滤
→ 增加 Reranker
→ 增加 Query 改写
```

每次只改变一个主要因素，才能知道收益来自哪里。

## 12. 故障定位顺序

```text
答案错误
├─ 原始知识是否正确、当前、可访问
├─ 文档是否解析错
├─ Chunk 是否切断关键事实
├─ Query 是否理解或改写错
├─ 路由是否选错
├─ 正确证据是否进入候选
├─ 是否融合或排序靠后
├─ 权限/版本是否误过滤
├─ 上下文是否丢失或冲突
├─ 模型是否忽略证据
└─ 引用和证据门是否失效
```

快速判断：

| 现象 | 优先检查 |
|---|---|
| 正确证据完全没出现 | 解析、Chunk、Embedding、BM25、Query、Top-N |
| 候选中有但最终没用 | RRF、Reranker、Top-K、上下文预算 |
| 证据正确但答案错误 | Prompt、模型、Claim—Evidence、规则校验 |
| 引用打不开 | ID、版本、页码/Sheet/bbox、权限 |
| 总引用旧制度 | active 状态、索引更新、缓存和 manifest |
| 空召回突然增加 | 模型服务、Milvus、索引加载、路由和权限 |

## 13. 报价中台的真实 RAG 映射

### 13.1 先讲清数据边界

系统不是所有地方都使用 RAG：

| 场景 | 事实源与方法 |
|---|---|
| 正式报价价格 | 账户定额、企业定额和数据库规则 |
| 精确成本、数量和聚合 | MySQL / 确定性计算 |
| 招标文件、合同和非结构化资料 | Tender Evidence RAG |
| Excel 报价需求 | 结构化解析、标准化和人工确认 |
| 图纸与图片 | OCR、视觉证据和专项 Agent 流水线 |

价格是强一致结构化事实，不应把“向量相似”当作权威价格。

### 13.2 Tender Evidence RAG

```text
招标资料
→ 解析为 Evidence Block
→ MySQL active manifest 作为事实源
→ 独立 Milvus 集合 + BM25
→ Query Planner 拆分
→ exact / semantic / hybrid 路由
→ RRF 融合
→ MCP 返回候选
→ Agent 读取上下文
→ Evidence ID 和 manifest 校验
→ 证据门
→ 生成建议或要求补资料
```

当前配置：

- `maidalun1020/bce-embedding-base_v1`
- 768 维
- COSINE
- Milvus HNSW
- BM25 + jieba
- RRF，当前 `k=60`
- exact / semantic / hybrid 路由
- scoped token 和项目隔离
- Milvus 不可用时可降级关键词检索

### 13.3 已实现与边界

已实现：

- Word/PDF、Excel 和图纸相关的真实解析链路；
- MySQL 事实源与 active manifest；
- 向量、BM25、RRF 混合检索；
- Query 拆分和自适应路由；
- Evidence ID、版本、权限和读取审计；
- 评测框架和合成样本；
- 证据门与无答案处理。

仍需诚实说明：

- 当前 Embedding 没有经过完整多模型 Gold 集选型证明；
- 真实历史 Gold Evidence 基线仍需扩大；
- Cross-Encoder Reranker 尚未正式上线；
- Excel 标准化主要服务报价输入，不等于通用 Excel RAG；
- 图纸专项视觉链路不等于已经建设通用视觉向量检索；
- 不应虚构 Recall、MRR 或业务提升百分比。

## 14. 12 个高频面试问题

### 1. 为什么不能只用向量检索？

向量适合同义语义，但企业文档包含大量编号、型号、金额和文件名，BM25 或精确匹配更稳定。结构化事实还应走 SQL，所以需要按 Query 路由多种通道。

### 2. BM25 和向量检索怎样配合？

两路先独立召回，再使用 RRF 等方法融合排名；候选较多时可使用 Reranker 精排。最终收益必须通过消融实验验证。

### 3. RRF 和 Reranker 有什么区别？

RRF 按多路排名融合，不理解文本语义，成本低；Reranker 重新判断 Query 与候选的相关性，通常更精细但更慢。常见顺序是先 RRF，再 Rerank。

### 4. Chunk 多大最好？

没有通用数值。应根据问题粒度、文档结构、Embedding、Top-K、上下文窗口和延迟评测。优先按条款、表格和业务信息单元切片。

### 5. Embedding 模型怎样选？

使用真实 Gold Query—Evidence 集，在固定 Chunk、索引和参数下比较 Recall、MRR、nDCG、延迟、吞吐和成本，再结合语言、领域、部署与合规决定。

### 6. 换 Embedding 模型为什么要重建索引？

不同模型的向量空间不可直接比较，维度和分布也可能不同。应新建 Collection 全量编码、影子验证并通过 Alias 切换。

### 7. Excel 怎样进入 RAG？

先识别 Sheet 角色、表头、逻辑表格、字段、行类型和公式；明细按逻辑行继承表头切片，说明和规则按段落切片；保留 Sheet、Row、Cell、原值、标准值、版本和权限。

### 8. 图片怎样进入 RAG？

保存原图，组合 OCR、Layout 和 VLM 得到带 bbox 的区域证据；可以先文本化检索，只有真实评测证明有收益时才引入视觉 Embedding。最终结论必须能回到原图区域。

### 9. RAG 怎样做权限隔离？

将 ACL 写入事实对象和索引，检索前过滤，召回后回事实库复核，原文或引用打开前再次鉴权；缓存键包含租户、项目和权限版本。

### 10. 如何减少幻觉？

高质量解析和召回只是基础，还要做 Claim—Evidence、版本与权限校验、证据门、结构化输出和拒答。RAG 不能保证模型一定遵守证据。

### 11. 无答案怎么办？

当证据不足、冲突、过期或无权限时，返回不知道、澄清问题、请求补资料或转人工，不能通过降低阈值塞入噪声后强行回答。

### 12. 怎样评测 RAG？

分层测解析、Chunk、召回、排序、生成、引用和端到端任务；用 Development 调参、Holdout 验证、真实 Bad Case 回归，并记录所有模型、数据和参数版本。

## 15. 项目介绍的 30 秒答案

> 我的报价中台没有把所有数据都塞进向量库。正式价格和计算由 MySQL 与确定性规则负责，RAG 用于招标文件和合同等非结构化证据。资料解析后以 MySQL active manifest 作为事实边界，Milvus 只做可重建的语义索引；在线通过 Query Planner 拆分问题，按 exact、semantic、hybrid 选择 BM25、向量或双路 RRF，结果再校验项目、文档版本和 Evidence ID。Agent 必须实际读取上下文并通过证据门，高风险证据不足时补资料或转人工。当前系统已有真实混合检索与评测框架，但 Reranker 和大规模真实 Gold 基线仍是后续工作。

## 17. 三轮复习法

### 第一轮：记主链

`解析 → 清洗 → Chunk → 元数据 → Embedding/索引 → Query → 多路召回 → RRF/Rerank → 权限/版本 → 证据生成 → 评测`

### 第二轮：讲项目

对每个主题回答：

1. 报价中台哪里使用；
2. 为什么这样设计；
3. 防住了什么错误；
4. 当前没有实现什么。

### 第三轮：做追问

重点练习：

- 为什么不用纯向量；
- 为什么不用 RAG 查价格；
- 换模型怎样上线；
- 没召回怎样定位；
- 怎样防越权；
- 怎样证明 Reranker 有收益；
- 无答案为什么不能强行生成。
