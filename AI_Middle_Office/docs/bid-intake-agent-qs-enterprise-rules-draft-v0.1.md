# 旗胜投标机会研判规则初稿 v0.1

> 状态：业务与架构讨论稿，未启用，不替换当前 `qs_bid_decision_policy_2026_01`，不作为自动审批规则。
>
> 适用范围：旗胜公司装饰工程投标机会的初步筛选、深入研判与负责人决策参考。
>
> 形成日期：2026-08-09。

## 1. 规则目标与边界

本规则用于回答两个不同问题：

1. 当前机会是否值得继续投入时间进行跟进和研究；
2. 在已有资料与企业信息支持下，是否倾向参与投标。

Agent 只提供参考建议，不拥有批准、否决或自动提交投标的权限。最终业务决定由企业负责人作出。

系统必须遵守以下原则：

- 先使用甲方已提供的资料和企业已有数据完成尽可能多的分析；
- 资料不足不等于风险不利，也不等于项目安全；
- 没有事实证据的内容不得写成结论；
- LLM 推测只能转化为“待核实事项”，不能进入评分或触发红线；
- 非必要不要求向甲方补充资料；
- 只有缺少可能显著改变建议的乙方企业信息时，才向负责人集中提问；
- 所有结论必须能追溯到招标证据、企业数据、负责人确认或可复算公式；
- 战略价值不能覆盖违法违规、资质不满足、确定性亏损等硬红线；
- 每次研判必须绑定资料 Manifest、企业画像、企业规则和定额数据的版本。

## 2. 双层研判输出

### 2.1 机会初筛

初筛回答“是否值得继续投入跟进成本”，允许在资料不完整时生成。

初筛输出四档：

| 代码 | 名称 | 解释 |
|---|---|---|
| `continue_research` | 建议继续跟进 | 当前未发现确定性硬红线，机会具备进一步研究价值 |
| `continue_with_focus` | 建议重点核实后继续 | 存在可能改变方向的重点问题，应先低成本核实 |
| `low_priority` | 暂不建议继续投入 | 已有事实显示机会吸引力较低或风险明显偏高 |
| `insufficient_information` | 信息不足 | 现有资料不足以判断是否值得继续跟进 |

初筛不能使用“批准投标”“通过立项”等措辞。

### 2.2 深入研判

深入研判回答“是否倾向参与投标”，需要更高的事实覆盖，但仍然只是负责人参考。

深入研判输出四档：

| 代码 | 名称 | 解释 |
|---|---|---|
| `recommend_participation` | 建议参与 | 事实覆盖充分、无硬红线，综合条件达到建议线 |
| `conditional_participation` | 建议有条件参与 | 可以考虑参与，但必须满足明确条件或核实重点事项 |
| `not_recommended` | 暂不建议参与 | 已有充分事实显示风险或收益不符合当前规则 |
| `insufficient_information` | 关键信息不足 | 不能形成可靠的参与倾向 |

## 3. 事实、证据与判断合同

### 3.1 允许使用的事实来源

| 来源代码 | 来源 | 使用规则 |
|---|---|---|
| `tender_evidence` | 招标文件、合同、清单、图纸、答疑、补充协议 | 必须引用文件版本、页码/Sheet、证据区块 |
| `enterprise_data` | 企业定额、资质、成本、客户、历史项目等结构化数据 | 必须记录数据集和版本 |
| `owner_confirmed` | 企业负责人明确确认的信息 | 必须记录确认时间和原始回答 |
| `verified_calculation` | 基于已知输入的可复算结果 | 必须保留公式、输入、单位和结果 |
| `historical_analogy` | 本企业历史类似项目 | 只作参考，不能替代当前项目事实 |
| `verified_external` | 可信且可追溯的公开信息 | 必须记录来源、发布日期和检索时间 |

以下内容不能作为事实：

- 模型常识性猜测；
- 无法定位出处的总结；
- 未验证的网络传言；
- 其他企业的数据；
- 仅因“行业通常如此”形成的当前项目结论；
- 历史项目结果对当前项目的直接类推。

### 3.2 每条研判发现的最小结构

```json
{
  "finding_id": "finding-uuid",
  "dimension": "payment_cashflow",
  "finding": "付款节奏偏后，存在资金占用风险",
  "finding_type": "rule_based_judgment",
  "support_status": "partially_supported",
  "severity": "high",
  "evidence_refs": [],
  "enterprise_data_refs": [],
  "calculation": null,
  "applied_rule_ids": [],
  "missing_inputs": [],
  "limitations": "当前不能计算具体峰值垫资金额",
  "recommended_action": "正式报价前补充资金计划"
}
```

`support_status` 只允许：

- `supported`：结论所需关键事实均有可靠来源；
- `partially_supported`：可以形成有限判断，但不能扩展到完整结论；
- `conflicted`：不同有效来源相互冲突；
- `unsupported`：没有足够证据，不得作为结论；
- `not_assessed`：当前没有执行该项分析。

### 3.3 冲突处理

出现冲突时按以下优先级处理：

1. 最新且明确生效的补充协议、澄清或答疑；
2. 正式合同条款；
3. 最新版招标文件；
4. 工程量清单和图纸；
5. 招标公告或邀请函；
6. 负责人补充说明；
7. 历史经验或外部信息。

优先级只能解决“文件效力已明确”的冲突。无法判断哪个版本有效时，必须保留冲突，不得由 LLM 自行选择。

## 4. 信息覆盖与研判等级

### 4.1 覆盖率计算

每个维度拥有固定权重。维度达到以下条件之一才计入“已覆盖权重”：

- 评分为 `favorable`、`acceptable`、`adverse` 或 `critical`，且有合格证据；
- 维度明确标记为“不适用”，并具有可核实原因。

`unknown`、`unsupported`、`conflicted` 和 `not_assessed` 不计入已覆盖权重。

```text
evidence_coverage = 已覆盖维度权重 / 全部适用维度权重 × 100%
```

未知维度不按 0 分处理，避免把“没资料”伪装成“不利”；但覆盖不足会限制系统可以输出的建议等级。

### 4.2 研判等级

| 研判等级 | 覆盖要求 | 允许输出 |
|---|---:|---|
| `scan` 快速扫描 | 无最低覆盖要求 | 已确认事实、明显风险、资料缺口 |
| `preliminary` 初步研判 | ≥ 30% | 机会初筛建议 |
| `standard` 标准研判 | ≥ 70% | 深入研判建议，但关键维度仍受门禁 |
| `deep` 深度研判 | ≥ 85% | 更完整的参与倾向与条件清单 |

覆盖率达到阈值不代表结论自动可靠；硬红线、关键维度缺失和证据冲突仍需单独检查。

## 5. 研判维度与建议权重

本初稿将原 11 个因素收敛为 8 个业务维度，避免保证金、资料准备度等因素重复计分。

| 维度 | 权重 | 核心问题 | 主要来源 |
|---|---:|---|---|
| 合规、资质与准入 | 15% | 是否合法合规，核心资质、业绩、证书和准入条件能否满足 | 招标资料、企业资质 |
| 范围与成本可控性 | 15% | 范围、清单、图纸、界面和材料标准是否足以支持成本判断 | 招标资料、清单、图纸 |
| 利润与价格空间 | 15% | 风险调整后的项目收益是否可接受 | 企业定额、成本数据、报价条件 |
| 付款与现金流 | 15% | 回款节奏、垫资峰值、保证金和质保金是否可承受 | 合同条款、资金模型 |
| 合同与法律责任 | 15% | 责任是否对等，违约、结算、变更和争议条款是否可接受 | 合同、招标文件 |
| 工期、技术与供应链 | 15% | 工期、技术、材料、地域和资源要求是否可实现 | 图纸、清单、技术规范、企业能力 |
| 甲方信用与项目真实性 | 5% | 客户付款可信度、项目资金和招标真实性是否存在重大风险 | 内部历史、可靠外部信息 |
| 战略价值与中标可能性 | 5% | 是否具备客户、区域、案例或中标价值 | 项目背景、企业战略 |

权重合计 100%。

## 6. 五档评价与综合分

| 档位 | 分值 | 含义 |
|---|---:|---|
| `favorable` | 100 | 明显有利，且证据充分 |
| `acceptable` | 75 | 风险处于可接受范围 |
| `adverse` | 40 | 明显不利，需要条件、谈判或风险准备 |
| `critical` | 0 | 命中硬红线或接近不可承受 |
| `unknown` | 不计分 | 无法基于事实评价 |

综合分只在已覆盖维度内归一化：

```text
observed_score = Σ(已知维度权重 × 档位分值) / Σ(已知维度权重)
```

报告必须同时展示 `observed_score` 和 `evidence_coverage`。禁止只展示高分而隐藏低覆盖率。

## 7. 硬红线初稿

硬红线只能由 `supported` 的事实或可复算结果触发。`unknown`、历史类比和未经验证的外部信息不能触发硬红线。

### 7.1 合规与诚信红线

命中任一项，深入研判输出 `not_recommended`：

- 明确要求或实质涉及围标、串标、商业贿赂、虚假材料或其他违法行为；
- 必须通过伪造资质、业绩、人员证书或授权才能满足准入；
- 明确要求违法转包、违法分包且无法通过合法方案消除；
- 企业或项目依法受到禁止参与该类投标的有效限制。

存在疑点但没有充分事实时，输出“重点核实”，不能直接认定违法。

### 7.2 核心资质与准入红线

命中任一项，深入研判输出 `not_recommended`：

- 强制资质、业绩、人员证书或信用条件在投标截止前确定无法满足；
- 招标文件禁止联合体或其他合法补足方式，且企业自身不能满足；
- 必须条件与企业现有状态存在不可修复冲突。

仅“尚未找到企业资料”属于未知，不触发红线，应按需询问负责人或查询企业资质库。

### 7.3 确定性亏损红线

风险调整后项目利润率定义为：

```text
(不含税合同收入 - 直接成本 - 项目间接成本 - 资金成本 - 风险准备金)
/ 不含税合同收入
```

建议初始阈值：

| 风险调整后利润率 | 档位 |
|---:|---|
| ≥ 8% | `favorable` |
| 5%～7.99% | `acceptable` |
| 0%～4.99% | `adverse` |
| < 0% | `critical`，触发硬红线 |

只有成本输入覆盖主要项目、计算口径明确时才允许触发亏损红线。仅有招标控制价或企业定额局部匹配时，不得推导“项目亏损”。

### 7.4 不可承受现金流红线

建议使用“预计峰值净资金占用”而不是仅看某一条付款比例。

在尚未完成真实项目校准前，采用以下暂定阈值：

| 峰值净资金占合同额比例 | 档位 |
|---:|---|
| ≤ 10% | `favorable` |
| 10%～20% | `acceptable` |
| 20%～30% | `adverse` |
| > 30% | `critical`，触发硬红线 |

同时满足以下情形之一，可评为 `critical`：

- 峰值资金需求超过企业负责人明确确认的单项目资金上限；
- 月度或节点累计支付长期低于已完产值 50%，且无预付款、保函或其他有效保障；
- 质保金比例超过合同额 10%，或释放时间、条件完全不明确；
- 现金保证金、履约保证和其他不可用资金合计超过合同额 15%，且无法使用保函替代。

无法计算峰值资金占用时，只能评价付款条款本身，不得输出具体垫资金额。

### 7.5 合同责任红线

以下条款若明确不可谈判且有可靠证据，可评为 `critical`：

- 乙方承担无限责任或违约责任没有任何累计上限；
- 甲方可以单方任意调价、拒绝确认已完成工程量或无依据拒绝结算；
- 重大工程变更不调整价款和工期，且范围本身明显不确定；
- 付款完全以第三方付款为前提，同时乙方没有有效保障；
- 争议、验收或结算机制实质上使乙方无法主张基本合同权利。

建议初始违约责任参考：

| 逾期违约责任 | 初始判断 |
|---|---|
| 日违约金 ≤ 合同额 0.05%，累计上限 ≤ 5% | 通常可接受，仍需结合工期 |
| 日违约金 0.05%～0.1%，或累计上限 5%～10% | `adverse` |
| 无累计上限、累计上限 > 10%，或日违约金 > 0.1% | 原则上 `critical` |

具体项目仍需结合工期长度、可归责条件、顺延机制和甲方责任综合判断。

### 7.6 甲方信用红线

以下事实可触发 `critical`：

- 企业内部正式黑名单；
- 与本企业存在超过 90 天且无合理解决安排的重大逾期款；
- 本企业历史合作中存在已确认的恶意拒付、重大欺诈或严重违约；
- 经可靠来源确认项目主体、资金来源或招标行为存在重大真实性问题。

公开网络负面消息、名称相似企业记录、模型推断不能单独触发红线。

### 7.7 明显无法履约红线

以下事实可触发 `critical`：

- 关键技术、资质或不可替代材料要求确定无法满足；
- 关键材料交付周期已超过可用施工窗口，且不存在等效替代；
- 经可复核的基准工期测算，要求工期压缩超过 35%，且没有可行的资源或工序方案；
- 项目地域、施工条件或资源需求超过企业明确确认的承载上限，且无法通过合规分包或外部资源解决。

仅凭 LLM 判断“工期看起来很紧”不能触发红线。

## 8. 条件性风险初稿

以下因素通常不会单独产生 `not_recommended`，但应进入 `conditional_participation` 的条件清单：

- 工程量清单、图纸或界面不完整，导致范围和成本存在较大不确定性；
- 主要材料品牌受限、供应周期长或存在单一来源；
- 付款比例偏低，但可通过预付款、保函、节点拆分或价格补偿缓解；
- 违约责任偏重，但存在明确谈判空间；
- 工期压缩 20%～35%，但可能通过资源投入解决；
- 项目金额明显高于企业常见承接区间；
- 异地施工导致管理、差旅、供应和税务成本增加；
- 甲方历史信息不足，但未发现可靠负面事实；
- 中标概率较低，投标成本较高；
- 资料截止时间过短，可能影响报价和技术响应质量。

每个条件必须写成可执行表达：

```text
风险：月度进度付款比例偏低。
参与条件：争取将累计支付提高至已完产值70%以上，或取得等价的预付款/资金保障。
责任人：企业负责人。
最晚确认节点：正式报价提交前。
```

## 9. 战略与机会因素

以下因素可以提高“继续跟进”的优先级，但不能覆盖硬红线：

- 重点客户或有明确复购机会；
- 进入重点区域或新业务领域的标杆项目；
- 能形成可公开展示的代表案例；
- 与现有项目、供应链或客户资源存在明显协同；
- 竞争格局有利，中标概率较高；
- 项目规模与企业能力高度匹配；
- 付款、工期或合同条件明显优于同类项目。

战略价值最高只占总分 5%，如企业负责人认为某类战略项目需要更高权重，应通过新规则版本调整，不能由模型临时加分。

## 10. 决策逻辑初稿

### 10.1 机会初筛

按顺序执行：

1. 如有已确认硬红线，输出 `low_priority`，并列出红线证据；
2. 如覆盖率低于 30%，输出 `insufficient_information`；
3. 如存在可能改变方向的关键问题，输出 `continue_with_focus`；
4. 如已知维度未见重大不利，且存在至少一个明确机会因素，输出 `continue_research`；
5. 如已知维度整体不利、投标成本较高且无明确战略价值，输出 `low_priority`；
6. 其他情况输出 `continue_with_focus`。

初筛允许只给方向，不得伪装成完整参与建议。

### 10.2 深入研判

深入研判前必须满足：

- 覆盖率不低于 70%；
- 合规、资质与准入维度不是 `unknown`；
- 付款与现金流、合同责任、工期履约不存在未解决的 `conflicted`；
- 利润无法评估时，只允许输出 `conditional_participation` 或 `insufficient_information`，不得输出无条件建议参与。

按顺序执行：

1. 任一已确认硬红线：`not_recommended`；
2. 覆盖率不足或关键维度未知：`insufficient_information`；
3. `observed_score ≥ 75` 且没有 `adverse` 的关键维度：`recommend_participation`；
4. `observed_score ≥ 60`，或存在可缓解的关键 `adverse`：`conditional_participation`；
5. `observed_score < 60` 且覆盖率充分：`not_recommended`。

输出 `recommend_participation` 时也必须显示剩余风险，不使用“安全”“无风险”等绝对措辞。

## 11. 缺失信息与负责人提问策略

### 11.1 默认行为

- 先完成当前资料能够支持的分析；
- 不因一般性缺失阻断初筛；
- 不自动要求向甲方索取资料；
- 缺失甲方资料时说明影响与建议获取时点；
- 优先查询企业现有数据库和历史资料；
- 必要时再询问企业负责人。

### 11.2 向负责人提问的准入条件

只有同时满足以下条件才允许提问：

1. 问题属于企业自身信息或负责人可以直接确认的信息；
2. 现有企业数据无法回答；
3. 答案可能改变硬红线、主要风险档位或最终建议；
4. 不能通过低成本的自动计算或检索获得；
5. 问题表达具体，可以直接回答。

每轮最多集中询问 3 个问题，按“对结论影响 × 获取成本”排序。

### 11.3 缺失信息的报告格式

每个缺失项必须包含：

- 缺失事实；
- 影响的分析维度；
- 当前仍可得出的有限结论；
- 缺失导致不能得出的结论；
- 建议来源：企业内部、甲方资料或可信外部来源；
- 是否值得现在获取；
- 建议获取的最晚业务节点。

## 12. 企业数据使用规则

### 12.1 企业定额库

- 只使用当前有效状态的企业定额；
- 必须记录定额条目、版本、地区、时间和匹配方式；
- 同名不同规格不得静默合并；
- 未命中定额不能由相似条目直接代替真实成本；
- 定额只能支持已覆盖清单项的成本参考；
- 覆盖不完整时不得推导完整项目利润率；
- AI 推断价不能写回 active 定额。

### 12.2 历史项目

- 历史项目事实需先结构化并人工确认；
- 类似项目只能提供经验提示和风险线索；
- 历史利润率不能直接作为当前项目利润率；
- 历史甲方评价必须保留项目、时间和事实依据；
- 项目结束后的结果先进入候选区，确认后再用于后续研判。

### 12.3 企业规则更新

- Agent 不得根据一次反馈自动修改硬红线；
- 负责人可显式“保存为企业规则”；
- 新规则必须生成新版本，不能原地修改历史版本；
- 新版本只影响后续创建的研判，历史报告保持原规则；
- 规则调整应通过历史项目回放后再启用。

## 13. 报告最小结构

每份报告至少包含：

1. 项目与资料概况；
2. 研判等级、证据覆盖率和资料截止时间；
3. 机会初筛或深入研判建议；
4. 建议成立的适用范围和限制；
5. 已确认硬红线；
6. 最重要的三个风险；
7. 最重要的三个机会因素；
8. 八个维度的档位、证据和缺失信息；
9. 条件性参与清单；
10. 事实冲突；
11. 值得获取的补充信息；
12. 不值得当前索取的资料；
13. 企业定额、企业规则和历史项目引用；
14. 资料 Manifest、规则版本、企业画像版本和报告版本。

## 14. 禁止性规则

Agent 不得：

- 在没有成本数据时编造利润率；
- 在没有资金模型时编造垫资金额；
- 将控制价、投标价和合同收入混为一谈；
- 因未知信息直接认定项目高风险或低风险；
- 把类似项目经验当作当前项目事实；
- 根据名称相似判断甲方信用；
- 根据单一条款忽略补充协议或上下文；
- 用总分覆盖硬红线；
- 用战略价值覆盖违法、资质、亏损等硬红线；
- 自动批准、自动否决或自动提交项目；
- 未经负责人确认自动改变企业规则；
- 隐藏证据冲突、检索失败或分析失败；
- 输出无法追溯来源的确定性陈述。

## 15. 开发验收规则

首版开发至少满足以下验收条件：

- 任意报告结论可以展开查看证据；
- 删除或失效证据后，相关结论不能继续显示为 `supported`；
- 未知维度不按 0 分惩罚，但会降低覆盖率；
- 低覆盖高分不能输出 `recommend_participation`；
- 未知信息不能触发硬红线；
- 已确认硬红线不能被高总分覆盖；
- 无清单和成本数据时不能输出项目利润率；
- 无资金计划时不能输出具体峰值垫资金额；
- 初筛资料不足时仍能生成有限报告；
- 每轮向负责人提问不超过 3 个；
- 新文件或补充协议加入后生成新 Manifest 和报告版本；
- 历史报告使用原绑定规则和数据版本回放；
- Agent 任何工具、解析或检索失败均在报告中显式降级；
- 最终建议始终标记为企业负责人参考，不产生批准状态。

## 16. 需要真实项目校准的参数

以下数字只是开发初始值，不代表企业负责人已经批准：

- 8% / 5% / 0% 利润率分档；
- 10% / 20% / 30% 峰值资金占用分档；
- 50% 月度或节点累计支付红线；
- 10% 质保金红线；
- 15% 保证金及担保资金占用红线；
- 0.05% / 0.1% 日违约金参考线；
- 5% / 10% 累计违约责任参考线；
- 20% / 35% 工期压缩参考线；
- 30% / 70% / 85% 研判覆盖率阈值；
- 75 / 60 综合评分阈值；
- 八个研判维度的权重。

正式启用前，应至少选择 10～20 个历史项目进行只读回放，包括：

- 实际参与且盈利的项目；
- 实际参与但亏损或回款困难的项目；
- 当时放弃且后来证明判断合理的项目；
- 当时放弃但可能错失机会的项目；
- 资料明显不完整的早期机会；
- 命中单一硬红线但战略价值较高的项目。

比较规则建议与企业当时决定、最终结果之间的差异，再形成 `v0.2`。

## 17. 与现有策略的关系

现有 `qs_bid_decision_policy_2026_01` 继续保持 `draft`，不得直接切换生产状态。

后续开发不建议在原 schema 上直接追加字段，而应先设计 `bid_decision_policy_schema_v2`，重点支持：

- 初筛与深入研判双层输出；
- 未知与不利分离；
- 已知权重归一化评分；
- 硬红线的证据充分性要求；
- 分维度覆盖率；
- 条件性参与清单；
- 企业画像、定额和规则版本绑定；
- 缺失信息的影响与获取价值；
- 只提供参考、不产生批准状态。

在 `v0.2` 业务规则完成历史回放前，不应修改 active policy、不应迁移数据库，也不应重构正式运行图。
