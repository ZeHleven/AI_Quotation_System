# BIZ-2w-5 自由文本同名不同规格拆行与工程量识别修复

> 状态：已完成代码层验证，待当前环境手工验收  
> 日期：2026-05-29  
> 阶段：内网验证阶段，`PUBLIC_ACCESS_ENABLED=false`  
> Alembic：不需要

## 1. 背景

真实输入：

```text
石膏板吊顶 9.5mm，8㎡、石膏板吊顶 12mm，8㎡
```

预审结果出现：

- 第一行工程量显示为 `0.00`，单位为空；
- 第二行变成“无匹配项目”占位；
- 同名不同规格没有稳定拆成两条可报价行。

定位后发现自由文本前置成本上下文存在两个问题：

- 文本拆行只按换行、分号拆，没有按顿号 `、` 拆分多项需求；
- 数量单位识别会把 `9.5mm` 误识别为 `9.5 m`，导致真正工程量 `8㎡` 没有作为主工程量。

## 2. 本阶段目标

- 将 `、` 串联的自由文本需求拆成独立需求行；
- 避免把 `mm` 中的 `m` 当成米单位；
- 同一段中存在规格厚度和工程量时，优先取最后一个真实“数量 + 单位”作为工程量；
- 将 `9.5mm`、`12mm` 提取为规格，辅助同名不同规格成本条目匹配。

## 3. 实现内容

`quote_cost_context` 调整：

- `QUOTE_ITEM_SPLITTER` 增加顿号 `、`；
- `QUANTITY_UNIT_PATTERN` 中的米单位改为 `m(?!m)`，避免误吃 `mm`；
- 一段文本中出现多个数量单位时，取最后一个作为工程量；
- 新增毫米规格提取，把 `9.5mm` / `12mm` 写入 source row 的 `spec`。

## 4. 验证结果

```text

```

覆盖：

- `石膏板吊顶 9.5mm，8㎡、石膏板吊顶 12mm，8㎡` 被拆成两条源需求；
- 两条源需求工程量均识别为 `8`，单位为 `㎡`；
- 两条源需求规格分别识别为 `9.5mm` 和 `12mm`；
- 同名不同规格成本条目可分别命中对应成本项；
- 既有成本参考优先、AI 改写防护和 AI 备注一致性回归保持通过。

## 6. 手工验收建议

输入：

```text
石膏板吊顶 9.5mm，8㎡、石膏板吊顶 12mm，8㎡
```

预期：

- 预审应出现两条有效行；
- 两条行工程量均为 `8`，单位为 `㎡`；
- 不应出现“9.5m”工程量误识别；
- 9.5mm 和 12mm 应作为规格参与成本依据判断；
- 若仍无对应 active 成本条目，应按无底价人工确认流程处理，而不是把第二行变成不明占位。

## 7. 回滚方式
