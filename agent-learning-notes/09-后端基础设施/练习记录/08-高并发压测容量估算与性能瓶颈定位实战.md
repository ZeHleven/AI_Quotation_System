# 练习 08：高并发压测、容量估算与性能瓶颈定位实战

## 实验结论

本次使用确定性的离散事件模拟，对 API、数据库、模型和结果处理四个阶段执行阶梯压测，通过 21 项断言。

核心结果：

```text
模型阶段理论容量：30.77 RPS
满足 P95 < 500ms 的最高实验负载：30 RPS
按 70% 余量规划的安全容量：21 RPS

30 RPS：P95 205.33ms，超时率 0%
35 RPS：P95 2754.57ms，超时率 87%
40 RPS：P95 5832ms，超时率 93.75%
```

40 RPS 下的单变量对照：

```text
数据库加速 2 倍：P95 只改善 0.15%
模型并发 4 → 6：P95 改善 96.67%，超时率降为 0%
```

N+1 对照：

```text
每请求 11 次数据库查询：P95 2307.33ms，超时率 91.56%
改成 1 次批量查询：P95 12ms，超时率 0%
```

结论：

> 性能优化不是“哪里都加缓存、线程和机器”，而是先用吞吐、长尾、排队和利用率找到容量最小的阶段，再做单变量优化。

## 2. 先定义 SLO 和负载

本次假设的 SLO：

```text
P95 ≤ 500ms
超时率 ≤ 1%
```

负载模型：

```text
开放流量：按固定 RPS 到达
持续时间：20 秒
阶梯：10 / 20 / 25 / 30 / 35 / 40 RPS
```

模拟链路：

```text
API
→ Database
→ Model
→ Postprocess
```

各阶段理论容量：

| 阶段 | 并发 | 平均服务时间 | 理论容量 |
|---|---:|---:|---:|
| API | 16 | 3ms | 5333.33 RPS |
| Database | 8 | 15ms | 533.33 RPS |
| Model | 4 | 130ms | 30.77 RPS |
| Postprocess | 8 | 10ms | 800 RPS |

单阶段近似：

```text
capacity ≈ concurrency / average_service_time
```

系统容量取最小值，因此理论瓶颈是 Model。

## 3. 阶梯压测结果

| 入口 RPS | P50 | P95 | P99 | 超时率 | 排空吞吐 | 模型利用率 | 模型 P95 排队 |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 10 | 154ms | 194ms | 194ms | 0% | 9.96 | 32.40% | 0ms |
| 20 | 154ms | 194ms | 194ms | 0% | 19.87 | 64.77% | 0ms |
| 25 | 154ms | 194ms | 194ms | 0% | 24.82 | 80.96% | 0ms |
| 30 | 154ms | 205.33ms | 205.33ms | 0% | 29.76 | 97.09% | 37.33ms |
| 35 | 1514.57ms | 2754.57ms | 2878.57ms | 87% | 30.57 | 99.68% | 2600ms |
| 40 | 3132ms | 5832ms | 6070ms | 93.75% | 30.61 | 99.72% | 5671ms |

### 容量拐点

30 RPS 时模型已达到 97.09% 利用率，但排队仍较短。

超过理论容量后：

```text
入口 35 → 排空吞吐 30.57
入口 40 → 排空吞吐 30.61
```

入口增加了，实际吞吐几乎不再增长；新增请求只进入队列：

```text
35 RPS 结束时积压 89
40 RPS 结束时积压 189
```

这就是饱和：

```text
吞吐不再增长
+ 排队持续增长
+ P95/P99 急剧恶化
+ 超时率上升
```

## 4. 为什么平均延迟不够

平均值会被大量正常请求稀释，用户体验更应该观察：

- P50：典型请求；
- P95：大多数用户的长尾；
- P99：接近故障边缘的请求；
- Max：极端诊断；
- 超时率：是否突破业务承诺。

压测报告不能只写：

```text
平均响应 200ms
```

还应写：

```text
P50 / P95 / P99
错误率 / 超时率 / 限流率
入口 RPS / 实际吞吐
队列长度 / 最老任务年龄
资源利用率 / 饱和度
```

AI 任务还应拆：

```text
队列等待
首 Token
生成耗时
RAG
Tool
结果校验
总耗时
```

## 5. Little 定律

公式：

```text
平均并发 L = 吞吐 λ × 平均停留时间 W
```

25 RPS 实验：

```text
实际排空吞吐 λ = 24.8164 RPS
平均停留时间 W = 0.157988s
λ × W = 3.9207
测得平均在途请求 = 3.9207
最大在途请求 = 5
```

用途：

### 估算并发

如果每秒进入 20 个任务，平均耗时 5 秒：

```text
平均在途任务 ≈ 20 × 5 = 100
```

### 估算模型资源

峰值每小时 120 个报价，每个占用模型 60 秒：

```text
平均模型并发 ≈ 120 × 60 / 3600 = 2
```

再加入 P95、突发、重试和安全余量。

Little 定律描述平均关系，不自动告诉你 P99、队列策略或错误率。

## 6. 用排队时间定位瓶颈

40 RPS 时各阶段 P95 排队：

```text
API = 0ms
Database = 0ms
Model = 5671ms
Postprocess = 0ms
```

同时 Model 利用率为 99.72%。

按 USE 方法：

```text
Utilization：99.72%
Saturation：P95 排队 5671ms
Errors：超时率 93.75%
```

证据共同指向 Model。

若只看总 P95，只能知道系统慢；拆分阶段排队后，才能知道慢在哪里。

## 7. 单变量优化

### 对照 A：优化非瓶颈

只把数据库服务时间减半：

```text
P95：5832ms → 5823ms
改善：0.15%
模型 P95 排队仍为 5672.5ms
```

数据库本来就没有排队，因此继续优化它几乎没有端到端收益。

### 对照 B：优化真实瓶颈

只把模型并发从 4 增至 6：

```text
P95：5832ms → 194ms
改善：96.67%
超时率：93.75% → 0%
```

正确实验方法：

```text
固定负载与数据
→ 一次只改一个变量
→ 比较延迟、吞吐、错误、成本和质量
```

注意：模型并发不能无限增加，还受 Provider 429、Token 额度、成本、连接池和质量约束。

## 8. N+1 查询实验

相同负载：180 RPS，数据库池并发 8。

### N+1

```text
每请求 11 次查询
数据库服务需求 = 55ms
数据库利用率 = 99.79%
P95 = 2307.33ms
超时率 = 91.56%
```

### 批量查询

```text
每请求 1 次批量查询
数据库服务需求 = 8ms
数据库利用率 = 17.99%
P95 = 12ms
超时率 = 0%
```

优化方向：

- 批量 `IN` 查询；
- Join 或预加载；
- 一次读取映射表；
- 避免循环内访问数据库；
- 用 SQL 日志统计每请求查询次数；
- 用 `EXPLAIN ANALYZE` 检查批量 SQL。

批量查询也需要控制参数数量和返回数据规模。

## 9. 理论、实测和规划容量

三者不能混用：

| 概念 | 本次结果 | 含义 |
|---|---:|---|
| 理论容量 | 30.77 RPS | 由最小阶段服务能力估算 |
| 实验 SLO 容量 | 30 RPS | 本负载模型下仍满足 SLO |
| 安全规划容量 | 21 RPS | 理论容量的 70%，保留余量 |

安全余量用于吸收：

- 突发流量；
- P95/P99 服务时间；
- 重试；
- 部分实例故障；
- 数据量增长；
- GC 和连接抖动；
- Provider 限速。

不能把压测极限值直接作为生产日常入口上限。

## 10. 压测与定位流程

```text
1. 定义业务 SLO
2. 固定版本、机器和测试数据
3. 描述真实请求比例与数据分布
4. 建立低负载基线
5. 阶梯增加 RPS 或并发
6. 同时采集 RED、USE 和 Trace
7. 找吞吐变平、长尾陡升的拐点
8. 定位排队最长、利用率最高的阶段
9. 一次改变一个因素
10. 回归正确性、质量和成本
11. 按余量制定容量和背压阈值
12. 再做 Spike、Soak、Failure、Recovery Test
```

### RED

```text
Rate / Errors / Duration
```

### USE

```text
Utilization / Saturation / Errors
```

### Trace

```text
一个请求在 API、数据库、队列、RAG、模型和 N8N 各花多久
```

三者结合，避免凭感觉定位。

不要直接对正式模型和客户数据做无边界压力测试。

## 12. 面试回答

### 怎样定位接口慢？

> 我先确认是平均值、P95 还是 P99 变慢，再用 Trace 拆分 API、数据库、队列、RAG、模型和结果持久化。服务层看 RED，资源层看 USE；重点找利用率接近上限且排队增长的阶段。在实验中 40 RPS 时只有模型 P95 排队达到 5671ms，利用率 99.72%，因此数据库加速两倍只改善 0.15%，扩模型并发才改善 96.67%。

### 怎样估算系统容量？

> 先用每阶段并发除以平均服务时间估算理论容量，系统容量取最小值；再通过阶梯压测找满足 P95 和错误率 SLO 的实测容量，最后保留突发、长尾、重试和实例故障余量。本实验理论瓶颈 30.77 RPS，实测 SLO 容量 30 RPS，按 70% 规划为 21 RPS。

### 并发越高越好吗？

> 不是。并发增加到下游容量前能提高吞吐，超过后吞吐会变平，排队、内存、P99 和超时率上升，还可能触发 Provider 429。并发值必须由下游容量、连接池、成本和压测结果决定，并配合有界队列与背压。

### 队列能提高吞吐吗？

> 队列可以削峰、异步调度和隔离生产消费速度，但不会提高下游真实处理能力。持续入口 40 RPS、下游只能处理约 30.77 RPS 时，队列只会每秒增加约 9 个任务；必须扩容瓶颈、降低服务需求或限制入口。

### 如何发现 N+1？

> 在相同请求下统计 SQL 次数和数据库服务时间，结合 Trace、慢查询和连接池等待。N+1 常表现为数据量越大查询次数线性增长。修复后要对比 SQL 数、P95、数据库利用率和返回正确性，而不只是比较一次本地耗时。

## 15. 本次没有证明什么

- 没有测量当前项目的真实容量；
- 没有启动真实 FastAPI、Celery、MySQL 或 Redis；
- 没有产生真实网络、CPU、内存和 GC 数据；
- 没有测量模型首 Token、Token/s 或 Provider 429；
- 没有覆盖突发、长稳、故障和恢复压测；
- 没有验证真实连接池配置；
