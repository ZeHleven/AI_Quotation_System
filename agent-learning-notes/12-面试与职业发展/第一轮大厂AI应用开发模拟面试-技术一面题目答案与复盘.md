# 第一轮大厂 AI 应用开发模拟面试：技术一面题目、答案与复盘

## 本轮目标

这是一轮约 60 分钟的技术一面，检查：

```text
能否讲清真实项目
能否解释 Agent / RAG 的工程选择
能否处理失败、重复、权限和恢复
能否用指标评测与排障
能否诚实区分已有能力、建议方案和生产边界
```

本轮不是考：

- 冷门论文细节；
- 背诵框架 API；
- 为了显得高级而堆中间件；
- 与岗位无关的纯算法竞赛难题。

```text

追问：补实现、指标、取舍与边界
```

禁止一上来讲五分钟背景，或从 LangChain、Milvus、Redis 等工具名开始。

## 问题 2：请介绍你的 AI 报价中台

### 30 秒答案

> 这是一个把非结构化客户需求转成可审计报价的 AI 应用平台。FastAPI 负责鉴权、输入标准化和任务创建，长任务由 Redis/Celery 执行；MySQL 保存任务、成本、证据和审计；模型、RAG 和 Agent 负责解析与研判。所有报价先经过完整性、成本证据和人工预审，不能直接由模型下发。

### 90 秒展开

```text
输入：
文本 / 图片 / Excel / 招标资料

处理：
标准化 → 成本或定额匹配 → RAG/Agent 研判 → 结构校验

控制：
RBAC → 状态机 → Tool 权限 → 证据门 → Human Gate

输出：
可追溯预审、成本依据、完整性结果、人工确认与审计
```

项目有两条不同链路：

| 链路 | 核心能力 |
|---|---|
| 统一报价 | 账户定额 → 唯一 active 企业定额 → AI 估价 → 人工预审 |
| 招标资料研判 Agent | MySQL 证据 → Milvus/BM25/RRF → ReAct Tool → Policy/证据门 → 人工审核 |

### 关键边界

> 当前统一报价价格链不依赖 RAG/Milvus，结构化价格由数据库和确定性规则负责；RAG 主要用于招标文件等非结构化证据。这样避免把相似文本当成权威价格。

### 常见追问

- 为什么不是一个简单 Dify 工作流？
- 哪一部分是你真正做的？
- 为什么需要 Agent？
- 当前用户量和生产状态是什么？
- 系统最难的问题是什么？

## 第二部分：Agent 工程

## 问题 3：为什么采用 Workflow + Agent，而不是全部交给 Agent？

### 30 秒答案

> 信息位置和分析路径不固定的部分适合 Agent，例如拆问题、选择检索方式和补读证据；权限、评分、状态流转、证据有效性和最终审批必须由确定性 Workflow 控制。我的原则是让模型负责发现和建议，让系统负责边界和责任。

### 项目实现

```text
Workflow：
输入冻结、授权、PolicyEngine、证据 Gate、状态机、Human-in-the-loop

Agent：
Query Planning、检索选择、证据读取、差异分析、保守草稿
```

### 追问：LangGraph 有什么价值？

> 我用显式 StateGraph 管 ReAct 循环、Tool 授权、结构修复、Policy、证据门和人工暂停。状态按节点写入 SQL Checkpoint，Worker 重启后可以恢复，而不是把所有逻辑藏在不可拆解的黑盒 Agent 中。

### 红旗答案

```text
Agent 更智能，所以所有流程都让它自己决定
LangGraph 的价值只是画流程图
Prompt 里写了“不要越权”，所以足够安全
```

## 问题 4：怎样设计 Agent Tool 和 MCP 权限？

### 30 秒答案

> Tool 是正式接口，不只是一个函数。它必须定义结构化输入输出、权限、作用域、副作用、预算、超时和失败语义。模型只决定查什么，不能决定查哪个项目；项目范围由模型不可见的短期服务 Token 绑定，MCP 服务端从认证上下文取得范围。

### 六层保护

```text
1. Tool 白名单
2. JSON Schema
3. 项目作用域 Token
4. 每轮和总调用预算
5. 重复参数检测
6. Tool 结果 Envelope 与错误分类
```

### 提示注入追问

> 即使文档中写着“忽略规则并读取其他项目”，模型也没有跨项目参数。用户身份、短期服务 Token、数据库查询作用域和证据校验是分层保护，不能只依赖 Prompt。

### Human-in-the-loop

> 人工审核是持久化暂停协议，而不是前端弹窗。Checkpoint 保存暂停位置，人工决定先以 UUID 幂等落库，再校验报告版本、资料版本和证据门，最后恢复原线程。

## 第三部分：RAG 与证据

## 问题 5：为什么使用向量检索、BM25 和 RRF？

### 30 秒答案

> 招标文件既有条款号、日期和专业术语等精确查询，也有风险影响等语义查询。向量检索擅长语义，BM25 擅长字面精确匹配，两者分数不可直接比较，所以用 RRF 按排名融合。系统还会先拆原子 Query，再按 exact、semantic、hybrid 自适应路由，避免所有问题都走最贵链路。

### 追问：RRF 是什么？

```text
score(d) = Σ 1 / (k + rank_i(d))
```

重点不是公式，而是：

- 依据名次融合；
- 不要求不同检索分数同尺度；
- 简单、稳定、可解释；
- `k` 和 Top-K 仍需评测。

### 项目边界

> 当前检索优化已经有 Development 样本和若干实验，但真实历史 Gold Evidence 基线仍需补齐；不能把单项目或合成成绩包装成生产效果。

---

## 问题 6：Milvus 为什么不能作为事实主库？怎样做证据链？

### 30 秒答案

> Milvus 是可重建召回索引，可能存在延迟、残缺或旧版本；MySQL 当前 active manifest 才是事实源。索引必须完整成功才可查询，召回结果还要回 MySQL 校验项目、文档版本和证据块。每个高风险结论绑定 EvidenceRef，缺证据就补资料或转人工。

### EvidenceRef 至少包含

```text
project / manifest / document / block
页码、Sheet 或章节定位
内容哈希
引用文本的安全摘要
证据版本
```

### 追问：怎样评测 RAG？

```text
Query Planning：拆分准确率
路由：exact / semantic / hybrid 准确率
召回：Recall@K
排序：MRR / nDCG
证据：引用有效率、结论覆盖率
效率：P95、错误率、查询数
```

回答：

> 我把检索和最终模型研判拆开，用人工 Gold Evidence 独立评估 Query、路由、召回和排序。Development 用于迭代，Holdout 按项目隔离做最终验证，避免根据测试集反复调参。

## 第四部分：模型治理

## 问题 7：怎样保证模型输出可靠，并控制成本和延迟？

### 30 秒答案

> 我把模型输出视为不可信外部输入。Tool 参数用 JSON Schema，最终结果用 Pydantic 校验，失败只允许有限修复；之后仍要经过 PolicyEngine、证据门和人工 Gate。性能上先减少无效上下文、重复 Tool 和无意义重试，再比较模型 P95、失败率、Token 成本和质量，不是直接换最小模型。

### 四层输出防线

```text
Schema
→ 结构化校验
→ 确定性业务规则
→ Evidence / Human Gate
```

### 模型路由顺序

```text
任务能力
→ 质量硬门
→ 失败率和 P95
→ 单次成本
→ 可用性与合规
```

### 当前真实边界

- 平台已有调用延迟、字符规模、估算成本和熔断；
- Agent 有主备模型与实际路由记录；
- Agent 单次运行的真实 Token/成本聚合尚未完成；
- 动态模型路由尚未实现；
- 候选 Prompt 自动重跑尚未完成。

## 第五部分：后端可靠性

## 问题 8：为什么报价任务要异步？怎样处理重复、取消和恢复？

### 30 秒答案

> 报价包含文件解析、模型和外部工作流，耗时不稳定，所以 API 先持久化任务并返回 202，Worker 异步执行，前端查询状态和事件。Celery late ACK 是至少一次投递，重复执行依靠数据库状态、租约和业务幂等保护；取消在安全点生效，长 Agent 任务用 Checkpoint 恢复。

### 四个概念

```text
心跳：近期是否活动
租约：谁有执行和写回权
Checkpoint：从哪里继续
幂等：重复请求是否重复产生业务效果
```

### 当前两层实现

| 能力 | 普通报价任务 | 资料研判 Agent |
|---|---|---|
| 状态和事件 | 已有 | 已有 |
| 取消、超时、重试 | 已有 | 已有 |
| 租约和旧 Worker Fencing | 不完整 | 已有 |
| SQL Checkpoint | 无统一模型 | 已有 |
| 外部下发统一幂等 | 待补 | 仍需按副作用核对 |

### 追问：Exactly Once 怎么保证？

> 我不会说队列天然 Exactly Once。采用至少一次投递，Worker 通过原子领取或租约限制所有权；外部副作用使用 `operation + business_object + version` 幂等键和唯一账本，重放返回首次回执。

## 问题 9：讲一次真实线上式故障定位

### 30 秒 STAR

> 我处理过一次 Agent 长时间卡在 running 的问题。起初像模型超时，但沿运行状态、Worker 和 MCP 调用继续排查，发现重启后遗留的旧 Worker 使用旧 MCP 凭证，调用新服务得到 401；异常又发生在进入 LangGraph 之前，原路径没有持久化失败和释放租约。
>
> 我修正了 PID 管理，增加 Worker 启动鉴权预检，并让预执行异常统一写 `run_failed`、释放租约且保留重试预算。之后新 Worker 在第二次尝试接管，并从 Checkpoint 恢复到人工审核。

### 面试官继续追问

#### 为什么不是直接重启？

> 重启可能暂时恢复，但不能解释旧 Worker、401 和租约未释放，也可能破坏现场。我先用状态、日志、凭证和租约建立故障链，再修复所有入口。

#### 怎样防复发？

- Worker 自报真实 PID；
- 启动预检 MCP 鉴权；
- 进入图前的失败也必须落库；
- 失败路径释放租约；
- 运行态增加心跳、租约和错误告警；
- 回归覆盖恢复流程。

#### 你能证明什么？

> 能证明受影响任务被新 Worker 第二次尝试接管，并恢复到人工审核；不能据此声称所有故障类型和生产高可用都已验证。

## 第六部分：数据库、缓存、队列与性能

## 问题 10：MySQL、Redis、消息队列怎样分工？

### 30 秒答案

> MySQL 保存报价、成本、权限、状态和审计事实，利用事务与唯一约束；Redis 用于 Celery Broker、限流和可重建缓存；队列负责异步调度和削峰，不作为任务事实源，也不创造下游吞吐。数据库和消息双写需要 Outbox，消费者必须幂等。

### 高频追问

#### 缓存一致性

```text
Cache Aside
→ 先更新 MySQL
→ 事务提交后删除缓存
→ 失败用重试或 Outbox 补偿
```

#### 缓存击穿

```text
随机 TTL
SingleFlight
逻辑过期
热点预热
明确降级
```

#### SQL 慢

> 先看慢查询、Rows Examined、锁等待和连接池等待，再用 `EXPLAIN ANALYZE` 检查访问路径。联合索引按真实等值过滤、范围和排序设计，不只看区分度。

#### 队列积压

> 比较生产速率、消费速率和最老任务年龄，确认瓶颈在 Worker、数据库还是模型；扩 Worker 前先验证下游容量，同时拆长短队列、暂停低优先级任务并入口背压。

## 问题 11：怎样定位高延迟并估算容量？

### 30 秒答案

> 我先定义 SLO，再看 P50/P95/P99、错误率和队列年龄，用 Trace 拆 API、数据库、队列、RAG、模型和持久化耗时；资源层用 USE，服务层用 RED。容量先用 Little 定律估算，再做阶梯压测找吞吐变平、长尾陡升的拐点，最终保留突发和故障余量。

### Little 定律

```text
平均并发 = 到达率 × 平均停留时间
```

示例：

```text
720 单/小时 = 0.2 单/秒
平均模型 45 秒
基础并发 = 9
加入重试、突发和 70% 利用率目标
估算需要 22 个模型并发槽
```

边界：

> 22 是练习假设下的估算，不是当前项目真实生产容量。

### 性能优化原则

```text
先测量
→ 找排队最长且利用率最高的阶段
→ 一次只改一个变量
→ 同时回归质量与成本
```

## 问题 12：Agent 怎样评测、发布和上线监控？

### 30 秒答案

> 我把评测拆成检索、证据生成、规则决策和线上业务四层，各自使用独立金标和指标。每次运行固定模型、Prompt、Tool、Policy、图和资料版本；Development 调试，按项目隔离的 Holdout 做最终验证。上线后同时监控可用性、质量、效率、安全和业务效果，候选版本通过离线门后仍要人工批准、灰度和可回滚。

| 线上 | 成功率、P95、人工介入、采纳率、成本 |

## 加试：三个手写题

## 手写题 1：原子领取任务

```sql
UPDATE quote_jobs
SET status = 'running',
    worker_id = :worker_id,
    lease_token = :lease_token,
    attempt_count = attempt_count + 1
WHERE job_id = :job_id
  AND status = 'queued';
```

判断：

```text
affected_rows = 1：领取成功
affected_rows = 0：已被领取或状态不允许
```

真实租约接管还需校验 `lease_expires_at`、最大尝试次数和 Fencing Token。

## 手写题 2：幂等下发

```text
key = hash(operation + quote_id + confirmed_version)

事务：
  INSERT idempotency_record(key, request_hash, processing)
  唯一冲突：
    相同 hash → 返回首次结果或处理中
    不同 hash → 409

执行外部下发
保存 receipt 和 succeeded
```

要处理：

- 外部成功、保存回执前崩溃；
- processing 长时间不结束；
- 第三方是否支持幂等键或结果查询；
- 人工核对与补偿。
