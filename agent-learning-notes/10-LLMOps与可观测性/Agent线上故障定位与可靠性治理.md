# Agent 线上故障定位与可靠性治理

## 核心认知

Agent 的线上故障不一定表现为代码异常，常见现象包括：

- 系统正常返回，但业务结果错误
- 工具调用成功，但数据不正确或已过期
- 模型输出正常，但下游无法解析
- 任务长期停留在处理中
- 同一输入在不同时间产生不同结果

定位原则：

> 不要从最终错误开始猜，要找到执行链路中第一个出现偏差的位置。

---

## 1. 四层故障模型

```text
业务层
  ↓
Agent 决策层
  ↓
模型与工具层
  ↓
基础设施层
```

### 业务层

先确认“正确答案”是否已被业务定义。

例如“价格合理”可能有多种标准：

- 与历史价格相比不超过 10%
- 与市场价相比不超过 15%
- 重要项目必须使用最新供应商报价
- 特殊客户必须使用指定品牌

如果规则模糊或相互冲突，模型表现必然不稳定。

### Agent 决策层

检查执行路径：

- 是否调用必要工具
- 是否选错工具
- 顺序是否正确
- 是否重复调用
- 是否过早结束
- 是否绕过人工审核

### 模型与工具层

检查：

- 模型是否理解错误
- 参数是否生成正确
- 工具逻辑是否正确
- 数据是否完整、有效和新鲜
- 模型是否正确理解工具结果

### 基础设施层

常见问题：

- Redis 断开
- Celery Worker 异常
- 模型 API 超时
- 数据库连接池耗尽
- 对象存储读取失败
- 队列积压

基础设施问题通常影响成功率、延迟、吞吐和可用性。

---

## 2. 标准故障排查流程

```text
1. 确认任务 ID 和影响范围
2. 检查原始业务输入与预期结果
3. 查看当前任务和步骤状态
4. 按 Trace 还原完整执行链路
5. 找到第一个偏离预期的位置
6. 判断所属故障层和责任组件
7. 使用相同版本和数据复现
8. 修复根因并补充防护
9. 运行专项及回归测试
10. 灰度发布并持续观察
```

报价链路示例：

```text
图纸
→ OCR
→ 材料提取
→ 材料匹配
→ 价格检索
→ 成本计算
→ 报价输出
```

如果前两步正确，而材料匹配首次出错，根因应定位在材料匹配，而不是最终计算模块。

### 排查时先回答

- 什么时候开始异常
- 影响哪些用户、任务和版本
- 是否能稳定复现
- 是单点问题还是趋势性问题
- 是否仍在扩大
- 是否需要先止损再查根因

## 3. Root Cause：从现象追到根因

```text
现象：报价少了 30 万元
  ↓
直接原因：缺少一种材料
  ↓
根因：材料表被 VLM 识别为普通文本，
      未进入表格 OCR 路由
```

应修复版面识别和任务路由，而不是只在最终 Prompt 中增加“不要遗漏材料”。

### 根因判断标准

一个可靠的根因通常能够解释：

- 为什么发生
- 为什么没有被更早发现
- 为什么只影响特定任务
- 修复后为什么能阻止同类问题

如果答案只是“模型不准”或“偶发网络问题”，通常仍未定位到可操作根因。

---

## 4. 七类常见根因

| 类型 | 典型问题 | 主要治理方式 |
|---|---|---|
| 输入 | 文件损坏、缺页、字段或地区缺失 | 输入校验、质量检测、缺失提示 |
| Context | 规则缺失、信息过多、内容截断、历史过期 | 检查最终上下文、预算和来源 |
| Prompt | 指令冲突、格式不清、缺失处理未定义 | 版本化、离线评测、结构化输出 |
| Retrieval | 未召回、误召回、切片或重排错误 | 分析 Query、候选、排序和最终上下文 |
| Tool | 参数错误、逻辑错误、结果结构不稳 | Schema、权限、契约测试、标准错误码 |
| Model | 理解、分类、幻觉、格式和选择错误 | 模型评测、路由、Verifier、人工审核 |
| System | 重复执行、超时、锁冲突、缓存过期 | Metrics、Trace、幂等、并发控制 |

### RAG 排查四个视图

```text
原始 Query
→ 改写后的 Query
→ 召回候选和 Top-K 排序
→ 最终进入模型的上下文
```

只看模型最终答案无法判断问题发生在检索还是生成阶段。

### 工具调用最小记录

```json
{
  "tool_name": "query_material_price",
  "arguments_summary": {
    "material": "Low-E玻璃",
    "region": "东莞"
  },
  "result_ref": "tool-result-9281",
  "source": "cost_items.active",
  "latency_ms": 530,
  "status": "success",
  "error_code": null,
  "retry_count": 0
}
```

敏感参数和完整业务内容应脱敏或保存引用。

## 5. Request ID、Task ID 与 Trace ID

| 标识 | 表示 | 生命周期 |
|---|---|---|
| Request ID | 一次接口请求 | 通常较短 |
| Task ID | 一次业务任务 | 可持续数分钟或更久 |
| Trace ID | 一次技术执行链路 | 可跨多个服务 |

关系示例：

```text
Task: quote_001
├── Request: req_create
│   └── Trace: trace_create
├── Trace: trace_async_execution
└── Request: req_review
    └── Trace: trace_review
```

一个业务任务可能包含多个请求和多个 Trace。

所有组件应透传相关 ID：

```text
前端 → FastAPI → Celery → OCR → VLM
     → RAG → LLM → MySQL → 报告生成
```

## 6. 日志与数据安全

### 日志级别

| 级别 | 用途 |
|---|---|
| DEBUG | 开发调试细节，生产默认谨慎开启 |
| INFO | 正常任务、状态和工具事件 |
| WARNING | 已降级或可继续的异常 |
| ERROR | 单个步骤或任务失败 |
| CRITICAL | 数据库、队列、模型提供商等系统级故障 |

### 不应直接记录

- API Key 和数据库密码
- 身份证号、手机号等隐私数据
- 完整合同和敏感报价
- 用户上传文件全文
- 未脱敏 Prompt 与工具参数

替代方式：

- 脱敏
- 摘要
- 哈希
- 截断
- 对象或记录 ID

日志既要支持定位，也要遵守最小化和保留期限。

## 7. Metrics 与延迟分位数

### 系统指标

- CPU、内存和磁盘
- 数据库连接数
- 队列长度
- 在线 Worker 数量

### 接口指标

- 请求量
- 成功率
- P50/P95/P99 延迟
- 错误率

### 模型指标

- 调用次数和成功率
- 超时率
- Token
- 延迟与成本
- 回退模型使用率

### Agent 指标

- 任务完成率
- 平均执行步数
- 工具调用次数
- 循环率
- 人工接管率
- 重试率

### 业务指标

- 报价耗时
- 人工修改率
- 报价接受率
- 节省工时
- 活跃用户数

### P50、P95、P99

```text
P50：50% 的任务在该时间内完成
P95：95% 的任务在该时间内完成
P99：99% 的任务在该时间内完成
```

例如：

```text
P50 = 20 秒
P95 = 90 秒
P99 = 300 秒
```

平均值可能掩盖长尾问题，用户体验和容量规划通常更关注 P95/P99。

## 8. 卡死任务、Heartbeat 与超时

任务卡住的常见原因：

- 工具反复超时
- Agent 无限循环
- Worker 崩溃
- 数据库锁等待
- 重试策略失控
- 状态未更新
- 消息丢失或未被消费

### 长任务建议字段

```json
{
  "task_id": "quote_001",
  "status": "processing",
  "current_step": "vlm_analysis",
  "started_at": "2026-07-27T10:00:00+08:00",
  "last_heartbeat_at": "2026-07-27T10:03:00+08:00",
  "deadline_at": "2026-07-27T10:10:00+08:00",
  "retry_count": 1,
  "worker_id": "worker_ai_03"
}
```

Heartbeat 表示 Worker 仍存活且任务仍在推进。

### 超时处理

```text
心跳过期
  ↓
确认 Worker 和任务状态
  ↓
防止旧 Worker 继续提交结果
  ↓
从 Checkpoint 恢复或转人工
  ↓
记录超时原因并告警
```

仅靠心跳不能证明任务有进展，还应观察 `current_step`、步骤耗时和产物更新时间。

## 9. 队列积压与队列拆分

当任务到达速度 `λ` 长期高于处理速度 `μ` 时，Backlog 会持续增长。

应同时监控：

- 待处理数量
- 最老任务等待时间
- 到达速率
- 消费速率
- 任务运行时间
- Worker 利用率
- 失败和重试率

队列长度相同，最老任务等待 10 秒和 30 分钟的业务影响完全不同。

### 处理方式

- 优化慢步骤
- 增加适量 Worker
- 限制提交速度
- 暂停离线任务
- 使用优先级
- 在存在资源争用时拆分队列

### 何时拆分队列

适合拆分：

- 长短任务互相阻塞
- 资源类型不同
- 优先级或 SLO 不同
- 失败和重试策略不同

不应一开始就为每个步骤建立独立队列。队列越多，部署、路由、容量和监控也越复杂。

第一阶段可考虑按资源和业务优先级拆分：

```text
ai_heavy_queue
file_report_queue
notification_queue
offline_queue
```

再依据真实指标细化。

## 10. 并发、并行与依赖

### 并发

系统在同一时间段管理多个任务。

### 并行

多个任务或步骤真正同时执行。

适合并行：

- 多页图纸独立识别
- 多材料独立查询
- 多文件处理
- 独立评测案例

不适合并行：

- 下一步依赖上一步结果
- 多任务修改同一资源
- 必须严格有序的审批

并行化前应明确依赖图、资源上限、合并规则和失败处理。

## 11. Race Condition 与并发保护

竞态示例：

```text
Worker A 读取：未完成
Worker B 读取：未完成
Worker A 生成报价
Worker B 也生成报价
```

治理工具：

- 数据库事务
- 唯一约束
- 幂等键
- 乐观锁
- 分布式锁

### 乐观锁

```sql
UPDATE task
SET status = 'completed',
    version = 4
WHERE id = 123
  AND version = 3;
```

更新行数为 0，说明版本已被其他执行者修改。

### 分布式锁

```text
SET lock:quote:123 worker_a NX EX 300
```

需要处理：

- 锁过期但 Worker 仍在执行
- 错误释放其他 Worker 的锁
- Worker 崩溃
- 锁续期失败

应使用随机持有者令牌校验释放，并在高风险场景考虑 fencing token。分布式锁不能替代数据库唯一约束和幂等。

## 12. 事务、补偿与 Outbox

单数据库事务可以保证：

```text
要么全部提交
要么全部回滚
```

但跨系统操作无法放进同一个本地事务：

```text
写 MySQL
上传对象存储
发送钉钉
调用第三方 API
```

### 补偿

```text
报价已生成
通知发送失败
→ 保留报价
→ 标记 notification_failed
→ 单独重试通知
```

### Outbox 模式

可将业务变更和待发送事件写入同一数据库事务：

```text
提交业务数据 + 写入 outbox
        ↓
后台可靠投递外部消息
        ↓
记录投递结果和幂等 ID
```

补偿动作同样需要幂等、可观测和人工处理边界。

## 13. 熔断、限流与背压

### Circuit Breaker

防止持续调用故障服务导致雪崩：

```text
Closed：正常调用
Open：快速失败或走回退
Half-Open：少量探测是否恢复
```

阈值、窗口和恢复时间必须根据服务特征配置。熔断要与重试协调，避免多个 Worker 同时制造重试风暴。

### 限流

常见维度：

- 用户
- 租户
- IP
- 接口
- 模型
- 项目

示例：

```text
每用户每分钟最多 10 个任务
每项目同时最多 1 个报价任务
VLM 每秒最多 5 次调用
```

### Backpressure

当下游无法承载时，上游应减速：

- 暂停或拒绝新任务
- 延迟提交
- 降低优先级
- 限制批量上传
- 返回预计等待时间

### 优先级队列

```text
P0：正式业务任务
P1：内部试用
P2：历史重处理
P3：离线评测
```

还需防止低优先级任务长期饥饿，可设置配额或老化策略。

## 14. SLI、SLO 与 SLA

```text
SLI：实际测量指标
SLO：内部可靠性目标
SLA：对外或对业务的正式承诺
```

示例：

```text
SLI：本月任务成功率为 97.8%
SLO：任务成功率 ≥ 98%
SLA：系统月可用性 ≥ 99.5%
```

内部系统应先建立可靠 SLI，再依据基线和业务需求设定 SLO，不必过早承诺 SLA。

### 报价系统候选 SLI

- 任务成功率
- P95 完成时间
- 人工审核任务不丢失率
- 重复报价生成率
- 模型故障自动恢复率
- 报价链路可用性

目标值必须根据真实试运行数据和业务容忍度确定，不应直接照搬示例。

## 15. Runbook

Runbook 是可执行的故障处理手册。

### 通用结构

```text
故障名称
触发条件
影响范围
检查步骤
止损动作
恢复步骤
验证方法
升级联系人
相关仪表盘和查询
```

### 队列积压 Runbook

1. 检查 Redis/Broker 状态。
2. 检查 Worker 数量、心跳和消费速率。
3. 查看最老任务等待时间。
4. 定位异常增长的任务类型和重试。
5. 暂停离线或低优先级任务。
6. 评估扩容或降低入口速率。
7. 确认积压下降且新任务恢复。

### 模型大面积超时 Runbook

1. 确认供应商与网络状态。
2. 打开熔断，避免请求堆积。
3. 按策略启用备用模型或降级。
4. 限制低优先级和高成本任务。
5. 通知业务负责人。
6. 恢复后逐步放量并观察。

Runbook 应定期演练，否则故障发生时可能已经过期。

## 16. Postmortem

重大故障复盘应包括：

- 事件摘要
- 时间线
- 影响范围
- 用户和业务影响
- 发现与恢复过程
- 根本原因
- 促成因素
- 为什么未提前发现
- 哪些防护有效或失效
- 改进项、负责人和完成期限

### 示例

```text
事件：报价任务重复执行

根因：
Celery 重复投递后缺少原子幂等校验。

改进：
增加唯一约束、幂等记录、重复任务指标和告警。
```

复盘重点是改进系统，不是简单寻找责任人。

## 17. 面向当前报价中台的渐进改造

当前系统已经具备 `quote_jobs`、任务事件、Celery Worker、重试/取消/超时入口、人工审核、证据链、看板和健康检查等基础。报价资料研判 Agent 还进一步具备任务租约、Worker Heartbeat、SQL Checkpoint 和安全执行 Trace。

### 优先级一：统一关联标识

- 复用现有业务任务 ID
- 增加并贯通 `request_id` 与 `trace_id`
- 让 FastAPI、Celery、n8n、Dify、模型与外部工具使用同一关联上下文

### 优先级二：步骤级事件

报价资料研判 Agent 已将 LangGraph 节点、工具授权、Tool、Observation、政策、证据门和人工暂停投影为安全 Trace。其他报价链路仍应优先使用步骤事件或 Span，而不是给任务表不断新增：

```text
drawing_convert_status
ocr_status
vlm_status
retrieval_status
...
```

任务表保留当前摘要状态，事件表记录步骤、输入输出引用、耗时、错误码和重试次数。

### 优先级三：卡死检测

- 复用已有 Celery 心跳、报价任务 Heartbeat 与 Agent Worker Heartbeat
- 让 Agent 任务租约、运行心跳和图节点进度联合判定卡死
- 对超过租约时长的单次运行增加 token 绑定的续租
- 监控状态无进展、租约过期和截止时间

### 优先级四：队列治理

先测量任务类型、等待时间和资源争用，再决定是否拆分队列。优先隔离：

- 正式业务与离线评测
- AI 重任务与通知轻任务

### 优先级五：并发与副作用保护

重点覆盖：

- 创建任务
- 生成和确认报价
- 提交审核
- 发送通知

采用唯一约束、原子幂等、乐观锁和必要的补偿机制。

### 优先级六：首批告警

- 任务失败率异常
- 最老队列任务等待过长
- 任务超时或心跳过期
- Worker 数量异常
- 模型连续失败或熔断

### 优先级七：Runbook

先为最常见的三类事故编写并演练：

1. Celery 队列积压
2. 模型或 RAG 服务大面积超时
3. 报价任务重复执行或状态卡死

## 18. 调用链追踪：不是“多打一些日志”

[来源视频：大模型为何要做调用链追踪](https://www.douyin.com/video/7663128008705969657)

传统接口的 HTTP 200 只能说明请求被处理，不能说明：

- 检索到了正确证据；
- 模型选择了正确工具；
- 工具参数与资源范围正确；
- 结构化结果通过业务校验；
- 总耗时是否浪费在排队、模型还是下游；
- 人工审核是否接收到了完整上下文。

调用链追踪的目标是：

> 把一次 AI 请求拆成可观察、可定位、可比较和可优化的执行阶段。

### Trace、Span、Log 与 Metric

| 对象 | 作用 |
|---|---|
| Trace | 串起一次端到端业务请求 |
| Span | 描述其中一个有起止时间的阶段 |
| Event | 记录 Span 内的重要离散变化 |
| Log | 保存可检索的诊断记录 |
| Metric | 聚合大量运行后的趋势与告警信号 |

只有 `trace_id` 还不等于完成了调用链追踪。必须把它传播到每个阶段，并形成父子关系和阶段语义。

### Agent 链路的 Span 模型

```text
request
├── gateway.validate
├── queue.wait
├── document.parse
├── context.build
├── llm.invoke
├── tool.authorize
├── tool.execute
├── observation.validate
├── policy.evaluate
├── evidence.gate
├── human.review
└── external.commit
```

最小 Span 字段：

```text
trace_id
span_id
parent_span_id
task_id / run_id
stage
status
started_at / ended_at / duration_ms
attempt
model_id / prompt_version / policy_version
tool_name
input_reference / output_reference
error_code
```

正文、密钥和私有思维链不应直接进入 Trace。

### 同时追踪性能与质量

性能问题：

```text
总耗时 = 排队等待 + 实际执行 + 重试与退避 + 人工等待
```

质量问题则要追踪：

```text
证据候选
→ 模型动作
→ 授权结果
→ 工具 Observation
→ 结构化结论
→ 规则与证据门
→ 人工最终判断
```

如果只记录延迟，能发现“慢”，但解释不了“为什么答错”；如果只记录最终输出，也找不到第一个偏差点。

### 当前项目映射

报价资料研判 Agent 已实现 `bid-intake-agent-trace/v1`：

- 从 LangGraph `tasks` stream 投影执行事件；
- 覆盖 LLM 安全输入、行动计划、工具授权、Tool、Observation、结构化草稿、经营政策、证据门和 Human-in-the-loop；
- 前端以动态图谱展示节点、连线、状态和检查摘要；
- 仅记录可审计摘要，不记录模型私有思维链；
- 敏感字段脱敏，旧记录可降级回放。

2026-07-28 的真实卡死任务恢复后累计 75 个事件，能完整看到 MCP 由 401 恢复、Worker 接管以及最终进入人工审核的过程。这说明 Trace 已从“开发日志”升级为恢复和验收证据。

当前仍应推进：

1. 将同一 `trace_id` 贯穿 FastAPI、Celery、n8n/Dify、模型和外部推送；
2. 为 Span 统一延迟、错误码、重试和版本字段；
3. 建立 `queue_wait / model / tool / human` 分阶段 P95；
4. 将 Trace 失败样本回流到回归评测集；
5. 明确 Trace 数据保留期、脱敏和访问权限。

## 19. 置信度校准：把“像是有把握”变成行动策略

[来源视频：为什么要做置信度校准](https://www.douyin.com/video/7664589597657389199)

模型语气坚定不代表结论可靠，模型自报 `confidence=0.95` 也不等于历史正确率为 95%。

生产系统需要的是系统级可信信号：

| 信号 | 可观测内容 |
|---|---|
| 证据充分度 | 是否存在权威来源、覆盖关键结论、版本是否新鲜 |
| 多次一致性 | 候选答案或不同模型是否稳定一致 |
| 工具一致性 | 不同工具、数据库和文档是否冲突 |
| 问题边界 | 是否超出知识、权限或可执行范围 |
| 输出稳定性 | 修复前后是否频繁反转 |
| 业务规则 | 是否触发硬红线、缺失项或高风险动作 |
| 历史表现 | 相似场景在金标样本上的实际正确率 |

### 校准是什么意思

将系统分数按区间分桶，并与真实结果比较：

| 分数区间 | 样本数 | 实际正确率 |
|---|---:|---:|
| 0.9–1.0 | 100 | 72% |
| 0.8–0.9 | 150 | 70% |
| 0.7–0.8 | 180 | 69% |

这种结果说明分数虽然不同，但几乎不能区分可靠性，而且整体过度自信。

较好的校准应接近：

```text
预测可信度 80%
≈ 历史同类样本约 80% 正确
```

可使用可靠性曲线、Expected Calibration Error（ECE）或 Brier Score 评估。面试中不必先背公式，先说明“分桶后的预测分数应与真实正确率一致”。

### 不同风险使用不同阈值

不能用一个全局阈值处理所有动作：

| 场景 | 风险 | 建议策略 |
|---|---|---|
| 只读摘要 | 低 | 中等可信即可自动返回，并保留引用 |
| 报价建议 | 中高 | 需要证据门和人工预审 |
| 正式推送 | 高 | 版本、完整性、权限与人工确认全部通过 |
| 删除或权限变更 | 极高 | 双人审批或禁止 Agent 自动执行 |

分数最终必须绑定动作：

```text
高可信 + 低风险
→ 自动执行

中可信或证据不足
→ 补检索、询问用户、降级

低可信或工具冲突
→ 转人工

命中硬红线
→ 无论平均分多高都阻断
```

### 校准数据集的正确做法

1. 保存真实历史输入、当时版本和最终人工结果；
2. 金标由有权限人员审核，修订产生新版本，不覆盖历史；
3. development 用于调阈值；
4. holdout 只用于最终盲测，防止针对测试集调参；
5. 对危险错误单独设发布门，不能只看平均准确率；
6. 数据和业务分布变化后重新校准；
7. 即使评测通过，也不自动发布高风险政策。

### 当前项目映射

报价资料研判 Agent 已经实现的是“业务决策策略校准”，而不是相信模型自报置信度：

- 为历史 Assessment 建立不可变总经办金标；
- 由异人复核后冻结校准数据集；
- 区分 development 与 holdout；
- 离线比较 active 与候选政策；
- 总样本至少 30、holdout 至少 10；
- 不报价和硬红线样本有最低数量要求；
- 发布门要求回放错误为 0、不增加危险报价、holdout 硬红线召回率 100%、金标一致率不低于 active 且至少 80%；
- 发布门通过也固定 `activation_allowed=false`，仍需总经办另行批准。

这是比“模型说自己有 90% 把握”更可靠的工程闭环。

仍需区分两个层次：

1. **现有能力**：对立项政策与决策阈值做历史金标回放和发布门控制；
2. **可继续补强**：对检索质量、字段提取、模型置信度等连续分数分别建立可靠性曲线，并把分数映射到自动、补证据、降级和人工动作。

不要把测试样本上的一次 100% 当作生产正确率。当前验收使用的 30 个临时样本证明流程可运行，不代表真实业务分布已经完成校准；仍需积累经复核的真实项目样本。

### 置信度校准检查清单

- [ ] 分数来自系统信号，而非只信模型自报
- [ ] 金标有权限、版本和异人复核
- [ ] development 与 holdout 严格隔离
- [ ] 高风险错误有独立指标和硬门槛
- [ ] 分数区间与真实正确率定期比较
- [ ] 每个风险等级都绑定明确动作
- [ ] 数据漂移后会重新校准
- [ ] 发布门通过不会自动上线高风险策略

### 面试速答

> 置信度校准不是让模型输出一个百分比，而是把证据充分度、工具冲突、规则命中和历史金标表现转成可验证的系统信号，再用独立样本校准阈值，并把不同分数绑定到自动执行、补证据、降级或转人工。高风险场景还要有独立硬门槛。

## 故障报告表达模板

避免：

```text
AI 又出错了。
```

推荐：

```text
该任务在材料匹配阶段首次偏离预期。

OCR 和字段提取结果正常；
材料归一化工具将“6+12A+6 Low-E 中空玻璃”
错误映射为“普通中空玻璃”；
后续价格查询和成本计算均按错误材料正常执行。

根因属于材料匹配规则与数据问题，
不是模型生成或成本计算问题。
```

一个合格的故障说明应包含：

- 影响
- 首个偏差点
- 根因层级
- 证据
- 临时止损
- 永久修复
- 验证结果

## 故障排查检查清单

- [ ] 已确认任务 ID、版本和影响范围
- [ ] 已找到链路中的第一个偏差点
- [ ] 已区分业务、Agent、工具模型和基础设施层
- [ ] 已验证输入、最终 Context、检索和工具结果
- [ ] 已使用相同版本复现
- [ ] 已先止损，再实施永久修复
- [ ] 已补充专项和回归测试
- [ ] 已灰度发布并观察
- [ ] 重大故障已完成 Postmortem

## 一句话总结

线上故障治理的核心不是“让 AI 再试一次”，而是用标识、Trace、指标、并发控制和标准应急流程，找到首个偏差点并修复真正根因。
