# 流量与故障保护：限流、超时、熔断、降级与隔离

> 配套实战：[练习 06：微服务超时、重试、熔断、降级、健康检查与隔离实战](./练习记录/06-微服务超时重试熔断降级健康检查与隔离实战.md)

## 核心结论

五种机制解决不同问题：

| 机制 | 解决的问题 |
|---|---|
| 限流 | 进入系统的请求超过允许速率 |
| 超时 | 单次等待没有明确上限 |
| 熔断 | 依赖持续失败，调用继续放大故障 |
| 降级 | 完整能力不可用时仍需有限服务 |
| 隔离 | 一个依赖耗尽所有线程、连接或并发额度 |

记忆：

```text
限流管入口
超时管等待
熔断管失败依赖
降级管可用能力
隔离管资源边界
```

这些机制必须与指标、告警和恢复策略一起设计。

---

## 1. 限流维度

可以按：

- IP；
- 用户；
- 租户；
- API Key；
- 接口；
- 模型；
- Token；
- 并发任务数；
- GPU/外部额度。

只按 IP 限流可能误伤 NAT 后的大量用户，也不能防止一个登录用户耗尽模型额度。

### 返回语义

HTTP：

```text
429 Too Many Requests
Retry-After: 10
```

响应应告诉客户端：

- 哪个限额；
- 何时可重试；
- 是否可转异步；
- Trace ID。

---

## 2. 限流算法

### 固定窗口

一个时间窗内计数。

优点简单；窗口交界处可能瞬时通过两倍流量。

### 滑动日志/滑动窗口

更准确反映任意时间区间，存储和计算成本更高。

### 漏桶

以稳定速率流出，适合整形，但突发能力弱。

### 令牌桶

按速率生成令牌，允许一定突发：

```text
桶容量 = 可接受突发
令牌速率 = 长期允许速率
```

AI API 常需要同时限制：

```text
请求速率
并发数
Token/成本预算
```

只限制 QPS 不能阻止少量超大请求耗尽资源。

---

## 3. 多实例限流

进程内计数只对单实例有效。多实例时：

- Redis 原子计数/Lua；
- 网关集中限流；
- 专用限流服务；
- Provider 额度回传。

当前项目 `app/core/rate_limit.py`：

- Celery 模式下使用 Redis 作为 SlowAPI 存储；
- local/disabled 模式使用进程内存；
- 登录接口应用限流。

因此面试中要说明：进程内限流适合本地或单实例，多实例一致性依赖共享存储或网关。

---

## 4. 超时预算

每个网络调用都必须有连接、读取和总超时。

### Deadline 传播

```text
用户总预算 30s
网关与序列化预留 3s
业务服务剩余 27s
RAG 最多 5s
模型最多 18s
结果处理预留 4s
```

下游不能不知道上游还剩多少时间。

### 常见错误

- 没有超时；
- 每层都使用相同超时；
- 超时后后台仍无限运行；
- 超时后立即多层重试；
- 把连接超时和读取超时混为一谈；
- HTTP 超时后假设外部副作用一定没成功。

## 5. 熔断器

典型状态：

```text
Closed：正常调用
→ 失败率超过阈值
Open：快速失败，不再调用
→ 冷却时间结束
Half-Open：少量探测
→ 成功则 Closed，失败则 Open
```

阈值可以基于：

- 连续失败次数；
- 滑动窗口失败率；
- 慢调用比例；
- 最小请求量。

熔断必须按依赖、接口或模型隔离。一个非核心模型失败，不应熔断整个系统。

---

## 6. 降级

降级必须明确降低了什么能力：

| 依赖故障 | 可接受降级 | 不可接受伪装 |
|---|---|---|
| RAG 不可用 | 返回“无证据，需人工确认” | 用模型常识冒充知识库答案 |
| 模型 A 不可用 | 路由模型 B，并标记版本 | 静默改变价格口径 |
| 看板聚合失败 | 返回最近快照和时间 | 显示成实时数据 |
| 通知失败 | 保存待通知并稍后重试 | 回滚已经成功的报价 |
| OCR 失败 | 转人工录入 | 编造文件内容 |

降级结果需要：

- 标记来源；
- 记录触发原因；
- 不越过权限和质量 Gate；
- 有恢复或人工处理入口。

---

## 7. 隔离与背压

### Bulkhead

像船舱隔板一样隔离资源：

- 不同依赖使用不同连接池；
- 长任务和短任务使用不同 Worker 队列；
- 每个模型设置并发信号量；
- 租户之间有额度；
- 文件解析与在线 API 分开。

### 背压

下游处理不过来时，上游必须减速：

- 拒绝或延后新任务；
- 返回 429/503；
- 限制队列长度；
- 降低非核心任务优先级；
- 暂停批处理；
- 告诉客户端预计等待。

队列无限增长不是背压。

---

## 8. 重试风暴

三层服务各重试三次，最坏可能把一次请求放大为：

```text
3 × 3 × 3 = 27 次
```

治理：

- 明确唯一重试层；
- 指数退避 + 抖动；
- 重试预算；
- 尊重 `Retry-After`；
- 熔断打开时不继续普通重试；
- 入口限流；
- 请求幂等。

---

## 9. AI 系统的特殊保护

除了 QPS，还要限制：

- 输入文件大小；
- 页数；
- Prompt/Context Token；
- 单任务最大循环；
- Tool 调用次数；
- RAG Top-K；
- 单用户并发任务；
- 单任务模型成本；
- 最大执行时长。

保护策略：

```text
接近预算：停止新 Tool，要求模型总结
超过质量边界：转人工
超过成本边界：降级模型或终止
外部额度不足：快速失败，不无意义重试
```

## 10. 报价中台映射

### 已有基础

- 登录接口使用 SlowAPI 限流；
- Celery 模式下限流状态使用 Redis；
- 模型、RAG、N8N 等 HTTP 调用设置超时；
- Worker 设置任务时间上限和低预取；
- 运维检查覆盖 MySQL、Redis、Celery、RAG、MinIO 和 N8N；
- 模型网关包含多 Provider 路由和调用记录；
- 报价结果进入人工预审，形成高风险副作用 Gate。

### 可继续补强

- 按用户、租户和模型成本的统一额度；
- 队列长度和最老任务年龄触发入口背压；
- 模型/RAG 依赖的统一熔断状态；
- 降级响应明确显示证据和版本；
- 全链路 Deadline 传播；
- 故障演练和 SLO 驱动阈值。

## 11. 指标

### 限流

```text
allowed / rejected
按用户/租户/接口分布
429 比率
额度使用率
```

### 熔断

```text
open 次数和持续时间
失败率
慢调用率
half-open 成功率
```

### 降级

```text
fallback_count
fallback_reason
人工接管率
降级结果采纳率
```

### 隔离

```text
连接池使用率
线程/Worker 利用率
队列长度
拒绝次数
各依赖并发
```

阈值应该来自容量和 SLO，不是拍脑袋。

## 12. 面试回答

### 限流、熔断和降级有什么区别？

> 限流控制进入系统的请求，防止容量被耗尽；熔断针对持续失败的下游，暂时停止调用以避免故障放大；降级是在完整能力不可用时返回明确标记的较弱结果。实际链路还需要超时限制等待，并用独立连接池、队列和并发信号量做资源隔离。

### 模型接口持续超时怎么办？

> 先设置总 Deadline 和单次超时，只对可恢复错误在预算内退避重试；失败率超过阈值后打开熔断，避免 Worker 和连接池被占满。如果备用模型保持相同业务口径，可以路由备用模型并记录版本；否则保存任务为可恢复失败或转人工，不能静默生成无证据结果。入口还应根据队列和模型额度建立背压。

### 怎样设计限流 Key？

> 需要结合资源成本。登录可按 IP 和账号，模型调用应按租户、用户、模型以及 Token/并发额度，管理员批处理还应使用独立队列。多实例必须使用共享存储或网关，进程内计数只能用于本地或单实例。

## 13. 动手练习

1. 为登录、报价创建和模型调用分别设计限流维度；
2. 实现令牌桶或使用 SlowAPI 返回 429；
3. 模拟模型 50% 超时，观察无熔断时的线程耗尽；
4. 加入熔断和半开探测；
5. 设计 RAG 不可用时的显式降级；
6. 让队列超过阈值后拒绝低优先级任务；
7. 记录限流、熔断和降级指标。
