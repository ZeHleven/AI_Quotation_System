# 代码 Agent 工程：仓库检索、规则护栏与补丁验证

## 核心结论

AI 写出的补丁能够编译、测试变绿，不代表改动正确。代码 Agent 的真正任务是：

```text
在完成目标的同时
保持未授权业务语义、接口契约和安全边界不变
并用可复核证据证明这一点
```

可靠的代码 Agent 需要两条主线：

```text
仓库理解：
精确搜索为主，动态探索依赖和测试，语义检索按需补充

补丁安全：
先识别业务不变量和变更边界，再做最小修改、分层验证和 Diff 审查
```

> 资料说明：本笔记依据视频公开简介和章节摘要整理，并结合当前 AI 智能报价中台的仓库规范、代码、测试与 Codex Worker 设计扩展，不是逐字字幕。

---

## 1. 最危险的错误不是语法错误

语法错误通常很快暴露；业务语义漂移可能长期隐藏。

例如，需求只是“修复报价列表为空时的提示”，AI 却顺手：

- 把 `404` 改成 `200`；
- 把“仅管理员”改成“登录用户”；
- 把 `draft` 也加入正式报价查询；
- 将低置信候选从人工确认改成自动采用；
- 重命名响应字段但没有同步前端；
- 修改默认时区、金额精度或单位；
- 为了让测试通过而删除关键断言。

这些补丁可能代码整洁、局部测试通过，却改变了业务结果。

### 风险层次

| 层次 | 典型问题 | 常见检测方式 |
|---|---|---|
| 语法与类型 | 无法解析、类型不匹配 | 编译、类型检查 |
| 局部逻辑 | 分支、循环、空值错误 | 单元测试 |
| 接口契约 | 字段、状态码、错误类型改变 | Contract Test |
| 业务不变量 | 状态、价格、权限、审批规则漂移 | 业务回归与负向测试 |
| 副作用 | 重复写入、错误下发、错误迁移 | 集成测试、幂等与审计 |
| 系统行为 | 性能、并发、部署或兼容性退化 | Smoke、压测、渐进发布 |

越靠下，越不能只依赖模型自检。

## 2. 修改前先定义“补丁合同”

代码 Agent 不应收到一个模糊目标后直接编辑。先把任务转换为可验证的变更合同：

```yaml
goal:
  修复未补价占位行仍可确认下发的问题

allowed_scope:
  - confirm_push 校验逻辑
  - 对应错误提示
  - 直接相关测试

must_preserve:
  - 已完整补价的正常报价仍可下发
  - HTTP 409 阻断契约不变
  - 成本库 draft/active 规则不变
  - N8N 请求结构不变
  - 旧报价历史可读取

forbidden_changes:
  - 不新增数据库结构
  - 不修改权限角色
  - 不重构无关模块
  - 不改变价格计算口径

verification:
  - 新增一个失败复现测试
  - 运行 confirm_push 专项回归
  - 运行 API 契约测试
  - 检查最终 Diff
```

这份合同回答四个问题：

1. 要改变什么；
2. 哪些行为绝对不能变；
3. 允许修改哪些范围；
4. 用什么证据判断完成。

没有 `must_preserve` 的任务说明，容易让 AI 把“修复”理解成重新设计。

## 3. 审查 AI 补丁的五个重点

视频给出了五类核心检查，工程上可扩展为以下审查框架。

### 3.1 语义保持

不要只问“新代码是否合理”，还要问：

```text
相同输入在未授权场景下，结果是否与修改前等价？
```

重点比较：

- 状态迁移；
- 金额、数量、单位和舍入；
- 权限和数据范围；
- 自动处理与人工确认边界；
- 默认值和空值；
- 错误码与重试语义；
- 外部副作用的时机。

### 3.2 边界条件

AI 容易围绕正常示例写代码，应主动列举：

- 空输入、零值、负值；
- 最大长度和大文件；
- 重复请求、乱序事件和并发写入；
- 缺字段、多字段冲突；
- 旧数据、旧版本和历史兼容；
- 超时、部分成功和下游空响应；
- 未授权用户与跨租户资源；
- 恰好位于日期、金额或状态边界的输入。

### 3.3 依赖契约

一个函数的“返回结果看起来差不多”仍可能破坏调用方。需要核对：

```text
参数名与默认值
返回字段、类型和可空性
异常类型与 HTTP 状态码
同步/异步行为
事务和提交时机
副作用次数
日志、事件和审计字段
排序与分页
向后兼容字段
```

搜索定义后，还必须搜索所有调用方、API 路由、前端消费者和测试。

### 3.4 测试覆盖

测试的目标不是证明“代码执行过”，而是证明：

```text
目标行为已改变
关键旧行为未改变
危险边界仍被阻断
```

一项修复至少需要：

1. 修复前失败、修复后通过的复现测试；
2. 正常路径测试；
3. 相邻危险路径的负向测试；
4. 相关接口和业务回归。

### 3.5 无关改动

AI 常顺手整理导入、重命名变量、格式化整文件或重构公共函数。这会：

- 扩大审查面积；
- 掩盖真正改动；
- 增加合并冲突；
- 让回滚和故障定位变难；
- 引入未被需求授权的行为变化。

推荐约束：

```text
先完成最小正确补丁
→ 验证
→ 如确需重构，再单独提交
```

## 4. 代码 Agent 如何探索仓库

代码仓库不是一堆独立文本块，而是由符号、导入、调用、配置、迁移和测试构成的动态图。

推荐探索顺序：

```text
仓库级说明与约束
→ 目录和技术栈
→ 入口、路由或失败现象
→ 精确符号定义
→ 调用方和数据流
→ 对应 Schema、模型与配置
→ 测试和历史文档
→ 形成变更影响图
```

### Agentic Search 循环

```text
提出一个局部假设
→ 用文件名、符号或错误文本精确搜索
→ 阅读最小相关上下文
→ 根据 import、调用或测试继续追踪
→ 更新假设
→ 信息足够后停止搜索
```

常用工具职责：

| 工具 | 适用场景 |
|---|---|
| `rg --files` | 按目录、扩展名和命名模式找文件 |
| `rg` | 查符号、路由、字段、错误文本和调用点 |
| AST / Language Server | 精确查引用、类型和安全重命名 |
| Git Diff / Log | 判断改动范围和历史约定 |
| 测试收集器 | 找到最接近业务行为的可执行规格 |
| 构建与静态检查 | 验证跨文件契约和产物 |

代码 Agent 不应一开始读取整个仓库，也不应只读第一个搜索结果。

## 5. 为什么代码检索不能照搬传统 RAG

传统文档 RAG 常把内容切片、向量化，再按语义相似度召回。直接用于活跃代码库会遇到：

### 5.1 精确标识符更重要

代码问题通常包含：

```text
函数名
类名
路由
环境变量
数据库字段
错误码
测试名
```

这些信息用精确搜索通常比语义向量更可靠。

### 5.2 切片会破坏结构

独立代码块可能缺少：

- 类型和 import；
- 装饰器；
- 调用方；
- 事务边界；
- 相邻分支；
- 继承和协议；
- 测试前置条件。

高相似片段不一定是实际运行路径。

### 5.3 索引容易过期

分支、工作区和生成代码频繁变化。如果索引没有绑定：

```text
repository
branch
commit SHA
working-tree state
permissions
```

Agent 可能依据旧实现修改当前代码。

### 5.4 权限与数据治理更复杂

代码索引可能意外包含：

- 私有仓库内容；
- 密钥和配置；
- 已删除但仍敏感的历史代码；
- 不属于当前用户的模块；
- 构建产物、依赖目录和运行时文件。

### 5.5 语义召回不提供依赖关系

向量相似只能说明“内容像”，不能证明：

```text
它被谁调用
哪个实现实际生效
哪个测试保护该行为
改变它会影响哪些接口
```

### 正确取舍

```text
精确 Agentic Search 作为主干
+ 符号/依赖图增强
+ 语义检索作为补充
```

语义检索适合：

- 不知道准确术语时找概念位置；
- 检索 ADR、设计文档、Issue 和长历史说明；
- 跨语言或命名已变化的概念发现；
- 超大 Monorepo 的候选目录召回。

召回候选后仍要回到当前工作区，用精确搜索和实际代码验证。

## 6. 建立“变更影响图”

编辑前至少画出这条最小链路：

```text
用户入口
→ API / Command
→ Schema
→ Service
→ Model / Database
→ 外部系统或副作用
→ 前端消费者
→ 测试
```

每个节点记录：

```text
文件与符号
输入输出契约
业务不变量
调用方
权限
失败行为
对应测试
```

例如修改报价确认逻辑，不能只读路由函数，还要查：

- 请求 Schema；
- 预审完整性校验；
- 成本证据与 draft 沉淀；
- N8N 下发；
- 报价历史；
- HTTP 409/500 行为；
- 前端按钮禁用；
- 专项和回归测试。

这能防止“局部合理、全链路错误”。

## 7. 可靠的补丁工作流

### 第一步：建立基线

- 阅读仓库级约束；
- 查看工作区是否已有用户改动；
- 复现问题或确认现状；
- 找到当前测试和运行结果；
- 记录输入、环境和版本。

### 第二步：明确范围

- 写补丁合同；
- 列出业务不变量；
- 标记高风险副作用；
- 确定允许修改的文件和组件。

### 第三步：探索影响

- 找定义；
- 找调用方；
- 找 Schema、数据库和配置；
- 找测试；
- 找历史设计与兼容约定。

### 第四步：做最小修改

- 优先修改权威实现；
- 不复制已有规则；
- 不顺手重构无关代码；
- 不删除用户已有改动；
- 数据库变化必须走正式迁移。

### 第五步：分层验证

```text
语法/类型
→ 新增复现测试
→ 直接相关单元测试
→ 接口与业务契约测试
→ 相邻模块回归
→ 前端构建或集成 Smoke
```

### 第六步：审查最终 Diff

逐项检查：

- 是否只改了授权范围；
- 是否出现大段重排或格式化；
- 是否改变默认值、错误码或权限；
- 是否新增未解释的依赖；
- 是否遗漏调用方；
- 测试是否真的断言业务结果；
- 文档和配置是否与实现一致。

### 第七步：交付证据

交付说明应包括：

```text
问题根因
修改位置和理由
保持不变的业务规则
执行过的验证
未验证的部分
风险与回滚方式
```

不要只说“已修复、测试通过”。

## 8. 测试是业务契约，不是通过仪式

### 测试分层

| 测试 | 保护内容 |
|---|---|
| 单元测试 | 局部计算和分支 |
| Schema / Contract Test | 字段、类型、状态码和兼容性 |
| 业务不变量测试 | 权限、状态、金额、审批和阻断规则 |
| 集成测试 | 数据库、队列、外部适配和事务 |
| 前端契约测试 | 页面依赖的接口与文案行为 |
| 迁移测试 | 新旧 Schema 与升级路径 |
| Smoke / E2E | 真实部署链路是否可用 |

### 必须有负向测试

高风险系统不能只证明“允许的事情能成功”，还要证明：

```text
未授权用户不能操作
未确认数据不能下发
无效状态不能迁移
失败后不能产生业务写入
重复请求不能重复生效
旧版本不能绕过新规则
```

### 防止“为了绿灯改测试”

修改既有断言前必须解释：

1. 是需求明确改变了契约，还是代码破坏了契约；
2. 哪个文档或业务负责人授权了变化；
3. 下游调用方是否已同步；
4. 是否需要兼容期和迁移方案。

如果只因新实现无法满足旧测试就删除断言，测试失去了护栏作用。

## 9. 代码 Agent 的权限与隔离

最小权限同样适用于开发 Agent。

### 默认可开放

- 读取当前任务范围内的源码和文档；
- 搜索符号和调用方；
- 在工作区修改授权文件；
- 运行约定的测试、静态检查和构建；
- 读取 Git Diff。

### 应限制或单独审批

- 读取 `.env`、密钥和用户数据；
- 访问任务外仓库；
- 安装新依赖或联网执行未知脚本；
- 修改数据库或生产配置；
- 删除大量文件；
- 自动提交、推送或部署；
- 执行不可逆迁移；
- 绕过测试和权限校验。

如果使用语义代码索引，还应保证：

```text
索引作用域与仓库权限一致
敏感文件明确排除
索引绑定 commit / branch
删除和权限变更能及时传播
查询和结果可审计
```

## 10. 当前 AI 智能报价中台的实现映射

以下结论来自 2026-07-28 对当前仓库的检查。

### 已有的强项

1. **仓库约束清晰**
   - 根目录和 `AI_Middle_Office/AGENTS.md` 保存架构、运行方式、冻结范围和当前阶段；
   - `ROADMAP.md` 对多数功能明确记录“不改什么、不启动什么、怎样验收”；
   - 这些内容可以直接转成代码 Agent 的 `must_preserve` 和 `forbidden_changes`。

2. **业务契约已有测试保护**
   - 统一 API 响应结构由 `api_ok` / `api_page` 和对应测试保护；
   - RBAC、报价任务、确认下发、完整性阻断、成本库状态和前端契约均有专项测试；
   - 大量测试明确断言 `401/403/409/410/422` 等失败行为，而不只测试成功路径。

3. **数据库迁移边界明确**
   - 新增字段和表必须走 Alembic；
   - 生产环境关闭 `AUTO_CREATE_TABLES` 和启动兼容迁移；
   - 这能防止 AI 为图省事在启动时偷偷补表。

4. **Feature Flag 与渐进发布**
   - 多个模块通过 `FEATURE_*` 控制；
   - 试运行功能与正式业务链路分离，适合小范围验证和回滚。

5. **已有 Code Agent 输出合同实例**
   - Codex Worker POC 不允许 Agent 修改源码、读取 `.env` 或直接写数据库；
   - 系统不信任 Agent 生成的 Excel，只读取 `codex_result.json`；
   - JSON 必须通过 Schema、必填字段、可列项状态和证据引用校验后才允许导出；
   - 这是“Agent 产出建议，确定性系统校验后消费”的优秀边界。

6. **测试资产较丰富**
   - 当前 `AI_Middle_Office/tests/` 下有 162 个测试模块；
   - 另有 Agent、MCP、政策数据和持久化专项检查；
   - 可按路由、服务、业务阶段和前端契约做分层回归。

### 适合当前项目的检索策略

当前仓库变化快、业务阶段多、精确字段和错误码密集，因此优先：

```text
AGENTS / ROADMAP 定边界
→ rg --files 找模块
→ rg 查路由、字段、错误码和测试名
→ 沿 import / 调用关系阅读
→ 用实际测试验证
```

暂时没有必要先把全部源码建立传统向量 RAG。若后续仓库继续扩大，可先对 ADR、长设计文档和历史决策做语义索引，源码仍以精确搜索和符号图为主。

### 仍需补强的地方

| 缺口 | 风险 |
|---|---|
| 大量规则分散在很长的 `AGENTS.md` 和 `ROADMAP.md` | Agent 容易漏读或无法判断哪条仍生效 |
| 业务不变量与对应测试没有统一索引 | 修改一个规则时难以选全回归集 |
| 测试文件带大量阶段编号 | 新成员和 Agent 不易从业务能力找到保护测试 |
| `archive/`、`runtime/`、`node_modules/`、`dist/` 等目录较多 | 搜索结果容易被历史或生成内容污染 |
| 前端 `package.json` 目前只有 dev/build/preview | 缺少统一 lint、单测和类型检查入口 |
| 没有统一的补丁合同和变更风险分级 | 不同 AI 编码任务的验证深度不一致 |
| 尚未看到仓库级符号/依赖影响图 | 大范围重构仍依赖人工追踪调用关系 |

### 推荐升级顺序

#### P0：机器可读的变更合同

为每个 AI 编码任务保存：

```text
goal
allowed_paths
must_preserve
forbidden_changes
risk_level
required_tests
runtime_smoke
```

高风险任务必须先由人工确认合同，再允许编辑。

#### P0：业务不变量—测试索引

建立简单映射：

```yaml
quote.confirm_push.unpriced_placeholder_block:
  owner: budget
  implementation:
    - app/api/v1/quote.py
  tests:
    - tests/test_quote_jobs.py
    - tests/test_quote_confirm_push_biz2m.py
  invariants:
    - 未补有效价格不得下发
    - 下发失败不得沉淀成本库
```

先覆盖权限、报价下发、价格口径、状态迁移和数据库迁移等高风险能力。

#### P0：固定搜索边界

代码搜索默认排除：

```text
archive
runtime
node_modules
dist
.git
缓存、日志和生成报告
```

需要历史实现时再显式进入 `archive/`。

#### P1：统一验证入口

提供一组标准命令：

```text
后端专项测试
API/业务契约回归
前端 lint/typecheck/test/build
Alembic heads/current 检查
关键运行态 Smoke
```

让 Agent 不能用“跑了一个测试”模糊代替完整验证。

#### P1：文档语义检索，源码精确检索

先为设计文档、ADR、Runbook 和历史决策建立权限受控的语义索引；返回结果必须标注文件、版本和 commit。源码只在出现真实规模瓶颈时再增加 AST 或代码图索引。

## 11. FDE 面试表达

### 问：AI 写补丁时怎样防止业务规则漂移？

可以回答：

> 我会先把需求转换成补丁合同，明确允许改什么、必须保持什么和怎样验收。然后沿定义、调用方、Schema、数据库、副作用和测试建立影响图，采用最小 Diff。验证不只跑正常单测，还会覆盖接口契约、业务不变量、负向阻断和相邻回归。最后单独审查默认值、错误码、权限、状态迁移和无关改动。测试通过只是证据之一，核心是证明未授权语义保持不变。

### 问：为什么代码 Agent 不应只用传统 RAG？

可以回答：

> 代码检索更依赖精确符号、当前工作区、调用关系和权限。传统切片向量检索可能破坏代码结构，索引也容易落后于分支和未提交改动。因此我会让 Agent 以精确搜索和符号追踪为主，像开发者一样逐步找定义、调用方和测试；语义检索用于发现概念、设计文档和跨命名候选。成熟方案不是完全不用 RAG，而是 Agentic Search 为主、语义召回为辅，并绑定仓库、分支、commit 和权限。

### 项目故事

当前项目可以这样讲：

```text
规则复杂：
报价下发、成本状态、权限、证据和人工确认存在大量边界。

治理方式：
AGENTS/ROADMAP 明确冻结范围；
Alembic 管理结构变化；
Feature Flag 控制试运行；
专项、契约和负向测试保护业务不变量。

Agent 边界：
Codex Worker 只能产出 JSON 草稿，不能改源码或写数据库；
系统通过确定性合同校验后才导出结果。

下一步：
把长文档中的规则转成机器可读补丁合同和“不变量—测试”索引，
让代码 Agent 自动选择验证范围并输出可审计证据。
```

## 12. 代码 Agent 检查清单

### 修改前

- [ ] 已阅读当前目录的仓库约束
- [ ] 已检查用户现有改动
- [ ] 已复现问题或建立行为基线
- [ ] 已写明目标、允许范围和禁止变化
- [ ] 已找到实现、调用方、Schema、数据和测试

### 修改中

- [ ] 修改集中在权威实现
- [ ] 没有复制已有业务规则
- [ ] 没有读取或暴露密钥
- [ ] 没有修改无关文件
- [ ] 数据库变化走正式迁移
- [ ] 高风险副作用仍受权限、幂等和人工确认保护

### 验证

- [ ] 新增了可复现问题的测试
- [ ] 正常路径和负向路径均覆盖
- [ ] API、错误码和字段契约保持兼容
- [ ] 运行了直接相关和相邻回归
- [ ] 前端构建或类型检查通过
- [ ] 最终 Diff 已人工或独立流程复核
- [ ] 未验证部分已明确说明
