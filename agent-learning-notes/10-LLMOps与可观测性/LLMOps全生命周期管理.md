# LLMOps：大模型与 Agent 的持续评测、发布和运营

## 定义

可以把 LLMOps 理解为：

> 对大模型应用和 Agent 进行版本管理、持续评测、安全发布、线上监控和反馈优化的工程体系。

传统软件主要管理代码，而 LLM 应用的行为同时受到多个可变组件影响：

```text
代码
+ Prompt
+ 模型
+ 知识库
+ Embedding 与检索策略
+ 工具
+ 业务规则
+ 运行数据
```

任何一个组件变化，都可能改变结果、延迟、成本或下游兼容性。

因此，Agent “能运行”只是起点；LLMOps 关注的是：

```text
能否评测
能否复现
能否发布
能否监控
能否回滚
能否持续优化
```

---

## 1. LLMOps 与 MLOps

### MLOps

传统 MLOps 更常围绕自训练模型：

```text
数据采集
→ 特征与训练
→ 模型验证
→ 模型部署
→ 漂移监控
```

### LLMOps

LLMOps 常围绕基础模型或模型 API 构建应用：

```text
选择模型
→ 设计 Prompt
→ 接入 RAG 和工具
→ 建立评测
→ 灰度发布
→ 监控质量、成本和安全
```

两者并非完全独立。LLMOps 可以视为面向大模型应用特征的一组 MLOps 扩展，尤其强调 Prompt、检索、工具轨迹和自然语言评测。

---

## 2. LLMOps 管理的对象

```text
LLMOps
├── 模型与路由
├── Prompt 与上下文
├── 数据与知识库
├── 工具和 Agent 流程
├── 评测集与评测结果
├── 发布与回滚
├── 可观测性
├── 成本与容量
└── 安全、权限与合规
```

### 运行版本清单

每个任务应能关联到一组完整版本：

```json
{
  "application_version": "quote-agent-2.3.0",
  "workflow_version": "quote-flow-v5",
  "prompt_version": "quote-review-v3",
  "model_provider": "provider_a",
  "model_name": "model_x",
  "model_revision": "2026-07",
  "knowledge_version": "materials-2026-07-27",
  "embedding_version": "embedding-v2",
  "retrieval_version": "hybrid-rerank-v4",
  "toolset_version": "quote-tools-v3",
  "rule_version": "pricing-rules-v8"
}
```

只有记录完整版本谱系，历史结果才可能复现。

## 3. 模型管理与路由

模型不应散落并写死在业务代码中。应集中管理：

```json
{
  "provider": "provider_a",
  "model_name": "model_x",
  "temperature": 0.1,
  "max_output_tokens": 2000,
  "timeout_seconds": 60,
  "max_retries": 2,
  "capabilities": ["text", "structured_output"]
}
```

### 路由维度

- 输入模态
- 任务复杂度
- 结构化输出能力
- 风险等级
- 延迟目标
- 成本预算
- 数据地域与合规要求
- 模型健康状态

```text
简单分类 → 小模型
复杂推理 → 推理模型
图纸理解 → VLM
向量化 → Embedding 模型
确定性计算 → 代码或规则
```

### 路由需要记录

- 初始目标模型
- 实际使用模型
- 路由原因
- 是否发生回退
- 各候选模型的失败原因

模型路由本身也需要评测，否则可能为了省钱而损失质量，或把简单任务路由到昂贵模型。

## 4. Fallback 与降级

主模型失败后可以采用：

```text
主模型
  ↓ 超时或不可用
备用模型
  ↓ 仍失败
规则方案 / 保存草稿 / 转人工
```

Fallback 不限于换模型：

- VLM 失败 → OCR + 规则提取
- 向量检索失败 → BM25
- 自动生成失败 → 保存草稿并转人工
- 实时价格接口失败 → 使用最近有效快照并标明日期

### 注意事项

- 备用模型必须满足输出 Schema
- 回退后的质量和能力可能不同
- 高风险结果不能静默使用低能力模型
- 所有回退都应进入 Trace
- 回退结果必须标明数据来源和限制

## 5. Prompt 管理

Prompt 应具备：

- 集中存储
- 稳定名称
- 版本号
- 变更记录
- 评测结果
- 发布状态
- 回滚能力

```text
prompts/
├── quote_extract_v1.txt
├── quote_review_v1.txt
├── risk_analysis_v2.txt
└── material_match_v3.txt
```

也可以存入数据库或专门的 Prompt Registry。

### Prompt 模板

```text
你是一名工程造价审核员。

项目地区：{{ region }}
项目类型：{{ project_type }}

审核规则：
{{ review_rules }}

报价数据：
{{ quote_items }}

输出 Schema：
{{ output_schema }}
```

模板化的价值：

- 变量边界清晰
- 容易测试
- 易于复用
- 可验证必填字段
- 便于比较版本

### 调用记录

```json
{
  "prompt_name": "quote_review",
  "prompt_version": "v3",
  "template_hash": "sha256:...",
  "model": "model_x"
}
```

敏感输入不应原样写入普通日志，可记录脱敏摘要、哈希或数据引用。

## 6. 灰度发布与 A/B 测试

### 灰度发布

新版本先处理少量任务：

```text
v1：90%
v2：10%
```

观察：

- 准确率
- 格式成功率
- 失败率
- 人工修改率
- 延迟
- Token 和任务成本

符合门槛后逐步扩大流量，否则回滚。

### A/B 测试

用于比较两个方案：

```text
A：Prompt v1 + 模型 A
B：Prompt v2 + 模型 A
```

原则：

- 一次尽量只改变一个主要变量
- 用户和任务应稳定分组
- 样本量应足够
- 同时设置质量、安全和成本护栏
- 高风险业务保留人工审核

如果模型、Prompt、检索和规则同时变化，只能说明“整个版本包”有差异，无法判断单一原因。

## 7. 评测体系

LLMOps 的核心不是换模型，而是建立可重复的比较方法。

### 离线评测

上线前在固定数据集上运行：

```text
候选版本
→ 固定评测集
→ 与基线比较
→ 决定是否发布
```

优点：

- 安全
- 快速
- 可重复

局限：

- 可能无法覆盖真实分布
- 容易被固定测试集过度优化

### 线上评测

关注真实行为：

- 用户是否接受
- 是否人工修改
- 是否重新生成
- 是否转人工
- 是否完成业务目标
- 是否发生投诉或安全事件

### 五层评测

| 层级 | 指标示例 |
|---|---|
| 模型层 | 字段准确率、分类准确率、JSON 合法率 |
| 检索层 | Recall@K、Top-K 命中率、引用正确率、重排效果 |
| 工具层 | 工具选择、参数正确率、成功率、重复调用率 |
| Agent 层 | 任务完成率、平均步数、循环率、人工接管率 |
| 业务层 | 人工耗时、报价周期、错误率、使用率、接受率 |

不能只看最终答案；还要判断过程、系统稳定性和业务价值。

## 8. Golden Dataset

Golden Dataset 是经过领域专家确认的高质量标准评测集。

报价系统可以沉淀：

- 原始图纸和清单
- OCR 标准结果
- 材料标准清单
- 正确规格与数量
- 合理价格范围
- 正确风险等级
- 人工最终报价
- AI 输出与人工修改差异

### 数据集治理

每个案例应记录：

- 案例 ID
- 输入版本
- 期望结果
- 允许误差
- 标签
- 审核人
- 数据集版本
- 生效时间

Golden Dataset 不是永远不变的。业务规则和价格变化后，需要复核和版本化。

## 9. 可观测性

生产 Agent 至少需要四类信号。

### Logs

记录离散事件：

- 任务创建
- OCR 开始
- 模型调用
- 工具失败
- 状态迁移
- 任务完成

### Traces

串联一次任务的完整链路：

```text
请求
→ Runtime
→ RAG
→ 模型
→ 工具
→ 数据库
→ 输出
```

### Metrics

聚合整体表现：

- 吞吐量
- 成功率和失败率
- 延迟分位数
- Token 消耗
- 工具错误率
- 队列长度

### Alerts

异常条件触发通知：

- 失败率超过阈值
- 模型连续超时
- 队列持续堆积
- 单任务成本异常
- 数据库或检索服务不可用

### 模型调用记录

```json
{
  "task_id": "task_001",
  "trace_id": "trace_001",
  "step_name": "quote_review",
  "model": "model_x",
  "prompt_version": "quote_v3",
  "input_tokens": 5200,
  "output_tokens": 860,
  "latency_ms": 4800,
  "success": true,
  "retry_count": 0,
  "created_at": "2026-07-27T15:00:00+08:00"
}
```

记录时需要脱敏，并设置访问权限和保留周期。

## 10. 成本治理

Agent 往往会调用多个模型和工具。不能只看单次 API 价格，而应计算完整任务成本：

```text
单任务 AI 成本
= 模型调用
+ OCR / VLM
+ Embedding
+ 检索与重排
+ 工具 API
+ 存储和计算
```

更进一步，应关注：

```text
每个成功任务的成本
每个被人工接受结果的成本
每个业务完成结果的成本
```

### 常见优化方式

#### 模型分级

简单任务使用小模型，复杂任务再使用大模型。

#### 缓存与结果复用

适合复用：

- 同一文件版本的 OCR
- 同一模型版本的图纸识别
- Embedding
- 稳定知识检索结果

缓存键至少考虑：

```text
租户 + 输入哈希 + 文件版本 + 模型版本
+ Prompt 版本 + 工具版本 + 权限范围
```

否则可能复用旧结果或造成跨租户数据泄露。

#### 上下文压缩

只提供任务所需信息。

#### 限制循环

设置步骤、时间和 Token 预算。

#### 批处理

一次提取多个同类字段，减少往返调用。

### 质量、速度、成本

三者通常需要权衡：

| 场景 | 优先目标 |
|---|---|
| 内部普通测算 | 成本和速度，保留人工复核 |
| 客户演示 | 响应速度和展示稳定性 |
| 高金额正式报价 | 质量、依据和可追溯性 |

## 11. 发布与回滚

Agent 发布物不只是代码，而是一个版本包：

```text
代码版本
+ Prompt 版本
+ 模型配置
+ 知识库和索引
+ 工具定义
+ Workflow
+ 业务规则
```

至少要支持回滚：

- Prompt
- 模型配置
- 知识库和索引
- Agent 流程
- 业务规则

### 发布门槛

- 离线评测不低于基线
- 安全指标无退化
- 格式和工具成功率达标
- 成本和延迟在预算内
- 回滚路径已验证

数据库结构和不可逆外部动作需要单独的迁移与补偿方案，不能假设切回版本就能自动恢复。

## 12. 知识库版本管理

历史回答需要能够解释：

- 使用了哪版文档
- 使用了哪天的价格数据
- 采用哪个 Embedding 模型
- 采用何种 Chunk 策略
- 使用哪个索引和重排器
- 最终召回了哪些片段

```json
{
  "knowledge_version": "materials-2026-07-27",
  "price_snapshot_id": "price-snapshot-018",
  "embedding_version": "embedding-v2",
  "chunking_version": "chunk-v3",
  "index_version": "milvus-green-042",
  "reranker_version": "rerank-v2",
  "retrieved_document_ids": ["doc_12", "doc_35"]
}
```

知识库版本不只是文档版本，还包括整个检索管线。

## 13. 漂移监控

### 数据漂移

输入分布发生变化：

- 新材料比例增加
- 图纸格式变化
- 项目类型变化
- 客户需求变化

### 概念漂移

同样输入对应的正确业务判断发生变化：

- 价格区间变化
- 审核标准变化
- 企业规则调整

### 系统漂移

外部依赖变化导致行为变化：

- 模型供应商更新
- OCR 版本变化
- 检索索引变化
- 第三方 API 返回格式变化

### 监控信号

- 未匹配材料占比
- 新材料占比
- 检索无结果率
- 低质量引用率
- 人工修改率
- 回退模型使用率
- 格式失败率

指标异常只表示需要调查，不一定能直接证明是哪一种漂移。

## 14. 反馈闭环

```text
AI 输出
→ 人工审核
→ 保存修改差异
→ 分类错误原因
→ 更新规则 / Prompt / 知识库
→ 离线评测
→ 灰度发布
→ 线上监控
```

修改差异示例：

```json
{
  "ai_value": "普通玻璃",
  "human_value": "6+12A+6 Low-E中空玻璃",
  "error_type": "SPECIFICATION_MISSING",
  "reviewer_id": "user_42",
  "reviewed_at": "2026-07-27T16:00:00+08:00"
}
```

人工修改也不应自动视为绝对真值，应考虑审核人资质、多人一致性和后续业务结果。

## 15. 错误分类

不要把所有失败归因于“模型不准”。

| 错误类型 | 含义 |
|---|---|
| `INPUT_ERROR` | 输入文件或参数问题 |
| `OCR_ERROR` | 文字识别错误 |
| `RETRIEVAL_ERROR` | 未召回正确知识 |
| `MODEL_ERROR` | 模型理解或生成错误 |
| `TOOL_ERROR` | 工具执行错误 |
| `RULE_ERROR` | 业务规则错误 |
| `DATA_ERROR` | 源数据错误或过期 |
| `SYSTEM_ERROR` | 网络、队列或基础设施错误 |

建议同时记录：

- 是否可重试
- 责任组件
- 影响范围
- 是否需要人工
- 修复方式

不同错误需要不同处理，分类是改进闭环的基础。

## 16. 最小 LLMOps 面板

### 总览

- 今日任务数
- 成功率
- 平均和 P95 耗时
- 平均单任务 Token
- 平均单任务 AI 成本
- 人工审核率
- 人工修改率
- 错误类型 Top 5

### 组件视图

- 各模型调用量、成功率和成本
- 各工具调用量和错误率
- 各步骤耗时
- Prompt 版本分布
- 回退与降级比例
- 队列长度和 Worker 状态

### 任务详情

- 任务输入引用
- 版本清单
- 模型和 Prompt
- 知识库和检索证据
- 工具调用链
- 每一步耗时与成本
- 失败原因
- 人工修改记录
- 最终结果

面板用于发现问题，原始 Trace 和审计记录用于深入定位。

## 17. 当前报价中台的最小改造建议

当前系统已经具备任务事件、报价证据、RAG Trace、Prompt 回归、反馈记录、运营看板和人工审核等能力。

在新增数据表前，应先盘点并复用：

- `quote_job_events`
- `quote_rag_traces`
- `prompt_regression_cases`
- `prompt_regression_runs`
- 报价证据和反馈记录
- 现有看板聚合接口

### 优先事项

1. 建立统一的 `trace_id` 和 Span 模型，贯通 FastAPI、Celery、n8n、Dify 与 RAG。
2. 形成统一运行版本清单，记录 Prompt、模型、知识库、检索、工具和规则版本。
3. 补齐每次模型调用的 Token、延迟、状态、重试和回退记录。
4. 将现有评测按模型、检索、工具、Agent、业务五层归档。
5. 在现有管理看板中增加单任务成本和版本分布，不急于新建独立平台。
6. 用现有人工修改和打回数据完善错误分类与 Golden Dataset。

如果现有表无法承载调用级 Trace，再通过 Alembic 设计统一日志表；不要先创建功能重叠的 `llm_call_logs`。

## 上线检查清单

### 版本

- [ ] 能还原代码、Prompt、模型、知识库、工具和规则版本
- [ ] 关键版本可以回滚
- [ ] 版本变更有负责人和说明

### 评测

- [ ] 有版本化 Golden Dataset
- [ ] 上线前与基线对比
- [ ] 同时检查质量、安全、延迟和成本
- [ ] 线上指标能够回流

### 可观测性

- [ ] 任务有统一 Trace ID
- [ ] 模型和工具调用可定位
- [ ] 日志脱敏并设置保留周期
- [ ] 关键异常有告警

### 成本

- [ ] 能计算完整任务成本
- [ ] 设置任务和组件预算
- [ ] 缓存键包含版本、租户和权限范围
- [ ] 回退与重试成本可见

### 发布

- [ ] 支持灰度
- [ ] 设置自动或人工停止条件
- [ ] 回滚路径经过验证
- [ ] 高风险业务保留人工确认

## 一句话总结

> 无法评测的 Agent 无法优化，无法追踪的 Agent 无法可靠上线，无法回滚的 Agent 无法安全迭代。
