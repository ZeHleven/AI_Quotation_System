# 练习 06：微服务超时、重试、熔断、降级、健康检查与隔离实战

## 实验结论

本次用 Python 标准库和虚拟时钟模拟下游服务，通过 29 项断言，验证：

- 短暂故障只重试 1 次后恢复；
- 业务或参数错误不重试；
- 总 Deadline 耗尽后停止重试；
- 剩余 20ms 时，下次调用的超时也只能是 20ms；
- 连续失败 2 次后打开熔断器；
- Open 状态快速失败，不再调用下游；
- 冷却后进入 Half-Open，探测成功再关闭；
- 熔断时可以返回明确标记的旧缓存；
- 没有安全降级结果时返回受控错误，不编造答案；
- Liveness 与 Readiness 分工明确；
- 核心依赖故障返回未就绪，可选依赖故障进入降级；
- 模型并发限制为 2、等待队列为 1，溢出请求快速拒绝；
- 模型资源池饱和时，独立的数据库资源池仍能工作。

一句话记忆：

```text
Deadline 管整条链路
Timeout 管单次等待
Retry 处理短暂故障
Circuit Breaker 阻止持续放大
Fallback 保留有限能力
Bulkhead 隔离资源
Health Check 决定重启或摘流
```

## 2. 保护顺序

推荐调用链：

```text
入口限流
→ Bulkhead 获取资源
→ 检查熔断器
→ 计算剩余 Deadline
→ 设置单次 Timeout
→ 调用依赖
→ 仅对短暂错误有限重试
→ 失败后安全降级或受控失败
→ 记录指标与 Trace
```

各机制解决的问题不同，不能互相替代：

| 机制 | 主要问题 |
|---|---|
| 限流 | 进入系统的流量过大 |
| Timeout | 单次调用等待无上限 |
| Deadline | 整条请求链超过用户预算 |
| Retry | 网络抖动、503 等短暂故障 |
| 熔断 | 故障依赖被持续调用 |
| 降级 | 完整能力不可用时保留有限服务 |
| Bulkhead | 一个依赖耗尽全部并发资源 |
| 背压 | 下游处理不过来时阻止队列无限增长 |

## 3. Timeout 与 Deadline

### 区别

```text
Timeout：一次调用最多等多久
Deadline：整个业务请求最晚何时结束
```

如果用户总预算为 250ms：

```text
第一次调用耗时 150ms
→ 退避 80ms
→ 只剩 20ms
→ 第二次调用的 Timeout 必须缩短到 20ms
```

本次结果：

```text
总预算 = 250ms
尝试次数 = 2
第二次 Timeout = 20ms
总耗时 = 250ms
结果 = deadline_exhausted
```

不能在只剩 20ms 时仍给下游 150ms，否则局部超时配置会突破全链路承诺。

### 工程公式

```text
remaining = deadline - now
attempt_timeout = min(configured_timeout, remaining)
```

还要为序列化、数据库提交和返回响应预留时间，不能把全部预算交给模型。

## 4. 有限重试

### 适合重试

- 网络瞬断；
- 连接重置；
- 读取超时；
- 明确可恢复的 502、503、504；
- Provider 返回 429，且尊重 `Retry-After`；
- 消费者在幂等保护下处理短暂故障。

### 不适合重试

- 参数校验失败；
- 权限不足；
- 业务状态冲突；
- 文件格式错误；
- 余额或额度明确不足；
- 非幂等写入且无法确认首次结果。

本次实验：

| 场景 | 结果 |
|---|---|
| 第一次 503，第二次成功 | 2 次调用，110ms 内成功 |
| 第一次 400 | 只调用 1 次，不重试 |
| Deadline 耗尽 | 第 2 次超时后停止 |

退避：

```text
delay = base × 2^(attempt - 1) + jitter
```

实验为了结果确定使用固定退避；真实多实例系统应加随机抖动，避免同时重试形成尖峰。

### 重试的三个前提

```text
错误可恢复
+ 操作幂等
+ Deadline 还有预算
```

若三层服务各重试 3 次，最坏可能放大为：

```text
3 × 3 × 3 = 27 次下游调用
```

因此应明确唯一重试层，并设置最大次数、总预算和指标。

## 5. 熔断器

状态机：

```text
Closed
  │ 连续失败达到阈值
  ▼
Open
  │ 冷却时间结束
  ▼
Half-Open
  ├─ 探测成功 → Closed
  └─ 探测失败 → Open
```

本次设置：

```text
失败阈值 = 2
冷却时间 = 30s
```

真实结果：

1. 连续两次 503 后进入 Open；
2. Open 状态的请求立即失败；
3. 下游调用次数保持 2，没有被继续打满；
4. 虚拟时间推进 30 秒；
5. Half-Open 放行一次探测；
6. 探测成功，回到 Closed，失败计数清零。

### 熔断粒度

推荐按：

```text
Provider + 模型 + 接口类型
```

隔离熔断。

不要因为一个 OCR 模型失败，就熔断整个模型平台；也不要用全局熔断器让不同租户互相影响。

### 熔断不等于重试

```text
重试：认为下一次可能成功
熔断：认为近期继续调用大概率失败
```

熔断打开后继续普通重试，会失去快速失败的意义。

## 6. 安全降级

本次在熔断打开时返回缓存：

```json
{
  "value": {"quote": 1260},
  "source": "stale_cache",
  "degraded": true,
  "warning": "CircuitOpenError",
  "cached_at": 123.0
}
```

降级必须回答三个问题：

1. 数据来自哪里？
2. 降低了什么能力？
3. 用户或下游是否需要人工确认？

AI 系统的安全边界：

| 故障 | 可接受降级 | 不可接受 |
|---|---|---|
| RAG 不可用 | 标记“无证据，需人工确认” | 用模型常识冒充知识库证据 |
| 模型不可用 | 切换已评测的备用模型并标版本 | 静默改变价格口径 |
| 看板聚合失败 | 展示带时间戳的最近快照 | 把旧数据显示成实时数据 |
| OCR 失败 | 转人工录入 | 猜测文件内容 |
| 无安全缓存 | 返回受控失败 | 编造一个“看起来合理”的结果 |

本次验证：存在缓存时明确降级；不存在缓存时抛出 `ServiceUnavailableError`。

## 7. Liveness 与 Readiness

| 探针 | 回答的问题 | 失败后的动作 |
|---|---|---|
| Liveness | 进程是否还活着 | 重启实例 |
| Readiness | 是否能接收新流量 | 从负载均衡摘流 |
| Startup | 慢启动是否完成 | 启动阶段暂缓其他探针 |

本次场景：

| 场景 | Liveness | Readiness |
|---|---:|---:|
| 全部健康 | 200 | 200 ready |
| 数据库故障 | 200 alive | 503 not_ready |
| 可选模型故障 | 200 alive | 200 degraded |

为什么数据库故障时 Liveness 仍应为 200：

> 进程本身仍正常响应，盲目重启可能造成重启风暴；Readiness 摘流更合适。

健康检查要求：

- 探针要轻量；
- 核心依赖和可降级依赖分级；
- 返回依赖状态和延迟；
- 设置探针自身超时；
- 不执行完整报价或模型推理；
- 不能永远固定返回 200 且没有状态语义。

## 8. Bulkhead 隔离与背压

本次模型资源池：

```text
并发上限 = 2
等待队列 = 1
```

四个并发请求的结果：

```text
2 个执行
1 个排队
第 4 个快速拒绝
最大实际并发 = 2
```

同时，独立数据库资源池返回：

```text
db-ok
```

说明模型池饱和没有耗尽数据库池。

### 为什么队列必须有界

无限队列只会把拒绝变成更晚的超时：

```text
请求不断进入
→ 排队时间增加
→ Deadline 到期
→ 客户端重试
→ 队列继续膨胀
```

背压做法：

- 有界等待队列；
- 溢出返回 429 或 503；
- 提供 `Retry-After`；
- 长短任务使用不同 Worker 队列；
- 在线请求和批处理隔离；
- 按租户、模型、任务类型设置并发额度。

## 9. 必须观测的指标

| 机制 | 关键指标 |
|---|---|
| Timeout | 超时率、阶段耗时、剩余 Deadline |
| Retry | 重试率、重试成功率、请求放大倍数 |
| 熔断 | Open 次数、持续时间、Half-Open 结果 |
| 降级 | 降级率、缓存年龄、人工接管率 |
| Bulkhead | 活跃数、等待数、拒绝数、队列等待时间 |
| Health | 各依赖状态、探针延迟、摘流次数 |

日志至少携带：

```text
trace_id
dependency
endpoint
attempt
remaining_deadline_ms
timeout_ms
circuit_state
fallback_source
bulkhead_wait_ms
error_type
```

阈值应由 SLO、容量测试和真实错误分布决定，不能长期依赖拍脑袋常量。

### 面试中要诚实说明的设计差异

- 当前 `/health/ready` 通过响应体表达 `ready/degraded`，路由本身未统一返回 503；
- 当前模型熔断器有失败阈值和冷却恢复，但不是本练习这种严格的单探针 Half-Open 状态机；
- AI 批处理已有 Semaphore，但有界等待队列和入口背压需要结合任务队列继续治理；
- 不同链路已有局部 Timeout/Retry，完整 Deadline 传播仍是可继续补强项。

这些是架构评审点，不代表应该未经兼容性分析直接修改现有系统。

### 报价链路的推荐保护

```text
FastAPI 接收报价
→ 用户/租户额度
→ 保存任务并返回 202
→ Celery 队列背压
→ RAG 独立 Timeout + 熔断
→ 模型独立 Bulkhead + Deadline + 有限重试
→ N8N 推送使用幂等键
→ 无证据或无安全价格时转人工
→ 全链路 Trace 与指标
```

报价属于高风险业务，降级不能静默改变价格和证据口径。

## 11. 面试回答

### 怎样防止下游故障拖垮整个系统？

> 我会先设置端到端 Deadline 和单次 Timeout，只对明确的短暂错误做幂等、有限、带退避抖动的重试。连续失败达到阈值后按依赖粒度熔断，冷却后只放少量 Half-Open 探测。每个依赖使用独立连接池或 Semaphore，并设置有界队列；完整能力不可用时只返回有来源、可识别的降级结果，否则受控失败。

### Timeout 和 Deadline 有什么区别？

> Timeout 限制一次调用，Deadline 限制整个用户请求。每次重试前都要计算剩余预算，把 `min(单次超时, 剩余预算)` 传给下游。我在实验中验证总预算只剩 20ms 时，第二次调用的 Timeout 自动缩短到 20ms，总耗时没有超过 250ms。

### 什么错误可以重试？

> 网络抖动、读取超时和明确可恢复的 503 通常可以；参数错误、权限错误和业务冲突不能靠重试修复。还必须保证操作幂等并且 Deadline 有剩余。重试应集中在明确的一层，否则多层三次重试会把一次请求放大为 27 次。

### 熔断和限流有什么区别？

> 限流保护系统免受过量入口流量；熔断保护系统免受已故障依赖的持续拖累。前者基于速率或并发，后者基于失败率、慢调用或连续失败。两者可以同时存在。

### 如何设计 AI 服务降级？

> 先定义质量红线。RAG 故障时可以返回“无证据、需人工确认”，但不能让模型常识冒充内部知识；缓存降级必须标明来源和时间；备用模型必须经过评测并记录版本；如果没有安全降级结果，就受控失败并提供人工处理入口。

## 14. 复习卡片

```text
1. 先有 Deadline，再谈 Timeout 和 Retry
2. 只重试短暂错误，写操作必须幂等
```
