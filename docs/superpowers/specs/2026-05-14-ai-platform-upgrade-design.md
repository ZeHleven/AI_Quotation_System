## 背景与目标

基于旗胜智能装饰"AI 落地方案"战略架构图，当前报价系统（03 AI 报价系统）已基本完整，需要在此基础上扩展完成另外三个模块：

| 模块 | 当前状态 | 本路线目标 |
|------|---------|-----------|
| 01 AI 知识库系统 | 🟡 基础已有，等待历史数据 | 数据到位后批量导入 + RAG 重评测 |
| 02 AI 执行系统 | ❌ 完全空白 | 会议纪要 → 任务拆解 → 跟踪闭环 |
| 03 AI 报价系统 | ✅ 已完整 | 持续优化准确率 |
| 04 AI 管理驾驶舱 | 🟡 仅有运维监控 | 三类效率指标全覆盖 |

**核心价值观**：团队效率，"快"是最重要的衡量标准。
- 报价快：客户需求到报价单的时长
- 响应快：客户咨询到有人接单的时长
- 执行快：会议决定到任务落地的时长

**架构决策**：所有模块在现有系统上扩展，不新建项目。共用用户体系（JWT）、数据库（MySQL）、基础设施（Redis/Celery/钉钉 Webhook）。

---

## 实施路径：路径 C（三段式交付）

```
第 1-2 周   阶段 0+1   前端升级 + 报价速度看板
第 3-4 周   阶段 2     响应速度追踪
第 5-6 周   阶段 3     执行速度追踪（为阶段 4 铺路）
第 7-12 周  阶段 4     02 AI 执行系统
等数据到位   阶段 5     01 知识库历史数据导入
```

### 预期成果
管理员一屏看到：过去 30 天报价了多少次、平均多久出结果、AI 被人工改了多少——有基线才能看优化效果。

## 阶段 2｜响应速度追踪

**时间**：第 3-4 周

### 任务清单
- [ ] 新增数据模型 `ClientInquiry`（客户咨询记录）

  ```
  字段：
  - id, created_at
  - source: 来源渠道（电话 / 微信 / 现场 / 其他）
  - inquiry_time: 客户咨询时间
  - first_response_time: 首次响应时间
  - responder_id: 跟进人（关联 users 表）
  - status: 跟进状态（待响应 / 已响应 / 已成单 / 已放弃）
  - notes: 备注
  ```

- [ ] 新增 Alembic migration
- [ ] 新增接口：
  - `POST /api/v1/inquiries` — 业务员手动登记咨询
  - `GET /api/v1/inquiries` — 列表查询
  - `GET /api/v1/admin/dashboard/response-speed` — 聚合统计
- [ ] 前端新增"客户咨询登记"入口（报价工作台侧边）
- [ ] 驾驶舱"响应速度"面板：
  - 平均首次响应时长
  - 各渠道咨询量分布
  - 各业务员响应速度对比
  - 逾期未响应数量预警

### 为什么这么做
响应速度是客户体验核心，但系统里目前完全没有这类数据。先建立手动登记习惯（成本低、阻力小），再逐步自动化采集。

### 预期成果
管理层第一次看到"客户从打电话到有人接单平均花了多久"，可以定向改进响应最慢的渠道和人员。

## 阶段 3｜执行速度追踪

**时间**：第 5-6 周

### 任务清单
- [ ] 新增数据模型 `Task`（执行任务）

  ```
  字段：
  - id, created_at
  - title: 任务标题
  - source: 来源（会议 / 报价 / 手动）
  - source_ref_id: 来源关联 ID（如 QuoteJob.id）
  - assignee_id: 负责人（关联 users 表）
  - due_date: 截止时间
  - completed_at: 完成时间
  - status: 状态（待处理 / 进行中 / 已完成 / 逾期）
  - notes: 备注
  ```

- [ ] 新增 Alembic migration
- [ ] 新增接口：
  - `POST/GET/PATCH /api/v1/tasks` — 轻量任务 CRUD
  - `GET /api/v1/admin/dashboard/execution-speed` — 聚合统计
- [ ] 驾驶舱"执行速度"面板：
  - 任务完成率（本周/本月）
  - 逾期任务数量预警
  - 平均任务完成时长
  - 各负责人任务量与完成率对比

### 为什么这么做
先建好 Task 数据模型，阶段 4 的 AI 会议纪要功能只需往这个模型里自动写入数据，驾驶舱不用再改。这是阶段 4 的技术铺垫。

### 预期成果
三类"快"全部有数字，驾驶舱三块面板齐全。管理层一屏看全报价快/响应快/执行快，红黄灯预警哪个环节在拖。

## 阶段 4｜02 AI 执行系统

**时间**：第 7-12 周

### 任务清单

#### 4.1 手动录入 + AI 任务拆解（第 7-8 周）
- [ ] 前端：会议纪要录入页（富文本框）
- [ ] 后端：`POST /api/v1/meetings/extract-tasks`
  - 调用 DeepSeek 解析会议纪要，提取任务列表
  - 返回结构化任务草稿（标题/负责人/截止时间）
- [ ] 前端：任务草稿确认弹窗，支持人工修改后一键创建

#### 4.2 语音上传转写（第 9-10 周）
- [ ] 接入讯飞实时语音 API（或阿里云语音识别）
- [ ] 后端：`POST /api/v1/meetings/transcribe`
  - 接收音频文件，返回转写文本
  - 转写结果自动进入 AI 任务拆解流程
- [ ] 前端：上传录音按钮 + 转写进度展示

#### 4.3 钉钉会议导入（第 9-10 周，与 4.2 并行）
- [ ] 申请钉钉企业应用权限（会议记录读取）
- [ ] 后端：`POST /api/v1/meetings/import-dingtalk`
  - 调用钉钉开放平台 API 拉取会议记录
  - 同步进入 AI 任务拆解流程

#### 4.4 任务分配与 24h 闭环提醒（第 11-12 周）
- [ ] 任务创建后通过现有钉钉 Webhook 推送给负责人
- [ ] 新增 Celery beat 定时任务：每小时扫描逾期任务
- [ ] 逾期自动发送钉钉提醒（复用 ops_monitor 的告警推送逻辑）

### 为什么这么做
执行系统集成点最多，放在最后做是因为：Task 模型（阶段 3）已就绪，钉钉 Webhook 已有先例可复用，语音转写是唯一真正新增的外部依赖。

### 预期成果
会议结束后，系统自动生成任务清单并推送至负责人钉钉，24 小时后未完成自动提醒，驾驶舱实时更新进度。战略图描述的"100% 任务分配、可视化进度追踪、闭环"全部实现。

## 阶段 5｜01 知识库历史数据导入

**时间**：等工程部提供历史成交数据后启动

### 任务清单
- [ ] 确认数据格式（Excel / CSV / 纸质扫描）
- [ ] 如为非结构化格式：用 GLM-4V 或 OCR 提取结构化字段
- [ ] 批量导入至 `materials` 表
- [ ] 触发 RAG 热更新（`/admin/reload`）
- [ ] 执行 RAG 评测（eval_rag.py），对比导入前后 Hit@K 和 MRR
- [ ] 如质量下滑，进入知识候选治理流程（knowledge_candidates）

### 为什么这么做
历史成交数据是报价准确率的根本，70 条当前数据远不够覆盖所有施工场景。但这是数据驱动的任务，技术层面已完备，只等数据到位。

### 预期成果
知识库从 70 条扩展至数百条真实成交行情，RAG 检索准确率显著提升，报价结果与市场行情更贴近。
