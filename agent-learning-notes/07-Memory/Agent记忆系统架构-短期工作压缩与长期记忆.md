# Agent 记忆系统架构：短期、工作、压缩与长期记忆

## 核心结论

模型 API 本身不会自动记住上一次调用。Agent 的“记忆”是系统在模型外部保存、筛选并重新注入信息的能力。

```text
交互与工具事件
→ 写入策略
→ 分层存储
→ 检索与任务视图
→ 上下文预算内组装
→ 模型决策
→ 新事件与状态更新
```

生产级 Memory 不是一个无限增长的向量库，而是一套外部状态系统。核心问题不是“存在哪里”，而是：

- 什么值得存
- 以什么结构存
- 什么时候更新
- 本轮取什么
- 怎样压缩
- 何时归档或遗忘

---

## 1. Memory、Context、State 与 RAG

| 概念 | 作用 | 示例 |
|---|---|---|
| Memory | 跨步骤或跨会话保存有用信息 | 用户偏好、历史决策、成功经验 |
| Context | 本轮实际交给模型的有限信息 | 当前问题、相关记忆、工具结果 |
| State | 当前任务可恢复的确定性状态 | 已完成步骤、下一步、重试次数 |
| RAG | 从外部知识中检索证据 | 企业制度、产品文档、合同条款 |

四者可能共用数据库或检索技术，但职责不同：

- Memory 是候选信息仓库
- Context Builder 决定本轮把什么放到模型“桌面”
- State 应优先结构化并可确定性恢复
- RAG 主要检索外部知识，不自动等于用户记忆

---

## 2. 推荐的分层架构

不同资料会使用“三层”或“四层”等不同名称。比层数更重要的是职责分离。

### 2.1 短期记忆

直接位于当前上下文窗口，包括：

- 最近几轮对话
- 当前输入
- 最近工具结果
- 临时变量
- 局部观察结果

特点：

- 每轮推理都能直接访问
- 容量有限
- 与当前任务最相关
- 超过预算后必须裁剪或压缩

### 2.2 工作记忆与任务状态

工作记忆像任务草稿本，但生产实现不应只靠自然语言摘要：

```json
{
  "task_id": "quote_123",
  "goal": "生成并复核工程报价",
  "completed_steps": ["parse_file", "match_cost"],
  "next_step": "review_exceptions",
  "open_issues": ["3 个项目无底价"],
  "artifacts": ["requirement_rows_v2", "quote_preview_v1"],
  "state_version": 8
}
```

它负责：

- 长任务推进
- Checkpoint
- 中断与恢复
- 用户重定向后继续
- 多 Worker 协作与并发控制

关键任务状态应写入数据库或持久化状态存储，不能只存在 Prompt 中。

### 2.3 压缩记忆

历史过长时，将早期过程压缩为结构化摘要：

- 当前目标
- 已完成步骤
- 关键结论及证据
- 用户已确认的决定
- 未解决问题
- 待办事项
- 失败尝试及原因

常用上下文组合：

```text
稳定约束
+ 历史结构化摘要
+ 最近若干轮原始对话
+ 当前任务状态
+ 本轮检索出的长期记忆
```

摘要会丢失细节，也可能引入错误，因此应保留原始事件引用、摘要版本和生成时间。重要事实不能只存在模型生成的摘要里。

### 2.4 长期记忆

保存跨会话仍有价值的信息：

- 稳定的用户偏好
- 结构化用户或项目档案
- 历史决策
- 重要事件
- 可复用业务规则
- 经过验证的任务经验

长期记忆不应默认参与每轮推理，而应按任务检索和筛选。

---

## 3. 长期记忆的三种类型

### 语义记忆

保存相对稳定的事实和规则：

- 用户偏好
- 项目约束
- 业务定义
- 已确认的规则

精确属性优先保存在关系数据库、JSON 档案或键值存储中，不要依赖模糊向量召回。

### 情景记忆

保存发生过的具体事件：

- 上周提交过一次审批
- 某次报价被人工打回
- 某个工具调用曾失败

应保留时间、参与者、结果、来源和任务 ID，适合按时间、实体和语义组合检索。

### 程序性记忆

保存“如何完成一类任务”的可复用经验：

- 标准工作流
- 工具调用顺序
- 排错 Runbook
- 经过验证的 Skill

程序性记忆不能由一次成功轨迹直接自动固化。更安全的流程是：

```text
收集成功轨迹
→ 提取候选流程
→ 去除偶然步骤和敏感数据
→ 人工或规则审核
→ 回归测试
→ 版本化发布为 Skill
```

## 4. 存储选型

| 记忆类型 | 优先存储 | 原因 |
|---|---|---|
| 当前对话窗口 | Runtime / Prompt | 直接参与本轮推理 |
| 任务状态 | SQL、状态存储 | 精确、事务、可恢复 |
| 会话缓存 | Redis | 低延迟、有 TTL |
| 用户档案 | SQL / JSON | 按字段精确读写 |
| 对话和任务事件 | 事件表 / 日志存储 | 可追踪、可回放 |
| 语义片段 | 向量库 + 元数据索引 | 支持模糊语义召回 |
| 规则与知识 | 文档库、RAG、关系库 | 版本、权限与证据 |
| 程序性技能 | Git、Skill Registry | 可评审、测试和版本化 |

向量数据库擅长“找相似内容”，但不擅长：

- 手机号等精确字段查询
- 判断新旧状态
- 事务更新
- 唯一约束
- 权限和删除的一致性

因此存储选择应服从数据语义，而不是把所有内容统一向量化。

---

## 5. Ledger、Views 与 Policy

一种实用抽象是：

```text
Ledger：发生过什么
Views：当前任务需要怎样看
Policy：什么能写、能读、要更新或删除
```

### Ledger

保存原始、可追溯事件，通常追加写入：

- 用户输入
- 工具调用与结果
- 状态迁移
- 人工修改
- Memory 写入和删除事件

### Views

从原始记录生成面向任务的视图：

- 当前用户档案
- 最近会话摘要
- 当前任务进度
- 与本轮问题相关的历史经验

View 可以重建，不应取代原始证据。

### Policy

负责：

- 写入条件
- 存储类型
- 更新与冲突处理
- 检索范围
- 权限过滤
- 保留期限和删除

这三者分开后，系统可以保留审计历史，同时向模型提供简洁、当前有效的状态。

---

## 6. 上下文组装

Memory 的价值最终取决于本轮上下文，而不是仓库里存了多少。

推荐优先级：

```text
系统与安全约束
→ 当前目标和确定性任务状态
→ 用户本轮输入
→ 最近必要对话和工具结果
→ 检索出的长期记忆
→ 压缩摘要
```

组装时检查：

- 与当前目标是否相关
- 是否仍然有效
- 来源是否可靠
- 用户是否有权限
- 是否与当前状态冲突
- 是否重复
- 是否超过 Token 预算

需要区分“记忆不存在”和“记忆存在但本轮没有召回”。两种情况的修复方式不同。

## 7. 最小数据模型

```json
{
  "memory_id": "mem_001",
  "tenant_id": "tenant_a",
  "subject_id": "user_12",
  "memory_type": "semantic",
  "key": "response_style",
  "value": {"preference": "concise"},
  "source_event_ids": ["evt_983"],
  "confidence": 0.92,
  "importance": 0.8,
  "valid_from": "2026-07-01T00:00:00+08:00",
  "valid_to": null,
  "recorded_at": "2026-07-28T15:00:00+08:00",
  "status": "active",
  "version": 3,
  "acl": ["user:12"]
}
```

至少应具备：

- 主体与租户
- 记忆类型
- 结构化值或内容
- 来源
- 时间与状态
- 版本
- 权限
- 置信度或验证状态

## 8. 评测

| 维度 | 指标示例 |
|---|---|
| 写入 | 有价值记忆写入召回率、错误写入率 |
| 更新 | 旧状态正确失效率、冲突解决正确率 |
| 检索 | Recall@K、Precision@K、关键约束命中率 |
| 上下文 | 有效信息占比、重复率、Token 消耗 |
| 生成 | 使用正确记忆的任务成功率、记忆导致的错误率 |
| 生命周期 | 过期记忆召回率、删除传播成功率 |
| 用户体验 | 纠正次数、可解释性、编辑和删除成功率 |

需要专门测试：

- 长任务中断后恢复
- 用户偏好更新
- 新旧事实冲突
- 跨会话召回
- 应该遗忘的信息
- 没有相关记忆时的行为

## 9. 面试回答模板

```text
模型 API 本身没有跨调用长期记忆，
Agent Memory 是模型外部的分层状态系统。

我会把它拆成短期上下文、工作状态、压缩摘要和长期记忆。
短期上下文保存最近对话和工具结果；
工作状态结构化保存目标、进度和待办，支持中断恢复；
压缩层减少长任务的 Token 消耗；
长期层再区分语义、情景和程序性记忆。

存储上不会把所有内容都放进向量库。
精确档案和任务状态使用数据库，
语义片段才使用向量检索，
可复用流程经过审核和回归后版本化为 Skill。

Runtime 通过读写、更新、召回和遗忘策略，
在权限、有效期和上下文预算内组装本轮信息。
真正难点不是存得多，而是稳定取出当前正确的信息。
```

## 10. 面向当前报价中台的落地映射

当前系统已经保存报价任务、需求行、预审草稿、成本证据、人工修正和任务事件，这些首先是业务状态与审计记录，不应全部复制成向量记忆。

如果后续引入 Memory，可优先从三个受控场景开始：

1. **任务恢复**：结构化保存当前报价目标、完成批次、异常和下一步
2. **项目偏好**：保存经过用户确认的输出格式、常用规则和项目级约束
3. **程序经验**：将反复验证有效的清洗、复核和异常处理流程沉淀为版本化 Skill

第一版不建议：

- 保存全部聊天作为永久记忆
- 让模型自行修改正式成本数据
- 自动把单次人工操作固化为通用规则
- 不经权限过滤跨用户召回

---

## 一句话总结

Agent Memory 的本质不是无限保存历史，而是将外部状态分层治理，并在每轮任务中用有限上下文提供当前最有价值、最可靠的信息。
