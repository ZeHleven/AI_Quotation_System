# Linux 与 Docker 生产运维：进程、网络、存储、安全与故障排查

## 核心结论

Linux 排障的主线是：

```text
进程是否存在
→ 端口是否监听
→ 本机能否访问
→ 网络是否可达
→ 依赖是否健康
→ 资源是否耗尽
→ 日志说明了什么
```

Docker 不是虚拟机。镜像是只读模板，容器是镜像的运行实例；Compose 用声明式文件组织多容器应用的服务、网络和卷。

面试时不要只背命令，要能说明“现象、证据、定位顺序和恢复动作”。

## 1. Linux 必须建立的五个视角

### 1.1 文件与权限

重点理解：

- 绝对路径与相对路径；
- 用户、用户组和 `r/w/x` 权限；
- 目录的执行权限代表能否进入和访问其中内容；
- 配置、日志、数据、程序文件应分离；
- 服务账号遵循最小权限，不使用 root 长期运行应用。

常用检查：

```bash
pwd
ls -lah
stat <path>
df -h
du -sh <path>
```

生产风险：

- 磁盘写满会连带导致日志、数据库和容器异常；
- 错误的属主或权限会造成“文件存在但进程读不到”；
- 密钥写进仓库、镜像或日志后，很难彻底撤回。

### 1.2 进程与服务

必须区分：

- 进程：正在运行的程序实例；
- 服务：由 systemd 等管理器托管的长期进程；
- PID：进程标识；
- 信号：优雅退出、重载或强制终止的控制方式。

常用检查：

```bash
ps aux
top
systemctl status <service>
journalctl -u <service> --since "30 min ago"
```

优雅停机应先停止接流量，再等待在途任务完成，最后退出。直接强杀可能造成任务重复、数据未提交或临时文件残留。

### 1.3 网络

必须能回答四个问题：

1. 域名是否解析正确？
2. 目标 IP 和端口是否可达？
3. 服务是否真的监听该地址？
4. 防火墙、代理或容器端口映射是否阻断？

常用检查：

```bash
ss -lntp
curl -v http://127.0.0.1:8001/health
getent hosts <domain>
ip addr
ip route
```

`127.0.0.1` 只代表当前网络命名空间。容器内访问宿主机或另一个容器时，不能想当然地使用 localhost。

### 1.4 资源

优先关注：

| 资源 | 常见现象 | 关键证据 |
|---|---|---|
| CPU | 延迟升高、超时 | 使用率、负载、热点进程 |
| 内存 | OOM、频繁重启 | 可用内存、进程占用、内核日志 |
| 磁盘 | 写入失败、数据库异常 | 容量、inode、增长最快目录 |
| 网络 | 连接失败、抖动 | 丢包、DNS、连接数、超时分布 |
| 文件句柄 | 无法打开连接或文件 | 进程限制与当前使用量 |

不要看到 CPU 高就立即扩容。先确认是正常流量、慢 SQL、死循环、重试风暴，还是下游超时造成的线程堆积。

### 1.5 日志

日志至少包含：

- 时间；
- 日志级别；
- 服务与环境；
- `trace_id` 或任务 ID；
- 操作对象；
- 结果与错误类型；
- 必要但已脱敏的上下文。

禁止记录密码、Token、完整密钥和敏感业务原文。日志要轮转、限额并设置保留期。

## 2. Docker 的核心机制

### 2.1 镜像、容器与 Dockerfile

```text
Dockerfile
  ↓ build
镜像（分层、不可变模板）
  ↓ run
容器（隔离的运行进程）
```

关键原则：

- 固定基础镜像版本，避免不可追溯的漂移；
- 使用 `.dockerignore` 排除密钥、缓存和无关大文件；
- 合理排序构建步骤，提高层缓存命中率；
- 使用多阶段构建，减少最终镜像体积；
- 默认用非 root 用户运行；
- 同一镜像通过外部配置适配不同环境。

### 2.2 容器的进程模型

容器的生命周期由主进程决定。主进程需要正确接收退出信号并回收子进程。

常见问题：

- 启动脚本吞掉信号，导致无法优雅停机；
- 应用把日志写进容器内部且不采集；
- 把临时状态误当持久数据；
- 容器能启动，但应用尚未准备好接流量。

### 2.3 网络

Compose 默认可为应用建立网络，同一网络中的服务通常用服务名解析，例如：

```text
rag-service → standalone:19530
standalone  → etcd:2379
```

要区分：

- 容器端口：服务在容器内监听的端口；
- 主机端口：发布给宿主机或外部访问的端口；
- 内部依赖：能不暴露到宿主机就不暴露。

### 2.4 存储

| 方式 | 适合内容 | 风险 |
|---|---|---|
| 容器可写层 | 临时文件 | 容器删除后丢失 |
| Named Volume | 持久数据 | 需要备份和容量治理 |
| Bind Mount | 宿主机文件、开发挂载 | 路径和权限耦合 |
| 对象存储 | 上传文件、模型产物 | 需要权限和生命周期策略 |

持久化不等于备份。卷损坏、误删或宿主机故障仍会造成数据丢失，必须单独验证备份和恢复。

### 2.5 配置与密钥

- 普通配置可用环境变量或配置文件；
- 密钥应来自专用密钥系统或受控挂载；
- 不把密钥写进镜像层、Compose 默认值或 Git；
- 日志和异常信息也要脱敏；
- 密钥需要轮换能力。

### 2.6 健康检查、重启与资源限制

三类健康信号：

| 类型 | 用途 |
|---|---|
| Liveness | 进程是否需要重启 |
| Readiness | 是否可以接收流量 |
| Dependency Health | 数据库、队列等关键依赖是否可用 |

`restart: unless-stopped` 只能让进程重新拉起，不能修复错误配置、数据损坏和持续性依赖故障。

应进一步设置 CPU、内存等资源边界，避免单个容器拖垮整机，并为 OOM 和频繁重启建立告警。

## 3. Docker Compose 的定位

Compose 适合：

- 单机多容器开发；
- 内网验证环境；
- 中小规模、运维边界清晰的部署；
- 用一个声明文件描述服务、网络、卷和依赖。

Compose 不自动提供：

- 跨节点调度与高可用；
- 自动水平扩缩容；
- 完整滚动升级和流量治理；
- 集群级密钥、策略和租户隔离。

规模、可用性和多节点调度需求明确后，再评估 Kubernetes，不能为了“技术先进”而迁移。

## 4. 标准故障排查顺序

以“RAG 服务访问失败”为例：

```text
1. 明确影响：全量失败还是部分请求失败
2. 查入口：网关状态码、超时和 trace_id
3. 查进程/容器：是否运行、是否反复重启
4. 查端口：8001 是否监听，映射是否正确
5. 查本机：容器内、本机分别 curl 健康接口
6. 查网络：服务名、DNS、路由、防火墙
7. 查依赖：Milvus、etcd、MinIO 是否健康
8. 查资源：CPU、内存、磁盘、文件句柄
9. 查日志：围绕同一 trace_id 还原时间线
10. 恢复：降级、重启、回滚或切换只读能力
11. 复盘：补监控、测试、Runbook 和容量阈值
```

先收集证据再变更。重启虽然可能暂时恢复，却也可能清除现场并掩盖根因。

## 5. 报价中台的真实映射

### 已具备

- Windows 运行 FastAPI 主网关，CentOS 运行 RAG 相关服务；
- `rag_docker/docker-compose.yml` 编排 Milvus、etcd、MinIO、RAG API 和 Redis；
- 多个服务配置健康检查、日志轮转和 `restart: unless-stopped`；
- 通过 Compose 网络使用服务名访问依赖；
- 模型缓存、向量数据和对象存储使用宿主机卷持久化；
- RAG API 对外发布 8001，Milvus 发布 19530。

### 仍需补强

- CentOS 7.9 已停止常规生命周期支持，应规划迁移到受支持系统；
- Compose 文件中存在可回退的默认口令，生产环境必须改成外部密钥并验证未泄露；
- 尚未形成跨节点高可用、自动扩缩容和标准化容器资源限制；
- 需要定期执行“从备份恢复”，不能只确认备份文件存在；
- 暂未部署 Kubernetes，这一点在面试中应如实说明。

## 6. 面试回答模板

### 如何排查 Linux 上接口超时？

> 我先确认影响范围和最近变更，再沿入口到依赖分层排查。先看进程、端口和本机健康检查，再看网络、DNS和防火墙，然后检查数据库、队列等依赖，最后看 CPU、内存、磁盘和连接池。全程用 trace_id 或任务 ID 关联日志。恢复阶段优先限流、降级或回滚，恢复后再做根因分析和防复发改进。

### Docker 与虚拟机有什么区别？

> 容器本质上是受命名空间和资源控制约束的宿主机进程，共享宿主机内核；虚拟机有独立来宾操作系统。容器启动快、密度高，但隔离边界和内核安全仍要认真治理。

### Compose 与 Kubernetes 如何选？

> 单机、内网验证或规模较小时，Compose 成本更低。只有出现多节点调度、高可用、弹性扩缩容、标准化发布和策略治理等明确需求时，Kubernetes 的复杂度才有回报。
