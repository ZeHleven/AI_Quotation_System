# RAG 检索策略：混合召回、融合、Rerank 与动态 Top-K

## 核心结论

Top-K 不是一个脱离数据和模型的固定数字。生产级检索需要分阶段平衡“找全”和“找准”：

```text
Query 理解与路由
→ 多路粗召回
→ 过滤、融合和去重
→ Reranker 精排
→ 阈值与上下文预算筛选
→ 最终证据集
```

粗排负责让正确证据进入候选池，精排负责减少噪声；最终送给大模型的数量由证据质量、任务复杂度和 Token 预算共同决定。

---

## 1. Recall 与 Precision

### Recall

应该被找到的相关内容，有多少进入候选集。

```text
Recall = 找到的相关内容 / 全部应找到的相关内容
```

### Precision

召回结果中，有多少真的相关。

```text
Precision = 相关结果 / 全部召回结果
```

两者通常存在张力：

- 候选太少：容易漏掉关键证据
- 候选太多：噪声、Token、延迟和成本增加

检索目标不是无限提高某一项，而是在业务风险下找到合适平衡。

---

## 2. 为什么不能只用向量检索

| 通道 | 擅长 | 典型问题 |
|---|---|---|
| 向量检索 | 同义表达、语义近似 | “退钱”匹配“退款流程” |
| BM25/全文检索 | 精确词和稀有词 | 合同编号、错误码、型号 |
| 元数据过滤 | 确定范围 | 时间、权限、版本、项目 |
| 结构化查询 | 精确字段和计算 | 金额、数量、状态、聚合 |

示例：

```text
“钱怎么退”
→ 向量检索：退款流程、退费规则
→ 关键词检索：退款、到账
→ 元数据过滤：当前地区、有效版本
```

结构化业务事实应优先走 SQL 或受控 API，不能为了统一架构而全部塞进向量库。

---

## 3. Query 理解、路由和改写

检索前可以识别：

- 查询意图
- 是否包含编号、日期、型号或专有名词
- 需要语义检索还是精确查询
- 是否需要时间、权限和版本过滤
- 是否为多跳或比较问题

### Query 改写

可以：

- 纠正口语和缩写
- 补充业务术语
- 拆分复合问题
- 生成多个检索表达

例如：

```text
原问题：钱怎么退？

改写：
- 退款条件
- 退款申请流程
- 退款到账时间
```

风险：

- 改写偏离原意
- 自动补充错误实体
- 多 Query 放大噪声和成本

因此要记录原始 Query、改写结果和各自产生的候选。

---

## 4. 第一阶段：多路粗召回

粗召回目标是较高 Recall，而不是直接生成最终上下文。

```text
Vector Top-N
+ BM25 Top-N
+ 精确编号匹配
+ 元数据或结构化结果
→ 候选池
```

候选池大小需要根据：

- 语料规模
- Chunk 粒度
- 查询复杂度
- Reranker 吞吐
- 延迟预算

视频中的“先取 50 条”只是解释两阶段检索的示例，不是固定配置。

---

## 5. 融合与去重

向量相似度和 BM25 分数不在同一尺度上，不能直接相加比较。

### 常见融合方式

| 方法 | 特点 |
|---|---|
| Rank Fusion / RRF | 基于排名融合，不依赖原始分数可比 |
| 分数归一化后加权 | 简单，但对分布和权重敏感 |
| 规则融合 | 可解释，适合明确业务优先级 |
| 学习排序 | 可利用标注、点击和反馈，成本更高 |

融合后还要处理：

- 相同 Chunk 被多路重复召回
- 同一文档多个相邻片段高度重复
- 某一来源占满候选
- 新旧版本冲突
- 权限不一致

RRF 是稳健起点，但不保证在所有数据集上最佳。

---

## 6. 第二阶段：Reranker 精排

Reranker 对 Query 与每个候选做更精细的相关性判断。

```text
粗召回候选
→ Reranker 打分
→ 重新排序
→ 保留少量高质量证据
```

价值：

- 纠正单路召回排序
- 降低语义相似但无答案的片段
- 提升正确证据进入最终上下文的概率

代价：

- 增加模型调用或本地算力
- 增加延迟
- 候选过多时吞吐下降
- 不同领域可能需要重新评测

是否启用、使用哪个模型及精排多少候选，应由离线评测和线上指标决定。

---

## 7. 动态 Top-K 与阈值

### 为什么不能固定

不同问题需要的证据数量不同：

- 精确事实题：可能一条证据足够
- 多条款对比：需要多个来源
- 汇总分析：需要覆盖多个章节或文档

### 推荐约束

```text
候选经过 Rerank
→ 应用最低质量要求
→ 保证最小证据数
→ 限制最大证据数
→ 检查来源和覆盖度
→ 适配上下文 Token 预算
```

### 阈值不是通用常数

视频以 `0.7` 作为解释示例，但实际分数受到以下因素影响：

- Embedding 或 Reranker 模型
- 语料领域
- Query 类型
- 分数校准方式
- 模型版本

不能把 `0.7` 当成通用合格线。阈值应通过验证集校准，并在模型或索引变更后重新评测。

### 动态策略示例

```text
简单事实题：
较少候选 + 较高阈值

复杂对比题：
较大候选池 + Rerank + 来源覆盖约束

低置信度查询：
返回澄清问题或拒答，而不是降低阈值塞入噪声
```

---

## 8. 上下文选择不等于取前 K 条

最终证据集还要考虑：

- Token 预算
- 证据是否完整
- 多来源覆盖
- 相邻 Chunk 合并
- 重复内容压缩
- 标题、表头和适用条件
- 时间与版本冲突

可使用 MMR 或来源配额提升多样性，但必须验证是否会牺牲关键证据。

对表格和合同条款，完整信息单元通常比机械取固定条数更重要。

---

## 9. 检索评测

### 构建黄金查询集

每个样本应包括：

- Query
- 应命中的文档、页面或 Chunk
- 必要过滤条件
- 问题类型
- 难度
- 是否应拒答

### 指标

| 阶段 | 指标 |
|---|---|
| 粗召回 | Recall@N、命中率 |
| 融合 | 融合后 Recall、重复率 |
| 排序 | MRR、NDCG、Top-1/Top-K 命中 |
| 最终证据 | Precision@K、证据覆盖率 |
| 端到端 | 答案正确性、引用支持度、延迟、成本 |

### 消融实验

依次比较：

```text
仅向量
→ 向量 + BM25
→ 增加元数据过滤
→ 增加 RRF
→ 增加 Reranker
→ 动态 Top-K
→ Query 改写
```

只有真实指标改善，才保留新增复杂度。

---

## 10. 常见失败

| 错误做法 | 后果 |
|---|---|
| 固定 Top-1 | 容易漏证据 |
| 固定取大量候选 | 噪声和成本上升 |
| 把所有分数直接相加 | 排序失真 |
| 不做权限和版本过滤 | 数据泄露或使用旧知识 |
| 改写 Query 但不记录 | 无法定位召回漂移 |
| Rerank 后仍机械取固定 K | 低分候选进入上下文 |
| 只看最终答案 | 无法区分召回和生成问题 |
| 凭感觉设置阈值 | 换模型或数据后失效 |

---

## 11. 面试回答模板

```text
生产级 RAG 检索不能只依赖单路向量检索。

我会先做 Query 分类和必要的改写，
然后通过向量、BM25、精确匹配和元数据过滤多路粗召回，
尽量保证正确证据进入候选池。

因为不同通道分数不可直接比较，
候选会通过 RRF、归一化加权或学习排序进行融合，
再用 Reranker 精排。

最终 Top-K 不设成固定常数，
而是结合 Rerank 分数、问题复杂度、来源覆盖和 Token 预算动态选择；
分数阈值也要用真实验证集校准。

评测上我会分别看 Recall@N、MRR/NDCG、
最终证据 Precision、答案引用质量、延迟和成本，
通过消融实验确认每个组件是否真的带来收益。
```

## 12. 面向当前报价中台的落地映射

当前 `hybrid_searcher.py` 已采用：

- Milvus 向量检索
- BM25
- RRF 融合

下一步不应直接增加所有高级组件，而应先建立检索基线：

1. 用真实报价问题建立黄金 Query—证据集
2. 分别测量向量、BM25 和混合检索的 Recall@K
3. 记录成本条目精确编号、名称变体和规格查询
4. 比较 RRF 前后的排序收益
5. 再评估 Reranker 是否改善最终证据
6. 用验证集校准候选数量和阈值
7. 观察延迟和硬件资源是否可以接受

对 `cost_items.active` 的精确价格、状态和聚合查询，应继续使用数据库逻辑；RAG 只负责需要语义理解的匹配和知识检索。

## 一句话总结

生产级检索的关键不是猜一个 Top-K，而是用多路粗召回保证覆盖、用融合与 Rerank 提升质量，再通过评测校准最终证据数量、阈值和上下文预算。
